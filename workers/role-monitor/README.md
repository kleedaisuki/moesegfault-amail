# Reserved-role mail monitor

This component implements the proposed monitored intake in [the design note](../../docs/role-mail-monitoring.md). It is **not** a mailbox or report-processing agent. The four public `abuse`/`postmaster` routes still forward directly to a confidential owner-controlled mailbox until a separate staged cutover; merely deploying this Worker changes no mail route and just leaves its initial send-gate lease expired. The staging Worker accepts only `amail-role-e2e@moesegfault.dev`. The public Worker accepts only the four exact apex/subdomain system aliases.

## Durable contract

`role_arrivals` stores an opaque random UUID, an enumerated role label, arrival time, accepted-or-unknown forwarding state, and alert time. There is **no** sender, subject, body, MIME, Message-ID, or forwarding destination column. Before forwarding, the Email handler inserts an `unknown` row; it then calls Cloudflare `forward()` exactly once with an `X-Amail-Role-Ref` header and marks the row `accepted` only after the returned promise resolves. It never reads the raw MIME stream. A failed initial insert or forward throws a sanitized error instead of claiming success; Cloudflare's actual SMTP retry/rejection behavior on that exception remains a required **live staging test**, not an assumed guarantee. After a forward exception, the random row remains unresolved; a provider acceptance may still have happened, so blind application-level replay is unsafe.

The five-minute Cron takes an immutable `arrival_seq` high-water snapshot, then sends a bounded digest of counts and at most 16 opaque references from `mail@moesegfault.dev` to the same verified destination. Only after provider send acceptance does it mark **snapshot members** alerted. A delayed handler insert with an old `received_at` receives a later sequence and cannot be falsely marked alerted. A crash between send and mark may duplicate the digest, but cannot mark an unsent digest complete. The digest does not include reporter content. The alert explicitly directs the owner to check Inbox **and Junk**, and to respond separately via the official sender; replying directly from the confidential destination would disclose it. Cron errors trigger a sanitized failure rather than being swallowed, so Cloudflare Cron Past Events should show failure; workers-rs 0.8.7 discards a returned scheduled-handler `Result`.

`role_monitor_health(singleton=1, lease_until, checked_at)` uses Unix **milliseconds**. Migration inserts an expired lease. Cron renews it for 30 minutes only after all pending alert groups have been submitted, the verified destination inventory is read completely, all role routes are exactly one enabled API-owned rule to this Worker, and there are no unknown forwards or stale unalerted rows. A missing/error/expired lease fails the separate mail API sending gate closed. A provider `send()` acceptance or a live lease is not proof of Outlook Inbox placement or owner attention; manual `abuse_contact_verified` attestation remains separate.

Cloudflare's routing GraphQL dataset is adaptively sampled, so it is suitable for reconciliation, **not** the per-message trigger. The existing outbound Email Sending Queue does not publish inbound routing events. See [official Email handler API](https://developers.cloudflare.com/email-service/api/route-emails/email-handler/), [send binding restrictions](https://developers.cloudflare.com/email-service/configuration/send-bindings/), and [D1 Worker API](https://developers.cloudflare.com/d1/worker-api/).

### Privacy-preserving observability

Both production and staging explicitly keep only reviewed application logs at full rate while disabling automatic `observability.traces` and `observability.logs.invocation_logs`. Cloudflare's [automatic span inventory](https://developers.cloudflare.com/workers/observability/traces/spans-and-attributes/) includes the untrusted sender on Email Handler root spans; sampling them less often is not redaction. The application logs fixed role labels, random references, counts and fixed failure phases, but never reporter sender, subject, MIME, confidential destination or provider error bodies. Cloudflare [Workers Logs](https://developers.cloudflare.com/workers/observability/logs/workers-logs/) documents that custom logs remain available with invocation logs disabled. Cron failure is still signaled by a sanitized thrown error and observable in [Cron Past Events](https://developers.cloudflare.com/workers/runtime-apis/handlers/scheduled/); a staging event must verify the deployed setting. Do not re-enable automatic traces without a privacy canary and explicit data-handling review.

## Staging deployment and evidence

The candidate-branch [staging deployment job](../../.github/workflows/ci.yml) reads the confidential destination only from a GitHub `staging` Environment secret, audits the isolated legacy-empty D1 before migration, tests native/Wasm in its prerequisite job, deploys with a secret file deleted in a shell trap, and confirms the synthetic route remains absent. It **never** mutates production role rules. After merge, the same job can be requested with `workflow_dispatch` target `staging`. Hosted CI also compiles the Worker and exercises the SQL and exact-route safeguards. A separate `staging_route.py --apply`/`--remove` changes only the one staging synthetic alias after manual review; absence is its default audit mode. Every route change requires exact readback and a finally-block removal during live tests.

The separate [production deployment workflow](../../.github/workflows/deploy-role-monitor-production.yml) is main-only and manual. It audits the isolated production D1 and requires the existing four **direct-forward** rules unchanged before and after uploading the unrouted Worker. It does not cut over any role address. If any role already targets the Worker, this conservative deployment path refuses replacement; a future rollout procedure must explicitly manage that maintenance/rollback condition. Production user sending remains held until the four-rule cutover, a complete live failure-path exercise, and owner-confirmed official alert arrival in **Inbox** with a usable response path.

Required private Worker secrets: `ROLE_FORWARD_DESTINATION`, `CF_EMAIL_ROUTING_TOKEN`, `CF_ACCOUNT_ID`. The token must have zone Email Routing Rules Read plus account Email Routing Addresses Read. The `ROLE_ALERT` binding is constrained at provider level to the official sender, but its recipient cannot be written into committed Wrangler config without disclosing it. Runtime code sends only to the secret-held destination, verified against the account destination inventory; residual broad-recipient binding capability is a deployment risk until an encrypted/generated binding config is separately proven not to disclose the destination in Wrangler logs. Review Worker releases and environment secrets accordingly.

An optional **staging-only** `ROLE_TEST_FAULT` Worker secret accepts `before_insert`, `before_forward`, `after_forward`, `before_alert`, or `after_alert`. Production ignores this secret unconditionally. Set one phase only for a controlled synthetic SMTP probe, record the provider SMTP and D1 outcomes, then remove the secret and redeploy or clear it before acceptance. The hook before insertion emulates a handler exception at the durable-write boundary; it does not simulate every possible D1 outage. `after_forward` and `after_alert` deliberately expose ambiguous-at-least-once outcomes rather than claiming exactly-once delivery.

Before **any** production cutover, use real external SMTP to verify: route propagation, forward and official digest delivery (including Inbox/Junk), owner response workflow, duplicate digest tolerance, D1-insert failure, `forward()` failure, alert-send failure, Cron outage, route drift, lease expiry and mail API denial. The current four direct-forward actions are the rollback target. Change one rule at a time under conflict detection, send a canary and read back before the next. Never add an `addresses` list to Wrangler because it can take ownership of unrelated API-managed routes. Keep public sending held until the full operational gate is met.

The offline-reviewed staging SMTP driver is [`acceptance.py`](acceptance.py), with the privacy boundary, ID-bound recovery marker, mandatory **externally enforced staging deploy freeze**, and separate provider/Inbox oracles documented in [`docs/staging-role-monitor-acceptance.md`](../../docs/staging-role-monitor-acceptance.md). It has **not** been run live. `--preflight` is read-only and does not check SMTP sender readiness; `--confirm-staging-smtp` checks that readiness with the SMTP token, creates only the disposable staging role route, submits at most one real SMTP message, and closes only its recorded provider rule ID in `finally`. `--recover-exact-route` is an explicit, marker-gated recovery operation; an unknown ID with a present route requires restricted manual reconciliation, never shape-only automatic deletion. A D1 row plus fresh lease is not a Cron Past Events or external Inbox acceptance.
