## Findings / live prerequisites

### P1: staging mutation jobs do not share quota's lock

Location: `.github/workflows/staging-ten-address-acceptance.yml:55-57`; committed `ci.yml` staging-worker and staging containment/settings jobs.

Quota holds `staging-native-mail-acceptance`, while the existing staging Mail deployment/settings writers hold `deploy-mail-staging`. CI's workflow-level `ci-{ref}` lock does not bridge the independently named quota workflow. Thus an approved staging deployment can execute concurrently with a quota campaign. If the Mail version changes after an add, `_observe` rejects the changed pin, and campaign finally begins with a pin check that rejects the same drift before retiring campaign resources. The run fails safely rather than producing a false quota pass, but leaves recovery-required allocations; original-pin recovery also refuses the changed deployment. This violates the design's explicit equivalent exclusion requirement and makes interruption recovery harder.

Confidence: high, directly traced lock identities and controller pin checks. Required correction before live: place same-repository staging Mail promotion/settings mutation jobs under the same non-canceling lock, with contracts that cover both workflows. Review the containing change; do not assume an uncommitted CI edit fixes it. Actions concurrency is repository-scoped, so sibling-repository Identity/Login writers and manual provider changes additionally require a real external freeze. Exact revision observations remain necessary and are not a substitute for exclusion.

### P2: fixed artifact expiry needs a concrete unresolved-run preservation procedure

Location: workflow `retention-days: 30` at line 129; `staging_ten_address_artifact.py::metadata`; design's recovery-key/retention section.

The artifact is immutably uploaded with a 30-day expiration. The reader deliberately rejects expired/missing artifacts; no fallback store is admitted. The design requires routine recovery within 24 hours, escalation rather than abandonment, and preservation of the sealed manifest in a protected durable store before expiry if cleanup remains unresolved. The supplied workflow/helper do not implement that preservation or identify a reviewed alternative recovery entry point. Keeping the key alone cannot reconstruct the authenticated complete baseline, and an always-run fixed availability label neither extends artifact lifetime nor proves cleanup.

Confidence: high about the source boundary; this is an operational live prerequisite, not a request to invent an automatic mutation or artifact-replacement mechanism. Required before live: name an accountable 24-hour escalation path and reviewed protected ciphertext escrow/export procedure before the 30-day limit, retain original run/attempt/SHA/artifact identity plus the key generation, and define how restricted intervention consumes that evidence if the Actions artifact is unavailable. Preserve the artifact now; do not weaken the current exact-ID gate or reupload under a new run and silently call it original recovery. If a reviewed external procedure already exists, link it and verify the prerequisite rather than adding another controller.
