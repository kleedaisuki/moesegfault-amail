## What the evidence does and does not establish

`crates/mail-worker/src/lib.rs::main` normally turns every returned `AppError` into a problem response, appends `x-amail-request-id`, and emits a bounded `request_exit` trace. `dispatch`'s authenticated `POST /v1/addresses` branch converts an `add_address` error to the same problem shape and, when the staging switch is active, appends `x-amail-address-diag`. `add_address` claims the D1 row as `provisioning` before Routing Rules GET/POST; it changes the row to `active` only after a rule ID is returned and a D1 update succeeds. Thus the observed rule plus provisioning row proves a side effect happened, but **not** that the original request's POST returned normally, nor where execution stopped. A normal handled provider/D1 error should usually carry the diagnostic header. Its absence plus a generic HTTP 500 makes an uncaught Rust/Wasm/JavaScript exception or Cloudflare-generated response plausible; it is not proof of a panic. The existing CLI `http_error` itself does not distinguish a non-problem body, malformed problem, or the exact status unless the hosted bounded diagnostic reports the numeric HTTP status separately.

Staging `crates/mail-worker/wrangler.toml` has Workers Logs enabled but `invocation_logs=false`, `traces.enabled=false`; it intentionally avoids automatic URL/path and storage-span retention. Prior scoped Observability queries returned opaque `source` objects and `UNVERIFIED`. Do not turn invocation logs or native traces on, widen that parser, use Tail, or print exceptions/stack/error pages to investigate this incident. Cloudflare's current Workers Logs can retain uncaught exceptions, and its error-query examples use `$workers.outcome` or `$metadata.error`; those events may include raw exception messages and stacks, so they are **not** an approved output surface here. [Workers Logs](https://developers.cloudflare.com/workers/observability/logs/workers-logs/), [errors and exceptions](https://developers.cloudflare.com/workers/observability/errors/).

## One bounded read-only query to run first

Use Cloudflare's **Workers Metrics GraphQL API**, not the raw Observability event view. Official `workersInvocationsAdaptive` supports account, exact `scriptName`, UTC `datetime_geq`/`datetime_leq`, and `dimensions.status` plus `sum.requests`/`sum.errors`. Query a narrowly justified window covering the one add invocation and possible adjacent health/Cron traffic; start from the hosted step timestamps, not an invented exact second. Have a reviewed CI helper validate the response schema and print **only** a closed invocation-status enum (`success`, `scriptThrewException`, `exceededResources`, `internalError`, `clientDisconnected`, `other`) and small bounded counts, never `dimensions.datetime`, raw GraphQL JSON, IDs or error messages. Require exact account/script filtering, no GraphQL errors, no truncation/limit exhaustion, and compare the request count with other known traffic before attributing a bucket to this add. No status bucket is a per-request causal link. The [official Workers Metrics tutorial](https://developers.cloudflare.com/analytics/graphql-api/tutorials/querying-workers-metrics/) provides the API call and field names; [Workers Metrics](https://developers.cloudflare.com/workers/observability/metrics-and-analytics/) explains that invocation status differs from HTTP status.

| Observed aggregate status during the bounded window | Supported inference, only if the relevant invocation can be isolated | Still unknown |
| --- | --- | --- |
| `scriptThrewException` | At least one Worker invocation threw an unhandled exception (Cloudflare associates this with 1101). A Rust/Wasm trap is a plausible mechanism, not proved. | Whether it was the add request, and the exact trap site. |
| `exceededResources` | At least one invocation exceeded a runtime resource limit (often 1102/1027); investigate CPU/startup/memory with separate safe evidence. | Whether the add caused it and which resource. |
| `internalError` | At least one Cloudflare runtime internal error, not necessarily Worker-code failure. | Whether the add was affected. |
| `success` only | The Worker invocations represented in that metric completed normally; an **application-produced** HTTP 500 or an upstream/edge response remains possible. | HTTP status, response source, and even whether the add is included in the aggregate. |
| No row, mixed buckets, or schema/permission/aggregation uncertainty | `UNVERIFIED`. | Everything causal; absence is not proof of no trap. |

This is materially more privacy-preserving than a raw log query because the selected GraphQL fields are aggregate counters and fixed status labels. It is also weaker: no path, request ID, body, or exception details are exposed, and therefore a busy time window cannot pinpoint a request. Workers Metrics may lag briefly; perform the read after aggregation, not as a rapid loop. The successful rule-write control-plane probe is independent of this runtime diagnosis.

## If metrics cannot identify the request

Do **not** replay this address add. First preserve the exact route and D1 state with the existing read-only reconciliation and safe cleanup protocol. For a future explicitly reviewed single-use attempt, add a fixed, request-local boundary marker *before* the potentially trapping call and a fixed completion marker after it, both tied to the server-generated request ID in an approved allowlisted event; log no `Error`/`Debug`, stack, SQL, address, provider payload, or URL. A catch boundary around a Rust `Result` cannot catch a Wasm trap, so the last observed phase is only a lower bound; a top-level trap cannot emit the usual `request_exit` or response header. Any future attempt needs its own address-state gates and separate cleanup audit. For this incident, aggregate status is the smallest useful next discriminator, not a full root-cause oracle.
