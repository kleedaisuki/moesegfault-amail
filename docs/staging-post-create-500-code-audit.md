At this revision, `platform::create_rule` constructs and sends the JSON POST, then awaits `response.text()` and `classify_create_response` (`crates/mail-worker/src/platform.rs:211-270`). In `add_address`, the next source operations are `trace.routing_create`, conversion of a typed create failure to `AppError`, duplicate-rule cleanup (only if prior matches existed), D1 activation, D1 readback, and response encoding (`crates/mail-worker/src/lib.rs:1344-1424`). An ordinary provider refusal, response read error, malformed response, or missing ID returns `routing_unavailable` 503 (or `capacity_exhausted` 409). An ordinary D1 `?` error maps to `service_unavailable` 503; the activation mismatch path returns 409/503. The staging dispatch wraps *all returned* `add_address` results in a problem/success response and adds its bounded diagnostic header; the top-level `main` adds `x-amail-request-id` (`lib.rs:715-732,810-821,1309-1424`). **No normal returned branch in this add path deliberately emits HTTP 500.** Thus a 500 without an accepted diagnostic is consistent with a failure outside these returned branches: an unhandled JavaScript/Wasm exception, runtime resource termination, an edge-generated response, or malformed/missing headers; this remains a classification, not an identified line of code. `http_error` is a deliberately broad CLI code for non-problem and unrecognized problem bodies, so it does not identify the response origin by itself (`crates/amail/src/api.rs::address_problem_code`).

The narrowest post-POST source interval is between the provider's rule-side effect and an accepted response from `add_address`. `response.text()`/JSON decode, `trace.routing_create`/console emission, D1 activation, and the final response/header path are candidates. The facts do **not** rank a `response.text()` panic over an activation-time runtime failure, because the provider's side effect precedes both. A plain malformed JSON result is *less* consistent with the observed 500, since the code maps it to 503 with a staging diagnostic. A D1 SQL failure is likewise *less* consistent unless it escapes the Rust `Result` path (for example, a JavaScript binding trap). A huge provider response, CPU exhaustion, or a specific `worker-rs` defect has not been observed and must not be asserted. The route and null rule ID are compatible with an exception at several later points and with a concurrent mutation before snapshot.
