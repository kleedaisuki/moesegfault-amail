Status: source-level incident analysis, **not** a live readback (2026-09-29). No new alias, mail, API request, route mutation, D1 query, or replay was performed for this analysis. The reported hosted run is [36589042183](https://github.com/kleedaisuki/moesegfault-amail/actions/runs/36589042183), source SHA `0e6064e`; verify the serving Worker version separately before treating source paths as deployed facts.

## Fixed observed boundary

The supplied run report says native PKCE and address add succeeded, followed by an exact one-owned route and D1 `active`, `needs_reconcile=0` readback. The harness printed `smtp_submitted`, then `mail_sync_failed_http_409_unknown_code`, and finally `message_cleanup_failed`. These facts establish SMTP submission, **not** provider acceptance, ingress, persistence, ZIP retrieval, or search acceptance. `message_cleanup_failed` is secondary: `cleanup_run` calls the same `amail sync --limit 100` to discover run-owned messages before deletion, catches any exception, independently retires the address, verifies route and CLI-list absence, and only then raises this label. Therefore reaching this particular label implies the harness saw the address/route absent at its final cleanup readback; it does **not** attest D1 address tombstone or deletion of either message.

## Single most discriminating next read-only check

First, pin the exact Mail Worker **serving version** at the run time. Its source determines whether the cursorless list's `search_job_stale` is indeed the only application 409 branch. The retained trace schema in `crates/mail-worker/src/trace.rs` intentionally records only coarse `conflict`, **not the exact public problem code**; the hosted harness discarded raw CLI stderr and the ephemeral run directory. Therefore ordinary retained application traces cannot settle which code was masked. Do not assume an exact-code log exists; aggregate invocation counts or a fresh list request cannot recover this historical code. If an already-retained, access-controlled HTTP response-code artifact happens to exist, inspect only an allowlisted exact code and opaque request ID privately. Otherwise classify the precise 409 code as `UNVERIFIED`, even if the pinned source makes `search_job_stale` overwhelmingly plausible. Do **not** run a new authenticated sync merely to see whether 409 recurs.

The highest-value actionable read-only check after the version pin is a separately reviewed, exact-run **D1 aggregate**, privately bound to the HMAC-derived run alias and synthetic principal, returning only: number of matching inbound messages by active/deleted state (and separately the two known fixture categories as counts), embedding pending/succeeded/failed counts, the current owner search generation, and exact address state/`needs_reconcile`; independently confirm exact route absence. Do not select raw message rows or log aliases, subjects, body, IDs, vectors, or tokens. This establishes whether SMTP crossed ingress/persistence and whether messages remain after failed cleanup; it cannot reconstruct the 409 instant or prove a generation race. If messages remain, plan **only exact run-owned cleanup** after review, not a new alias or broad delete. The failed acceptance gates remain failed until a separate guarded retest is justified; no automatic replay or blind SMTP resubmission.

## Implementation issue for later review, not an emergency mutation

The harness's `SAFE_API_CODES` should include the documented search consistency codes and its cleanup should not depend solely on a fallible mailbox list to discover known run-owned deliveries. Merely adding `search_job_stale` to the allowlist improves diagnosis but does not make this run pass. A bounded retry policy may be appropriate for cursorless list **only after** tests show that 409 is transient and replay-safe; it must not obscure persistent failures or conflate them with successful delivery. Keep the privacy boundary and established CLI response contract intact.

## Decision for the next run's own cleanup (2026-09-30)

**Harden `staging_mail_e2e.py::cleanup_run` before another normal SMTP run.** The cursorless `sync` replay addresses one likely read conflict, but current cleanup still reads only the first 100 messages, exits on another 409, and deletes any row with one of two matching subjects without checking mailbox, sender, MIME, or source-generated Message-ID. The fifth run demonstrated the operational consequence: alias retirement succeeded while two active, indexed fixtures remained. A new run should not knowingly repeat that cleanup contract. This is a harness-safety gate, not a reason to broaden production CLI retries or claim the historical 409 cause.

The small current-run design is:

1. Preserve `finally` and its independent address-delete/routing readback. Have `main` pass to cleanup the **in-memory MIME oracles generated before SMTP** (or `None` if it never reached mail construction) and whether SMTP was attempted. This distinguishes a partial SMTP submission from a pre-send failure without reconstructing mail from a title alone. Do not print the oracles. A failed message phase must never suppress alias retirement; preserve both fixed primary and cleanup labels.
2. Replace one-page `sync` discovery with a bounded, complete owner-scoped `amail search --mailbox <exact run alias> --limit 100` inventory. Exhaust `next_cursor`; reject malformed/repeated cursors, duplicate IDs, mismatched mailbox/direction, incomplete pages, and oversized output. Resume a still-running search job by its returned job ID. On only `search_job_stale` or `search_cursor_stale`, discard the **entire** partial inventory and restart from page 1 at most twice after bounded delays; never append pages from different generations, retry a delete, or reinterpret an unknown 409 as an empty mailbox. The reviewed fifth-run cleanup has this pagination logic, but imports `staging_mail_e2e`; importing it back would create a cycle. Move only the generic inventory/status parser into a neutral test helper, or implement the same small function locally; do not import fifth-run coordinates, account-specific D1 audit, or its one-shot dispatch contract.
3. Before any delete, require the *complete* inventory to be a subset of the two generated fixture subjects and at most one row per subject. If an oracle is absent, delete no message. For each active ID, run owner-scoped `amail get ID` and compare exact ID, mailbox, inbound direction, title, `From`, `To`, generated Message-ID, and expected text/HTML/attachment shape; for the rich mail, the still-live source oracle also permits checking ZIP body phrase and attachment SHA-256 before deletion. A different delivered Message-ID is unexplained, not a waived check. An extra row, duplicate, changed inventory, or unverifiable field stops message mutation. Re-inventory immediately before the first delete. The HMAC alias and matching headers are locators, not proof against an adaptive forger; this is an accidental-wrong-ID guard for a controlled synthetic mailbox, not a general mail-authenticity mechanism.
4. Delete **one verified ID at a time**, then require `get ID` to return exact `404/not_found` and a fresh complete inventory to equal the previous inventory minus that ID before considering the next. If delete times out or yields a non-204/unexpected response, read back the same ID once and report uncertainty rather than blindly retrying. Already-deleted fixtures are simply absent from the active inventory. Finally require zero active rows in the exact mailbox. Because SMTP delivery can lag both submission and the first cleanup read, an empty inventory immediately after SMTP attempt is **not** positive cleanup evidence: wait a bounded settling interval and corroborate with a parameterized exact-alias D1 active/deleted count after route retirement; if ingress is still ambiguous, report `message_cleanup_unverified` and retain a targeted delayed audit. Do not treat a successful address/route readback as message deletion proof.

This adds no user-visible CLI contract and no production Worker branch. Focused hosted synthetic tests should cover a first-page and mid-pagination 409, repeated cursor, extra same-title wrong-mailbox/Message-ID row, partial SMTP submission, ambiguous delete, and the invariant that address retirement is attempted after every message-phase failure. A normal E2E that reaches ZIP/search but reports cleanup uncertainty remains a failed overall acceptance; it does not justify an automatic second live probe.
