# Fifth hosted staging acceptance: message-list HTTP 409 after SMTP

Status: source-level incident analysis, **not** a live readback (2026-09-29). No new alias, mail, API request, route mutation, D1 query, or replay was performed for this analysis. The reported hosted run is [36589042183](https://github.com/kleedaisuki/moesegfault-amail/actions/runs/36589042183), source SHA `0e6064e`; verify the serving Worker version separately before treating source paths as deployed facts.

## Fixed observed boundary

The supplied run report says native PKCE and address add succeeded, followed by an exact one-owned route and D1 `active`, `needs_reconcile=0` readback. The harness printed `smtp_submitted`, then `mail_sync_failed_http_409_unknown_code`, and finally `message_cleanup_failed`. These facts establish SMTP submission, **not** provider acceptance, ingress, persistence, ZIP retrieval, or search acceptance. `message_cleanup_failed` is secondary: `cleanup_run` calls the same `amail sync --limit 100` to discover run-owned messages before deletion, catches any exception, independently retires the address, verifies route and CLI-list absence, and only then raises this label. Therefore reaching this particular label implies the harness saw the address/route absent at its final cleanup readback; it does **not** attest D1 address tombstone or deletion of either message.

## Single most discriminating next read-only check

First, pin the exact Mail Worker **serving version** at the run time. Its source determines whether the cursorless list's `search_job_stale` is indeed the only application 409 branch. The retained trace schema in `crates/mail-worker/src/trace.rs` intentionally records only coarse `conflict`, **not the exact public problem code**; the hosted harness discarded raw CLI stderr and the ephemeral run directory. Therefore ordinary retained application traces cannot settle which code was masked. Do not assume an exact-code log exists; aggregate invocation counts or a fresh list request cannot recover this historical code. If an already-retained, access-controlled HTTP response-code artifact happens to exist, inspect only an allowlisted exact code and opaque request ID privately. Otherwise classify the precise 409 code as `UNVERIFIED`, even if the pinned source makes `search_job_stale` overwhelmingly plausible. Do **not** run a new authenticated sync merely to see whether 409 recurs.

The highest-value actionable read-only check after the version pin is a separately reviewed, exact-run **D1 aggregate**, privately bound to the HMAC-derived run alias and synthetic principal, returning only: number of matching inbound messages by active/deleted state (and separately the two known fixture categories as counts), embedding pending/succeeded/failed counts, the current owner search generation, and exact address state/`needs_reconcile`; independently confirm exact route absence. Do not select raw message rows or log aliases, subjects, body, IDs, vectors, or tokens. This establishes whether SMTP crossed ingress/persistence and whether messages remain after failed cleanup; it cannot reconstruct the 409 instant or prove a generation race. If messages remain, plan **only exact run-owned cleanup** after review, not a new alias or broad delete. The failed acceptance gates remain failed until a separate guarded retest is justified; no automatic replay or blind SMTP resubmission.

## Implementation issue for later review, not an emergency mutation

The harness's `SAFE_API_CODES` should include the documented search consistency codes and its cleanup should not depend solely on a fallible mailbox list to discover known run-owned deliveries. Merely adding `search_job_stale` to the allowlist improves diagnosis but does not make this run pass. A bounded retry policy may be appropriate for cursorless list **only after** tests show that 409 is transient and replay-safe; it must not obscure persistent failures or conflate them with successful delivery. Keep the privacy boundary and established CLI response contract intact.
