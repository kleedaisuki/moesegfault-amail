# Read-only gate for two prior staging E2E aliases

Status: **implemented but not dispatched**. The two historical hosted address attempts are [run 36524101354](https://github.com/kleedaisuki/moesegfault-amail/actions/runs/36524101354) and [run 36533465672](https://github.com/kleedaisuki/moesegfault-amail/actions/runs/36533465672), both attempt 1. The first had a private readback at 05:15 UTC showing no exact route or CLI-visible address and a retired, reconciled D1 row; the second's hosted `address_route_retired` marker proves route and CLI-list absence at cleanup time, **not** final D1 reconciliation. This new gate checks current state for both; it does not recover either original failure cause.

## Fixed procedure

The manual `staging-prior-alias-reconcile` CI target requires `READ_PRIOR_STAGING_ALIASES`. `infra/tests/staging_prior_alias_reconcile.py` receives existing protected staging secrets only within its one read step. It reproduces `staging_hosted_e2e.py::recoverable_run_nonce`'s HMAC-SHA256 v1 derivation using the synthetic password and fixed run ID/attempt coordinates; addresses never leave process memory except as private provider query parameters. It requests all pages of Cloudflare Email Routing Rules with the existing routing token and makes one fixed, parameterized `SELECT` per address using the staging D1 query API with the existing operator token. D1's HTTP `POST /query` executes a read-only SQL statement; the script has no routing-rule POST, mail API mutation, SMTP, browser login, or Worker deployment path.

The acceptance predicate for each alias is: **zero exact literal `to` routing rules**, plus **zero D1 address rows or one row with `state=retired`, `cf_rule_id=NULL`, `needs_reconcile=0`, the expected staging issuer, and a bounded nonempty OIDC subject**. If both rows exist, their private subjects must match; no new owner-subject secret is needed. Missing credentials, incomplete rule pagination, unrecognized response shapes, duplicate D1 rows, or any read failure fail closed. The script prints exactly one fixed `clean|not_clean|unverified` label per historical run and one overall gate label. It never prints aliases, rule IDs, subject, secret values, raw JSON, or exception text. The job uploads no artifact. A `clean` result is a current readback, not a proof about historical intermediate operations.

The job deliberately does **not** perform a fresh Identity login or CLI `address list`: authorization would require the synthetic account's login flow and would materially expand this diagnostic. The original hosted cleanup already observed CLI absence for each alias; current exact D1 owner/state plus independent provider-route readback are the stronger current isolation gate. If either is not clean, do not attempt a third address add; reconcile only that exact alias through the reviewed existing process. No new E2E run is authorized merely because this read-only gate passes.

The D1 check establishes that any retained row has the staging issuer and a bounded subject, and that the two subjects agree if both rows exist. It does **not** independently prove that the subject belongs to the synthetic account; that would require a separate trusted Identity-to-subject assertion. The private HMAC-derived exact address, immutable D1 primary key, retired/reconciled state, and exact provider-route absence are the isolation evidence used here. Do not describe this as an independently verified account-ownership proof.

## Reproducibility and decision

From the reviewed branch, manually dispatch `CI and deploy` with `target=staging-prior-alias-reconcile` and `confirm=READ_PRIOR_STAGING_ALIASES`. Do not supply addresses, passwords, or tokens as dispatch inputs. Review the branch SHA and workflow diff before dispatch. Record only the GitHub run URL, source SHA, fixed outputs, and whether all three gate labels indicate clean. If the job fails, classify it as `not_clean` versus `unverified` from the fixed output; never infer a routing permission fault from a read failure alone.
