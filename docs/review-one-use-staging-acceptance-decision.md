# Review: one-use staging product-acceptance decision after historical log limits

Status: independent documentation/operational review (2026-09-29); **not a test dispatch or unconditional approval**. Scope: the proposed amendment to `staging-address-add-incident-36533465672.md`, its validation-note counterpart, the prior [controlled-acceptance review](review-controlled-staging-e2e-without-tail.md), and the existing hosted E2E and prior-alias readback source. This review made no online request, ran no tests, and did not alter production code.

## Assessment

The distinction between **product acceptance** and **precise historical/provider-phase diagnosis** is sound. One normal CLI-created, HMAC-derived staging alias can establish whether the currently deployed path works for that synthetic account, without an invalid Rules POST or an unfinished Live Tail observer. The amendment correctly leaves the two old failures unexplained, does not equate the token-details 403/9109 with a Rules Write denial, and does not infer Write from a successful Rules GET. A failed new operation likewise cannot establish a missing Write grant. Public sending remains held; no production promotion follows from the proposed staging run.

The operational approval should remain conditional on the following gaps being closed **before** one dispatch, rather than treating the prior-alias `clean` label or a green CI/deploy as full preflight:

1. **Prior-alias CLI visibility:** `staging_prior_alias_reconcile.py` checks complete exact-rule inventory and staging D1 state for both earlier aliases, but does not call the authenticated CLI list. The amendment now supplies a code-backed implication: the pinned `lib.rs::list_addresses` query excludes `state='retired'`, and the readback found both exact rows retired (or absent). This resolves the earlier third-check concern for that pinned Worker implementation; do not misdescribe the `clean` marker as a direct CLI-list observation.
2. **Per-run preflight:** The amended checklist now pins checkout SHA, 100%-serving version, effective privacy and D1/R2 bindings, source-level secret injection, a quiet window, candidate absence, quota and route capacity. The newly committed `009ff1c` harness asserts the owned count, candidate absence and complete-inventory capacity before `address add`; previously it called `address list` and discarded the rows. `staging-serving-pin` was added for read-only version/configuration readback. These are **implemented gates awaiting hosted CI and live preflight**, not already passed facts. The operator artifact should contain only fixed booleans, timestamps and run/version identifiers, never address or credential.
3. **Exact post-run D1 verification:** The hosted harness's seven-minute cleanup checks Cloudflare route and CLI-list absence but does not read D1. The newly committed `e00fbd1` provides a separate exact-run HMAC-derived read-only route/D1 workflow, including crash/cancel cases. Confirm that this workflow is deployed and runnable before the E2E, then execute it after the E2E; uncertainty freezes creation. A source-level workflow definition alone is not a completed reconciliation.
4. **Historical stop language:** The amendment now marks the old no-rerun rule as historical and superseded solely for a normal, guarded one-use *product acceptance* run, not for repeated provider-phase diagnosis. This resolves the apparent conflict with the earlier live-observer design.

## Harness boundary checked

`staging_mail_e2e.py` calls `address add` at most once after an exact-rule absence preflight, reports only allowlisted public API codes, waits for an active address and exact literal route before submitting two synthetic SMTP messages, and attempts address deletion in `finally`. Its cleanup independently checks exact route and authenticated CLI-list absence under a seven-minute deadline. `staging_hosted_e2e.py` derives the alias from protected synthetic credentials and GitHub run coordinates, constrains child environments and local files, and publishes fixed labels. The Actions job has explicit `RUN_STAGING_E2E`, Windows runner, staging Environment, 40-minute timeout and a job-family concurrency group. That group is **not** a global Cloudflare routing lock; the quiet window remains an operator gate. The harness itself does not prove D1 reconciliation or effective permission-policy clauses.

## Decision boundary

Once the source changes and workflow wiring have passed hosted CI, and the **live, same-window preflight** explicitly passes, a **single** pinned hosted product-acceptance dispatch is proportionate. This review does not authorize dispatch before those gates. A positive active-address plus exact-route readback is a functional Write result for that operation; it is not a token-policy audit or a historical diagnosis. `service_unavailable`, `routing_unavailable`, generic error, missing output, or uncertain cleanup means staging acceptance failed and the next action is exact state reconciliation/instrumentation, **not** an automatic second mutation. The same conclusion holds if the historical retained event remains `UNVERIFIED (unreviewed_source_object)`; do not broaden that query just to justify the run.
