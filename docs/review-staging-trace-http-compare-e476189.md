## Contract and failure-path assessment

- The Rust binary is feature-gated by `required-features = ["staging-diagnostics"]` and built by the manual Windows job with `--features staging-diagnostics --locked`. It uses the same `reqwest::blocking::Client` version, TLS feature set, and 30-second timeout as `Api::new`; its deliberate redirect-stop policy is the documented deviation from ordinary amail API transport. It accepts only HTTPS on the exact staging host, no userinfo, explicit port, fragment, extra route or different query marker. The one generated URL is delivered on stdin, never as a process argument.
- The Python side's custom `HTTPRedirectHandler` records but refuses a redirect; the Rust policy likewise stops before following it. A redirect cannot count as the positive Worker-response contract. Both requests use one random synthetic path/query marker from the same hosted runner, without Bearer authentication, mailbox access, or mail/routing mutation. This comparison changes client transport and associated defaults (such as User-Agent/proxy behavior), so a difference is a discriminator, **not** attribution to WAF, Access, a proxy, or the Worker.
- The only emitted observations are fixed status labels, canonical application-request-ID syntax as a boolean, single `cf-ray` presence as a boolean, and redirect as a boolean. Python discards child stderr and admits only a fully matched, bounded Rust stdout line; exceptions reduce to fixed labels. The Rust child receives a narrow OS/proxy environment rather than Cloudflare credentials, and there is no artifact upload. Raw URL, marker, header values, Ray ID, response body, proxy, and provider error are not printed. A syntactically valid application ID supports but does not prove Worker provenance.
- The caller is branch-gated to `main` or `codex/amail-v0.1.0` and manual `workflow_dispatch`; the called workflow repeats the branch gate and requires an exact confirmation before build/probe. It uses the protected staging Environment, runs on GitHub-hosted Windows, and performs the existing effective privacy-settings plus Observability service-key preflight before the two GETs. The preflight is not a retained-record query; even two `401` plus IDs must not be promoted to retained-log or distributed-trace acceptance. The manual target does not select production deployment.
- The Python offline fixtures cover status bucketing, duplicate/malformed headers, 403 and redirect non-acceptance, and child credential stripping. The Rust `valid_target` test is feature-gated and the regular `cargo test --all-targets` does not exercise it; the diagnostic workflow builds but does not run that unit test. Adding a hosted `cargo test -p amail --features staging-diagnostics --bin staging-http-compare --locked` step would improve coverage, but this is not a demonstrated unsafe path: the exact generated URL and the manual build remain constrained. Do not run heavy tests on the developer machine.

## Disposition

Any 403, mixed result, redirect, network/preflight error or unrecognized output stays `UNVERIFIED`; investigate its specific boundary before changing edge policy. The historical 403 and retained-log privacy remain unproven by this source review.
