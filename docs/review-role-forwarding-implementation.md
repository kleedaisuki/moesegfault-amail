# Independent review: confidential role-forwarding automation (2026-09-28)

Scope: reviewed the frozen `infra/provider/ensure_role_forwarding.py`, `infra/tests/test_role_forwarding.py`, `.github/workflows/role-forwarding.yml`, and the existing role-intake/forwarding design notes. This is a static review, not a Cloudflare API run or proof of external SMTP receipt. The confidential destination value is intentionally absent from this artifact. No production code was modified during review.

## Assessment

No demonstrated P0/P1 confidentiality or routing-rule defect was found in the four-production-role automation. The workflow is manual, restricted to `main`, targets the `production` GitHub Environment, and requires an additional fixed confirmation phrase for `apply`. The Python entry point reads the destination from an environment secret rather than a workflow input, never prints request/response bodies or the destination, and maps network/API/JSON failures to redacted messages. The test suite checks successful output for non-disclosure; it should eventually exercise failure paths too. All four production role aliases are explicit; no user mailbox, catch-all, or unrelated route is created or mutated.

The provider client traverses all advertised pages before deciding, bounds response size/page count, and fails closed on malformed pagination. It verifies that the destination registry entry has a non-null verification timestamp before `audit` or `apply`. Existing role matches are detected case-insensitively, including malformed multi-matcher rules; only one enabled, `source=api`, exact lowercase literal-to matcher with one forward action to the selected destination is accepted. Duplicates, disabled/worker/drop/wrong-destination rules and missing ownership metadata block writes. A non-idempotent POST with an uncertain outcome is followed by read-back rather than blind retry. These are appropriate controls for provider state that cannot be transacted with GitHub Actions.

### Read-only live provider-shape correction

The first restricted local `request-verification` attempt **did not create a destination**: it stopped during the preliminary address listing because the initial pagination parser required `result_info.total_pages`. A read-only Cloudflare API probe on 2026-09-28 found both account destination and zone rule lists return `page`, `per_page`, `count`, and `total_count`, but omit `total_pages` (observed `per_page=50` for the requested page size). The implementation now derives the bounded page count from `total_count/per_page`, checks every page's `count`, page number, and stable total, and optionally cross-checks `total_pages` if present. Offline fixtures cover empty/nonempty inventories, a 51-rule second-page conflict, and truncated counts. This is provider-shape evidence and a source correction, **not** a passed hosted test or a verification email having been sent.

## Non-blocking documentation/scope mismatch

`docs/operator-intake.md` previously described two staging-subdomain role aliases as part of the planned automation. This workflow and script intentionally implement only the four public/canonical **production** aliases, and production external receipt is the release gate; staging role forwarding is not a user-facing or release requirement according to the current project decision. Clarify that staging sentence as an optional future probe rather than implying the current automation deploys it. This is documentation alignment, not a defect in the production four-role path.

## Conditional operational considerations, not demonstrated defects

1. `destination_state` compares the configured destination to Cloudflare's returned `email` string exactly. If Cloudflare canonicalizes the domain or casing differently from an owner-entered secret, a verified destination might be reported missing and a create attempt could fail as duplicate. The safe result is failure rather than misrouting; normalizing only the domain and testing a mixed-case destination fixture would improve idempotence without treating distinct local parts as the same mailbox. No source or live API observation here proves Cloudflare actually rewrites the value.
2. `expected_rule` requires a `source="api"` field in read-back, while the API schema marks `source` optional and defaults writes to `api`. If Cloudflare omits it for an API-created rule, the automation will fail closed after creating the rule and require manual resolution. This is a conditional availability concern, not an unsafe takeover. A live read-back probe is decisive before relaxing the check; do not assume absence means API ownership if Wrangler rules may also omit metadata.
3. Separate API credentials need account-level destination read/write and zone-level rule read/write. The workflow references a token secret but cannot prove its scopes statically. Environment protection rules and actual secret provenance likewise require repository-settings review. Failure should remain fail closed and redacted.

## Catch-all conclusion and live gate

An existing apex catch-all is **not** inherently a conflict with exact role rules. Cloudflare's [email lifecycle](https://developers.cloudflare.com/email-service/concepts/email-lifecycle/) says the catch-all applies only *if no configured routing rule matches*; the [API schema](https://developers.cloudflare.com/api/resources/email_routing/subresources/rules/) supports `literal` and `all` matcher types. Therefore `matched_roles` correctly focuses on literal role matches rather than rejecting a catch-all. A test now records this coexistence. Cloudflare also warns that duplicate exact email patterns can select only the first dashboard rule, which is why the script's duplicate audit matters. Nevertheless, read-back and DNS presence do **not** prove delivery to the intended external mailbox. Before attesting `abuse_contact_verified`, send distinct external SMTP canaries to all four roles (including a mixed-case recipient), inspect the destination's Inbox **and spam**, verify monitoring ownership, and keep the global send policy held until that evidence exists. See [Cloudflare routing rules](https://developers.cloudflare.com/email-service/configuration/email-routing-addresses/).

## Suggested hosted acceptance checks

- Run offline tests in GitHub Actions, including malformed/missing pagination, verified timestamp, duplicate and mixed-case role aliases, multi-matcher, uncertain POST, confidentiality on both success and failure.
- Run `request-verification` and `audit` with restricted production Environment approval; ensure action logs and artifacts contain no configured destination, provider response body or token.
- After owner-controlled verification, run `apply`, re-audit every role and provider rule ID, then perform the four real SMTP canaries and a negative unmatched-alias check. Do not set the release gate from API success alone.
