In `mail-worker/src/lib.rs`, any `worker::Error` from `platform::rules_for_address` maps to HTTP 503 `service_unavailable`, whereas a typed `create_rule` provider failure maps to 503 `routing_unavailable` or 409 `capacity_exhausted`. Thus a **pre-POST Routing Rules list failure** is a concrete alternative explanation for the bare label. The successful preflight `assert_route` used the harness's GitHub routing token, while the Worker uses its deployed secret; success of one does not validate the other. Other possibilities are CLI transport/non-HTTP failure, a code outside the harness allowlist, or a failure after a successful provider operation. The bare label alone cannot rank them reliably.

All returned records stay in memory; the script rejects unreviewed custom `source`/message payloads, extracts only schema-checked application events, and requires exactly one failed `addresses_add` request-exit plus causally linked `routing_list` and optional `routing_create` phase. It outputs only a fixed classification and bounded numeric HTTP/error facts. No raw event, address, URL, token, request ID, provider text, screenshot, or artifact is emitted.

Cloudflare's [query API](https://developers.cloudflare.com/api/resources/workers/subresources/observability/subresources/telemetry/methods/query/) documents `dry=true` as execution without persisting results and the event cursor; its [Workers Logs limits](https://developers.cloudflare.com/workers/observability/logs/workers-logs/) specify at most seven days of paid-plan retention and possible sampling after account limits. Consequently a missing result cannot be promoted to a finding about whether the Worker executed a phase.

### Observer contract and causal readout

An implementation can adapt the existing `staging_trace_canary.py::embedded_events` and `allowlisted_event` validators and `staging_address_failure_logs.py::classify`, but **must not** reuse the retained-query record wrapper unchanged: live tail has a different envelope with `logs[]`, `event.request`, and `exceptions`. Review and offline-test that wrapper first. The observer discards envelope request URL, headers, exception text, and all non-event console messages without displaying them. It accepts only schema-version-1 `mail_api` events with fixed `addresses_add` operation, `request_exit`/`routing_list`/`routing_create` phases, valid causal IDs, bounded numeric provider status/code, and no unknown keys. It tracks a single failed root and matching children by `request_id`, `trace_id`, and `parent_span_id`; a second root, malformed event, dropped/sampled stream, missing root/list phase, or inconsistent event order yields only `UNVERIFIED`. Do not identify the run from an address or URL. A success root is a normal E2E outcome, not evidence that the two historic failures had any particular cause.

The E2E's **public** output remains only its existing fixed stage code and cleanup marker. The observer's final public report is one of `routing_list_failed`, `routing_create_failed_provider_http_<3-digit-or-absent>_code_<numeric-or-absent>`, `routing_create_succeeded_later_failure`, `e2e_address_add_succeeded`, or `UNVERIFIED (<fixed reason>)`; it must never include the Cloudflare tail session URL/ID, request/trace IDs, rule ID, address, raw status line, stderr, or raw event. A 200 provider status with `routing_create` phase failure is possible (`success=false`), so status alone is not success. If full validation cannot be made reliable before the authorized run, retain only the already-reviewed direct fixed CLI error capture and report provider detail unavailable; **do not claim live-tail classification**.

Suggested integration order, with a root review before wiring or dispatch: (1) pure parser and hostile fixtures under `infra/tests`, proving unknown fields and sensitive strings never reach stdout; (2) bounded live-tail adapter with a real connected/ready handshake, timeout, byte/event caps, no raw files, no unhandled tracebacks, fixed exit labels, and `finally` closing the session; (3) offline test of observer-ready gating, loss during the create boundary, duplicate roots and cleanup failure; (4) only then a single hosted dispatch, with observer established first and preserved through cleanup. The current workflow does **not** provide those gates. Do not patch it opportunistically or run the existing E2E while the observer is merely planned.

### Stop, reconcile, and freeze

One authorized attempt is **not** a retry loop. On either success or failure, complete the existing seven-minute exact-route and CLI-list cleanup readback. A cleanup timeout, missing observer event, unexpected provider outcome, or ambiguous ownership freezes further creates. The private operator then checks the one run-derived alias's provider route and D1/CLI state, waits for or invokes only the existing reconciler path as appropriate, and records a fixed cleanup classification. A public `address_route_retired` means route and CLI list were absent at the harness deadline, **not** that D1 is proven clean; verify D1 privately before lifting the freeze. Do not rerun with a new nonce to see whether an error is transient. A proven missing Write grant calls for owner action on the deployed credential, not a provider POST with `{}`; provider validation/auth ordering is not a permission oracle. Even if the new attempt passes, call the historic failures indeterminate unless their own records later become available.
