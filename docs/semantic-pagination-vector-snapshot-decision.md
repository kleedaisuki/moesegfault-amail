# Semantic pagination: reuse the scored query vector

Status (2026-09-30): **design decision, not implemented or live-verified**. The protected exact-cosine staging run `36699356379` at `11127a8` stopped at `query_vector_unstable`: two independently requested, normalized Qwen3-Embedding-8B 256-dimensional `f32` query vectors differed before the first public page. This is evidence that the existing external repeatability prerequisite failed, **not** that the Worker computed a wrong cosine. Native inbound/ZIP/basic semantic checks and cleanup passed in that run. No new provider request, local test, deployment, or live probe was performed for this decision.

This supersedes only the *pagination architecture choice* in [the v4 oracle note](staging-exact-cosine-oracle.md#architecture-choice-semantic-v4-vector-commitment-not-a-server-snapshot): v4 correctly detects drift but cannot deliver page 2 when the provider drifts. It does not supersede the release/privacy contract in [search privacy research](search-privacy-research.md), [automatic indexing decision](semantic-indexing-privacy-decision.md), or the existing [durable search job contract](search-jobs.md).

## Decision and invariant

**Use the first completed semantic `search_jobs` row as the owner-scoped, 24-hour vector origin for its cursor chain.** Emit a version-5 semantic cursor containing an opaque origin job UUID, the existing request/owner/generation/high-water/rank binding, and the v4 vector commitment. A later page loads the *same normalized `f32` vector that scored page 1* from that origin and never calls OpenRouter again. The origin row retains the vector only if page 1 actually has `next_cursor`; a one-page fast search keeps today's deletion/scrub behavior. Subsequent page jobs hold a temporary copy only while running and clear it on completion. Lexical v3 cursors and public `POST`/`202`/poll/CLI response schemas remain unchanged.

The core invariant is: for one semantic cursor chain, `q_page = q_origin` bit-for-bit for all 256 coordinates, and every page ranks all eligible documents by the same `(exact cosine DESC, received_at DESC, id DESC)` order within one account generation. A changed provider route, unavailable OpenRouter, or a later provider response cannot alter a continuation because no continuation asks the provider. This solves the *observed* failure mechanism rather than adding another special-case retry/tolerance. It does **not** make semantic relevance or document embedding versions stable; the existing document-compatibility checks and generation invalidation remain necessary.

### State model and representative transition

The existing `search_jobs` schema already has `(id, owner_iss, owner_sub, request_json, state_json, state, version, lease_started_at, created_at, expires_at)` and an owner index. `SearchState` already persists `query_vector`, `query_model`, and `vector_commitment` for a running job; `advance_claimed` currently clears the vector on every completion, and `search` deletes a fast completed semantic job. The new durable distinction should be expressed explicitly in typed state (`origin_job_id`, `is_origin`, and a versioned query-input tag), not inferred from a fragile combination of nullable fields. Do not introduce an independent snapshot service or a vector cache keyed by query text.

| Event | Durable state | Public behavior |
| --- | --- | --- |
| First semantic POST, no cursor | Admit one active job and one provider request under existing quotas; normalize/round once; scan using that exact `q`. | Existing 200 or 202/poll behavior. |
| First page completes with no next cursor | Clear `q`; delete a fast unexposed job as today, or keep a scrubbed `done` row for a publicly exposed 202 job's replay. | Final 200; no new vector retention. |
| First page completes with next cursor | In the **same completion update that makes the result publishable**, mark the job `done` with its `q`, model, commitment, generation, high-water, and expiry intact. | Return v5 cursor with `origin_job_id = this job's UUID`. If the update fails, return a typed retriable failure and publish no cursor. |
| Later semantic POST with v5 cursor | Validate syntax, owner/request hash and generation; load **only** `state='done'`, unexpired origin under `(id, owner_iss, owner_sub)`; verify origin is the cursorless first-page job and recompute commitment from its stored vector/model/tag. Copy `q` into a new bounded page job; reserve search work but **not** provider-query quota. | Existing 200 or 202/poll; no OpenRouter call. A missing/expired/stale origin is a typed restart condition, never a fallback re-embed. |
| Later page completes | Scrub its temporary `q`; if more pages exist, emit a new v5 cursor with the **same** origin UUID. Keep the origin until its original 24-hour expiry, even if this page reaches EOF. | Completed 202 page-job replay can reconstruct its cursor from origin ID + retained commitment without keeping its own `q`. |
| Origin expires or account mutates | Existing cleanup scrubs `request_json`/`state_json` at expiry, then deletes tombstone the next day. Generation checks invalidate every cursor/page job. | 410 `search_cursor_expired` (origin gone/expired) or 409 `search_cursor_stale` (generation/incompatible input version); no silent fresh-vector page. Missing and foreign-owned origin UUIDs must receive the **same** fixed response, never an existence oracle. A model mismatch in a document remains `semantic_index_incomplete`, because the retained query vector/model are still internally coherent. |

There is no all-pages materialization: each page still performs the existing bounded exact scan/checkpoint over the eligible mailbox and retains only `limit+1` hits. The origin is a *vector*, not a frozen document snapshot. Existing `search_generations` triggers are what prevent a mixed corpus epoch. A continuation can be admitted just before origin expiry and run for multiple 202 polls; check origin validity on admission and before final publication. The completion SQL should conditionally require both the account generation and an unexpired, done origin, so a cleanup race cannot publish a new cursor referencing a scrubbed row. An in-flight lease may safely rescan from its last committed marker after Worker failure; a later lease holder still wins through existing `version` compare-and-swap. A 202 result whose origin expires after its own completion may be replayed under the existing completed-job contract, but its returned cursor is expired; document this bounded token lifetime rather than silently renewing the origin.

The v5 cursor's *whole rank boundary* should also be authenticated. The reviewed v4 cursor is base64 JSON: its commitment detects vector drift, but a caller can change `last_score_bits`/time/ID and skip or repeat their own rows. Generate a random 256-bit **per-origin MAC key** (not an application-global secret), keep it only in the origin row, and HMAC-SHA-256 a canonical, versioned byte encoding of all v5 cursor fields (including origin UUID, owner/request hash, generation, high-water, last score bits/time/ID, model/input tag and vector commitment). Verify in constant time after loading the owner-scoped origin and **before scanning**. `crates/mail-worker/Cargo.toml` already declares `hmac`, `sha2`, `subtle`, and `getrandom` with the Worker JS feature, so this needs no new cryptographic dependency. A per-origin key expires with the row: ordinary global key rotation and multi-key deployment windows are unnecessary. Emergency revocation is the existing origin scrub/delete, with typed cursor expiry. The key must never appear in cursors, CLI output, traces, or operator artifacts. If implementing HMAC would delay the correctness fix, it is separable, but then v5 must explicitly retain the inherited v4 boundary-tampering limitation rather than advertise cursor integrity.

## Why this physical model

| Option | Benefit | Cost/risk | Judgment |
| --- | --- | --- | --- |
| **Completed origin `search_jobs` row** | Existing owner-scoped lookup, active-job CAS/leases, 24-hour TTL/cleanup, quota and 202 replay; no new table, global crypto secret, or extra D1 write on first-page completion. | New fast multi-page searches retain private query + vector for up to 24 hours; the existing 256 retained-job cap can become visible. A later page adds one indexed origin-row read; 202 pages temporarily duplicate `q`. | **Choose now**. It turns the existing job's vector into a purposeful bounded lifetime instead of maintaining a second lifecycle. |
| Dedicated `semantic_query_snapshots` TTL table | Clean separation from job replay/caps; could keep only canonical hash/model/vector, not full request text; independent snapshot cap/TTL. | Add schema, admission/GC, origin/page transaction boundary, race handling, and new operating surface. Page jobs still need a temporary copy for resumability. | Consider only if measured retained-job cap or privacy minimization makes the shared row materially harmful. |
| Authenticated-encrypted self-contained cursor (AES-GCM) | No D1 vector origin lookup/storage after page 1; no origin TTL table. | Carries ~1 KiB of private vector bytes in every CLI-visible cursor (plus nonce/tag/metadata); leaked stdout/history/artifacts become disclosure risks; deployment key rotation invalidates old cursors unless old keys are retained; no practical server-side revocation. Requires careful AEAD associated-data and size limits. | Reject for this privacy-sensitive CLI. Encryption is not a substitute for a safe server-owned data lifecycle. |
| Keep v4 commitment and re-embed each page | No new state/lookup. | Observed provider drift yields typed 409 and prevents pagination; provider cost and outage dependency recur each page. | Retain only as a one-release compatibility path for already-issued v4 cursors, not the new product path. |

Cloudflare documents a [2 MB D1 row/string limit and single-threaded per-database execution](https://developers.cloudflare.com/d1/platform/limits/), while [D1 pricing counts rows read/written and storage](https://developers.cloudflare.com/d1/platform/pricing/). A 256-coordinate `f32` vector is 1,024 raw bytes; JSON is larger but orders of magnitude below a 2 MB row. Existing job `state_json` already carries it while running. The chosen design adds roughly one indexed origin read per continuation request and retains one bounded origin row per cursor chain, not one extra provider call per page. Exact D1 bytes, row-read cost, and retention prevalence must be measured on staging rather than inferred from raw-vector size. D1's [batch semantics](https://developers.cloudflare.com/d1/worker-api/d1-database/#batch) can atomically group statements when required, but a single conditional `done` update should be preferred here. The embedding API documents `dimensions`, `input_type`, and provider routing parameters, but not a cross-request bitwise identity guarantee; provider repeatability must not be a pagination invariant ([OpenRouter API](https://openrouter.ai/docs/api/api-reference/embeddings/create-embeddings)).

### Privacy and compatibility boundary

The vector and query text are mail-derived account data, not telemetry. Existing 202 jobs already retain both while active; this decision extends retention **only** for first-page origins with another page, to at most the current 24-hour job TTL. **A fast 200 multi-page search previously deleted its job, so retaining its origin now also retains its private `request_json` query text for up to 24 hours.** This is a real privacy-contract change, not just a vector-cache implementation detail; update the public manual/first-use privacy wording and operator retention documentation before release. Keep an owner cap and count retained origin rows under the existing total-job cap; never evict an unexpired origin behind a valid cursor merely to admit a new search. Make quota exhaustion explicit (`search_job_quota`). Scrub vector/query/MAC key on expiry, generation-invalidated stale detection, or deliberate revocation. Do not put raw query, vector, MAC key, full cursor, or digest in logs/traces/Actions artifacts. The cursor exposes an opaque UUID and the pre-existing owner/request-bound commitment, not the vector. Continued pagination still sends no new text to OpenRouter; automatic document indexing remains an independent, explicitly disclosed third-party transfer.

Do not reinterpret v4 semantic cursors as v5: they contain no origin ID. For **one release after v5 rollout**, keep their existing re-embed + strict vector-commitment check, which either continues with the *same* vector or returns typed 409 `search_cursor_vector_changed`; it must never silently accept drift. New cursorless first pages emit v5, so no new v4 chains are created. Explicitly retire v4 semantic continuation in the next planned release, with typed 409 `search_cursor_stale` and restart guidance. A calendar cutoff measured from deployment would require a separately configured rollout timestamp, while v4's `high_water` is a snapshot time rather than a contractual issuance/expiry field; do not mislabel it as a 24-hour token expiry. Current v3 lexical cursors remain readable; v3 semantic cursors already return `search_cursor_stale`. Public `POST /v1/messages/search`, `GET /v1/messages/search/jobs/{id}`, CLI `--cursor`/`--resume`, HTTP 200/202 bodies, and deterministic ordering do not change. CLI must surface cursor expiry/staleness as a restart-from-page-1 instruction and must not append restarted rows to an old page stream. Preserve `search_job_expired` for an expired job ID; distinguish the new origin-cursor expiry code only for cursor use. No destructive migration is required: old rows lack origin fields and keep old behavior; new typed fields should be `serde(default)`/version-gated. The source repository currently has no released production Mail user base, but a rolling staging deployment still needs this old-cursor path.

## Implementation slices and gates

1. **Model and wire:** add typed origin identity/query-version/MAC state, v5 cursor encoding/decoding, and a fixed canonical HMAC fixture. Keep v3 lexical decoding and the existing strict v4 semantic compatibility path for one release. Validate malformed UUID, score, digest, MAC, mismatched owner/filter/generation and origin state before any scan or provider call; v4's provider call remains after its current preflight validation.
2. **First page:** preserve its exact in-memory vector on `done` **only when `has_more`**, generate/store the per-origin MAC key, and retain a fast job only in that case. Ensure failure to persist the origin cannot return a v5 cursor. Test fast 200, long 202, completed poll replay, and no-cursor cleanup separately.
3. **Continuation:** load/verify origin before admission; reuse its vector, skip `platform::embed` and semantic provider quotas, keep existing scan-work admission, lease/checkpoint/generation guards, and copy-scrub on completion. Check origin again at publish. Preserve the same origin through page 3+, not a chain of page jobs.
4. **Retention/operations:** ensure 24-hour cleanup scrubs all private fields including MAC, stale-triggered scrubs do the same, and no logs or telemetry serialize state/cursors. Measure retained-origin count/bytes, origin lookup row reads, 202 poll cost, cursor-expiry/stale rates, and jobs hitting the 256 cap using aggregate fixed labels only. Tune caps from production-like synthetic workloads, not theoretical page counts.
5. **Independent acceptance:** fake a provider returning `q1` on the first request and incompatible `q2` thereafter. Fetch at least three `limit=1` pages over synthetic stored vectors; assert only one provider call, all scores equal independently computed cosine with `q1`, no duplicate/skip, stable tie order, and no `q2` use. Exercise concurrent/replayed cursors, a page crossing a 202 lease, account mutation, origin TTL/cleanup race, owner isolation, malformed/tampered cursor, model/input-version mismatch, and old-cursor compatibility. Record D1 meta rows read/written and byte size. No live claim follows from these tests alone.

**Oracle consequence.** The old protected oracle required two independent provider vectors to be bit-identical *before* searching, so the reported run stopped before it could assess actual Worker scores. Under v5, the operator can read the exact first-page origin vector after the first result and before the two synthetic messages are deleted, using a fixed owner-scoped, job-ID-scoped D1 `SELECT`. Independently compute cosine from that vector and the already restricted document-vector snapshot, verify the v5 commitment and public scores/order over both pages, and assert the second page made no provider embedding request via a restricted count/controlled fake-provider gate. No provider repeatability assumption is needed. The protected process must keep query/vector/IDs/cursors in memory only and emit fixed labels plus bounded numeric error; a missing origin is `oracle_vector_unavailable`, not a conditional score pass. Revise the existing oracle's status and harness only after implementation and reviewed hosted tests; the current failure is not retroactively repaired.

**Unresolved assumption to measure:** the existing 256 retained-jobs-per-owner/24h cap may be too restrictive if users create many distinct multi-page semantic searches rather than consume pages from a few origins. A staging workload of 1, 32, and 256 concurrent/serial cursor chains with realistic `limit` values should measure cap incidence, D1 bytes, origin lookup latency, and cleanup lag. If this is material, split origins into a dedicated TTL table with its own measured cap; do not pre-emptively add that machinery.
