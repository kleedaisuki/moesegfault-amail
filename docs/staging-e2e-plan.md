# Staging end-to-end acceptance plan

Status: **test design, not execution evidence** (2026-09-28). The staging mail API, Email Routing ingress, and Email Sending lifecycle consumer were deployed in [run 36435391147, attempt 2](https://github.com/kleedaisuki/moesegfault-amail/actions/runs/36435391147/attempts/2); `/health` plus unauthenticated denials were observed (`docs/validation.md`). No authenticated SMTP-to-ZIP-to-search or outbound lifecycle canary has passed. This plan specifies the smallest real probes that can distinguish control-plane, data-plane, authorization, provider, and privacy failures. Run build/cross-platform work and automated tests on GitHub Actions, not the developer workstation.

## Contract and test boundary

Use `docs/architecture.md`, `docs/search-jobs.md`, `docs/outbound-abuse-operations.md`, and `skills/amail/references/archive.md` as the expected behavior. **The deployed response, not the source or this plan, determines observed status.** The test account is a synthetic staging Identity account created through the separately controlled verification-code channel. A second distinct synthetic principal is needed for cross-account isolation. Do not use a real person's mailbox or promote staging credentials to production. The staging CLI environment must pin all three values before login:

```text
AMAIL_HOME=<repository>/.temp/staging-e2e/<run-id>/<principal>
AMAIL_API_BASE=https://mail-staging.moesegfault.dev
AMAIL_ISSUER=https://identity-staging.moesegfault.dev
AMAIL_CLIENT_ID=amail-cli-staging
```

The login step must complete an actual native-client Authorization Code + PKCE flow with the synthetic account, with CLI and browser/verification channel colocated on a GitHub-hosted runner so the `127.0.0.1` callback reaches the CLI. A remote human browser cannot complete a loopback callback on a different runner. If a safe hosted browser/OTP arrangement is unavailable, mark the authenticated E2E **blocked**, not passed; do not inject a bearer token, disable audience checks, expose the authorization URL in public logs, or copy a user's refresh token into GitHub Secrets. The user's production login evidence is not staging authorization evidence.

The one-time synthetic-account setup and exact native-login sequencing are specified separately in [staging Identity flow](staging-identity-flow.md). Registration and email verification must finish **before** the CLI's five-minute loopback listener starts.

All test addresses, messages, subjects, asset bytes, semantic queries, and external recipients must be synthetic and generated per run. Keep ZIPs and transient auth state only under repository `.temp`; GitHub logs/artifacts may contain **only** redacted status codes, opaque request/trace IDs, durations, count/size buckets, booleans, and test-case IDs. Treat D1, R2, Queue and provider logs as restricted: inspect via scoped operator access, never dump raw rows or Queue payloads into Actions logs. Use a controlled external SMTP sender and recipient inbox; do not substitute a direct call to `/internal/inbound` for SMTP or provider acceptance for delivery.

## Minimal discriminating sequence

| Gate | Hosted probe and independent oracle | Expected result; failure distinguished | Evidence to retain |
| --- | --- | --- | --- |
| 0. Environment/Identity | In one Actions run, confirm staging `/health` = 200 and unauthenticated address/search/archive requests = 401. Check staging issuer/client/host from `amail config` before two synthetic-account browser logins; run `auth status` in new processes. | A/B sessions authenticate against staging issuer, with distinct immutable subjects. A 401 after successful login implicates token audience/issuer/Worker verification; a browser failure implicates Identity/loopback. No production host touched. | Commit SHA, Actions run/job URL, opaque request IDs, status; no token/subject. |
| 1. Address + literal route | A registers one run-unique local part; `address list` reports `active` only after provision. Independently query the exact Cloudflare Rules matcher/action and D1 state under restricted access. Retry the same add; try `admin`, then have B attempt A's name. | One **enabled literal** rule targets `amail-inbound-staging`; retry creates no second rule; reserved/collision reject with stable typed errors. A mismatch between D1 `active` and rule presence is a control-plane bug. No apex or production-domain rule. | Status/error codes, rule-count delta and opaque rule ID held privately; never print alias. |
| 2. Real SMTP → ZIP | External controlled sender sends **two** run-tagged RFC 5322 messages through public MX: a multipart alternative with unique text phrase, HTML `cid:` image, and a binary attachment with a precomputed SHA-256; a second semantic distractor with different meaning. Use CLI `sync/search` to locate message IDs, `get`, `read -o`, `unpack`; compare manifest, UTF-8 text, sanitized HTML/CID, filename, attachment hash and read state. | Exactly one delivery per message to A. ZIP has safe root manifest/body/assets; no implicit read on `get/read`; absent/malformed MIME or missing CID/asset isolates ingress/parse/archive path. SMTP acceptance alone is insufficient—CLI must retrieve both. | Message count, archive/attachment hashes and validation booleans only; no body or raw MIME in logs. |
| 3. Search + mutation | On the two messages, combine mailbox, inclusive `after`, exclusive `before`, title, sender, body, allowlisted `message_id` metadata, unread, regex and case-sensitive predicates. Use a known negative for each boundary (wrong case, out-of-range timestamp, wrong mailbox). Mark one read, search read/unread, then delete only that delivery and repeat search/read. | AND semantics, exact boundary/case/regex behavior; `read` changes only by `mark`; deleted message disappears from list/search/archive while other message remains. A positive-only query is insufficient—negative controls catch ignored filters. | Case IDs → expected/observed counts, HTTP status/error code, opaque IDs. |
| 4. Exact semantic search | Wait for both indexed messages or report explicit `semantic_index_incomplete`; run one synthetic semantic query and one query with a lexical filter. Confirm 256D model metadata, finite score, descending score/time/ID order, cursor replay without duplicate/skip. For **exact cosine**, under restricted staging operator access compare API scores to an independently calculated dot/norm over the persisted 256D document vector and a separate OpenRouter query vector from the same model/input type; do not log vectors. | Correct 256D and exact-cosine scores within a declared floating-point tolerance (e.g. `1e-5` for f32 persistence); lexical filter excludes the distractor even if semantically close. A provider-shape success alone is not search proof. If an indexing delay occurs, record duration and bounded retry behavior, not one lucky final pass. | Model slug/dimensions, score-error maxima, order/cursor booleans, `index_state`; no query/vector/text. |
| 5. Ownership isolation | B lists/searches, GETs/archives, marks, deletes A's opaque message ID; B tries to retire A's address. Also test A cannot send with B's `from` (while held, sender-ownership precedence may vary; a separate ownership-specific check is needed after a canary grant). | No A content or state exposed/mutated by B; absent-vs-foreign resource response must not leak A's existence. Compare A's state before/after B attempts. One-account testing cannot establish this gate. | Status/error codes and unchanged-state booleans only. |
| 6. Held send + idempotency | A natively `pack`s a single-recipient synthetic draft ZIP, then `send`s while global policy is `held`; inspect D1 policy and provider call count privately. After the one-use canary grant below, send **once** with an explicit UUID key; replay byte-identical ZIP/key; try changed ZIP with same key. | Before grant: `send_held`, zero provider submissions. Canary: one `accepted` response and **one** provider submission; replay returns same ID/state without resend; changed payload/key = conflict. Do not use a fresh key for a retry after unknown provider outcome. | Status/state, opaque idempotency/request/provider IDs under restricted access, provider-call count. |
| 7. One-use outbound canary → lifecycle Queue | Only after gates 0–6 and controlled external inbox readiness, operator grants `grant-send-canary` to A's immutable subject and exact recipient SHA-256 for 15 minutes. Send the single ZIP to that consented inbox. Verify actual received MIME text/HTML/CID/attachment hash and SPF/DKIM/DMARC alignment. Verify Cloudflare Event Subscription emits a delivery/failure event to **staging** Queue, Rust consumer attributes it to the send request, D1 outcome is updated once; inspect DLQ/backlog. | `202 accepted` is **not delivered**. Inbox + authentication + correlated Queue/D1 lifecycle event prove the distinct provider/data-plane stages. Canary cannot be reused with a second key/recipient. A missing event after external delivery isolates subscription/consumer; a Queue event without inbox delivery is not a delivery pass. Do not manufacture a complaint to an unconsenting third party. Keep global send held and all public release attestations false. | Provider outcome type, queue/consumer/DLQ counts, opaque correlation IDs, MIME/hash/auth booleans; no envelope/body/Queue payload. |
| 8. Privacy/tracing | For one successful inbound and one accepted canary, correlate CLI SQLite span → Worker request ID/Cloudflare trace → OpenRouter/Rules/provider/Queue opaque IDs. Inspect the CLI journal and restricted Worker/Queue traces for synthetic body/query/address/token sentinel strings; check telemetry opt-out by comparing upload counts with `AMAIL_TELEMETRY=off`. | Correlation survives without subjects, bodies, raw addresses, queries, ZIP paths or tokens in application diagnostics. A full mailbox/content trace is a privacy failure even if operations succeed. Distinguish app logging from Cloudflare automatic span fields and document retention/access controls separately. | Correlation completeness matrix and forbidden-sentinel hit count; never export raw records. |
| 9. Cleanup and negative delivery | Delete A's disposable address, confirm rule absent and name retired; send one synthetic SMTP attempt to the now-unregistered recipient and verify rejection/no new mailbox delivery. Remove only run-owned ZIPs/auth homes and staging fixtures; leave provider Queue/DLQ evidence until review. | No orphan enabled route or residual discoverable delivery. If route deletion is indeterminate, stop and reconcile exact rule ID before another run; do not create a replacement alias to hide it. | Resource-count delta, rejection code/category and cleanup booleans. |

The absolute minimum credible inbound result is gates **0–3 + 5 + 9** with one real SMTP message and its ZIP/asset comparison; semantic gate 4, privacy gate 8, and outbound gates 6–7 are separate launch claims and must remain marked unverified until their own oracles pass. A two-message corpus is deliberate: one positive and one distractor expose ignored filters and semantic sorting without flooding Email Routing or OpenRouter.

## Long-search and quota addendum (not first probe)

The small SMTP corpus cannot force a resumable `202` search job, the 10-address limit, or route-capacity exhaustion. Do **not** send thousands of SMTP messages or fill 198 literal rules just to exercise those branches. After the basic route is healthy, use a separate GitHub-hosted, staging-only fixture job that seeds synthetic, prefix-tagged D1/R2 data for the two test owners under an audited operator credential, preserving schema constraints and recording exact cleanup IDs. It must validate `202` job poll/replay, equal-time cursor no-dup/skip, concurrent poll CAS, mutation-generation invalidation, 24-hour expiry semantics (prefer a controlled clock/test environment rather than waiting or modifying production code), and explicit resource-bound behavior. This fixture verifies the deployed D1 search implementation but **not SMTP ingestion**; keep the two evidence categories distinct. The account's eleven-address denial can be checked in a bounded later control-plane run that creates and cleans up ten unique staging rules; do not risk the first inbound probe or production capacity for it.

## Execution and stopping rules

1. Use a workflow-dispatched GitHub-hosted runner and pin the deployed staging commit/Worker versions. The synthetic test account and OTP channel must be ready before starting; no CI log may contain login URLs, codes, raw token data, aliases, message bodies or external recipient addresses. Never relax Identity, sender-ownership or ingress-secret checks for testing.
2. Gate outbound on confirmed staging global `held` state. If an ordinary send succeeds before a grant, **stop immediately**, re-hold, and investigate. Grant one canary only after inbound, ownership, provider privacy settings, monitored recipient, Queue subscription/consumer, and operator review are ready. The `grant-send-canary.yml` dispatch requires its workflow on the default branch; before that, an explicitly approved, restricted and audited staging operator action with identical one-use semantics is the only alternative. Do not edit D1 ad hoc to bypass the gate. A delivery canary is not permission to set the global policy `allowed`.
3. For each probe, record the expected result **before** invocation, then observed status, state transition, timestamp, attempt count, sanitized trace IDs and Actions job URL in `docs/validation.md`. Treat a retry that changes the outcome as an investigation, not an automatic pass. Preserve the first failure and its conditions.
4. Fail closed on orphan rules, mismatched owner, unexpected provider send, lost Queue event, or sensitive logging. Clean up only resources created by this run. Do not delete/replay a Queue or DLQ to make a dashboard green; investigate with restricted operator access.
5. Keep production untouched. Passing staging evidence narrows risk but does not attest production DNS, native login, real delivery, official `mail@moesegfault.dev` sender, abuse/postmaster intake, or the v0.1.0 Release. Those remain separate promotion gates.

## Prepared harness and remaining hosted automation

A tracked, one-time deployed-probe harness is available at `infra/tests/staging_mail_e2e.py` for **after** the synthetic account's verified native login. It accepts an existing staging `AMAIL_HOME` and the CI-built Windows `amail.exe`; it does not create an account, invoke a browser, grant sending, or touch production mail API. The operator must supply separate private `AMAIL_TEST_SMTP_TOKEN` (Cloudflare Email Sending: Edit **and read access to the sending-domain status**), `CF_EMAIL_ROUTING_TOKEN` (zone routing read), and `CLOUDFLARE_ZONE_ID` environment values. A read-only provider GET on 2026-09-29 returned `enabled=true` for the exact `mail-staging.moesegfault.dev` [Email Sending subdomain](https://developers.cloudflare.com/api/resources/email_sending/subresources/subdomains/methods/get/); the harness rechecks that status and fails closed if it cannot read or confirm it. It sends from a **staging-domain synthetic sender**, never the production official sender. It uses the documented [Cloudflare authenticated SMTP endpoint](https://developers.cloudflare.com/email-service/api/send-emails/smtp/) with implicit TLS on port 465, not a direct ingress HTTP call or a REST-send substitute. It independently audits the exact staging routing rule, waits 60 seconds after rule activation, sends two run-unique MIME messages, then uses CLI commands for `sync`, `get`, `read`, `unpack`, combined search predicates, `mark`, `delete`, and address retirement. The source-generated Message-ID and delivered-header Message-ID remain separate: the harness records only a fixed preserved/changed-unattributed label, then checks ZIP/API/search **internal consistency** against the delivered header, while body and asset checks use independent source-generated phrase and digest oracles. A changed ID is a discrepancy with **unknown cause**, not proof that the SMTP provider rewrote it; resolving attribution requires an independent raw-ingress header or trusted provider record. Cleanup attempts message removal and alias retirement independently even after a CLI timeout; it requires independent route and address absence before claiming cleanup. It suppresses raw CLI/SMTP outputs and only emits fixed phase labels; local ZIP/body data remain under repository `.temp`. Mock-only failure-path and semantic-stage tests are discovered by the GitHub-hosted infrastructure test job under `infra/tests`; they are **not** deployed acceptance evidence. Review the harness and source/API contracts immediately before live use; retain the first failure conditions. The semantic two-message check is now opt-in on the **same** existing deliveries via `--check-semantic`, with only typed incomplete-index retries bounded by seven minutes. It does not establish exact 256-dimensional cosine or cursor completeness; those require the restricted full-snapshot oracle in `docs/staging-semantic-e2e.md`. The harness also does not implement the second-principal isolation, outbound canary, or post-retirement SMTP rejection gates, so even a basic inbound pass would not attest those claims.

Before the single `address add`, the harness derives its run-owned alias and performs only read-only preflights: normal CLI `address list` must show a well-formed non-retired account inventory with fewer than ten entries and no candidate alias; the complete paginated Cloudflare Rules GET must show no exact candidate or conflicting run-rule name and fewer than 200 literal rules for the staging mail subdomain. The Rules GET requires consistent `page`, `per_page`, `count` and `total_count` on every page, rather than treating a short page or missing `total_pages` as proof of completeness. The [Cloudflare per-domain routing-rule cap](https://developers.cloudflare.com/email-service/platform/limits/) is a provider ceiling, not evidence that its token has Rules Write. The CLI intentionally outputs only address rows, so the service's D1-wide `capacity.registered` and `remaining_estimate` response fields cannot be verified by this CLI harness; the Worker/provider remain authoritative at the create boundary. A preflight failure occurs before any mutation and emits only a fixed label. The existing `finally` cleanup still owns any attempt that crosses the create boundary.

## Manual GitHub-hosted native/inbound probe

The existing `.github/workflows/ci.yml` now has a **manual-only** `staging-e2e` dispatch target (not a push-triggered smoke). It runs on `windows-latest` under the `staging` Environment, with the additional literal confirmation `RUN_STAGING_E2E`; neither ordinary pushes nor the `staging`/`production` targets execute this job. **The native/inbound job has not been dispatched or passed.** Do not dispatch before the generic Identity authorization-resume origin fix has deployed to staging, the exact synthetic account is already verified, and `STAGING_E2E_USERNAME` and `STAGING_E2E_PASSWORD` are set as protected `staging` Environment Secrets. The latter are the *synthetic test principal* only, not a human's credentials. Use the existing repository/Environment `CLOUDFLARE_API_TOKEN` for staging Email Sending SMTP and status GET, `CF_EMAIL_ROUTING_TOKEN` for exact-rule audit, and the public zone ID. Missing secret **values** fail before browser activity; insufficient provider scope is reported by the later bounded provider preflight, not inferred from secret presence.

GitHub's [documented workflow syntax](https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax#onworkflow_dispatch) says `workflow_dispatch` requires the workflow file on the default branch. This repository's current behavior is narrower counter-evidence: `origin/main` has no `.github/workflows` files, yet the already registered feature-only `probe-queues.yml` accepted a `--ref codex/amail-v0.1.0` manual dispatch and its **read-only** job succeeded in [run 36521996961](https://github.com/kleedaisuki/moesegfault-amail/actions/runs/36521996961) at feature SHA `9feba94e7d45a622db726f17015dfa0d5df19fb9`. Do not generalize that one repository-specific API behavior into a guarantee for a changed `ci.yml`; after this change is pushed, a feature-ref dispatch may work, but if GitHub refuses it, merge the reviewed workflow to `main` before the staging acceptance run. Do **not** use an unsafe push workaround or deploy production to test dispatch eligibility.

The hosted job tests and builds amail on the Windows runner, copies its binary under `.temp`, creates a same-runner Windows DPAPI blob from the protected synthetic secrets, and removes the secret variables from the Python environment before launching Chrome or the CLI. `staging_identity_cdp.native_login` exercises the normal Login frontend and loopback PKCE, then `staging_mail_e2e.main` registers a new disposable staging alias, waits for route propagation, sends two synthetic messages through authenticated Cloudflare SMTP, retrieves a ZIP and checks content/asset/search/read/delete, and retires the alias with independent route readback. Setting `AMAIL_STAGING_SEMANTIC_E2E=1` for an explicitly confirmed hosted invocation additionally checks semantic search on those **same two** messages before read/delete; the basic target does not set this switch. All browser profiles, auth SQLite, ZIPs and test MIME remain inside a freshly created repository `.temp/staging-hosted-e2e-*` directory and are removed even after a normal stage failure; no credential, URL or mail artifact is uploaded. The runner log prints only bounded harness-owned stage labels, including both the first failure and cleanup failure where applicable; both subprocess harnesses suppress their raw output. The SMTP token is never inherited by Chrome or the amail child process. This hosted probe does **not** grant outbound sending, verify independent external delivery, exercise a second principal, attest exact semantic cosine, or prove production readiness.

The checkout `GITHUB_SHA` identifies the probe/CLI source, **not necessarily the deployed staging Worker revisions**. Record the Identity API, Login frontend, mail API and ingress deployment IDs independently just before the run and correlate them with the run time. A functional pass proves the deployed combination observed then, not that all live services were built from the checkout commit. Do not claim source-revision parity without a separate readback. The current repository `CLOUDFLARE_API_TOKEN` also powers existing deployment jobs; before a secret-bearing feature-ref dispatch, confirm its effective permissions and staging Environment policy. Prefer a staging-scoped Email Sending test token when one can be provisioned, and never treat staging URL checks as a substitute for a capability boundary.

For crash recovery, the synthetic alias suffix is the first 16 lowercase hex digits of `HMAC-SHA256(key=STAGING_E2E_PASSWORD, message="amail-staging-e2e/v1:<GITHUB_RUN_ID>:<GITHUB_RUN_ATTEMPT>")`. The password must remain protected; the public run URL alone cannot predict the active alias. The default local harness still uses an unpredictable random suffix. If the hosted process is cancelled or killed before `finally`, a restricted operator can reconstruct **only that exact run-owned staging alias** from the protected secret and run coordinates, audit the literal routing rule and retire it; do not remove wildcard or unrelated rules. A harness-reported `address_or_route_cleanup_failed` or `run_cleanup_failed` is a failed test requiring reconciliation, not a pass. This deterministic run suffix is only a recovery locator, not an authentication secret. Clear or rotate the standing synthetic credential after the acceptance campaign through normal Identity account controls; never copy the local DPAPI blob to GitHub, because it is user/machine bound.

The manual trigger, after all prerequisites pass, is `gh workflow run ci.yml --ref codex/amail-v0.1.0 -f target=staging-e2e -f confirm=RUN_STAGING_E2E`; `main` may be used after merge. Dispatch is an active mail/D1/Routing probe, **not** a unit test. Review the staging deployment IDs and secret provenance immediately beforehand. The first hosted run must be recorded in `docs/validation.md` with the run URL, commit, deployed revision IDs, fixed phase markers, cleanup outcome and any first failure. No authenticated SMTP-to-ZIP E2E run is claimed at the time of writing.
