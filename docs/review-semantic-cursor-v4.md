# Review: semantic cursor v4 vector commitment

Status (2026-09-30): **GO for source commit `6e39f56`, not a hosted or live acceptance claim.** Reviewed the feature diff and surrounding search-job, embedding, CLI, and error paths. No local heavy tests or live requests were run. The cursor-integrity limitation below is inherited from v3 and should be documented or addressed separately; it does not invalidate the new provider-vector drift guard for an unmodified server-issued cursor.

## Contract trace

| Contract | Source evidence and assessment |
| --- | --- |
| Exact vector representation | `platform::embed_classified` requests 256 dimensions, rejects nonfinite/zero-norm input, normalizes in `f64`, and returns 256 rounded `f32` coordinates. `search_jobs::vector_commitment_for_version` hashes those same in-memory `f32::to_bits()` values as little-endian `u32`s; no second provider response or JSON-number conversion intervenes. Length and finite checks fail closed. |
| Canonical binding | Preimage is the v4 ASCII domain plus NUL, the 64-character lowercase SHA-256 `query_hash` plus NUL, UTF-8 model length as little-endian `u32`, model bytes, query input-version `1` as little-endian `u32`, dimension `256` likewise, then 256 coordinate words. `query_hash` canonicalizes omitted/default `limit`, `regex`, and `case_sensitive`, excludes only `cursor`, and includes principal `(iss,sub)` plus serialized filters. This matches the design preimage. The input-version constant is a manually maintained protocol tag, not automatically derived from provider configuration; any future transformation change must deliberately bump cursor version/tag. |
| Before-scan rejection | `search` calls `decode_cursor` before quota admission, transient job insertion, or provider use. After embedding, `check_vector` compares the freshly computed digest before the preparing job becomes running or `advance` calls `scan_batch`. A mismatch yields HTTP 409 `search_cursor_vector_changed`; the preparing-row deletion path runs. The provider and daily quota may already be spent, which the design explicitly allows. A persisted job is rechecked by `advance_claimed` before its first or resumed scan. |
| Compatibility and replay | Lexical continuation still emits v3 with the optional field omitted; a matching v3 lexical cursor decodes. Matching v3 semantic returns HTTP 409 `search_cursor_stale` before provider work. Completed semantic jobs retain only `vector_commitment` and model after `query_vector=None`; `result_page` reconstructs the same v4 cursor on replay. Cursorless fast semantic POST removes its transient job after success. The CLI only retries a cursorless `search_job_stale`, not any cursorful mismatch, preventing silent page concatenation. |
| Errors and privacy | `problem` returns fixed code/detail strings and a request ID; neither vectors nor digest, search text, or raw cursor are included. `request_json` and active `query_vector` remain D1 account data subject to existing job expiry/scrub. The completed digest is query-derived sensitive metadata and is not logged. |
| Resource bounds | A digest is 32 bytes/64 hex characters; hashing 256 words is negligible beside the existing full exact cosine scan and OpenRouter request. Each semantic page still re-embeds and spends one admitted provider request plus work quota; repeated vector drift becomes an explicit 409 rather than transparent continuation. No new D1 table or per-row storage is introduced. Cloudflare's [D1 limits](https://developers.cloudflare.com/d1/platform/limits/) still motivate the existing bounded/checkpointed scan and separate scale acceptance. |

## Non-blocking inherited limitation: cursor boundary is not authenticated

`decode_cursor` validates the v4 commitment's shape and later matches the real query vector, but the cursor is base64 JSON, not a signed token. A caller with a valid server-issued v4 cursor can change the finite `last_score_bits`, `last_time`, or `last_id` while keeping the valid commitment and query hash. The next scan will then use that altered boundary in `semantic_rank`, potentially omitting or repeating *that caller's own* results without an error. The v3 lexical/semantic cursor already had the same rank-boundary property; this commit neither introduces nor fixes it. No cross-owner read is apparent because SQL owner predicates and the owner-bound query hash remain enforced. If product language promises corruption/tampering detection for the **whole cursor**, add a keyed MAC over all cursor fields (with versioned key rotation) or server-owned opaque cursor state; a vector SHA-256 commitment alone only detects vector drift. An RFC-standard [HMAC](https://www.rfc-editor.org/rfc/rfc2104.html) is an appropriate integrity primitive. Do not turn this into a last-minute change without considering existing v3 lexical cursor compatibility.

## Verification gaps before a deployed claim

The new unit tests cover coordinate, model, and tag drift; malformed digest syntax; lexical v3 and semantic v3; and a serialized completed-state shape. They **do not** execute the `search`/`advance` D1 lifecycle, observe that a mismatch performs zero row scans and deletes the preparing job, or poll/replay a completed 202 through HTTP. They also compare commitment implementations with themselves rather than an independently precomputed canonical SHA-256 fixture. Hosted integration and the protected two-message live oracle in [staging-exact-cosine-oracle.md](staging-exact-cosine-oracle.md) remain necessary before claiming production exact-cosine attestation. A clean hosted CI result should be reported separately from this source review.
