# Synthetic address-add Worker boundary tests

The hosted Worker CI job builds the **same Rust/Wasm bundle** used by Wrangler and then runs `infra/tests/worker-boundary/address-add.test.mjs` in Cloudflare's Miniflare/workerd runtime. It does not call `mail-staging.moesegfault.dev`, create a real address, or invoke Cloudflare Routing Rules. The test creates a fresh local D1 database with the repository migrations, signs an ephemeral RS256 access token, and serves OIDC discovery/JWKS and exact Routing GET/POST fixtures through a network mock with external network access disabled. It dispatches the real `POST /v1/addresses` request through the shim and checks its HTTP response, bounded staging diagnostic header, and durable D1 state.

The original post-create/reconciliation outcomes cover: a success envelope with rule ID must activate and return 201; a success envelope without an ID must return a handled 503 and leave the row in `provisioning`; a synthetic D1 trigger that rejects only activation must return `address_provision_unknown` 503, leave the row in `provisioning`, and leave the mocked provider DELETE unused; two existing exact rules must select one active ID, set `needs_reconcile=1`, and leave both rules untouched in the add request; a scheduled reconciliation must then prune only the extra exact rule and clear the flag; a stale `pending` row with a reconciliation flag and exact rule must return to `provisioning` without deleting the rule. The D1-error case checks the important safety contract: a D1 write error does not prove that an externally created rule is safe to remove. The duplicate case guards a Cron/add race: Cron could adopt either listed ID before add activation, so pre-activation pruning could strand an active mailbox. Duplicate evidence is monotonic through activation; a mismatch between an add request's chosen ID and an already-active readback can only mark that active row for later state-aware pruning, never delete in the request. Cron observes `provisioning` and reconciles the exact address against the provider; a concurrent `deleting` row is also reconciled. An `active` row flagged for reconciliation prunes only provider rules other than its confirmed, still-listed `cf_rule_id`. A readback of the exact owned `active` row with the same rule ID permits 201 even if the write response was lost; only a confirmed zero-change plus `deleting`/`retired` row retains the existing 409 state-conflict code. This exercises the Rust `add_address` implementation, worker-rs JS fetch/response conversion, JWT verification, and D1 bindings, not just a pure parser. It is an integration regression guard, **not** evidence that the fourth staging HTTP 500 has been reproduced or fixed. In particular, Miniflare's local D1 cannot establish what the historical deployed Cloudflare D1 binding or provider response did.

The duplicate marker is monotonic across activation, but it is not a generation counter. If active reconciliation clears the flag after a racing add marks it, an extra exact rule can remain undiscovered and consume route capacity. This is a recoverable capacity leak, not permission to delete a possibly active rule; a future reconciliation epoch or provider-side audit should close the lost-wakeup race. This synthetic suite does not force that interleaving.

The locked `worker-rs` D1 `prepare` implementation can unwrap a synchronous JavaScript exception, so a trap between provider creation and D1 activation is a relevant hypothesis. The trigger fixture injects an asynchronous `run()` error only; it deliberately does **not** claim to reproduce a synchronous `prepare` exception or the historical 500. If captured request-local evidence later points to a synchronous trap, add a targeted fixture then, without replaying a live alias.

Run only on GitHub-hosted CI, per the project's workstation resource constraint. The Worker job installs the pinned Miniflare dependency from `pnpm-lock.yaml` after building the Wasm bundle. Local lightweight `node --check` checks syntax only. See [Cloudflare's Miniflare test guidance](https://developers.cloudflare.com/workers/testing/miniflare/writing-tests/), [current Miniflare outboundService API](https://github.com/cloudflare/workers-sdk/blob/main/packages/miniflare/README.md), and [module/Wasm support](https://developers.cloudflare.com/workers/testing/miniflare/core/modules/).

The disabled-rule fixtures add a separate deliverability invariant. A listed exact rule with `enabled=false` or no `enabled` field remains owned for deletion and duplicate accounting, but cannot activate D1 and cannot trigger a blind second POST. A disabled-only, aged `provisioning` row remains in the repair journal rather than reverting to `pending`; deletion still removes that exact rule before retirement. An enabled exact rule may be selected past a disabled remnant, and later active-row reconciliation prunes only the remnant. If the committed active ID is later listed as disabled, even alongside another enabled exact rule, reconciliation retains its marker and deletes neither rule: automatically switching or deleting could race with another actor. A POST 200 claiming a disabled rule is treated as an uncertain create result, not delivery proof. These fixtures test local behavior, not historical staging root cause or continuous detection of externally disabled active rules that have no reconciliation marker. See [the disabled-rule adoption decision](disabled-routing-rule-adoption.md).

Migration `0008_address_reconcile_schedule.sql` adds a per-address due time for bounded Cron scans. Each selected row moves its due time five minutes forward **before** provider I/O, so an unavailable provider or a permanently disabled exact rule cannot pin the oldest thirty slots. A new user deletion sets due time to `-1` for urgent cleanup; new add claims and external active-duplicate flags set it to `0`. One due-time order then rotates all states without a separate permanent state priority. The hosted fixture inserts thirty older disabled `provisioning` rows and one later urgent `deleting` row; deletion completes in that same Cron run while only the twenty-nine visited backlog rows advance. A pure SQLite regression shows that after thirty failing deletes advance, an untouched `provisioning` row appears in the next bounded batch even with a thirty-first failing delete. Fixed warnings for a non-enabled observed rule or a full thirty-row batch contain no address, account, rule ID, or provider response. The full-batch warning indicates saturation, not proof of remaining rows. This is bounded fairness for a stable finite backlog, not a latency guarantee under indefinitely growing new urgent work.

The synthetic suite has a small exact-rule inventory and does **not** prove reconciliation capacity near the planned 198-alias routing ceiling. Each selected row currently performs a separately paginated zone Rules list: at four pages per list, a thirty-row Cron batch could require about 120 external fetches. Cloudflare's [Workers limits](https://developers.cloudflare.com/workers/platform/limits/) distinguish the Free plan's fifty external subrequests per invocation from the Paid plan's much larger allowance. The account plan has not been verified here; before release near that scale, either establish sufficient plan capacity or list the zone inventory once per Cron and partition exact owned rules locally under the same ownership checks. This is a conditional scalability risk, not evidence that current staging traffic exhausted a limit.
