# Synthetic address-add Worker boundary tests

The hosted Worker CI job builds the **same Rust/Wasm bundle** used by Wrangler and then runs `infra/tests/worker-boundary/address-add.test.mjs` in Cloudflare's Miniflare/workerd runtime. It does not call `mail-staging.moesegfault.dev`, create a real address, or invoke Cloudflare Routing Rules. The test creates a fresh local D1 database with the repository migrations, signs an ephemeral RS256 access token, and serves OIDC discovery/JWKS and exact Routing GET/POST fixtures through a network mock with external network access disabled. It dispatches the real `POST /v1/addresses` request through the shim and checks its HTTP response, bounded staging diagnostic header, and durable D1 state.

Six post-create/reconciliation outcomes are covered: a success envelope with rule ID must activate and return 201; a success envelope without an ID must return a handled 503 and leave the row in `provisioning`; a synthetic D1 trigger that rejects only activation must return `address_provision_unknown` 503, leave the row in `provisioning`, and leave the mocked provider DELETE unused; two existing exact rules must select one active ID, set `needs_reconcile=1`, and leave both rules untouched in the add request; a scheduled reconciliation must then prune only the extra exact rule and clear the flag; a stale `pending` row with a reconciliation flag and exact rule must return to `provisioning` without deleting the rule. The D1-error case checks the important safety contract: a D1 write error does not prove that an externally created rule is safe to remove. The duplicate case guards a Cron/add race: Cron could adopt either listed ID before add activation, so pre-activation pruning could strand an active mailbox. Duplicate evidence is monotonic through activation; a mismatch between an add request's chosen ID and an already-active readback can only mark that active row for later state-aware pruning, never delete in the request. Cron observes `provisioning` and reconciles the exact address against the provider; a concurrent `deleting` row is also reconciled. An `active` row flagged for reconciliation prunes only provider rules other than its confirmed, still-listed `cf_rule_id`. A readback of the exact owned `active` row with the same rule ID permits 201 even if the write response was lost; only a confirmed zero-change plus `deleting`/`retired` row retains the existing 409 state-conflict code. This exercises the Rust `add_address` implementation, worker-rs JS fetch/response conversion, JWT verification, and D1 bindings, not just a pure parser. It is an integration regression guard, **not** evidence that the fourth staging HTTP 500 has been reproduced or fixed. In particular, Miniflare's local D1 cannot establish what the historical deployed Cloudflare D1 binding or provider response did.

The duplicate marker is monotonic across activation, but it is not a generation counter. If active reconciliation clears the flag after a racing add marks it, an extra exact rule can remain undiscovered and consume route capacity. This is a recoverable capacity leak, not permission to delete a possibly active rule; a future reconciliation epoch or provider-side audit should close the lost-wakeup race. This synthetic suite does not force that interleaving.

The locked `worker-rs` D1 `prepare` implementation can unwrap a synchronous JavaScript exception, so a trap between provider creation and D1 activation is a relevant hypothesis. The trigger fixture injects an asynchronous `run()` error only; it deliberately does **not** claim to reproduce a synchronous `prepare` exception or the historical 500. If captured request-local evidence later points to a synchronous trap, add a targeted fixture then, without replaying a live alias.

Run only on GitHub-hosted CI, per the project's workstation resource constraint. The Worker job installs the pinned Miniflare dependency from `pnpm-lock.yaml` after building the Wasm bundle. Local lightweight `node --check` checks syntax only. See [Cloudflare's Miniflare test guidance](https://developers.cloudflare.com/workers/testing/miniflare/writing-tests/), [outbound fetch mocking](https://developers.cloudflare.com/workers/testing/miniflare/core/standards/), and [module/Wasm support](https://developers.cloudflare.com/workers/testing/miniflare/core/modules/).
