# Synthetic address-add Worker boundary tests

The hosted Worker CI job builds the **same Rust/Wasm bundle** used by Wrangler and then runs `infra/tests/worker-boundary/address-add.test.mjs` in Cloudflare's Miniflare/workerd runtime. It does not call `mail-staging.moesegfault.dev`, create a real address, or invoke Cloudflare Routing Rules. The test creates a fresh local D1 database with the repository migrations, signs an ephemeral RS256 access token, and serves OIDC discovery/JWKS and exact Routing GET/POST fixtures through a network mock with external network access disabled. It dispatches the real `POST /v1/addresses` request through the shim and checks its HTTP response, bounded staging diagnostic header, and durable D1 state.

Two post-create outcomes are covered: a success envelope with rule ID must activate and return 201; a success envelope without an ID must return a handled 503 and leave the row in `provisioning` for reconciliation, rather than pretend the route is active or repeat the POST. This exercises the Rust `add_address` implementation, worker-rs JS fetch/response conversion, JWT verification, and D1 bindings, not just a pure parser. It is an integration regression guard, **not** evidence that the fourth staging HTTP 500 has been reproduced or fixed. In particular, Miniflare's local D1 cannot establish what the historical deployed Cloudflare D1 binding or provider response did.

The locked `worker-rs` D1 `prepare` implementation can unwrap a synchronous JavaScript exception, so a trap between provider creation and D1 activation is a relevant hypothesis. This harness does not inject a synchronous `prepare` exception: corrupting the database after the provider fixture would test a deliberately artificial schema failure and would not identify the historical cause. If a reviewed runtime mechanism or captured request-local evidence later points there, add a targeted fixture then, without replaying a live alias.

Run only on GitHub-hosted CI, per the project's workstation resource constraint. The Worker job installs the pinned Miniflare dependency from `pnpm-lock.yaml` after building the Wasm bundle. Local lightweight `node --check` checks syntax only. See [Cloudflare's Miniflare test guidance](https://developers.cloudflare.com/workers/testing/miniflare/writing-tests/), [outbound fetch mocking](https://developers.cloudflare.com/workers/testing/miniflare/core/standards/), and [module/Wasm support](https://developers.cloudflare.com/workers/testing/miniflare/core/modules/).
