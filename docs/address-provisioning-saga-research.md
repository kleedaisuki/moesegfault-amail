# Address provisioning across D1 and Email Routing: bounded saga

Status: research synthesis and code-informed design review, 2026-09-29. No production mutation, live route operation, or historical root-cause claim. This complements [the architecture contract](architecture.md), [the uncertain-activation decision](address-activation-uncertain-outcome.md), [the fourth staging incident](staging-fourth-address-incident-36567571204.md), and [hosted boundary tests](worker-address-boundary-tests.md).

## Question and evidence

The practical question is how to preserve *deliverability* when one registration changes both D1 and Cloudflare Email Routing, but neither service participates in the other's transaction. A Cloudflare rule can exist while D1 still says `provisioning`; the fourth staging attempt observed exactly that pre-cleanup state alongside a bare HTTP 500. The later exact route/D1 audit was clean. These facts prove a provider-side rule effect and subsequent cleanup, **not** the 500's instruction, whether the Worker decoded the POST success, or which actor reconciled the state. The bounded invocation aggregate saw one `scriptThrewException` in the same window, but was not request-correlated.

The system already has a minimal durable *saga* rather than a distributed transaction: D1 claims a slot and records `provisioning`, the Worker finds or creates an exact rule, and D1 conditionally activates with its rule ID. Cron reconciles `provisioning`, `deleting`, and flagged rows. This is aligned with García-Molina and Salem's original [Sagas](https://doi.org/10.1145/38713.38742): locally committed steps require domain-specific continuation or compensation rather than an imaginary global rollback. Helland's [Life Beyond Distributed Transactions](https://www.cidrdb.org/cidr2007/papers/cidr07p15.pdf) is a useful systems framing, not evidence that every consistency problem should become an asynchronous workflow.

Cloudflare's [rule-create API](https://developers.cloudflare.com/api/resources/email_routing/subresources/rules/methods/create/) documents POST and a returned rule ID, but does not advertise a client idempotency key. Therefore the safe current assumption is that a timed-out or malformed POST response **may have created a rule**. Amazon's production discussion of [idempotent APIs](https://aws.amazon.com/builders-library/making-retries-safe-with-idempotent-APIs/) explains why retrying a side-effecting create without a stable provider-supported token can duplicate resources. Cloudflare also warns that if multiple rules match one email pattern, [only the first rule processes the message](https://developers.cloudflare.com/email-service/configuration/email-routing-addresses/); duplicates are a correctness and capacity concern, not merely untidy metadata.

## One invariant, not many ad hoc exceptions

**Do not acknowledge `active` unless an exact owned enabled route is known to exist and D1 identifies the intended rule; never delete a route solely because an activation write or its acknowledgement was uncertain.** A brief route-with-`provisioning` interval is recoverable; an `active` row with no effective route silently loses mail. Retired names remain reserved, so a cleanup error cannot misdeliver to a new owner.

| Boundary outcome | Conservative action | Why |
| --- | --- | --- |
| D1 claim succeeds; provider GET/POST has no conclusive response | Preserve `provisioning`; later *list exact rules* before any new POST | A network failure does not prove no provider commit. |
| Provider rule exists; D1 activation result is error, missing metadata, or zero changes | Exact owner-scoped D1 readback; return success only for matching `active`; otherwise preserve route for reconciliation | D1 may have committed despite failed acknowledgement, or Cron/delete may have won a race. |
| Delete races with creation | Persist `deleting`; state-aware reconciler removes only exact owned rules, then retires | Immediate compensation after a stale read can delete the route for an `active` row. |
| More than one exact rule appears | Preserve the committed active rule; flag and later prune only other proven-owned IDs | In-request pruning can race with activation and the provider's first-match behavior. |
| Provider rule is disabled or points elsewhere | Do not count it as evidence of deliverability | The routing rule's enabled state and target are part of the invariant, not optional decoration. |

The first four rows largely describe current intended code in `crates/mail-worker/src/lib.rs` and `platform.rs`, with hosted synthetic coverage in `infra/tests/worker-boundary/address-add.test.mjs`. The **last row reveals a code-level gap**: `CfListedRule` and `rules_for_address_typed` validate the exact rule name, literal recipient, and expected Worker action, but do not deserialize/check `enabled`. Both `add_address` and Cron can consequently adopt a disabled otherwise-owned rule and mark D1 `active`, although Cloudflare states disabled rules do not forward. This is a source-derived risk, **not** a claim that the fourth incident involved a disabled rule. The minimal remedy is to carry enabled status in the provider list model, distinguish enabled matching rules from disabled remnants, and require an enabled rule for activation. A disabled exact rule needs an explicit policy—reactivate by exact ID, or delete/recreate after state-aware ownership checks—rather than a blind duplicate POST. Validate the policy against actual provider API semantics before implementation.

## What not to add yet

A separate transactional outbox table is not automatically a fix. The [transactional outbox pattern](https://microservices.io/patterns/data/transactional-outbox.html) makes a database mutation and *enqueue intent* atomic, but its relay may publish more than once; the downstream consumer still needs idempotency. Here the address row's `provisioning`/`deleting` states already carry durable intent for a bounded, 200-rule control plane. Adding a queue/outbox without a provider idempotency key or exact-rule reconciliation would simply move the ambiguous POST and duplicate problem to a relay. Prefer extending the existing state machine until a demonstrated throughput or latency need justifies more machinery.

Likewise, do not automatically compensate an uncertain create by DELETE. Compensation in this domain is safe only after exact ownership **and current D1 state** permit it; the reverse action is not a mathematical inverse when another actor has adopted the rule. D1's [primary-write and session-consistency documentation](https://developers.cloudflare.com/d1/best-practices/read-replication/) supports exact readback as positive evidence under the current no-session binding, but a failed read is not negative evidence of a failed write. If read replication is enabled through Sessions later, use `first-primary` or a carried bookmark for this readback rather than a potentially stale unconstrained replica.

## Next discriminating tests (hosted, no live alias)

1. Extend the Worker-boundary fixture with an exact, correctly named **disabled** rule and assert that `address add` cannot return 201 or leave an `active` row that relies only on it. Include a second enabled exact rule to verify selection and later duplicate cleanup. This tests the newly identified invariant gap without reproducing a live incident.
2. Inject a provider POST that has a side effect but loses its response; verify the first request remains `provisioning`, then a later reconciliation lists and adopts the *same* ID without a second POST. Separate this from a true provider rejection. The current hosted suite covers malformed success and D1 activation rejection; it does not prove this ambiguous-commit recovery sequence end-to-end.
3. Force the interleaving in which an active-row duplicate marker is cleared while another actor flags a new duplicate. A persistent extra route is a recoverable capacity leak, but a missed cleanup matters under the 200-rule limit. Decide whether a simple periodic exact-rule audit or a monotonic reconciliation epoch is warranted based on this test, not on an abstract desire for stronger machinery.

These tests should report state transitions, provider-call counts, and rule IDs only inside isolated CI fixtures; no mailbox, token, provider body, or live route data belongs in Actions output. Passing them would validate the modeled recovery paths, **not** retrospectively identify the fourth staging 500 or authorize production cutover.
