# Review: hosted address-add Worker boundary harness (`ed16ac0`)

Reviewed on 2026-09-29. Scope: `infra/tests/worker-boundary/address-add.test.mjs`, its package and lockfile, the Worker job change in `.github/workflows/ci.yml`, and relevant address registration/auth/provider code. This is a static review; I did not install dependencies, run a local toolchain, invoke a provider, or create an address. The hosted test result remains to be observed.

## Assessment

No release-blocking defect found in the test design. It dispatches `POST /v1/addresses` through the built Rust/Wasm Worker with an ephemeral signed token, local D1, and Miniflare's `fetchMock` with network access disabled. The fixtures target the same discovery/JWKS and Routing GET/POST paths used by `auth.rs` and `platform.rs`. The success assertions require a `201`, active response, and active D1 row containing the mocked rule ID; the malformed-success assertion requires a handled `503`, a bounded diagnostic, and a provisioning row. Therefore neither test can pass by merely skipping the Worker path or POST request. The test contains only synthetic identity, domain, zone, address, token, and rule values. The CI change adds a step after the existing Worker bundle; it does not alter deployment configuration or production code.

These tests **do not reproduce the historical fourth staging 500**. They cover two provider response envelopes, not the deployed provider/D1 interaction or an exception after a successful provider POST. The accompanying documentation states that limit correctly. The mock denies unregistered outbound `fetch()` calls as documented by [Cloudflare's Miniflare API](https://developers.cloudflare.com/workers/testing/miniflare/core/standards/); no live Routing Rules API or user alias is reached by this harness. Cloudflare also notes that only the Worker (not the Node test file) runs inside workerd and that Miniflare does not read Wrangler configuration, so parity remains limited to the manually supplied bindings and compatibility date ([test guide](https://developers.cloudflare.com/workers/testing/miniflare/writing-tests/)).

## Follow-ups (non-blocking)

0. **Existing production-path defect exposed by this review, outside `ed16ac0`: do not conflate a D1 activation error with a zero-row state race.** In `crates/mail-worker/src/lib.rs::add_address`, `transition = ...run().await` is converted to `changed=0` for **both** `Err` and a successful update affecting zero rows. The branch then attempts to delete the already-created provider rule and reports `409 address_state_changed` when `changed==0`. If D1 rejects activation, this labels a backend fault as a client state conflict; if the database committed the update but its response was lost, deleting the provider rule could leave an active D1 address without a receiving route. Preserve the `Result` distinction and reconcile uncertain commit state before destructive provider cleanup. This is material production behavior, but a targeted D1-failure fixture is **not required to accept the first synthetic CI gate**: the gate's stated aim is to establish that the real Worker/Wasm path runs at all, and an artificial local D1 exception would not prove the historical 500's cause. Add this case after the basic hosted harness is green, with an explicit injected failure and expected recovery contract.

1. **Pin the Node/pnpm test runner in the Worker job.** The new step uses `corepack enable; pnpm install` on `ubuntu-latest` without `actions/setup-node` or `pnpm/action-setup`, unlike the site job, and the new package has no `packageManager` field. The test may pass today but its pnpm major version and behavior depend on runner image/Corepack defaults; a future runner change can fail CI before executing the regression guard. Reuse the site's explicit Node 22 and pnpm 12.4.1 setup, or add an equivalent fixed toolchain. Location: `.github/workflows/ci.yml`, new boundary-test step; `infra/tests/worker-boundary/package.json`.

2. **Make D1 migration loading future-proof.** `exercise()` loops over migrations `0001` through `0007` rather than enumerating every `.sql` file. When migration `0008` lands, the harness will still run against an older schema and can give a misleading green result about deploy parity. Load all migration files in sorted order and assert the expected naming format, or explicitly fail if the highest migration number differs from a reviewed constant. Location: `address-add.test.mjs`, migration-loading loop.

3. **Consider asserting provider request semantics, not just the response path.** The POST mock matches only method and path; it does not check the Authorization header or the literal matcher, worker action, and enabled flag in the submitted JSON. The current tests still exercise the intended post-create activation path, so this is not a defect in their stated regression target. Such assertions would make the harness a stronger guard against future accidental changes to provider-rule creation. Location: `address-add.test.mjs`, `fakeNetwork()` POST fixture.

## Evidence and limits

- `crates/mail-worker/src/lib.rs::add_address` allocates a D1 row, claims it as provisioning, lists/creates the provider route, activates D1, then encodes a 201 response.
- `crates/mail-worker/src/platform.rs::create_rule` sends the Routing POST and decodes its response; a success envelope without `result.id` is a typed `UnexpectedResponse`.
- `crates/mail-worker/src/auth.rs::authenticate` requires the staged issuer/client, RS256/JWKS, and an access token; the test's synthetic key and fixtures satisfy this path.
- The local migration directory contains `0001`–`0007` at review time.
- No hosted CI result for this commit was available at review time. A green hosted run is necessary before treating the harness as working, but would not by itself diagnose the historical live failure.
