# Review: forwarding standard role mail to a confidential external inbox

Date: 2026-09-28. Scope: replace the proposed operator Worker / Access intake for the first release with Cloudflare Email Routing `forward` rules. This is a design review, **not** evidence that any destination or rule has been created or that mail has been delivered. The destination's literal value is intentionally absent from this repository, CI inputs, rule names, logs and this note.

## Decision

Use one owner-controlled, monitored external mailbox as a **verified account-level destination** and four exact production aliases: `abuse@` and `postmaster@` on both the public mail subdomain and zone apex. A staging role-alias probe is optional, not part of the current production workflow or intake gate. Each production rule has one `literal`/`to` matcher, one `forward` action whose value is the confidential destination, `enabled=true`, `source=api`. Do not deploy the isolated operator Worker or Access application and do not create a catch-all. Preserve any existing apex rule; conflict means stop, not replace. The external mailbox is an interim human fallback pending a future notification/agent-operations center, **not** a claim of autonomous abuse triage.

Cloudflare requires a forward destination to be **verified first**; an unverified destination leaves forwarding rules disabled. The destination belongs to the Cloudflare **account**, reusable across zones, and its `verified` timestamp can be read through the account API. Creating it needs `Email Routing Addresses Write`; reading it needs Addresses Read or Write. Rule creation separately needs zone-scoped `Email Routing Rules Write`. A token proven to list rules therefore cannot be presumed able to create a destination or rules. See [destination setup](https://developers.cloudflare.com/email-service/configuration/email-routing-addresses/), [create destination API](https://developers.cloudflare.com/api/resources/email_routing/subresources/addresses/methods/create/), [list destination API](https://developers.cloudflare.com/api/resources/email_routing/subresources/addresses/methods/list/) and [create rule API](https://developers.cloudflare.com/api/resources/email_routing/subresources/rules/methods/create/).

## Required control-plane sequence

1. Supply the destination through a restricted GitHub environment secret or a local secret channel, never through `workflow_dispatch` input. Query account destinations with pagination and compare exact normalized address **without printing the inventory**. If absent, create once; if present, confirm unique exact match and non-null `verified`. The owner must complete Cloudflare's verification message in the external mailbox. Do **not** create active role rules before this is confirmed. A 200 response from destination creation is not proof of verification.
2. Query all zone routing-rule pages. For each exact alias, accept exactly one enabled `forward` action to the verified destination. Reject duplicates, disabled rules, any `worker`/`drop`/different destination action, and any rule managed by Wrangler; never take over a user or unrelated existing apex rule. After creating only missing API-owned rules, re-read and compare exact matchers/actions/enabled state. Avoid putting the destination in rule **name**. Cloudflare documents that duplicate patterns use only the first dashboard rule, and deleting a destination disables every rule that references it; both are fail-closed hazards. [Routing rules and addresses](https://developers.cloudflare.com/email-service/configuration/email-routing-addresses/).
3. Perform real external SMTP probes for every alias (including mixed-case `Postmaster`) and inspect the owner mailbox's Inbox **and spam folder**. Verify a stable message identifier and receipt time, not just successful API read-back or SMTP acceptance. Cloudflare documents Sender Rewriting Scheme and ARC/DKIM on forwarded mail, but the final mailbox provider can still filter or reject it; its postmaster notes say upstream SMTP errors may return in-session. Capture only opaque evidence references, not body or destination. [Cloudflare postmaster notes](https://developers.cloudflare.com/email-service/reference/postmaster/), [route-mail guide](https://developers.cloudflare.com/email-service/get-started/route-emails/).
4. Only after production external delivery is observed and a concrete periodic mailbox-checking responsibility exists may `abuse_contact_verified` be attested with an opaque case reference. Staging success does not attest production. This gate proves reachability and monitoring, **not** that direct reports automatically trigger an account hold. Keep the global send policy `held` if destination verification, exact rules, external receipt or monitoring fails; revoke the gate on later failure. `infra/operator/attest_gate.py` merely records reviewed evidence and cannot establish it itself.

### Operational limits

Cloudflare caps verified destinations at 200 **per account**, but this design needs only one destination, not one per role. Forwarding each role alias to a single destination is supported directly; a Worker is necessary only for fan-out to multiple destinations, not here. [Email limits](https://developers.cloudflare.com/email-service/platform/limits/). The user-selected destination is confidential, not an authentication secret; nevertheless it must not be rendered in public docs or logs because it becomes an abuse target. At least one owner action is unavoidable: click the verification link delivered by Cloudflare to that mailbox. Once verified, the remaining provisioning and probes can be automated with narrowly scoped tokens and sanitized output.
