# Address activation: uncertain D1 outcome and literal-route safety

Status: architecture decision for the current address-registration fix; source inspection only, no live mutation or test. This is not a diagnosis of the fourth staging 500. See the [run-specific incident](staging-fourth-address-incident-36567571204.md) and [exception-path audit](staging-post-create-exception-path-audit.md).

## The data and destructive boundary

`addresses.address` is a unique D1 row. Its `state` is `pending | provisioning | active | deleting | retired`; `cf_rule_id` links an exact Cloudflare Email Routing rule to that row. The provider route and D1 transaction cannot commit atomically. `add_address` first claims `provisioning`, lists or creates an exact owned rule, then conditionally updates the row to `active` with that rule ID. Cron reconciles `provisioning` by finding and adopting an exact rule, and `deleting` by removing exact rules and retiring the row (`crates/mail-worker/src/lib.rs`). A delete request during provisioning intentionally leaves the row in `deleting` for that reconciliation.

The present activation code reduces *all* of `run().await` error, unavailable/erroring result metadata, and acknowledged `changes == 0` to `changed = 0`, then executes `delete_rule(rule_id)`. This is unsafe. An error on an asynchronous write is not an acknowledgement that no write committed. If D1 committed the `active` row but the acknowledgement failed, deleting its route leaves a user-visible active address that cannot receive mail; Cron does **not** scan an ordinary active row. Even an acknowledged zero-change result does not license deletion: Cron may have adopted this exact rule between the provider create and the request's conditional UPDATE, leaving the row already `active` with the same ID. The row/rule must be interpreted together.

## Chosen rule: preserve an uncertain side effect

Treat the provider rule as a durable external side effect until exact ownership and D1 state establish a safe transition. Never infer that a write did not commit from `Err`, missing metadata, or a later non-active snapshot. Never issue a second provider POST just because the first request got a 500/503 or the client timed out. Keep the existing public endpoint, status/code vocabulary, and idempotent add semantics; this is an internal state-machine correction, not a new API.

| Activation observation | Exact owned D1 readback | Safe response/action |
| --- | --- | --- |
| `Ok(changes=1)` | `active`, matching `cf_rule_id` | Existing 201 success. If readback fails or differs, return uncertainty; do not delete the rule. |
| `Err`, missing/erroring metadata, or implausible change count | `active`, matching `cf_rule_id` | Positive evidence that the desired row state exists; existing 201 success is acceptable. The route ID was returned by a successful provider create or an exact-rule lookup. |
| Same uncertain observations | `provisioning`, `deleting`, absent, different ID, or readback failure | Preserve the rule; return existing `address_provision_unknown` 503 (or the pre-existing conflict response only where a confirmed state change justifies it). Do not rewrite the row merely to manufacture a definitive result. |
| Acknowledged `Ok(changes=0)` | `active` with matching ID | Another actor, notably Cron, may have completed activation; return idempotent success, not a destructive conflict. |
| Acknowledged `Ok(changes=0)` | `deleting` or `retired` | Return the established state conflict; leave exact provider-rule removal to the state-aware reconciler. Do not delete from the request on a stale snapshot. |

Readback is **positive evidence**, not a safe absence test. A concurrent delete can follow any read (including a successful add); that is an ordinary interleaving, not a reason to retry provider creation. Cloudflare documents that D1 writes go to the primary and that calls without Sessions use the primary, while Sessions explicitly provide sequential consistency if read replication is used. This supports a successful exact readback as useful evidence, but does not make a failed read or a non-active snapshot a proof that an earlier write did not commit ([D1 read replication and consistency](https://developers.cloudflare.com/d1/best-practices/read-replication/), [D1 result metadata](https://developers.cloudflare.com/d1/worker-api/return-object/)).

The existing `provisioning`/`deleting` states are the repair journal; do not add a second table or use `needs_reconcile=1` on an active row without changing Cron first. Current Cron treats any selected state other than `provisioning` as a removal candidate, so marking `active` for reconciliation would **delete** the valid route. If activation remains `provisioning`, Cron can adopt the exact rule; if a concurrent delete won, Cron can retire it. An active row with a matching route needs no repair. A `pending` row with an exact rule is a rarer residual race not selected by current Cron; it should be surfaced as a bounded anomaly and handled by an explicit state-aware reconciliation change, not resolved by a blind delete. The provider lookup's exact literal recipient, rule name, and expected ingress-worker matcher are important ownership gates, not just a substring search (`platform::rules_for_address_typed`).

## Implementation and hosted verification sequence

1. Replace the `unwrap_or(0)` collapse with explicit `Result`/metadata branches. Keep the rule ID in memory through an exact owner-scoped readback. Return 201 only for a confirmed `active` row with the same ID; otherwise preserve the rule and use the existing 503/409 contract as appropriate. No inline `delete_rule` in an ambiguous activation branch.
2. Add a small pure decision test matrix covering `Err` after commit, `Err` before commit, missing metadata, acknowledged zero after Cron adoption, acknowledged zero after concurrent delete, and readback failure. Assert **zero provider DELETE and zero duplicate POST** on all uncertain outcomes. Exercise the actual Worker/D1 boundary in hosted synthetic tests where practical; pure tests do not establish D1 binding behavior.
3. Deploy to staging through the existing hosted CI and review serving version. A further one-use live address attempt requires the separate reviewed acceptance plan, pre-cleanup exact rule/D1 snapshot, and delayed absence audit. The fourth incident did not establish the failing instruction, and this safety fix alone must not be reported as its root-cause repair.

The favored trade-off is temporary recoverable external state over silent mail loss. A duplicate exact route or stalled `provisioning` row can be inspected and reconciled; an active D1 row whose only route was deleted is a direct user-visible break and is outside current Cron's normal repair set.
