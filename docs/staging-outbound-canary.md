# Staging-only outbound canary: prepared, not executed

Status (2026-09-29): `infra/tests/staging_outbound_canary.py` and its offline contract tests are prepared. **No amail outbound message has been sent; no external delivery or Queue feedback has been observed.** Do not set `delivery_canary_verified`, `feedback_verified`, or the global send policy to `allowed` based on this code. It is deliberately separate from the manual native-login/inbound job in `.github/workflows/ci.yml`.

## Exact trust boundary and remaining gap

The existing `staging` Environment has a verified synthetic Identity credential for native login, but the repository has **no configured controlled external IMAP inbox** and no protected `AMAIL_CANARY_*` capability set. A GitHub-hosted run therefore cannot yet prove delivery. Provider HTTP 202, an amail `accepted` result, or a Queue event alone is not a delivery oracle: Cloudflare defines `message.delivered` as the *recipient mail server accepting* a message, not necessarily a mailbox-user observation ([Cloudflare Email Sending event semantics](https://developers.cloudflare.com/email-service/platform/event-subscriptions/)). Do not route the canary to the project's own staging/apex domain, use the private Identity OTP inbox, paste an external mailbox address into a workflow input/log, or treat a manually asserted success as automated evidence.

The operator must first control and consent to one external mailbox whose raw RFC 5322 messages are readable over TLS IMAP on the same hosted runner. Add protected **staging Environment Secrets**, not workflow inputs, for `AMAIL_CANARY_RECIPIENT`, `AMAIL_CANARY_IMAP_HOST`, `AMAIL_CANARY_IMAP_USER`, `AMAIL_CANARY_IMAP_PASSWORD`, and `AMAIL_CANARY_AUTHSERV_ID` (the receiving server's expected `Authentication-Results` identifier). Also provide the synthetic immutable `STAGING_E2E_OWNER_SUB` through a protected secret, obtained from restricted Identity/D1 operator access. The existing `CLOUDFLARE_ACCOUNT_ID` and scoped `CLOUDFLARE_API_TOKEN` must support read-only D1 queries and Sending subdomain GET ([Cloudflare subdomain metadata API](https://developers.cloudflare.com/api/resources/email_sending/)). The canary script makes no policy write. **Downloaded MIME cannot authenticate its own `Authentication-Results` provenance**: an attacker can insert a field with the same authserv-id if the receiver does not strip it ([RFC 8601 §7.1](https://www.rfc-editor.org/rfc/rfc8601.html#section-7.1)). The script rejects duplicate same-ID fields and requires one field *claiming* SPF, aligned DKIM and DMARC pass, but that is only an ambiguity filter, **not authentication proof**. The mailbox operator must independently establish that the surviving field was added by the trusted receiving server (for example through that provider's authenticated message trace or documented header insertion/stripping behavior) before recording SPF/DKIM/DMARC as verified. If this provenance cannot be established, leave the authentication and release-gate evidence pending even if inbox delivery and D1 feedback pass.

## Human-reviewed one-use sequence

1. Run the hosted offline tests on GitHub Actions. Finish the native PKCE login for the verified **synthetic staging** principal before any 15-minute grant. Pin `AMAIL_HOME`, `AMAIL_API_BASE`, `AMAIL_ISSUER`, and `AMAIL_CLIENT_ID` as in `staging-e2e-plan.md`; keep the CLI binary, session, draft and ZIP under this repository's `.temp`. Verify one active sender alias belonging to this same principal; do not create a new alias merely to hide an orphan route.
2. Verify the exact staging Sending subdomain is enabled with `preview_enabled=false` and `drop_suppressed_recipients=false`; exact staging Event Subscription → staging Queue/consumer/DLQ exists. Confirm the external inbox can be read and its mailbox operator knows the test window. Confirm staging global policy is `held` and all production gates remain unchanged. A read-only D1 and provider preflight is built into the script; subscription/DLQ identity remains an operator check before grant.
3. In a restricted local operator session, compute SHA-256 of the lowercased external recipient from stdin, never a shell argument or public Actions input. On `main`, dispatch `grant-send-canary.yml` with `target=staging`, the synthetic immutable subject, the digest and opaque case reference. This authorizes exactly one fresh idempotency key for 15 minutes; it does **not** unhold global send. The raw recipient remains only in the protected Environment secret. Grant only after the inbox and subscription are ready; if fewer than 120 seconds remain, the probe fails before submission.
4. On a GitHub-hosted Windows runner, run the script with `GITHUB_ACTIONS=true` and `--confirm-staging`, supplying only private `.temp` paths and the already-owned staging sender:

   ```text
   python infra/tests/staging_outbound_canary.py --confirm-staging \
     --home .temp/<run>/amail-home-1 --amail .temp/<run>/amail.exe \
     --run-dir .temp/<run>/outbound --sender <owned-staging-alias>
   ```

   The parent `.temp/<run>` directory must already exist; the script creates the **fresh, previously absent** `.temp/<run>/outbound` leaf itself and rejects reuse or traversal. The sender argument is private and must not appear in a public workflow dispatch value, command echo, or Actions log. Invoke via a PowerShell step with command echo disabled and sender supplied from a protected secret or private file. Do **not** wire this into ordinary `ci.yml` push/production jobs. Review a dedicated manual staging workflow separately before enabling dispatch; this document does not claim one exists.
5. The probe checks read-only global hold, unused exact `(issuer, subject, recipient SHA-256)` grant, active sender ownership, provider privacy settings, and TLS IMAP availability **before** `amail pack/send`. It creates one synthetic text/HTML/CID/attachment ZIP using the native CLI, then invokes `amail send` **once** with an explicit UUID. An ambiguous timeout/5xx is `canary_send_uncertain`: stop and reconcile the original key and D1/provider record, never generate another key to retry. After acceptance it reads back that the *same* key consumed the grant while global send remains `held`. It prints `canary_provider_accepted_not_delivered` after acceptance, not a success claim.
6. Within an eight-minute bounded poll, two independent checks must both pass: (a) raw MIME from the controlled external inbox has the unique subject/body, HTML CID image and attachment bytes, with exactly one unambiguous same-ID authentication *claim*; and (b) staging D1 has the same request's provider ID, exactly one `delivered` provider event and the attributed `recipient_outcomes.kind=delivered` for the exact external recipient. The script reports `canary_external_inbox_and_feedback_verified_auth_manual_pending`, **not** a complete authentication or release-gate pass. A delivery with no event diagnoses subscription/consumer/attribution; an event with no inbox MIME is not delivery proof. Record only case/run URL, fixed stage outcome, durations and opaque correlation IDs in restricted validation evidence. Inspect Queue/DLQ/backlog and the actual event schema under restricted operator access, without exporting payloads.
7. Retain first failure conditions and private artifacts until operator review, then delete only this run's `.temp` directory. Do not manufacture a complaint, purge a DLQ, re-grant automatically, or change any production gate. A passing staging canary still does not establish production sender/DNS, operator abuse intake, global release readiness, or production delivery.

## Evidence and test limits

`infra/tests/test_staging_outbound_canary.py` simulates missing oracle credentials, wrong/used/expired grants, a global unhold, a non-delivered feedback outcome, untrusted authentication headers and attempted D1 mutation. These are source-level safety contracts, not deployed acceptance. Run them only on GitHub Actions per project practice. The script intentionally lacks an automatic canary grant and cannot silently create an external mailbox. The current hard blocker is **a consenting, independently readable external inbox plus its protected staging secret configuration**; until supplied, the honest result is *not run / not verified*.
