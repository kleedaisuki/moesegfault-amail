# Independent review: Workers Observability event-view correction

Scope: static review on 2026-09-29 of the four-file change in `infra/tests/staging_trace_canary.py`, `staging_address_failure_logs.py`, and their synthetic tests. No local tests, hosted query, address mutation, or raw retained logs were accessed for this review. The change was reviewed before its first hosted verification.

## Contract finding and disposition

The [official Cloudflare TypeScript SDK source](https://github.com/cloudflare/cloudflare-typescript/blob/main/src/resources/workers/observability/telemetry.ts) defines `TelemetryQueryParams.view` at the top level (lines 2034–2132). Its `TelemetryQueryResponse.Run.Query.Parameters` (lines 280–348) has datasets and filters but **no** view field; the encompassing `Run.Query` also lacks one. The earlier implementation sent `parameters.view=events` and required the same undocumented response echo. The [bounded read-only run 36541929727](https://github.com/kleedaisuki/moesegfault-amail/actions/runs/36541929727) returned a completed, dry, correctly scoped query with `view` echo unavailable and `result.events` absent. That outcome is consistent with the schema mismatch, but by itself does not prove causation or event retention.

The reviewed correction sends `view=events` at the documented top level while preserving the exact service filter and bounded historical timeframe. It no longer demands the undocumented view echo; an explicitly contradictory legacy echo still fails. Crucially, `query_page()` continues to reject an absent event container and requires completed/dry status, exact timeframe/datasets/filter echoes, a typed count/list, and bounded cursor-complete pagination before records are used. Thus omission of the undocumented echo cannot turn a missing events view into a privacy or causal pass.

The Values endpoint returned the expected service alongside others despite a service filter. Permitting that **positive membership** to pass the historical classifier is defensible only because `classify()` calls `reviewed_events()`, which requires `$metadata.service` to equal the expected Worker on **every** returned row, and because `retained_events()` requires a complete, exact-scope event query. The changed synthetic test includes both the mixed-values positive case and a wrong-service row rejection. Values membership alone is not evidence that its filter was enforced, and an absent/empty event view still leaves the incident unverified. The full privacy canary does not use the relaxed Values gate.

**Verdict:** No substantive blocking defect found in this static change. The correction addresses the documented request-schema mismatch without weakening the fail-closed event and scope checks. The accepted result of a future hosted query may still be UNVERIFIED because historical records are missing, the provider's actual record wrapper differs, or log retention/sampling is insufficient. These are operational evidence limits, not reasons to accept ambiguous data. A single read-only, exact-window hosted diagnostic is the next useful verification; it must not be described as passing the full privacy canary or as proving the earlier address failure until its strict causal classifier succeeds.

## Causal attribution limit

The historic E2E discarded its private request identifier and local journal. The classifier requires exactly one failed `addresses_add` root and linked routing phases inside the known 33-second interval, but cannot mathematically prove that this unique root belonged to that E2E rather than an unrelated concurrent request. The quiet-window assumption and exact timing make it useful for diagnosis, not an absolute identity proof. If any other add could have occurred in that interval, treat a positive classification as a strong bounded inference, not proof that should alone authorize production send or release. Future probes should bind the privately captured CLI correlation ID to Worker events without printing it.
