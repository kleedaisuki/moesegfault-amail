## Positive checks

* Source admission reads GitHub attempt 1 metadata and complete bounded job inventory. It requires the exact repository, feature branch, push event, full checkout SHA, workflow path and successful completed run. All six actual named CLI/Worker/site/infrastructure jobs must separately be completed/successful at that checkout. Duplicate, missing, skipped or truncated jobs fail. The real encryption step must actually execute successfully; a green aggregate run alone is insufficient. The selected names match the source workflow.
* Provider readers are existing bounded, timeout-limited, no-redirect helpers. Source admission makes two GitHub reads; service admission makes two three-service passes, each with deployments/version/deployments bracketing (18 Cloudflare reads), and two actual hold reads when wired to the readback method. There are no retries or mutation APIs in this increment.
* Mail uses the reviewed phase-aware exact resource checker, not a loose latest-upload check. Identity pins the explicit staging D1/audit/avatar resources and protocol-critical issuer/origins/environment plus sender restriction, rejects duplicate/incomplete inventories and unknown persistent/service/network kinds. Scalar/key names remain version-bound without coupling Identity key rotation to amail's own mechanism. Login requires an explicitly complete empty binding inventory.
* Each service must have a single 100%-serving version. The version-scoped bindings are read between equal deployment observations; two complete service version relations must then agree. Failure or observed drift does not supply a pin. These are observations, not an atomic cross-service transaction or a rollout lock; the design retains original-pin rechecks around mutation/recovery.
* The D1 `sending_state` method reads the same exact global policy coordinates used by the Mail send-policy enforcement path. Only one explicit `held` row passes; absent, duplicate, malformed or allowed rows fail. This does not infer a hold from missing rows.
* No production caller or live workflow entry point exists here. Injected raw readers/hold callbacks support synthetic tests, not a live caller supplying a success Boolean. Future wiring must bind the hold callback to actual `Readback.sending_state`, independently obtain source/provider observations and compare original pins; the current GO does not approve a fabricated callback or unspecified wrapper.
* No sibling runtime/config import is added. Mail config lookup stays inside this repository; Identity expectations are explicit constants retrieved during design, not a dependency on a developer's sibling checkout. Private responses remain in memory, pins suppress dataclass repr, and outward exceptions have fixed codes without raw provider exception chains. The change introduces no output/artifact containing private aliases, contacts or provider response bodies.

## Coverage limits and next admission boundary

Synthetic fixtures cover source SHA/event/attempt mismatch, skipped/duplicate/incomplete jobs, missing/skipped crypto, split traffic, provider exceptions, hold drift, wrong Identity origin/resource and unknown bindings. Additional focused drift fixtures may improve regression coverage, but the inspected executable comparisons already reject drift; absence of every possible fixture is not a demonstrated defect.

This slice deliberately does not validate uploaded/downloaded CLI artifact bytes or assemble native authentication, manifest durability, recovery and workflow cancellation. It also does not prove effective Mail observability capture-off: the reused `bindings_match` function is resource admission, not `pin_staging_mail.run`'s broader privacy readback. Those remaining gates must stay explicit before any live campaign is authorized. No claim is made about deployed quota, reserved-name behavior or cross-principal mailbox isolation.
