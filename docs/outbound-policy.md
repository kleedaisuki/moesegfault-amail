# Outbound mail usage decision (2026-09-28)

## Answer for v0.1.0

Cloudflare Email Sending is **technically capable** of sending from an onboarded `@mail.moesegfault.dev` domain to arbitrary, unverified external recipients on Workers Paid. That is not the same as a clear authorization for a public, multi-tenant mailbox whose users/agents compose arbitrary correspondence. The [product overview](https://developers.cloudflare.com/email-service/) calls Sending Beta an outbound **transactional** service, and the [FAQ](https://developers.cloudflare.com/email-service/reference/faq/) says it is intended **only for transactional emails** (and explicitly excludes marketing). However, Cloudflare's [2026 agent-email announcement](https://blog.cloudflare.com/email-for-agents/) expressly discusses receiving, persisting and replying, calls out a full email client, and offers its own Agentic Inbox reference application. These primary sources establish that agent replies and email-client patterns are contemplated; they do **not** explicitly define whether an open service offering user-composed, potentially first-contact person-to-person mail from many independent account holders is in scope. Therefore neither “Cloudflare forbids amail” nor “the API succeeds, so amail is approved” follows from the published evidence.

**Recommended narrow choice:** retain the already-built Cloudflare transport for controlled staging and operator-owned canaries; before advertising public arbitrary outbound sending, send Cloudflare Support/Email Service a concrete use-case description and obtain an affirmative written scope answer for *multi-tenant, agent-composed correspondence to unverified recipients, including first-contact messages and replies*, plus any required abuse controls or account review. An answer covering only transactional notifications or a single owner's agent replies is not sufficient. If Cloudflare declines or cannot confirm, choose an outbound provider that explicitly approves this workload **before** switching production transport or claiming v0.1.0 complete. Do not silently change the product to forwarding-only or pretend a send API `202` resolves policy.

## Provider question and acceptance record

Send this exact scope, through the Cloudflare account's support channel or the Email Service contact channel; preserve the response in the private operations record rather than copying credentials or user data into this repository:

> We are building `amail`, a public agent-facing mailbox service. Authenticated independent account holders may register up to ten `@mail.moesegfault.dev` addresses. Their agents compose individual messages in ZIP archives; the service would send from the holder's registered address to arbitrary external recipients, including first-contact mail and replies. Current implementation includes authenticated sender ownership and per-account quotas. We intend to prohibit bulk marketing and spam, but do not yet have a complete abuse-reporting workflow, bounce/complaint event handling, suppression integration, or complaint monitoring. Is Cloudflare Email Sending Beta permitted for this multi-tenant mailbox use, including first-contact user-composed messages, under our current account/plan? Which abuse, consent, suppression, review, monitoring and volume controls must be operational before launch? Please distinguish this from a single application's transactional notifications and from Cloudflare's Agentic Inbox reference app.

Acceptance record should include date, Cloudflare case ID, responding team, exact confirmed scope and limits, and any conditions; do not infer blanket approval from an informal example or transport acceptance. If no affirmative answer is available, public arbitrary outbound remains a release blocker. A reply-only or transactional-only scope would require a **visible product-scope decision by the owner**, not an undocumented backend filter.

### Separate implementation gap: abuse feedback loop

Even if Cloudflare approves the use case, the present source audit found sender ownership and sending quotas, **not** an implemented abuse-reporting intake/workflow, bounce and complaint event ingestion, per-recipient suppression reconciliation, or complaint-rate monitoring/response. Cloudflare's [suppression documentation](https://developers.cloudflare.com/email-service/concepts/suppressions/) says the platform creates some suppressions after eligible bounces and spam complaints, but that automatic platform behavior is not an application-level complaint handling program. Cloudflare's [FAQ](https://developers.cloudflare.com/email-service/reference/faq/) provides an abuse reporting address and ties sender reputation to bounce/complaint rates. Before public send, implement the controls Cloudflare requires, exercise them with provider events and a controlled abuse-report fixture, and document escalation/disablement of an abusive account. Do not tell Cloudflare or users these controls already exist.

## Migration posture if Cloudflare says no

Keep the user-facing ZIP format, sender ownership checks, compiled MIME semantics, idempotency and message status stable. Replace only the server-side delivery adapter with a provider that affirmatively accepts multi-tenant user-composed mail and supports the verified `mail.moesegfault.dev` sender domain, arbitrary recipients, delivery/bounce/complaint events and suppression. The provider credential belongs only in Workers secrets; user agents and CLI must never receive it. Re-test DKIM/SPF/DMARC alignment, actual attachment/CID rendering, callback authenticity, rate limits, failure mapping, and trace redaction. The official `mail@moesegfault.dev` identity remains separate. This is a contingency, **not** a recommendation to migrate to Mailgun, SES or another named provider without explicit approval.

## Current project state

`docs/feasibility.md` and `docs/product-audit.md` already identify this risk. The Worker uses a sending binding for user mail and an official sender-constrained binding exists, but no production outbound delivery has been demonstrated. The pending Email Routing Rules token concerns dynamic **inbound** address provisioning; obtaining it does not answer the outbound-use question. This note changes neither code nor deployed policy.
