# Outbound mail scope and launch controls (2026-09-28)

## Product decision

The owner clarified that amail is an **agent-workflow mail tool for transactional notifications and replies**, not a general human mailbox or a promise of unlimited, unsolicited first-contact correspondence. Preserve the CLI/ZIP sending contract and user-owned `@mail.moesegfault.dev` identity, but describe intended use as messages arising from a concrete workflow: replying to inbound mail, following up on an existing interaction, or notifying a recipient about work the agent performed. Do not market it as bulk marketing, cold outreach, or a sender of arbitrary unsolicited campaigns.

Cloudflare's [FAQ](https://developers.cloudflare.com/email-service/reference/faq/) describes Email Service as transactional and excludes marketing. Its [email-for-agents announcement](https://blog.cloudflare.com/email-for-agents/) explicitly discusses receiving, persisting, replying and notifying users when agents finish work, and presents Agentic Inbox as a full email application reference. The clarified amail scope is therefore aligned with the use cases Cloudflare publicly describes. This is a **product-scope inference**, not an assertion that every conceivable agent-generated message is permitted. The former proposed release blocker—written approval for *arbitrary multi-tenant first-contact mail*—was based on a broader product interpretation the owner explicitly rejected and is removed. An unexpected provider restriction or rejection during real delivery must still be investigated rather than bypassed.

## What must work before public send

| Gate | Evidence required | Why it matters |
| --- | --- | --- |
| Real user-domain delivery | Send a ZIP-authored transactional reply/notification from an active owned `@mail.moesegfault.dev` address to a controlled external inbox; inspect received MIME/HTML/CID/attachments, SPF/DKIM/DMARC alignment and provider [delivery logs](https://developers.cloudflare.com/email-service/observability/logs/). | Provider `202` means accepted for processing, not delivered. A sending-domain DNS check is not enough. |
| Official sender separation | Send one operator-controlled canary from `mail@moesegfault.dev` using a narrow Cloudflare [Email Sending REST API](https://developers.cloudflare.com/email-service/api/send-emails/rest-api/) credential; inspect received sender/authentication. Never let a user ZIP select that identity. | The production `OFFICIAL_EMAIL` binding is sender-constrained but currently unused; its existence alone does not prove mail can arrive from the apex sender. Do not invent a welcome-mail feature just to exercise it. |
| Abuse containment appropriate to bounded launch | Verify active address ownership, fail-closed account/global send holds, bounded per-account/day and burst/recipient attempts, provider quotas, recipient/attachment limits, idempotent retries, monitored abuse-report intake, and a tested operator stop/disable path. Correlate [bounces, complaints and suppressions](https://developers.cloudflare.com/email-service/concepts/suppressions/) to the sender and take timely action. | Even transactional workflows can be abused or misaddressed. Platform suppression helps but does not substitute for account-level intervention. `docs/outbound-abuse-design.md` defines the preferred native Cloudflare Event Subscription → Queue → Rust consumer/DLQ integration and concrete acceptance probes; implementation is underway, not yet deployed or proven. |
| Honest product language | The site/manual and agent skill must not imply unlimited unsolicited sending or guaranteed delivery. A send response should say accepted/submitted, not delivered. | Technical ability to address unverified recipients does not change the transactional product boundary. |

The [Email Service limits](https://developers.cloudflare.com/email-service/platform/limits/) and [pricing](https://developers.cloudflare.com/email-service/platform/pricing/) make quota, message size, and Paid-plan eligibility separate from the usage-category decision. Do not conflate a successful synthetic OpenRouter probe, onboarded DNS, or staging HTTP health with any mail gate above. Do not commit test bodies, recipient identities, tokens or complaint details; record sanitized status and trace IDs in `docs/validation.md`.

### Feedback-path fallback if native provisioning is blocked

The preferred release path is the native event Queue and holds in [outbound-abuse-design.md](outbound-abuse-design.md), including recipient attribution, retries/DLQ, complaint-triggered review, and a real operator intake. Do not downgrade that design silently merely because Cloudflare Queue/Event Subscription provisioning is unavailable. If provisioning is blocked, the owner must make a **visible, time-bounded fallback decision** before public outbound is enabled: either defer public send or approve a measured operational alternative that uses Cloudflare activity/suppression data, assigned monitoring ownership and cadence, a tested account/global hold, recipient-level complaint response, and lower send/recipient/burst limits matched to demonstrated human response capacity. Record the reason, volume ceiling, alert and review times, drill evidence, and a date/condition for returning to event-driven feedback. A manual dashboard glance without reliable sender attribution or a tested stop path is not an acceptable fallback. Regardless of feedback transport, actual external delivery and abuse intervention remain release gates; no Queue source/configuration or manual process should be called complete before a deployed canary and complaint/bounce drill pass.

## Escalation and future scope

If a future product proposal expands from workflow replies/notifications into general-purpose or unsolicited first-contact mail, revisit provider policy and consent/abuse infrastructure **before** changing the public promise. Obtain provider clarification where the expanded category is genuinely uncertain; do not demand written approval for a category amail is not offering now. If Cloudflare rejects a message in the current transactional scope, preserve the ZIP/API contract, diagnose the concrete reason, and only then evaluate another outbound transport. A provider swap is a contingency, not part of the v0.1 acceptance definition.

`docs/feasibility.md` records the earlier, broader uncertainty as historical research; this decision supersedes its proposed approval gate for v0.1. The pending Email Routing Rules token is for dynamic **inbound** address provisioning and has no bearing on outbound product classification.
