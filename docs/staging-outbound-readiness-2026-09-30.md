These facts do not establish that a fresh alias is still active, that the subscription processed a real send, or that an external inbox is available. The fifth-run fixture cleanup retired its run alias; the normal inbound E2E also retires its disposable alias in `finally`. Do not assume either leaves an outbound sender.

The repository has `grant-send-canary.yml`, but it runs only on `main`; the new reusable canary workflow is not wired into a manually dispatched hosted `ci.yml` hook. `origin/main` did not contain that grant workflow at the time of the inspection. These are **historical configuration observations**, not a fresh secret-name readback or a claim about undisclosed secret values or future GitHub dispatch behavior.

## One guarded run and honest outcomes

Sequence: finish the fresh inbound acceptance; provision/retain a dedicated synthetic sender; provision/consent to an external IMAP oracle; install protected staging secrets; run read-only privacy, Inbox, sender, subscription/Queue/DLQ and policy preflights; establish same-runner native login; issue **one** 15-minute recipient-pinned grant; execute the existing script **once** while at least 120 seconds remain. The script checks ZIP assets (text, HTML CID image, exact binary attachment), one external raw MIME and one same-request `delivered` provider event plus attributed D1 `recipient_outcomes`. It prints only `canary_provider_accepted_not_delivered` after acceptance and `canary_external_inbox_and_feedback_verified_auth_manual_pending` if both independent oracles pass. The latter still requires operator provenance review before SPF/DKIM/DMARC can be called verified. Record the fixed label, run URL, deployed Worker versions and restricted opaque correlations; inspect Queue/DLQ health privately. An HTTP 202, provider `delivered` event alone, or a sender-domain DNS record is **not** mailbox-delivery proof: Cloudflare defines `message.delivered` as recipient mail-server acceptance ([Event subscriptions](https://developers.cloudflare.com/email-service/platform/event-subscriptions/)).

If send times out or returns an ambiguous 5xx, preserve the original key and inspect exact D1/provider state; do not issue a second key or grant. If the Inbox is empty but D1 says delivered, inspect the controlled mailbox's Junk/quarantine and receiver trace **privately** rather than marking delivery passed. If MIME arrives but no event/outcome appears, diagnose exact subscription/consumer/DLQ/attribution without replaying the email. A staging pass never sets production gates or general `allowed`; the production canary is separate.

## Source-level follow-up before a live dispatch

The existing script searches only IMAP `INBOX` and requires one `Authentication-Results` field claiming the configured authserv-id. This is a deliberately strict oracle: a valid message filed to Junk/quarantine or a receiver that omits/rewrites headers yields no pass. Choose a mailbox with an independently readable receive path or explicitly review a narrow, private folder/trace extension before execution; do not weaken SPF/DKIM/DMARC provenance. The current `grant-send-canary.yml` subject-as-input and missing guarded `ci.yml` dispatch hook remain execution/privacy gaps, not reasons to bypass the global hold. Review that design separately and run hosted contract tests before the first grant; do not rerun unrelated successful CI or release packaging merely to prepare this probe.
