# Independent role-monitor review (2026-09-29)

Scope: uncommitted Rust `workers/role-monitor` Email/Cron Worker, isolated D1 migration, staging-only route helper/deployment, CI additions, and the mail API lease gate. This is a source review, not a live SMTP or deployment acceptance. The four existing production direct-forward rules were not changed. Cloudflare's current [Email Worker API](https://developers.cloudflare.com/email-service/api/route-emails/email-handler/) documents awaited `forward()` and `X-` forwarding headers; the [Scheduled Handler API](https://developers.cloudflare.com/workers/runtime-apis/handlers/scheduled/) documents outcome reporting.

## Resolved P1 — The alert outbox previously could mark an unseen arrival as alerted

At `workers/role-monitor/src/lib.rs:101-110`, an Email invocation samples `received_at` **before** awaiting the D1 insert. At `:144-168`, Cron captures a timestamp cutoff, queries the rows satisfying `received_at < cutoff`, sends a digest, then runs a broad `UPDATE role_arrivals SET alerted_at=... WHERE alerted_at IS NULL AND received_at < cutoff`. These are not the same frozen row set. If one D1 insert was delayed while another row already caused a digest, the late insert can commit after Cron's SELECT but before its UPDATE while retaining the earlier sampled `received_at`. Cron then marks it alerted although the sent digest excluded it. Once forwarding is accepted, the later `pending` and `unknown` checks can both pass and renew a healthy lease. This is a concrete silent missed-notice path, not merely duplicate delivery.

Re-review: the revised schema now assigns `arrival_seq INTEGER PRIMARY KEY AUTOINCREMENT`. Cron snapshots `MAX(arrival_seq)` and uses the same high-water bound for group selection, reference selection, and the post-send update (`src/lib.rs:158-190`). A delayed insert has a later sequence even if its timestamp predates the cutoff, so it remains pending for a subsequent digest. `infra/tests/test_role_monitor_schema.py::test_delayed_insert_is_not_falsely_marked_alerted` exercises this interleaving. This resolves the reported silent-miss path for the fresh schema. Since this was an edit to migration `0001`, a previously applied old schema would not gain `arrival_seq`; see migration note below.

## Resolved P2 — Failed Cron runs previously were reported as successful invocations

`workers/role-monitor/src/lib.rs:127-132` catches every `run_monitor` error, prints one `console_warn!`, and resolves the scheduled handler. Cloudflare says the returned promise's outcome is observed by the runtime and that rejected work is reported as failed in Cron Trigger Past Events. Here a D1 outage, routing-audit error, send failure, or unresolved forward is therefore shown as a successful Cron invocation. The lease eventually expires, so this is not a direct send-gate bypass, but it defeats prompt end-to-end failure monitoring and hides the reason in a generic warning.

Re-review: the revised handler emits a static warning then panics on monitor failure (`src/lib.rs:130-139`). The locally pinned `worker-macros 0.8.7` scheduled glue invokes the attributed function and discards any returned `Result`, so a static panic is a plausible way to reject the invocation without including secrets in the error. This removes the false-success path at source level; the actual Cloudflare Cron Past Events state still requires a staged fault-injection acceptance test. The static warning does not classify which phase failed, limiting diagnosis but not reopening the original failure-status finding. [Cloudflare Scheduled Handler](https://developers.cloudflare.com/workers/runtime-apis/handlers/scheduled/).

## Resolved conditional migration guard

The deploy guard now reads `PRAGMA table_info` for both role tables and requires the reviewed columns and integer primary keys before reusing a pre-existing schema (`workers/role-monitor/check_staging_db.py:16-89`). This rejects the earlier migration shape if it had been applied. For an empty isolated D1, Wrangler applies the migration normally; on subsequent deployments, the schema guard passes and Wrangler's migration ledger prevents replay. No source-level migration blocker remains, subject to hosted and live deployment checks.

## Final scoped deploy-workflow review

The new `.github/workflows/deploy-role-monitor-production.yml` is `workflow_dispatch`-only on `main`, runs the forwarding helper with `ROLE_FORWARD_PHASE=audit` before and after deployment, and does not call its write phases. The helper's audit requires each of the four enabled literal API-owned `forward` rules to match the protected destination. The Worker Wrangler config has no `addresses` or HTTP route; its production deployment therefore cannot intentionally take ownership of routing rules. The candidate-branch staging job in `.github/workflows/ci.yml` audits that its single synthetic route is absent before and after Worker replacement. The staging route helper only mutates that exact alias on explicit `--apply`/`--remove` and refuses conflicting ownership. Secret values are read from protected environment secrets, written to a permission-restricted ephemeral runner file for `wrangler deploy --secrets-file`, and never interpolated into workflow output; shell trap deletes the file after the deploy step. No production-rule mutation or secret-disclosure blocker was found in these workflows by source inspection.

## Positive checks and limitations

- Production recipients are fixed to four literal addresses, staging to a separate synthetic alias. Unexpected envelope recipients are rejected. No HTTP handler is exposed, and the staging helper audits all pages, refuses rule conflicts, and restricts mutations to the synthetic alias.
- D1 schema is content-free (random UUID, role enum, timestamps, states); forwarding destination is a secret, and digest sender is fixed to `mail@moesegfault.dev`. The send binding constrains sender but deliberately not recipient to avoid committing the private address; code and account verification limit the live destination. Cloudflare [send-binding docs](https://developers.cloudflare.com/email-service/configuration/send-bindings/) confirm that an unqualified binding can reach any verified destination; this is a residual privilege acknowledged in the README, not a newly demonstrated routing defect.
- The initial D1 insert precedes `forward_with_headers`; `forward_state='accepted'` only follows the provider call. An exception after actual provider acceptance remains `unknown` and blocks lease renewal, favoring safety over availability. Real SMTP exception/retry behavior and final recipient Inbox placement are **not** established by the source or unit tests.
- The isolated D1 binding in the mail API has database write capability at the platform level despite the code reading only the health row; the current trusted mail API uses it read-only. This is an architectural least-privilege limit to document rather than a claim that the code currently writes that database.
