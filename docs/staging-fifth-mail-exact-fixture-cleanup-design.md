## Third cleanup stop: submitted Message-ID is not a valid provider invariant

The [third hosted cleanup dispatch 36670874444](https://github.com/kleedaisuki/moesegfault-amail/actions/runs/36670874444) passed its serving-version preflight, native authentication, full owner-scoped inventory, title matching, and every preceding `get` field, then emitted `fifth_cleanup_failed:fixture_get_message_id_mismatch`. By the reviewed `verify_row` ordering, the observed `metadata` was an object and the ID, mailbox, direction, subject, From, To, text/HTML and attachment-shape predicates all passed **for at least the first checked active fixture**. The fixed label does not reveal the observed Message-ID, whether the second fixture would pass, or which upstream hop changed it. The first deletion remains after both `get` validations, a second control read, repeated inventory, and a second serving pin; this stop issued no `amail delete` from this script. A fresh aggregate after this run is still desirable before any later mutation, rather than assuming historical counts persist forever.

The test's `make_mail` constructs `EmailMessage` with `Message-ID: <amail-e2e-<nonce>-signal|distractor@mail-staging.moesegfault.dev>` and submits its serialized MIME using authenticated Cloudflare SMTP. `smtplib.sendmail` reports refused recipients but this harness discards the SMTP `DATA` 250 response and its provider-assigned identifier. Cloudflare's current [Email headers reference](https://developers.cloudflare.com/email-service/reference/headers/) says that SMTP uses the same header allowlist and that `Message-ID` is platform-controlled, generated for unique tracking; its [SMTP reference](https://developers.cloudflare.com/email-service/api/send-emails/smtp/) says the successful `DATA` reply normally includes the assigned Message-ID. This is a **strong mechanism hypothesis** for the mismatch and means strict equality to the submitted header is not a sound general SMTP acceptance invariant. The docs do **not** establish what exactly happened to this old MIME: notably their explicit `E_HEADER_NOT_ALLOWED` wording is about the structured API `headers` object, while this SMTP submission was accepted and two fixture-shaped messages were later stored. Possible actual outcomes include replacement, omission, an added duplicate field ahead of the original, or another representation change. Do not assert any one without readback.

Our source has a short custody chain: `workers/mail-ingress/src/lib.rs` copies `ForwardableEmailMessage.raw_byte_stream()` bytes to the private `MAIL_API` service binding without modifying headers; `crates/mail-worker/src/lib.rs::inbound` stores that input as restricted `raw/{id}.eml`, calls `archive::inbound_archive`, and stores both the resulting ZIP and `metadata_json` in D1. `archive::inbound_archive` uses `mailparse::MailHeaderMap::get_first_value("Message-ID")`, which [returns the first case-insensitive matching header](https://docs.rs/mailparse/0.16.1/mailparse/trait.MailHeaderMap.html); its value decoding can unfold whitespace, so byte-for-byte raw-header equality is not the right parser test. It writes the parsed value to both D1 `metadata.message_id` and ZIP `manifest.toml`. Thus `amail get` versus ZIP manifest agreement would verify archive/metadata consistency, but these are two outputs of **one parse**, not independent proof of sender origin. The retained R2 raw MIME can independently test what the ingress Worker actually received and whether multiple `Message-ID` fields existed; it is still downstream of Cloudflare Sending and cannot by itself prove the original SMTP submission or rule out a matching-header forger.

### Search consistency and privacy rules

`search_job_stale` (HTTP 409) may be retried **only for the read-only search**, from a fresh first page, at most twice with bounded delay (e.g. 2 s then 5 s). Treat `search_cursor_stale` similarly, discarding the entire partial pagination snapshot; never combine pages from different generations. Resume an already accepted search job privately using its job ID instead of resubmitting while it is running. Any third stale outcome, persistent/unknown 409, 429, 5xx, timeout, incomplete page, or unclassified CLI failure is a no-go, not an empty result. The same bounded policy applies to post-delete readback, but a readback failure must report cleanup **unverified** rather than prompting a second mutation. Avoid concurrent account/mailbox probes during the narrow cleanup window; indexing may still mutate search generations.

Capture raw CLI stdout/stderr only inside the protected process. Parse only allowlisted status/code and expected JSON shapes; never echo raw subjects, aliases, message IDs, search cursors/job IDs, bodies, ZIPs, auth codes, tokens, or raw provider responses to Actions logs, diagnostics, or artifacts. Set `AMAIL_TELEMETRY=off` for this operation, recognizing that this does not disable background embedding. The generated nonce and submitted Message-ID are **locators, not authentication**: anyone able to see or copy a mail can spoof headers and subject. The multiple independent checks reduce accidental deletion risk, but only a trusted provenance record can resolve an adaptive same-title/same-header spoof. If such a record is unavailable when ambiguity exists, fail closed and leave the message for restricted manual review.

## Why this is not the existing cleanup

`staging_mail_e2e.py::cleanup_run` uses a single `sync --limit 100` page and title equality. That is incomplete for an old run and cannot distinguish a forged same-title message. Search plus exact mailbox scoping, complete pagination, account/D1 agreement, `get` corroboration, single-ID deletion, and readback replace that unsafe shortcut **for this fallback only**. The Worker currently scopes `get`/`delete` by `(owner_iss, owner_sub)` and marks `deleted_at`; its Cron later purges deleted rows. Cloudflare documents that D1 queries outside its Sessions API read from the primary, which supports the separate control-plane aggregate as a current readback, but the route audit and CLI observations are still separate systems and must agree: [D1 read-replication guidance](https://developers.cloudflare.com/d1/best-practices/read-replication/).

## Risk-based decision for the historical synthetic fixtures (2026-09-30)

**Decision: conditional go for a revised, separately reviewed exact-ID cleanup without requiring provider event provenance.** This section supersedes the stricter *deletion authorization* rule above, but not its read-only forensic proposal, privacy constraints, or the rule to stop on any actual inventory/content ambiguity. The goal here is **cleanup of two synthetic messages in an isolated staging test account**, not proof that the 2026-09-29 SMTP acceptance produced a particular byte sequence or a successful mail E2E. The current script still blocks on the submitted `Message-ID`; it must not be dispatched unchanged. Cloudflare documents `Message-ID` as platform-controlled even for SMTP MIME, and the SMTP 250 receipt that could have independently identified the historical submissions was not retained ([headers](https://developers.cloudflare.com/email-service/reference/headers/), [SMTP](https://developers.cloudflare.com/email-service/api/send-emails/smtp/)). The observed mismatch is therefore a **failed test oracle**, not positive evidence of a foreign message. It does not by itself prove a particular provider rewrite.

The 16-hex-character HMAC-derived mailbox nonce has at most 64 bits of guessing resistance: an attacker who did not learn the alias would have probability at most approximately `q / 2^64` after `q` independent guesses. **Do not multiply this by the subject, phrase, or CID**, which reuse the same nonce and add no independent secret entropy. The alias is a private locator, not an authentication credential; an attacker who learned it while its route was enabled could spoof sender, subject, body and MIME shape. The 73-byte attachment *length* and static inline PNG are weak fingerprints; the random attachment digest was not retained. Conversely, the Mail Worker allocates each inbound D1/CLI message ID with UUIDv4; the cleanup selects those existing owner-visible IDs, not a sender-supplied `Message-ID`. A spoof can at worst be one of the two selected rows in this synthetic account. It cannot cause a broad deletion or reach a different principal's mail because `get` and `delete` both constrain `(owner_iss, owner_sub)` and the script issues one delete per selected ID. The present aggregate excludes foreign-owner rows, so this is **not** evidence of global absence, only of the exact authenticated principal's visible inventory and expected-owner counts.

The material wrong-delete risk is therefore bounded by the **blast radius**: at most two active records at the retired, route-absent test alias, in the expressly synthetic staging account, with no other owner-visible or expected-owner inbound/outbound mail. A deliberate perfect spoof or a coincidental unknown foreign-owner record cannot be ruled out, but deleting a perfect spoof from that synthetic mailbox is still within the intended cleanup; a foreign-owner record is not selected by the principal-scoped CLI. This conclusion would **not** transfer to a real user's mailbox, an alias still receiving traffic, a partially enumerated mailbox, or a demand to prove SMTP provenance. The historically observed aggregate (two active fixtures and zero other mail) and the third run's field-specific `get` checks are supporting evidence, **not a fresh mutation authorization**. Require a fresh full preflight immediately before any delete.
