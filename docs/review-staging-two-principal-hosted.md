# Independent review: hosted second principal and mailbox isolation

Scope: source review of the final opt-in staging registration and two-principal E2E slice (`55dbf80`), its GitHub Actions wiring, the native CDP/PKCE helper, Identity's staging schema, the Mail Worker owner predicates, and Cloudflare's documented R2 object API. Earlier local revisions were consolidated into this source commit without changing the reviewed final tree. No live account, Email Routing rule, SMTP message, or Worker was created by this review. No local heavy test was run; hosted CI and live evidence remain separate gates.

## Decision

**Source GO for the reviewed committed correction, conditional on a green hosted CI run. Live provisioning is not yet authorized by this source review.** The source now has a defensible two-principal oracle: it requires the staging Identity contact-to-username-to-pairwise-subject relation, normal native PKCE for both homes, A's real two-message positive controls, B's negative list/search/ID operations, and A's immediate unchanged-state readback. This is an authorization regression probe, not a proof that every API route or future semantic query is isolated.

## Findings and correction status

1. **P1, authorization proof — corrected at source.** The first implementation read two distinct verified contact rows and pairwise subjects, but did not establish that the protected usernames used by native CLI login belonged to those rows. An unrelated B login could make the subject comparison irrelevant. The correction queries each contact principal's unique normalized username in the final Identity `identifiers` schema, and compares it with the protected A/B usernames before A creates an address. Identity's final migration enforces one username per principal (`migrations/0004_email_verification.sql`). A second safeguard is behavioral: B's address/sync preflight and later A-positive/B-negative differential cannot pass if B is accidentally A once A's fixture exists. The source test exercises mismatched B contact ownership.
2. **P1, owner oracle — corrected at source.** Mail `get_message` injects a fresh `request_id` into each response (`crates/mail-worker/src/lib.rs`). Comparing complete A GET dictionaries after B operations always failed, even when mail was unchanged. The correction projects away only this documented volatile field before equality, with a test where request IDs differ but stable message fields do not. It checks after *each* B ID operation: checking only after `mark --read` followed by `mark --unread` could miss transient unauthorized side effects that cancel out.
3. **P1, private OTP cleanup — corrected at source.** The initial cleanup deleted only the R2 key selected as the OTP. If two new objects appeared before selection, or a second arrived later, the selected-key list was empty/incomplete and private MIME remained after the job failed. The correction inventories the bounded post-baseline delta after exact route closure, deletes only those run-window keys in two passes separated by a short settle period, and requires a final empty delta; baseline objects are never removed. A read/list/delete error fails closed and requires exact manual reconciliation. The success label is emitted only after route, object, and local artifact cleanup succeeds. A cancelled runner remains outside Python `finally` and still requires external reconciliation.
4. **P2, same-account recovery — corrected at source, live UI unverified.** The workflow deletes the run-local DPAPI blob even after partial registration, so recovery cannot depend on a *saved* blob. Identity permits username/password sign-in while the email contact is unverified (`crates/identity-worker/src/password.rs`), and Account Center provides an unverified-contact verification/resend flow (`apps/account/src/pages.ts`). The separate `staging-second-principal-recover` target uses the protected B credentials, requires the existing B contact to be unverified/pending and bound to B's username, opens only the audited exact B route, verifies via the first-party Account UI, then closes the route and cleans R2 before native attestation. It is separately confirmed, and mock tests check the mode gate and route-close-before-code order. Never rerun new-account provisioning after POST 201 or uncertain outcome.

## Boundaries checked

- The new provisioning job is `workflow_dispatch` only, staging Environment gated, and separately confirmed. The ordinary `staging-e2e` path defaults `isolation=false`; the follow-up workflow hunk passes B secrets only when isolation is requested. No B route or extra SMTP is created by the isolation helper.
- The private challenge Worker has no HTTP handler, requires an exact configured recipient, and writes a fresh UUID-named MIME object. The route helper's exact-address apply/remove is bounded to B; deployment interlocks for both A and B were reviewed in the earlier private-inbox review.
- The R2 OTP selector requires one new object, a single exact `From`/`To`, fresh `Date`, one text/plain code and the address in the body. These visible MIME fields are not cryptographic sender authentication; successful first-party verification completion is the decisive OTP proof. Cloudflare documents object listing, binary GET, and DELETE through its [R2 API](https://developers.cloudflare.com/api/resources/r2/subresources/buckets/subresources/objects/methods/list/).
- Browser authorization URLs, credentials, OTPs, subjects, raw provider responses, ZIP bytes and CLI stderr are held in memory or suppressed; Actions output uses fixed labels. A denied B archive is removed immediately if erroneously written. Cancelling a hosted runner cannot execute Python `finally`; the exact B route/R2 inventory and A run-owned alias still require documented post-cancel reconciliation.
- B checks owner-scoped address list, `sync --all`, title and Message-ID metadata search, GET, ZIP read, mark in both directions, message delete, and address delete. The Mail Worker scopes individual message reads and mutations to `(owner_iss, owner_sub)` and returns the same `404/not_found` for foreign and nonexistent IDs. The test deliberately does not cover raw API variants absent from the CLI, sender ownership, quota races, or semantic-index isolation.

## Remaining evidence before live use

Green hosted Python/CLI/Worker CI on the final source; deployed private-inbox recipient/R2 binding readback and version pin; current exact A/B route absence; current Identity B-contact absence; current R2 list/get/delete permission probe before mutation; B secret placement and recovery runbook; then exactly one confirmed hosted B provisioning. A successful provisioning is **not** an ownership pass: run the separately confirmed two-principal E2E only after B's verified contact and native session are attested, and record exact A route/message cleanup. Do not infer live success from source tests.

**Source GO; no live rerun by this reviewer.** Hosted read-only run `36695119073` at `1a5764d` stopped with the previous aggregate `r2_inventory_invalid` after the deployed-inbox, route and Identity D1 reads, before B-state classification or any mutation. That label did not identify the actual R2 response shape. Commit `eb14e23` distinguishes absent `result_info`, invalid pagination metadata, malformed entries/keys and duplicate keys using fixed labels only. It still rejects a missing or non-boolean `is_truncated`, requires a new cursor for truncated pages, bounds pages/keys, and rejects duplicate keys even across pages. The synthetic cases include empty result with missing metadata, invalid metadata, bad and duplicate keys, and cross-page duplication. No permission or B-contact conclusion follows from the old aggregate failure. Cloudflare documents `result_info` as optional in its [R2 List Objects API](https://developers.cloudflare.com/api/resources/r2/subresources/buckets/subresources/objects/methods/list/); treating absence as complete would weaken the inventory gate, so the fail-closed choice is justified. A later single read-only probe may classify the live shape after hosted CI, but no automatic retry or one-shot registration should follow merely from this source review.
