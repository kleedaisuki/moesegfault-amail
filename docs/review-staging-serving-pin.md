# Review: staging Mail Worker serving-version pin

Reviewed `dd76324` and `52d44fb` plus the uncommitted `staging-serving-pin` job in `.github/workflows/ci.yml`. This was a static review only: no local tests, Cloudflare calls, GitHub dispatch, or address/routing mutations were performed.

## Assessment

No remaining substantive code blocker was found for a **read-only, fail-closed preflight**. The initial design checked the serving Version ID but read bindings only from unversioned `/settings`, which could not prove that those bindings belonged to the serving version. The correction now fetches `GET /versions/{version_id}` and requires matching `result.id` plus exact staging D1 IDs, R2 bucket, binding names/types, and reviewed plain-text values. It rejects absent, opaque, duplicate, extra, or wrong-target bindings. Cloudflare documents that [the first listed deployment is actively serving](https://developers.cloudflare.com/api/resources/workers/subresources/scripts/subresources/deployments/methods/list/) and that [the version GET returns resources for a specific version](https://developers.cloudflare.com/api/resources/workers/subresources/scripts/subresources/versions/methods/get/). The two deployment reads compare both deployment and Version IDs, so even a same-version redeploy during the inspection window fails.

The job uses only GET requests and keeps the existing broad project token in one step-scoped environment variable. Account IDs, resource identifiers, provider bodies, token values, and unexpected Version IDs are not printed by the normal path; output is one fixed label. The contemporaneous `/settings` and `/script-settings` checks reuse the existing observability privacy predicate. Since the version GET schema does not expose observability and the settings URLs do not take a Version ID, the documentation correctly limits this to **script-level readback at inspection time**, not an immutable version-specific privacy proof. The retained-log privacy canary remains a separate gate.

The official version GET example renders `resources.bindings` as an object, while binding metadata in other Cloudflare API surfaces appears as arrays. The implementation accepts only a direct list or an exact `{ "result": [...] }` wrapper and rejects the empty `{}` example. This is a reasonable fail-closed parser, but the **real endpoint shape remains unverified** until the first hosted pin run. A `bindings_mismatch` result must not be interpreted as actual resource drift before provider-shape evidence is obtained. The synthetic tests cover both accepted shapes, wrong targets, extra bindings, split traffic, unsafe privacy settings, and a same-Version-ID/different-deployment-ID race; they establish parser logic, not Cloudflare live behavior.

## Residual boundary

A successful pin attests an observed interval only. It cannot prove that a later authenticated E2E request hit that deployment, that Email Routing Rules Write works, or that retained logs are free of sensitive content. Freeze competing staging deploys and run the controlled E2E soon after a successful hosted pin; preserve its exact run URL, checkout SHA, and expected Version ID in `docs/validation.md`.
