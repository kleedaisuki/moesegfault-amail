Before either one-shot registration or same-account recovery, run the separate **strictly read-only** manual `staging-second-principal-preflight` target with `confirm=READ_STAGING_SECOND_PRINCIPAL_PREFLIGHT`. It uses the existing repository-level B credential Secrets to validate their shape and, through current Cloudflare credentials, checks deployed private-inbox settings/privacy, both exact routes absent, A's verified Identity contact, B's contact status and matching username, and a bounded private R2 object listing. It never opens/removes a route, launches a browser, creates an account, reads an OTP object, or deletes an object. Output is only one fixed label: `..._absent`, `..._pending_same_account`, or `..._verified_same_account` (otherwise a fixed failure). A denied D1 query and a denied R2 list return different fixed phase labels without provider response bodies. A green result proves current D1 read and R2 **list** capability, not R2 object get/delete permission, future token validity, or live Worker serving-version pin. Those remain independent prerequisites before mutation.

The new manual `staging-second-principal` Windows Actions target is intentionally **not** a secret generator. Before any dispatch, place one fresh B-only username/password in repository-level `STAGING_E2E_B_USERNAME` and `STAGING_E2E_B_PASSWORD` Secrets (not duplicate environment Secrets), keep the job under the existing staging Environment gate, and independently confirm the current `CLOUDFLARE_API_TOKEN` can read Identity staging D1 and list/get/delete objects in the private verification R2 bucket. The workflow demands `confirm=RUN_STAGING_SECOND_PRINCIPAL_PROVISION`. It runs a final-schema contact preflight, both exact-route absence checks, private R2 baseline inventory, then opens only B's exact route. The existing first-party CDP registration enters a single fresh, exact-recipient Identity text-code from R2 *in memory*, closes the exact route before OTP submission, completes normal verification, performs native PKCE, and checks A/B's different registered pairwise subjects, binding B's protected login username to B's verified contact. Finally it removes B's route, deletes/readbacks the run's private MIME, and removes `.temp` browser/credential material. Logs contain fixed labels only. The contact preflight makes this job non-repeatable: **after an ambiguous registration, do not dispatch it again; recover the same B account instead**.

A separate manual `staging-second-principal-recover` target uses `confirm=RUN_STAGING_SECOND_PRINCIPAL_RECOVER` and the **same** B repository Secrets only when restricted Identity readback finds the exact B contact still `unverified` or `pending` and owned by that username. It does **not** call registration. It signs in through the first-party Login page, opens the exact B contact in Account Center, starts a fresh verification transaction, receives one private R2 code, closes B's route before submission, and then performs native PKCE and A/B subject readback. A verified B contact must proceed directly to the isolation E2E, not to either provisioning target. A failed recovery may be retried only after exact route/object state and the same B contact are independently reconciled; do not create a replacement principal. The existing Account Center contact-verification flow and username login support this recovery without preserving a runner-bound DPAPI blob.

The first hosted run is still conditional on version pinning and independent review. The R2 MIME's visible sender/address/date and fresh single-object selection limit confusion but are not cryptographic authentication of the sender; Identity's 200 verification-completion response is the decisive code proof. An ambiguous/multiple delivery, unsupported provider response, or missing R2 permission stops the job and requires exact route/object reconciliation, never guessed OTP or account recreation. [Cloudflare's R2 object API](https://developers.cloudflare.com/api/resources/r2/subresources/buckets/subresources/objects/methods/list/) documents list/get/delete for this bounded private retrieval.

## R2 object-operation capability gate (first guarded probe inconclusive)

**Decision: NO-GO for B registration on the list-only preflight.** The B flow must read a private OTP object and delete it after use. Cloudflare documents separate [GET](https://developers.cloudflare.com/api/resources/r2/subresources/buckets/subresources/objects/methods/get/) and [DELETE](https://developers.cloudflare.com/api/resources/r2/subresources/buckets/subresources/objects/methods/delete/) REST endpoints and distinct read/write [R2 permission groups](https://developers.cloudflare.com/r2/api/tokens/). A GET of a randomly chosen absent key may return `404` for several reasons; the published contract does not establish that this proves object-read authorization. A DELETE of an absent key, even if reported successful, cannot prove deletion of an existing object. Neither is a sufficient discriminator by itself.

The separate, explicit-confirmation Actions target `staging-r2-object-capability` now implements this **hosted-only** check. Dispatch it only from `codex/amail-v0.1.0` with `confirm=RUN_STAGING_R2_OBJECT_CAPABILITY`, after independent review and staging Environment approval. It uses the current repository-level `CLOUDFLARE_API_TOKEN`, account and private bucket as the B job, but neither B credentials nor Identity registration nor Email Routing mutation. Its secrets enter only the last workflow step. The target shares `staging-native-mail-acceptance` concurrency with B verification and other staging mail acceptance jobs, without canceling a running job.

The script first requires deployed private-inbox settings, public-domain and one-day lifecycle checks, every configured exact test route absent, and a complete bounded `verification/` keyset inventory. It derives one Worker-compatible UUIDv4-format key `verification/<uuid>.eml` and tiny non-email sentinel bytes **deterministically** from the numeric GitHub run ID and attempt using separate SHA-256 domains. Both remain reproducible after runner loss or cancellation; neither contains credentials, OTP, mail nor private user data. The key is potentially inferable from public run metadata, **not a bearer capability**: the bucket must remain private and all object operations require the Cloudflare token. The probe rechecks exact-key absence before uploading the sentinel through the REST API's multipart `body` field. It GETs and compares exact bytes in memory, DELETEs only the generated key, then requires both GET-not-found and a fresh complete inventory excluding it. Every exit after a possible PUT runs bounded exact-key cleanup/readback. An ambiguous DELETE is not blindly retried: cleanup first GETs the key and only reissues DELETE if it still contains the exact sentinel. Neither the key, body, provider response, token nor inventory is printed; output is a fixed success or phase-failure label. A GitHub rerun (`attempt > 1`) is refused rather than silently deriving another key.

The success marker `staging_r2_object_capability_verified` proves PUT/GET/DELETE for this token and bucket **at that time**, with the sentinel absent at final readback. It tests more than B strictly needs (PUT is extra), so `r2_put_denied` is inconclusive about GET/DELETE, not proof B would fail. Any failure, cancellation or uncertain outcome is **NO-GO for B** until the original run's exact sentinel is reconciled. Independently read the failed Actions URL and attempt number; confirm they belong to the original R2 capability probe, not another job. Dispatch `staging-r2-object-recover` with `confirm=RECOVER_STAGING_R2_OBJECT_CAPABILITY`, `r2_prior_run_id=<original numeric GitHub run ID>` and `r2_prior_run_attempt=<original numeric attempt>` on the reviewed branch, under the same staging Environment and concurrency group. Recovery performs **no PUT**: it derives the original key and bytes, GETs only that key, refuses any body mismatch or denied read, DELETEs only byte-matching synthetic content, and proves GET-not-found plus complete LIST absence. `staging_r2_object_capability_recovered_absent` means no object remains **for the supplied identity**; an incorrect run ID or attempt can produce the same label and must not authorize B. It does not retroactively prove a failed probe's operations. An ambiguous recovery DELETE is read back before conditional retry. On recovery failure, do not dispatch a new probe or B; reconcile the exact key with a privileged operator. The one-day `verification/` [lifecycle rule](https://developers.cloudflare.com/r2/buckets/object-lifecycles/) is a fallback, **not guaranteed immediate cleanup**. A process death or provider outage cannot guarantee cleanup, so the invariant is fail-closed plus exact-key recovery, not an absolute guarantee.

### First guarded object-capability result and source diagnosis

The one guarded [probe run 36713412204, attempt 1](https://github.com/kleedaisuki/moesegfault-amail/actions/runs/36713412204) stopped with `staging_r2_object_capability_failed:r2_put_ambiguous`. Its exact-key [recovery run 36718905227](https://github.com/kleedaisuki/moesegfault-amail/actions/runs/36718905227) returned `staging_r2_object_capability_recovered_absent`. No B principal or route was created by these jobs. The latter proves the derived sentinel was absent at recovery time, **not** that the PUT never persisted or that GET/DELETE against an existing object succeeded. B registration remains **NO-GO**.

At the probe's source revision, `r2_put_ambiguous` combined any non-200/non-403 HTTP status with a 200 response whose JSON envelope failed a strict `result.key`/`result.size` equality check. A socket timeout would instead have produced `r2_outcome_ambiguous`, and HTTP 403 would have produced `r2_put_denied`; neither explains the observed fixed label. The historical label cannot distinguish a provider 400/401/5xx from a successful 200 response omitting optional metadata. [Cloudflare's current Upload Object REST contract](https://developers.cloudflare.com/api/resources/r2/subresources/buckets/subresources/objects/methods/upload/) describes `result.key` and `result.size` as **optional**, while the request uses PUT with multipart `body` file data and literal slashes in the object-key path. The source's multipart construction and path follow that documented shape; a provider-side validation error remains possible but unproven. The strict metadata requirement was a source-level false-negative risk, not proof of the live cause.

The revised source accepts a successful 200 envelope with omitted optional key/size, rejects mismatching metadata when present, and still requires a subsequent exact-byte GET before any success. Non-200 PUT responses now produce bounded fixed HTTP categories (for example `r2_put_http_400` or `r2_put_http_500`), while an invalid 200 envelope reports `r2_put_response_invalid`; no provider body, key or token is emitted. Every possible PUT still enters exact-key reconciliation; ambiguous transport and DELETE outcomes are not blindly retried. The later guarded attempt below stopped before PUT, so this revised upload handling remains **unexercised live**. Do not re-dispatch the old run or launch a new probe merely because recovery succeeded; obtain independent review and decide a controlled next investigation first.

The latter narrows that separate failure to the private-inbox checker subprocess, but does not prove the earlier probe failed at the identical call or identify whether the managed R2 domain, custom domains, lifecycle, deployed Worker settings, source config, or process/transport failed. Do not infer changed bucket exposure or retry PUT from these aggregate labels. No B principal or route was created.

The B preflight now maps only **source-controlled** `check_config.py` errors to fixed phase labels: R2 managed-domain, custom-domain, lifecycle and Worker settings read/transport/policy, Worker binding mismatch, source-config mismatch, or checker subprocess failure. Unknown or multi-line stderr remains `private_inbox_checker_unclassified`; captured checker output, provider bodies, addresses and credentials are never forwarded. HTTP0 from the checker means transport unavailable, while a nonzero HTTP status or malformed read falls under that phase's `*_read_failed` label. These labels are diagnostic, not authorization or a change to the checker policy. The next independently reviewed **read-only** B preflight can locate the failing phase before any further probe or B mutation; there is no approval here to dispatch either mutation. This source change has not yet passed hosted CI.

Alternative when a synthetic write is unacceptable: independently inspect the exact GitHub token's **effective** account/bucket permission grants, then conduct a narrowly guarded hosted GET and exact-key DELETE against a disposable, independently created non-OTP object, followed by absence readback. Merely seeing a grant, a list result, or a 404 for a nonexistent key is weaker evidence than an exercised existing-object path. Regardless of the option, repeat the B read-only contact/route/object preflight immediately before its one-shot mutation because permissions and state can change; do not use probe success as a substitute for that preflight.

Cloudflare's [R2 List Objects REST contract](https://developers.cloudflare.com/api/resources/r2/subresources/buckets/subresources/objects/methods/list/) explicitly makes `result_info` optional and defines `start_after` as returning keys lexicographically after the supplied key. Rather than requiring optional metadata or treating a short page as terminal, the inventory now uses one uniform keyset walk: fixed `prefix=verification/` and `per_page=100`, then `start_after` set to the last validated key, continuing until an **explicit empty result page**. It requires every returned key to match the Worker UUIDv4 path and be strictly increasing, caps each page at 100 keys, total keys at 1,000 and requests at 20, and rejects duplicates, malformed data and nonterminating scans. Opaque `result_info` cursors are not used; malformed *present* metadata is rejected, and an otherwise empty page explicitly marked `is_truncated=true` fails closed rather than certifying completeness. This is not an atomic snapshot under concurrent R2 writes: keep the route closed and registration windows serialized, then re-audit immediately before mutation. A future read-only dispatch requires hosted CI and independent review of this change, not an automatic retry.

## Purpose and model

The address-isolation acceptance needs two distinct Identity `(issuer, sub)` principals with separate encrypted CLI homes. Reusing one account with two mail aliases would not prove authorization isolation. The second synthetic principal has a distinct exact **Identity contact** at the zone apex, `amail-e2e-isolation@moesegfault.dev`, not a user mailbox at `mail-staging.moesegfault.dev`. This is a test control-plane address, not a public role or permanent user address. Normal first-party registration, email verification and native OIDC/PKCE are mandatory; no D1 fixture or bearer-token injection is permitted.

The private staging verification Worker has a small explicit `TEST_RECIPIENTS` allowlist in its Wrangler configuration. Source code does not branch on “principal B”: the exact recipient is a parameter to the route and browser-registration helpers. The first alias remains the default for backward compatibility; the first account's older DPAPI credential blob remains readable, with a missing encrypted `address` interpreted only as that legacy alias. The second alias requires an explicit `--address` and a fresh run directory. The Worker accepts only configured recipients, while **each registration window still requires one independently audited literal Email Routing rule**. Route ownership checks remain exact and reject foreign, disabled or duplicate rules.
