# amail v0.3.0

Release record: 2026-10-25 (Asia/Singapore).

Terminal-bound profiles, a shared local daemon and short-lived test mailboxes
bring concurrent agent workflows into one account without multiplying resource
allowances or weakening send recovery.

## Client, daemon and profiles

- A thin CLI automatically connects to or starts the local daemon. Configuration,
  SQLite state and installed binaries live under `~/.amail` (Windows:
  `%USERPROFILE%\.amail`); `config.toml` overrides convention-based defaults.
  Binaries belong in its `bin` subdirectory. The daemon coordinates network I/O,
  mail processing and a bounded shared concurrency budget.
- Multiple CLI processes in one terminal share its active profile. A profile
  cannot be active in two terminals. `profile deactivate` removes the terminal's
  selection but retains the reservation for recovery; `profile release`
  relinquishes it. Thirty minutes without actual use automatically releases it.
- The initial `user` profile and profiles created by `user` persist after release.
  Profiles created by other profiles are deleted on release; reusable names do
  not confer access to the previous profile's data.
- `user` requires one-use browser approval for each protected operation unless
  the human explicitly configures YOLO. Profiles are not an OS security sandbox;
  YOLO does not approve spending or bypass server sending policy.
- Cloud-enforced mailbox occupancy allows shared readers or one exclusive writer,
  with no preemption. Expired sessions cannot reclaim another holder's occupancy.

## Temporary mailboxes

Any active profile may register `@tmpaddr.moesegfault.dev` test addresses with
`amail address add NAME --tmp`. Only `user` may register permanent
`@mail.moesegfault.dev` addresses.

Temporary mailboxes expire no later than six hours after creation. Activity and
paid plans do not extend that lifetime. Release is silent and irreversible;
expired or released mailboxes immediately disappear from queries. Reuse requires
completed data cleanup, route retirement and a fixed one-hour cooldown. A later
holder of the same textual address never obtains the previous mailbox generation.
Delayed incoming mail remains the address user's responsibility; temporary
addresses are unsuitable for long-lived identity or password recovery.

Export retained history while the mailbox is live and readable:

```sh
amail mailbox export NAME@tmpaddr.moesegfault.dev --output history.zip
```

The private bundle contains the mailbox manifest, message summaries and message
ZIPs across all result pages. Export is not undelete and does not extend expiry;
a lifetime change or expiry during export fails rather than publishing a partial
successful backup.

| Included concurrent addresses | Free | Lite | Plus |
| --- | ---: | ---: | ---: |
| Permanent | 1 | 3 | 5 |
| Temporary | 3 | 6 | 10 |

Address allowances are separate; all profiles and both address kinds share the
account's existing send and storage resource pools. Existing paid grants,
grandfathered permanent addresses and explicitly approved budgets remain intact.

## Upgrade and compatibility

1. Preserve original ZIPs, idempotency keys and accepted/unknown send journals.
   Inspect an unresolved intent using its original key; never rotate the key to
   work around an upgrade or an uncertain provider result.
2. Stop old CLI processes **before replacing binaries**. If a v0.3 daemon is
   already running, stop it with `amail daemon stop`; v0.2 clients have no daemon.
   Install the CLI and matching Agent Skill from the same release, verifying
   `SHA256SUMS`. The next operation starts the matching daemon automatically.
3. Coordinate old automation before enabling profiles for its account. Unenrolled
   owners retain v0.2.0 client behavior. Once enrolled, requests require a valid
   profile session; old no-profile clients cannot bypass mailbox occupancy and
   must upgrade. Deactivation is not a switch back to the legacy protocol.

The compatibility path also preserves old v0.2.0 `preparing` send intents:
validated, never-submitted permanent-mail intents can capture the new mailbox
fields without changing their original key, payload, message identity or journal.
Accepted and uncertain submissions are not reset, adopted as fresh sends or
resubmitted. JSONL output, explicit read-state mutation and ZIP message contracts
continue unchanged.

## Privacy and deployment boundaries

Eligible subjects and bounded body excerpts still automatically cross the
OpenRouter/upstream indexing boundary even without `--semantic`; diagnostic
telemetry settings do not disable that processing. This also applies to temporary
mail. Profile isolation does not change the account's subscription or authorize
additional recipients, payments or overage.

For lifecycle and migration details, see the
[versioned architecture](https://github.com/kleedaisuki/moesegfault-amail/blob/v0.3.0/docs/v0.3.0/architecture.md).
Actual deployment and end-to-end verification are recorded separately in
[validation](https://github.com/kleedaisuki/moesegfault-amail/blob/v0.3.0/docs/validation.md);
release publication alone does not prove a particular remote environment upgraded.
