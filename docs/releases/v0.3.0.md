# amail v0.3.0 candidate

This is the multi-tenant architecture candidate, not a publication or production
deployment receipt. Existing v0.2.0 release coordinates remain historical facts.

## User-visible changes

- A thin CLI connects to an automatically started local daemon. Configuration,
  SQLite state and installed binaries live under `~/.amail` (Windows:
  `%USERPROFILE%\.amail`); `config.toml` overrides convention-based defaults.
- Terminal-bound profiles share one activation across repeated CLI invocations.
  A profile cannot be active in two terminals. Deactivation retains its reservation;
  release relinquishes it. Thirty minutes without use releases the profile.
  Profiles created by `user` persist; profiles created by other profiles are
  deleted on release and their names can be reused.
- The initial `user` profile requires browser approval for each protected operation
  unless the human explicitly configures YOLO. This is not a sandbox against code
  running as the same OS user, and is not payment or overage authorization.
- Cloud-enforced mailbox ownership permits shared readers or one exclusive writer,
  never preemption. Expired sessions cannot silently regain another holder's lock.
- Temporary addresses under `tmpaddr.moesegfault.dev` expire no later than six
  hours after creation. Release is silent and irreversible; export retained history
  while the mailbox remains live. Reuse requires completed cleanup, route retirement
  and cooldown, and never exposes a previous generation's data.
- Permanent mail addresses can be registered only by `user`; any active profile
  may register temporary addresses. Temporary address limits are higher than
  permanent limits, while send and storage allowances remain account-wide.

## Compatibility and privacy

Owners not enrolled in profiles retain the existing v0.2 protocol behavior. Once
an owner enrolls, requests without a valid profile session cannot bypass mailbox
ownership; upgrade the CLI and matching Skill together rather than impersonating
a supported version or retrying an unresolved send with a new key.

JSONL output, explicit read-state mutation, ZIP boundaries and original send-intent
recovery remain in force. Eligible subjects/body excerpts still automatically
cross the OpenRouter/upstream indexing boundary even without `--semantic`;
diagnostic telemetry settings do not disable that processing.

See [architecture](../v0.3.0/architecture.md) for authority, lifecycle and migration
contracts. See [validation](../validation.md) for actual hosted and staging results.

## Hosted candidate lane

Use `codex/v0.3.0-multitenant` with the existing `CI and deploy` workflow:

| Target | Confirmation | Purpose |
| --- | --- | --- |
| `checks` | None | Credential-free hosted source and native candidate checks |
| `staging-inspect` | `INSPECT_STAGING_V030` | Inspect the fixed staging graph without mutation |
| `staging` | `RUN_STAGING_V030` | Deploy the checked same-run candidate to staging |
| `staging-e2e` | Existing journey confirmation | Consume an exact same-SHA `source_run` |

The native bundle is `cli-candidate-v0.3.0-RUN_ID`. Existing separate Billing and
owned-send confirmations remain necessary; the candidate lane grants no new
spending, sending, production-deployment or release authority. Trusted-branch Rust
and bundler caches and lock-keyed pnpm caches shorten repeated source checks.
Following [GitHub cache isolation](https://docs.github.com/en/actions/reference/workflows-and-actions/dependency-caching),
a cache hit is reusable build work, not proof that an artifact passed admission;
the immutable same-run tested-artifact boundary remains mandatory.
