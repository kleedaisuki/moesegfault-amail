# Mail Worker observability/privacy review (2026-09-29)

Scope: static review of the API, ingress, event-consumer, and role-monitor Worker source/config plus Cloudflare's current automatic telemetry documentation. A staging mail API readback was reported to the team as `redact_query_string=false` with traces, logs and invocation logs enabled; this note does **not** independently read deployed settings or any private logs. The checked-in API configuration can explain enabled tracing/logging but does not itself specify `redact_query_string=false` or `invocation_logs=true`; those are **effective-deployment observations, not claims about explicit source fields**. No private mail, secret, or log was queried.

## Material findings

1. **API automatic capture is inconsistent with the mail privacy boundary (high confidence).** `crates/mail-worker/wrangler.toml` enables observability and traces at head sampling `1.0` and enables logs, but does not opt out of invocation logs. The staging environment does not declare its own observability block. Cloudflare documents that Fetch invocation messages include `<Method> <URL>` and that automatic Fetch spans include `url.full`, `url.path`, and `url.query`. The observed effective `redact_query_string=false` means a query placed in any API URL is retained; the supported `GET /v1/messages` uses `limit` and a base64url cursor. The cursor is not plaintext search text: `search_jobs.rs` encodes a SHA-256 filter/owner hash plus rank/id/time fields, so it is still a linkable mailbox-derived token, not body/subject content. Client mistakes, probes, or future GET filters can place addresses/search strings or bearer tokens in URLs, and the platform captures them before application-level parsing or redaction. The current POST search sends filters in JSON body, and no documentation reviewed shows automatic logging of that body. Avoid claiming ZIP bytes, Authorization headers or POST search text are automatically captured merely because traces/logs are enabled.

2. **Automatic dependency spans have a narrower but real metadata exposure (high confidence).** Cloudflare lists `db.query.text` on D1 spans and R2 object keys and custom/HTTP metadata on R2 spans. This code generally uses D1 bound parameters for addresses, search predicates and content, so the documented `db.query.text` should expose SQL structure rather than those bound values. R2 keys are random message IDs (`messages/{id}.zip`, `raw/{id}.eml`), not ZIP bytes or attachment names; they are nevertheless persistent message identifiers. The outbound OpenRouter embedding request carries bounded email-derived text in a POST body and an Authorization header; Cloudflare's listed Fetch-span attributes do not include headers or request body content. The payload is deliberately delivered to OpenRouter, a distinct provider-processing risk, not evidence of Observability capture. An exception from a platform API could in principle have sensitive error text, but source code mostly converts errors to fixed codes and application logs use fixed strings; live exception behavior remains unverified.

3. **Ingress/event/role boundaries are already stronger in source.** `workers/mail-ingress/wrangler.toml` disables observability explicitly in production and staging; same for `workers/mail-events/wrangler.toml`. This matters because Cloudflare's Email Handler root span inventory includes `cloudflare.email.from` and `.to`, while Queue payloads may contain addresses and subject. `workers/role-monitor/wrangler.toml` explicitly disables traces and invocation logs in both realms while retaining reviewed application logs; its prior staging effective readback is documented in `docs/staging-role-monitor-acceptance.md`. Recheck deployed values after any deploy; source configuration alone does not prove effective settings.

## Minimal compatible action

- Make API prod **and staging** observability explicit: keep `observability.enabled=true` and reviewed application `logs.enabled=true`, set `logs.invocation_logs=false`, set `traces.enabled=false`; do not rely on sampling as redaction. If traces are a hard operational requirement, first define a data-handling exception and run a synthetic canary review of actual emitted attributes, retention, export destinations and exception paths.
- Set `redact_query_string=true` directly under `[observability]` (and `[env.staging.observability]`) in Wrangler, **not** under `[observability.logs]`, as defense in depth for URL-based telemetry; then read back the effective deployed settings. The Cloudflare REST API presents observability settings in a different nested response shape, so validate against the Wrangler configuration schema before editing TOML. Redaction does **not** remove path identifiers or D1/R2 attributes, and does not sanitize custom logs. A no-mutation deployment verifier should fail on unexpected traces/invocation logs or absent URL redaction, analogous to `infra/deploy/verify_role_monitor_staging.py`.
- Keep address deletion and search predicates in request bodies. Do not move search text or authorization tokens to URLs. Preserve existing routes/wire contracts; these recommendations only change telemetry storage and verification.

## External evidence

- [Cloudflare Workers Logs](https://developers.cloudflare.com/workers/observability/logs/workers-logs/): invocation records contain request/response metadata; Fetch invocation message includes method and URL; `invocation_logs=false` is supported.
- [Cloudflare automatic spans and attributes](https://developers.cloudflare.com/workers/observability/traces/spans-and-attributes/): Fetch, Email, D1 and R2 attribute inventory, including URL, email envelope, SQL text, and R2 key fields.
- [Cloudflare Workers API observability schema](https://developers.cloudflare.com/api/resources/workers/): `redact_query_string` removes query strings from request URLs in logs and traces; enabled/head-sampling/invocation fields have independent controls.
