## Finding: deployed static warning set is incomplete (P2, high confidence)

`infra/tests/staging_address_failure_logs.py::INCIDENT_STATIC_WARNINGS` enumerates ten unique fixed literals, but `git show 565fa299:crates/mail-worker/src/lib.rs` has another fixed `console_warn!` literal: `amail semantic index retry failed`. It is emitted when the scheduled `reindex(&env)` call returns an error. If that exact warning appears in the 33-second incident window, `reviewed_events()` rejects it as `unreviewed_source_string` or `unreviewed_message_string`, although it is as content-free and revision-pinned as the listed warnings. This cannot falsely pass or leak data; it can needlessly leave the incident `UNVERIFIED` after another hosted read-only query. Add only this exact literal and a fixture covering its recognized transport wrapper. Do not broaden to prefixes or arbitrary console records.

**Resolved in `56eddbb` (static re-review):** the exact eleventh literal was added, a singleton `{message: ...}` recognition assertion was added, and the incident note's count was corrected. No other acceptance rule changed. This resolves the diagnostic completeness finding at source level; CI and the actual hosted record shape remain unverified.

## Safety assessment of the changed boundary

The new `incident_static_warning()` accepts a literal only through a string, an exact singleton `{message: ...}` mapping, or a singleton array, with bounded nesting. It does not accept extra object keys, a string suffix, or arbitrary provider text. `reviewed_events()` rejects a static warning mixed with a structured trace in the same row, rejects disagreeing source/message warning echoes, and still requires every accepted record's `$metadata.service` to match the staging Worker. Unknown source or message payloads become only six fixed field/type codes; no raw value, address, URL, provider response, request identifier, or record count is printed. The derived `routing_create_*` label includes only reviewed bounded numeric HTTP/error codes already admitted by the trace schema. These checks preserve the historical diagnostic's fail-closed behavior for an unreviewed wrapper.

`infra/tests/staging_trace_canary.py::assess()` was not modified by `2479538`; it still rejects any nonempty source or message that is not a recognized application trace. Therefore the historical classifier's narrow exception cannot be read as a full retained-log privacy-canary pass. Even a later successful historical classification establishes only a bounded causal inference: the original E2E discarded its private request ID and journal, so a unique failed `addresses_add` root in the exact 33-second window could in principle be an unrelated concurrent add while the target event was absent or sampled out. The existing incident document and `docs/review-observability-event-view-correction.md` state this limitation. A positive classification should be reported as a time-window-correlated inference, not proof of the E2E's request identity, and must not alone unlock production send.

The synthetic tests correctly exercise exact warning copies, unknown text, mixed warning/trace, and conflicting echoes. They do not establish the actual Cloudflare record wrapper or presence of the warning in run `36544143133`; a hosted read-only diagnostic is still required after the missing literal is corrected and CI passes. If it yields an unknown payload kind again, do not print raw rows or incrementally accept arbitrary shapes; keep `UNVERIFIED` and use a separately reviewed private inspection path.
