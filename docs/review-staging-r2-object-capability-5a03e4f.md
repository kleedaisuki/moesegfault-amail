# Review: staging R2 object-capability sentinel (`5a03e4f`)

**Original decision (`5a03e4f`): NO-GO for hosted dispatch until failed-run key recovery is designed; NO-GO for B registration on this source review alone.** This is a focused source review, not a local test, hosted CI result, or live Cloudflare probe. The working tree contains unrelated changes; none were reviewed or modified. The status of the recovery correction is updated below.

## Necessary correction

**P1 — A killed or uncleanable PUT can leave an unidentifiable private object.** `execute()` creates a fresh random `verification/<uuid>.eml` key only in process memory (`infra/tests/staging_r2_object_capability.py`, `key = ...`), then marks `put_possible` and uploads it. The workflow has an eight-minute timeout; a process kill, cancellation, or provider failure can occur after the PUT but before `finally` or successful cleanup. The script intentionally prints no key, and neither workflow nor runbook provides a protected way to reconstruct or retrieve it. The runbook nevertheless requires *exact-key* reconciliation before any new probe or B mutation. After such a failure, an operator with only the fixed failure label cannot identify that exact key among existing `verification/` objects without inspecting all private object bodies or relying on an unrelated earlier inventory snapshot. This makes the documented recovery gate non-executable and potentially strands a sentinel until lifecycle expiration, which the runbook correctly says is not immediate. Persist a recovery handle before the PUT in a protected, operator-retrievable form (for example, an encrypted artifact scoped to the staging Environment or a reproducible keyed derivation from the Actions run ID), and specify an exact-key readback/cleanup procedure. Do not print the key or weaken the one-use/random-key property. A unit case that simulates cleanup failure cannot exercise process death, so the existing mock coverage does not close this gap.

## Supported observations and limits

- The new job is manual-dispatch-only, branch-pinned to `codex/amail-v0.1.0`, confirmation-gated before the secret-bearing step, Environment-gated, and serialized with staging native-mail acceptance. It does not receive B credentials and its script makes no Identity registration, Email Routing mutation, or production-bucket call.
- The script checks the exact deployed staging inbox binding and private-domain/lifecycle state through existing helpers, requires every configured test route absent, and walks a bounded strict `verification/` inventory. It does **not** classify A/B Identity contacts; the runbook appropriately says to repeat the separate B contact/route/object preflight before B mutation. A successful sentinel marker must not be treated as B readiness.
- UUIDv4 key shape matches the Worker-compatible key expression. Two complete list walks establish absence before PUT, subject to the unavoidable non-atomic window. With a private unlogged random key, accidental collision risk is negligible; the workflow concurrency group reduces, but does not eliminate, external writers.
- The intended happy path performs one multipart PUT, exact-byte GET, exact-key DELETE, GET-404 plus complete LIST absence, and another final GET/LIST reconciliation. The Cloudflare [upload API](https://developers.cloudflare.com/api/resources/r2/subresources/buckets/subresources/objects/methods/upload/) documents the multipart `body` field and returned `result.key`/`result.size`; the [delete API](https://developers.cloudflare.com/api/resources/r2/subresources/buckets/subresources/objects/methods/delete/) documents exact-key deletion. These are source-contract checks, not hosted proof that the current token can perform them.
- The probe uses a no-redirect opener and no explicit retry. It emits fixed labels rather than object keys, bodies, credentials, inventory or provider error bodies. Cleanup reads the exact key before retrying an uncertain DELETE and fails closed when readback cannot establish absence. A denied PUT is correctly treated as inconclusive about B's needed GET/DELETE capability.
- The new tests are discoverable by the CI `python -m unittest discover -s infra/tests -v` step and cover several mock success/failure paths. Per task instruction, I did not run them locally. Hosted CI and a deliberate guarded probe remain unverified.

## Narrow re-review of recoverability correction (`e38d40a`)

**Decision: original P1 recovery gap resolved in design; still NO-GO for hosted dispatch because the committed CI test has a deterministic failure.** No local tests, hosted dispatch, or production calls were made in this re-review.

**P1 CI blocker — stale assertion after workflow-step rename.** `test_workflow_is_manual_branch_only_and_secret_final_step()` in `infra/tests/test_staging_r2_object_capability.py` still calls `job.index("Require explicit object-operation confirmation")`. The same commit renames that step to `Require explicit probe or recovery confirmation` in `.github/workflows/ci.yml`. The old substring is absent, so the test raises `ValueError` during the normal `python -m unittest discover -s infra/tests -v` CI step. Correct the assertion to the new step name (or assert the structural secret boundary without coupling to a human-facing label), then allow hosted CI to run before dispatch.

The recovery model itself now reconstructs a UUIDv4-**format** key and a distinct synthetic body from the original numeric GitHub run ID and attempt using domain-separated SHA-256. This is deterministic, not a cryptographically random UUIDv4 draw; effective key space is approximately 122 bits after version/variant bits, subject to unique GitHub run identity. The probe rejects attempts greater than 1 and checks exact-key absence twice before PUT. A failed or cancelled run's ID and attempt are available from Actions metadata, allowing later exact-key recovery without exposing the key in logs. The recovery workflow is manual, branch-, staging Environment-, confirmation-, and shared-concurrency-gated; only its final step receives Cloudflare secrets. Recovery performs no PUT, requires exact body equality before any DELETE, reads back after ambiguous deletion, and requires GET-404 plus complete LIST absence. A wrong supplied run ID can also return `recovered_absent`, so the runbook correctly requires independent verification of the originating Actions run and forbids using that marker as capability or B-registration proof. The private bucket and bearer-token requirement, not key unpredictability, are the authorization boundary.

Remaining limits: a writer with the Cloudflare token can race between absence check and PUT; the 122-bit collision resistance does not make LIST plus PUT atomic. A recovery attempt with invalid permissions or mismatching bytes fails closed and may require privileged manual action. The earlier source checks of no redirects, fixed output labels, exact staged bucket, route/config preflight, and no B mail/registration mutation remain applicable; hosted behavior is unverified.
