# Native CLI OAuth credential storage

`amail` is a native public OIDC client. A full access/refresh/ID-token set may exceed the Windows Credential Manager 2,560 UTF-16-character password attribute limit. The OS keyring therefore stores only `amail:v2:<base64url 32-byte random key>` (52 ASCII characters). It never stores a serialized token set in new sessions.

The complete token set is encrypted with ChaCha20-Poly1305 and stored in `AMAIL_HOME/auth.sqlite3`. A fresh 96-bit nonce is generated for every write. AEAD associated data binds the ciphertext to the exact configured issuer and OAuth client ID. The SQLite table stores nonce, ciphertext, and a session key; it stores no plaintext token or mail content. The operating system protects the small random key. On Unix, the database mode is set to `0600`, and the application directory is `0700`. The database is deliberately separate from `telemetry.sqlite3` so diagnostics cannot accidentally include credentials.

An OS file lock serializes login, refresh and logout. The existing durable refresh-in-progress marker remains in `telemetry.sqlite3`: it contains only `(issuer, client_id, boolean)`, never tokens. The marker is committed before a rotating refresh call; any ambiguous outcome clears the local session rather than replaying a potentially consumed predecessor. Ciphertext replacement is a transaction **in the separate auth database**, not an atomic transaction with the telemetry marker. If a process crashes after ciphertext replacement but before clearing the marker, the next invocation conservatively discards the session, even if the new refresh token may have been valid. For legacy sessions whose keyring entry still contains JSON, a successful refresh writes encrypted SQLite first, then replaces the keyring JSON with the bounded v2 key; a crash before keyring replacement leaves the legacy session readable. Logout attempts to remove **both** the OS key and ciphertext even if either operation fails; deleting either half makes the remaining half unusable.

The browser loopback callback is acknowledged **only after** token exchange, ID-token validation, encrypted persistence, and refresh-marker reset. A failure receives a generic static page with no token, code, state, or detailed exception. The CLI remains the diagnostic channel. Response headers prohibit caching, framing, and outgoing referrers, and a restrictive CSP blocks all network resources. This corrects the earlier false-success page that could appear before Windows rejected an oversized keyring value.

Focused tests exercise a token set larger than the Windows limit, bounded keyring payload, encryption/decryption, wrong-key, wrong-issuer, tampered-ciphertext rejection, and fragmented/oversized loopback request lines. Cross-platform compilation and tests run in GitHub Actions; live login must be re-exercised with a CI-built Windows binary after deployment.

## Completion-page audit (2026-10-01)

The previously plain `Login complete. You may close this tab.` result is already replaced by the bundled `crates/amail/src/oauth_success.html` and `oauth_failure.html`. Revision `9cb410a` aligned both pages with MoeSegfault Style's gold/coral background, Identity co-branding, status-specific color, responsive layout, light/dark preference, and forced-colors support. They are static and self-contained: no JavaScript, external fonts/resources, account names, provider error text, or reflected callback parameters. Existing desktop/mobile visual evidence is retained under `.temp/oauth-{success,failure}-{desktop,mobile}.png`; the success desktop image was reinspected during this audit. No duplicate redesign or login attempt was needed.

The rendering boundary is intentional. Identity owns human authentication, the registered-client authorization mechanism, and the Login interface. The native relying party owns the final browser result because only it can establish whether code exchange, token validation, and protected local persistence succeeded. Identity must not claim that an application's local session was saved. A visually unified result does not require moving the loopback page to a provider-hosted endpoint, transmitting tokens to a frontend, or changing registered redirects. This follows the external-browser/native-callback division in [RFC 8252](https://www.rfc-editor.org/rfc/rfc8252.html); the persistence-before-success rule is an application invariant rather than an additional OAuth protocol requirement.

The [staging deployed end-to-end run 36719116852](https://github.com/kleedaisuki/moesegfault-amail/actions/runs/36719116852) separately established a native login plus authenticated Mail workflow; it is not a screenshot assertion. A user running an old binary can still see its old embedded page; changing Identity alone cannot update it.
