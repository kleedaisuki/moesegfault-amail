# Rust-native Cloudflare Email ingress: evidence and migration decision

Date: 2026-09-28. Scope: the Cloudflare Email Routing event consumer, not the already-Rust mail API or the Astro release site. This note corrects the older claim in `docs/architecture.md` and `docs/backend-operations.md` that `workers-rs` 0.8.x cannot handle email events.

## Answer

**Replace the handwritten JavaScript adapter with a small Rust/Wasm Email Worker.** `workers-rs` has supported `#[event(email)]` since [PR #715](https://github.com/cloudflare/workers-rs/pull/715) merged on 2026-05-14 and shipped in [v0.8.4](https://github.com/cloudflare/workers-rs/releases/tag/v0.8.4). The upstream [receive-email example at v0.8.6](https://github.com/cloudflare/workers-rs/blob/v0.8.6/examples/receive-email/src/lib.rs) demonstrates `#[event(email)] async fn email(message: ForwardableEmailMessage, env: Env, ctx: Context) -> Result<()>`. The v0.8.6 [binding](https://github.com/cloudflare/workers-rs/blob/v0.8.6/worker/src/bindings/email.rs) exposes `raw_size()`, `raw_byte_stream()`, `raw_bytes()`, `to()`, and `set_reject()`. The `raw_bytes()` helper is unbounded, so the ingress must enforce the 25 MiB limit both before and during stream collection. The upstream [Rust guide](https://developers.cloudflare.com/workers/languages/rust/) explains that generated JavaScript glue is an implementation detail of Rust/Wasm Workers, not hand-maintained application code.

The [docs.rs `#[event]` prose](https://docs.rs/worker/0.8.6/worker/attr.event.html) still omits `email` from its supported-attribute list; the upstream merged implementation, versioned example, and v0.8.6 macro source are stronger evidence than this stale prose. In particular, [v0.8.6 `worker-macros/src/event.rs`](https://github.com/cloudflare/workers-rs/blob/v0.8.6/worker-macros/src/event.rs) has an `Email` branch. Do not mistake this documentation inconsistency for missing runtime support.

## Present local contract

`workers/mail-ingress/src/index.js` receives an `email` event, checks `rawSize`, buffers raw MIME, generates a W3C `traceparent`, and calls `MAIL_API.fetch(.../internal/inbound)` over a private service binding with `x-amail-ingress-secret` and `x-amail-envelope-to`. `crates/mail-worker/src/lib.rs::inbound` validates the shared secret, reads the recipient and bytes, and performs the actual mail work. `workers/mail-ingress/wrangler.toml` disables automatic observability because an email-event span may carry address PII. Routing rules target the stable `amail-inbound` / `amail-inbound-staging` Worker names.

The adapter is only transport, but its hand-maintained JavaScript still violates a literal reading of “CLI and Workers both Rust.” No new mail feature needs JavaScript. Preserve the two-Worker boundary for the first migration: it keeps existing literal routing-rule targets and private service binding unchanged, avoids any routing-control-plane migration, and changes only the ingress implementation. Later consolidation into one Rust Worker could remove the service binding and shared secret, but provides little immediate user value while increasing cutover risk.

## Proposed implementation contract

1. Add a `cdylib` crate `crates/mail-ingress` to the workspace, using `worker >=0.8.4` pinned to a tested version (prefer the same version for both Rust Workers). Change `workers/mail-ingress/wrangler.toml` to generated `build/.../shim.mjs` or the `worker-build` versioned example's output; replace the JS entrypoint only after CI deploys the Rust one under the **same Worker name**. Do not hand-edit generated JavaScript glue.
2. In `#[event(email)]`, compare finite `message.raw_size()` against `25 * 1024 * 1024` before reading. Collect `message.raw_byte_stream()` with checked cumulative length and reject if the stream exceeds the cap even when metadata disagrees. Avoid `raw_bytes()` alone; it materializes all bytes without enforcing a limit. Preserve bytes exactly; never parse MIME or reserialize in the ingress.
3. Build a private service-binding POST with `content-type: message/rfc822`, the existing secret and envelope-to headers, and an opaque `traceparent`. The Rust API remains the sole policy/validation authority. Do not emit sender, recipient, subject, raw MIME, secret, or provider response body in logs. Use only constant generic SMTP rejection reasons.
4. Preserve status classification: API 4xx means deterministic invalid/unavailable recipient and `message.set_reject(...)`; API 5xx or transport failure must surface as a handler error rather than an intentional permanent rejection. However, **do not assume Cloudflare retries the original SMTP transaction on handler failure**; verify actual sender bounce/retry behavior in staging. The [Cloudflare Email handler documentation](https://developers.cloudflare.com/email-service/api/route-emails/email-handler/) specifies `setReject` as a permanent SMTP error, but does not promise retries for thrown errors.
5. The v0.8.6 [`#[event(email)]` macro](https://github.com/cloudflare/workers-rs/blob/v0.8.6/worker-macros/src/event.rs) logs and panics with any returned `Err` text. Therefore, return only sanitized static or numeric-code errors from the handler, never provider, MIME, address, secret, or request-body details. Keep automatic ingress observability disabled until Cloudflare demonstrates redaction of email envelope fields.

## Migration and acceptance

| Risk | Required evidence before replacing live ingress |
|---|---|
| `worker-build` version skew with `worker` crate or generated entrypoint path | CI compile Wasm and Wrangler bundle for both production and staging configurations; pin a compatible `worker-build` release. |
| Binary corruption or oversized stream | CI fixture tests with multipart/CID/attachment MIME, a non-UTF-8 octet sequence, exactly-at-limit and over-limit lengths; compare received R2 raw bytes or ZIP representation, not decoded text only. |
| SMTP reject semantics | Live staging external SMTP send to registered and unregistered recipients, over-limit case, and controlled downstream 4xx/5xx; inspect delivered/bounced result. |
| Secret/binding breakage | Live staging ingress-to-Rust API request with correct trace correlation; negative probe with wrong secret returns 403; no secret or envelope in logs. |
| Existing routing rules | Deploy new Rust code at the same `amail-inbound-staging` name first; do not delete/recreate dynamic rules during implementation. Promote production only after stage end-to-end pass. |

No local Rust build was performed: the user requires cross-platform and deployment validation through GitHub Actions. This conclusion is source-level feasibility, **not** a claim that amail's Rust ingress is already implemented or deployed.

## Migration implementation (source state; deployment still to verify)

The implementation is now `workers/mail-ingress/src/lib.rs`, a Rust workspace crate built as a Wasm `cdylib`. The handwritten `src/index.js` was removed, and the existing `amail-inbound` / `amail-inbound-staging` Wrangler configurations point to `worker-build`'s generated `build/worker/shim.mjs`. This preserves literal routing rules and the private `MAIL_API` service binding; no email route migration or production cutover is implied by the source change. The ingress reads raw MIME using `raw_byte_stream()` with per-chunk cumulative bounds, then sends the exact octets and envelope recipient to the Rust mail API with the same shared-secret header. The generated `traceparent` uses two fresh UUIDv4 values; it is never derived from user data. The email event handler maps every internal error to one static, PII-free error string before the `workers-rs` macro logs/panics.

The GitHub `worker` job now tests, checks Wasm, and bundles both Rust Workers. Staging deploy builds the ingress Wasm bundle and deploys to the existing staging Worker name with its own secret. **A green build and `/health` check do not prove SMTP delivery.** The live staging gate remains: register a staging address through an interactive user-authorized CLI login, send a multipart attachment message from an external sender, compare retrieved raw bytes, and verify routed/bounced behavior for invalid recipient and a controlled failure. Only then promote the same implementation to the production Worker name. The provider documentation does not guarantee that an email-handler exception retries SMTP; record observed behavior instead of assuming it.

`worker-build` must be **at least 0.8.5** for this crate: the upstream 0.8.3 shim generator only exports fetch, queue, and scheduled handlers, whereas 0.8.5 also exports `email`. The Worker test job and ingress deploy jobs pin 0.8.5. The API Worker deploy jobs may continue to use 0.8.3 because their entrypoints are fetch and scheduled only. Keep the generated shim path `build/worker/shim.mjs`; do not substitute the older example's `build/index.js` path without changing the bundler mode.
