# Independent review: bounded staging address-add diagnostic

Status: **source review complete, hosted CI/deployed behavior not verified** (2026-09-29). Scope is the staging-only Worker response header, typed Rules GET failure, CLI error rendering, hosted pre-cleanup readback, and synthetic tests, including the one-line staging E2E account-secret injection and host fail-fast check. This is a source review only: no local heavy test, live Worker request, Email Routing mutation, address creation, or production change was performed. The design baseline is [staging-address-runtime-diagnostic-decision.md](staging-address-runtime-diagnostic-decision.md).

## Findings and dispositions

1. **Resolved in draft: CLI public error-code compatibility.** An early `crates/amail/src/api.rs::public_problem_code` map changed every non-2xx Mail API call and omitted current Worker search/send codes including `semantic_index_incomplete` and `provider_daily_limit`. The hosted semantic E2E retries only the former. The revised code confines `address_problem_code` to `addresses.add`; existing other commands keep their prior code extraction. The address-add path itself never copies an unrecognized response code into stderr. Final hosted compilation/tests remain pending.

2. **Resolved in draft: correlation header privacy.** The early CLI diff copied `x-amail-request-id` or its fallback into stderr and telemetry without checking its contents. The revised `response_correlation` accepts one canonical UUID and rejects duplicate/hostile values; synthetic tests exercise this. A separate causal-pairing issue remains below.

3. **Resolved in draft: causal pairing.** A later CLI draft's `address_response_diag` requires a single canonical primary `x-amail-request-id` before it attaches `diag=`. Tests cover missing/fallback-only/invalid/duplicate primary IDs. This prevents a diagnostic-looking header without the Worker's causal key from becoming a stage conclusion.

4. **Accepted limitation to document: `http_error` conflates absent/non-problem body and unknown problem code.** The address-add whitelist maps both cases to `code=http_error`, avoiding payload leakage but not delivering the design's separate `http_non_problem` and `http_problem_unknown_code` labels. The CLI implementer kept the existing output contract with only an optional `diag=` addition. Interpret `http_error` without a trusted Worker diagnostic as one inconclusive HTTP-response category, not as a gateway diagnosis. This is an information-quality gap, not proof of a Worker defect.

## Final source-level assessment and limits

- The Worker header is built from request-local `AddressDiag` only after successful authentication, gated on both `ADDRESS_DIAGNOSTICS=v1` and the exact staging mail domain. The `problem` conversion retains the existing status and public code, then appends the fixed header; production omits the switch. `RuleListFailure` carries only a bounded numeric status after a response, distinguishing request, HTTP, provider-negative, and decode boundaries. `RuleCreateFailure` retains its earlier uncertain-response semantics. No SQL, address, rule ID, provider message/body or error `Debug`/`Display` is included. The new unit tests cover grammar and typed GET envelope cases; full authenticated Worker responses require hosted/deployed verification.
- The hosted snapshot uses pagination-checked exact-rule inventory and a parameterized, read-only staging D1 `SELECT`, reduces provider/row data to finite labels, and rejects malformed/duplicate rule IDs and row shapes. The E2E workflow now supplies `CLOUDFLARE_ACCOUNT_ID` from the protected staging environment; `staging_hosted_e2e.py` rejects non-32-hex values before browser activity. These secrets are excluded from CLI child processes. The Cloudflare read helper rejects redirects, so bearer credentials cannot be forwarded to another host. The synthetic failed-add test asserts add → snapshot → cleanup order, even when the snapshot unexpectedly raises private text; it asserts separate fixed primary/cleanup labels and no private text output. Unverified/conflicting snapshots stop acceptance, and cleanup uncertainty remains a failure.
- There is no substantive source-level blocker remaining for hosted CI and controlled staging deployment. **This review is not approval to create another alias yet.** First run the relevant hosted Rust/Python checks and staging deployment, pin the serving Worker/version and private secret path, reconfirm exact prior aliases and new candidate are clean, and ensure independent cleanup/recovery is available. A malformed-success Rules POST may have created a rule; neither a diagnostic header nor D1 snapshot licenses blind retry. `http_error` without a trusted stage stays inconclusive.

These are source-level findings, not a diagnosis of the three historical address-add failures or a conclusion about the currently serving Worker's routing capability.
