# Independent contract review: fifth staging `messages.list` 409

Status: source-only review on 2026-09-29. No live API, D1, SMTP, mutation, local test, or historical-log query was performed. The incident's observations and privacy-preserving investigation plan are in `docs/staging-fifth-mail-sync-409-incident-36589042183.md`; this review assesses the source contract, not the deployed serving version or historical response code.

## Scope and exact path

The harness first calls `await_messages`, which invokes `amail sync --limit 100` with no cursor and aborts on the first CLI error (`infra/tests/staging_mail_e2e.py`, around lines 604–614). Cleanup independently invokes the same cursorless command, suppresses that exception, retires the address, verifies route and CLI-list absence, then reports `message_cleanup_failed` if message enumeration failed (around lines 731–779). Consequently the two labels do not prove a common response code, that ingress persisted, or that cleanup deleted messages.

`main.rs::sync` delegates to `Api::messages(limit, cursor)`. For this command, `api.rs::messages` sends authenticated `GET /v1/messages?limit=100`, not a search-job poll, with operation `messages.list`. `execute_with_status` reads the actual HTTP status and JSON `code` (or `error_code`, else `http_error`) and passes through non-address-add codes. The Worker dispatches this GET to `search_jobs::search` with default filters, limit, and absent cursor (`lib.rs`, around lines 815–838). The harness's `cli_failure` parses the CLI status and syntactically valid code but replaces codes absent from `SAFE_API_CODES` with `unknown_code`; neither `search_job_stale` nor `search_cursor_stale` is in that list (around lines 146–211). The 409 was therefore reported by the CLI as a real HTTP status; the exact code is not recoverable from the public label.

## Possible 409s on the pinned source

| Source code | Trigger | Applicable to initial cursorless list? |
| --- | --- | --- |
| `search_cursor_stale` | `decode_cursor` sees a supplied v3 cursor whose generation differs from the current account generation (`search_jobs.rs`, around line 96). | No: this invocation supplied no cursor. It is relevant to `sync --cursor` and later pages under `--all`, not this command. |
| `search_job_stale` | Generation changes between initial read and post-scan read, or between initial read and atomic continuation-job admission; `result_page` also maps a vanished summary hit to stale (`search_jobs.rs`, around lines 150–219, 592–658). | Yes. This is the only normal application 409 code on this route with no cursor in the reviewed source. |

Other Worker `AppError::conflict` codes in `lib.rs` belong to address, send, or storage paths, not this GET route. An intermediary, a different serving version, or an unretained response could change the historical answer; **do not infer that the run actually returned `search_job_stale`** merely because this is the strongest source-level explanation.

The migration `0005_search_jobs.sql` increments owner generation on every message insert, update, or delete. Ingress insert and the asynchronous embedding-field update (`lib.rs::persist_embedding_success`, around lines 670–699) can each advance it. A list races only when the generation changes *during its own multi-query execution*, not simply because an insertion happened before the list began. This makes a transient 409 a designed consistency rejection under concurrent mutation, not by itself evidence of corrupted data or broken ingestion. Conversely, the current E2E treats that rejection as terminal; a consistency safeguard can still be a user-facing availability problem when routine inbound work overlaps listing. Repeated 409s deserve investigation rather than being declared expected.

## Findings and safe correction

1. **P1 — harness diagnosis loses documented consistency codes.** Add the two fixed public codes to `SAFE_API_CODES` so future failures can distinguish `search_job_stale` from `search_cursor_stale`, without printing raw stderr, correlation IDs, message data, or unknown codes. This corrects classification only; it cannot turn this run into a pass or reveal its historical code. The existing incident plan for serving-version pin plus retained request-local metadata remains the discriminating check, if such metadata exists.
2. **P1 — one transient cursorless 409 aborts delivery observation and can also prevent cleanup.** A fresh cursorless GET is read-only and may safely start a new search generation after `search_job_stale`; a small bounded retry with delay/jitter is appropriate for the harness and potentially the CLI, provided it matches the exact status/code pair, has an explicit deadline, and surfaces exhaustion as failure. Do not retry arbitrary 409s, pretend a retry proves SMTP delivery, or resume a stale cursor/job: those require restarting the list/search from page one. A separate cleanup improvement should retain exact run-owned identifiers as soon as learned and retry enumeration within a bound, while keeping the current independent address-retirement path. Unknown delivery IDs after failed enumeration require a narrowly scoped operator readback and reviewed cleanup, not broad deletion or blind SMTP replay.

For tests, use a deterministic mocked first `messages.list` response of 409 `search_job_stale` followed by 200 to prove one retry and no duplicate visible output; persistent stale must fail after the bound; `search_cursor_stale` and unrelated 409 must not silently restart an existing pagination flow; a failed cleanup list must still retire the address. Those are proposed tests, not tests run in this review.

The principal follow-up is the incident document's restricted, request-local code/version check, then exact-run read-only D1 aggregates. Neither a new sync request nor aggregate invocation counts can reconstruct the historical 409 code.
