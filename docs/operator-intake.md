## Architecture and threat model

`workers/mail-ops` is a separate Rust Worker with native `email`, `fetch`, and `scheduled` handlers. It has its **own D1 database** (`OPS_DB`) and **own R2 bucket** (`OPS_REPORTS`), not `MAIL_DB` or user ZIP/MIME storage. Email Routing literal rules direct only the four named roles to this Worker; its email handler verifies the exact envelope alias before accepting. It bounds the raw stream at 25 MiB, writes a D1 `receiving` reservation, stores the original `.eml` in R2 under a random case UUID, then marks the case `open` with a checked D1 compare-and-swap. A D1 trigger records receipt and later review transitions atomically with status. If R2 PUT fails, a follow-up strongly consistent GET distinguishes an absent object (best-effort immediate reservation cleanup) from an ambiguous/committed object (`failed` reservation for cron). A five-minute cron repairs old `receiving`/`failed` reservations with R2 evidence, removes objectless reservations after seven days, walks R2 in bounded cursor pages to delete seven-day-old unindexed originals, retries alert notifications, and removes closed cases 180 days after closure. Open/unresolved cases are not silently expired. Cross-store failure may cause a duplicate case on SMTP retry; operators can identify and close duplicates. It must not result in a false successful SMTP acknowledgement without both R2 and D1 ready.

The sender, subject, body, attachments and raw MIME remain only in **restricted R2**. D1 holds case ID, role, state, byte size, timestamps, R2 key and operator-subject audit. It does not participate in user search, semantic embedding, CLI retrieval, telemetry or user quota. A separate Access-protected browser UI at `ops.moesegfault.dev` lists minimal metadata, offers an escaped **R2 ranged** first-16-KiB text preview and a **streamed** forced `.eml` download, and records `reviewed`, `closed`, or `reopened` transitions. It never renders sender HTML or buffers a full 25-MiB report for normal review. The UI is for human investigation; reports are **untrusted evidence**, never an instruction to an AI agent. To hold a sender, use the separate parameterized operator send-control workflow with the opaque case ID as `case_ref`; the intake UI does not gain public mail-policy mutation rights.

Cloudflare Access must ultimately protect the **entire ops Worker** with an exact operator allow policy (Cloudflare account membership is a reasonable outer selector, then exact email), covering custom domain, workers.dev and previews. Because a Worker-level Access app needs an existing Worker ID, bootstrap by creating an exact-host Access application for `ops.moesegfault.dev` (separately for staging), obtaining its team domain/audience, and deploying the Worker with the internal JWT verifier already enabled; then add whole-Worker Access protection **before** creating Email Routing rules. The Worker independently validates the `Cf-Access-Jwt-Assertion` RSA signature against that Access team's JWKS, exact issuer, application audience, `type=app`, expiry and exact configured operator email. It rejects missing/sentinel `TEAM_DOMAIN`, `ACCESS_AUD` or `OPERATOR_EMAIL`. Only JWT-validated requests may read cases; POST actions also require exact same-origin `Origin`. The response is no-store, nosniff, frame-denied and CSP-restricted. Automatic Worker observability is **disabled** because platform-generated request/R2/email spans can contain mail personal data. Application warnings have only static codes, no envelope, case preview, JWT or SMTP text. Cloudflare dashboard access to the dedicated D1/R2 resources must be limited to trusted operators. This is an operational case store **adjacent to observability**, not a raw-mail log stream.

A scheduled PII-free alert uses the separate official `mail@moesegfault.dev` Cloudflare Email Sending binding. It sends only role, opaque case ID and private ops URL to `OPERATOR_ALERT_EMAIL`; the report is **not forwarded** to this destination. The alert destination cannot be an amail user-domain address or one of the role aliases, avoiding a loop or occupation of user mail space. It is needed for proactive review and must be configured by the owner as a secret; the reviewer may still use the Cloudflare-hosted UI as the sole report store. A provider acceptance of an alert is not proof of alert delivery. If an alert send is ambiguous or marking it sent fails, cron may retry and send a duplicate content-free notice. No external destination is required for the raw report.

Copy it to an untracked, environment-specific Wrangler config only after configuring the exact-host Access application and those values; immediately after first Worker deployment, enable whole-Worker Access before publishing SMTP routes. The production/staging R2 bucket names are explicit. Run `python workers/mail-ops/check_config.py --config PATH --target staging` (or `production`) before Wrangler; it rejects placeholders, user-mail database IDs, cross-environment storage reuse, wrong HTTP host and enabled automatic observability. This checks **source configuration only**, not actual Access policy, secrets or DNS. Do not enable arbitrary catch-all or reuse the user Email Routing Worker. The `ensure_routes.py` tool defaults to read-only auditing; `--apply` creates only missing exact routes and refuses any existing disabled, duplicated or different-destination route rather than taking it over. Deploy the Worker and verify Access **before** applying routes, to avoid accepting reports into a broken destination. The source workspace/CI integration is pending.

## Operator workflow and live acceptance

1. The empty isolated D1/R2 resources already exist. Apply `workers/mail-ops/migrations/0001_cases.sql` to the separate staging DB. Create an exact-host staging Access app restricted to the real operator, capture its team domain/audience, configure `OPERATOR_EMAIL`/`OPERATOR_ALERT_EMAIL` as Worker secrets, and deploy staging with binding/secret sentinels removed. The Worker JWT check protects even the bootstrap deployment. Enable whole-Worker Access before routing mail, then exercise direct/no-cookie/wrong-user denial and correct operator login. Production follows the same sequence on its separate Access audience and storage resources.
2. Run `python workers/mail-ops/ensure_routes.py --target staging` to audit, then `--apply` only after the destination Worker is healthy. Repeat for production after production ops access works. The apex MX presently resolves to Cloudflare Email Routing in one recursive lookup; check authoritative DNS and actual Cloudflare routing status rather than treating DNS alone as receipt proof. Both `postmaster@mail.moesegfault.dev` and `abuse@mail.moesegfault.dev` are mandatory compatibility paths.
3. From an external controlled sender, send four distinct reports (two in staging) containing an opaque canary marker, including one `.eml` attachment. Verify SMTP acceptance, R2 original byte fidelity, D1 case count/role, Access-restricted browser preview/download, 403 from unauthenticated/wrong operator, and PII-free alert delivery. Test a wrong alias and an oversized report. Confirm no case appears in amail CLI or user D1/R2. A synthetic D1 row or unit test alone does **not** count as intake proof.
4. Review a report, record the appropriate sender hold/recipient block via the separate operator workflow with `case_ref`, verify its audit row and API effect, then close/reopen the case. Test storage outage as a retryable SMTP failure; examine for duplicates after recovery. Test retention against a staging fixture and ensure no raw report leaked into Workers Logs/Trace or GitHub output.
5. Only after direct-report receipt and staffed alert/review are proven, set `abuse_contact_verified=1` through the audited release-gate workflow. Keep global send held until the other send gates also pass. Document who reviews the queue, response objective, appeals and coverage; access to a page without an attending operator is not a functioning abuse contact.

## Sources and decision rationale

- [RFC 5321 §4.5.1](https://www.rfc-editor.org/info/rfc5321/) requires the SMTP-receiving domain's `postmaster` role; [RFC 2142](https://www.rfc-editor.org/info/rfc2142/) standardizes the `abuse` role. This is why apex-only aliases are not enough for `mail.moesegfault.dev`.
- [Cloudflare literal routing rules](https://developers.cloudflare.com/email-service/configuration/email-routing-addresses/), [subdomain routing](https://developers.cloudflare.com/email-service/configuration/subdomains/) and [routing limits](https://developers.cloudflare.com/email-service/platform/limits/) support separate exact Worker destinations but not a subdomain catch-all; avoid Wrangler `addresses` reconciliation because it may manage and remove rules on redeploy.
- [Cloudflare Access for Workers](https://developers.cloudflare.com/workers/configuration/cloudflare-access/) supports Worker-level protection of all its URLs; [Access JWT validation](https://developers.cloudflare.com/cloudflare-one/access-controls/applications/http-apps/authorization-cookie/validating-json/) requires signature validation, not merely trusting a request header.
- [Cloudflare R2 consistency](https://developers.cloudflare.com/r2/reference/consistency/) specifies strong read-after-write for direct R2 bindings; a rejected PUT still merits delayed orphan reconciliation because cross-service error paths can be ambiguous.
- [Workers Logs](https://developers.cloudflare.com/workers/observability/logs/workers-logs/) can capture invocation details and errors; disable automatic observability for the raw-mail Worker and keep only minimal explicit operational state in D1.
