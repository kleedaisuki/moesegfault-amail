# Agent-first operator mail workflow

Status 2026-09-28: **deferred future design, explicitly outside v0.1.0**. The selected release path is exact forwarding of four production system roles to one confidential, verified external mailbox; see [`operator-intake.md`](operator-intake.md). No operator Worker, Access application, internal agent CLI, ticket UI or scheduled agent is needed for that release. The isolated `workers/mail-ops` prototype, which had only a human Access JWT check and browser case routes, has been removed from the release tree; its unused D1/R2 resources were left untouched. This document must not be used to assert operational readiness, block the simpler forwarding deployment on unneeded features, or attest `abuse_contact_verified`. The public sender remains held until the forwarding route and monitored response path are actually accepted.

## Decision and user problem

The owner rejected a ticket page as the primary *future* workflow: they want AI agents to operate the system, not a standing human duty to visit an inbox. For v0.1.0, however, they explicitly chose forwarding to a confidential external mailbox rather than building that system now. `abuse@moesegfault.dev` and `postmaster@moesegfault.dev` are system roles, with `@mail.moesegfault.dev` compatibility roles required for the receiving domain. They consume neither a user's ten addresses nor user mail/search storage. A later replacement could be a *restricted operational case service adjacent to observability*: metrics tell an agent **that** a delivery/abuse problem occurred; a durable case stores the original untrusted evidence needed to decide **what** happened. Never put raw reports into telemetry, user archives, semantic indexes, or an agent's long-lived context by default.

In this **future replacement**, the intended primary actor is a specifically enrolled **operator agent**, not every amail user agent. A normal `amail` user's Identity login never confers operational authority. The agent should be able to discover pending cases, inspect only what is necessary, correlate trusted provider events, record disposition, and execute bounded policy actions without asking the owner to perform routine review. A human page or Cloudflare dashboard would be a break-glass fallback for credential loss, ambiguous urgent cases, appeals, and recovery—not the daily queue. The current external-mailbox forwarding path has **no such agent integration** and requires a genuinely monitored response owner; do not imply otherwise.

### Trust and authentication boundary

Prefer a separate internal `amail-ops` CLI (or equally discoverable internal tool namespace), using a Cloudflare Access **Service Auth** application policy and a named, rotatable service token. The CLI sends `CF-Access-Client-Id` and `CF-Access-Client-Secret` from a protected local secret store/runner secret; never accepts either as a command argument, writes them to SQLite telemetry, or publishes them in a skill or ZIP. Use separate staging/production application audiences and, preferably, distinct credentials so a staging agent cannot act on production. A future Worker must verify Access's signed `Cf-Access-Jwt-Assertion`, issuer, audience, expiry and an allowlisted service-token `common_name`/client ID before any data access; Access at the edge alone is insufficient. Cloudflare's service-token JWT has an **empty `sub`** and a `common_name` client ID, not an operator `email`; the removed prototype's exact-email-only check therefore **could not** authenticate an agent and must not be recreated as an unauthenticated fallback. Name the internal actor from the verified client ID and credential registry; audit every state change with that actor plus opaque case ID, rule ID and causal request ID. Human Access sessions may be separately exact-email allowlisted for break-glass access. [Cloudflare service tokens](https://developers.cloudflare.com/cloudflare-one/access-controls/service-credentials/service-tokens/), [application token claims](https://developers.cloudflare.com/cloudflare-one/access-controls/applications/http-apps/authorization-cookie/application-token/), [JWT validation](https://developers.cloudflare.com/cloudflare-one/access-controls/applications/http-apps/authorization-cookie/validating-json/).

Service-token authentication is **not** authorization for all operations. A read/triage credential cannot also change global send policy. Grant action scopes in the Worker, not merely in a broad Access application policy; separate narrowly scoped credentials or a distinct high-impact control surface make accidental privilege escalation visible. Revocation/rotation and the absence of an available agent runner must fail closed. The internal CLI/API must never use a direct `workers.dev` URL to evade Access, and both custom and alternate routes require equivalent protection.

## Coherent operator journey

The following verbs describe a **future observable contract**, not behavior implemented by v0.1.0. Exact spelling can evolve before that separate service is designed, but one compact CLI and one versioned authenticated API should have equivalent capabilities.

| Intent | Suggested CLI verb | Default response / boundary |
| --- | --- | --- |
| Discover actionable work | `amail-ops status` and `amail-ops cases list --state open --since …` | Health and counts by role/priority, oldest age, continuation cursor; then one compact JSON record per case with ID, role, state, received time, byte count, trust/triage state and opaque correlation hints. **No subject, sender, body or preview.** |
| Narrow a case | `amail-ops cases get ID` | Structured status, timestamps, policy/event correlations, disposition and audit references; no raw message unless requested. A wrong/missing ID has a typed failure, not a misleading empty result. |
| Inspect evidence | `amail-ops cases preview ID` / `amail-ops cases export ID -o PATH` | Bounded, escaped/plain-text preview with an explicit untrusted-content delimiter; full original `.eml` only by opt-in export to a new protected path. No rendered HTML or auto-followed URLs/attachments. |
| Record triage | `amail-ops cases triage ID --kind … --evidence REF` and `amail-ops cases close ID --resolution …` | Idempotent transition with actor, time, evidence class, rule/version, opaque audit ID and new state. Reopen remains possible; closing is not proof a sender was held. |
| Correlate control | `amail-ops policy inspect --case ID` / `amail-ops policy propose --case ID` | Trusted provider feedback and current holds/blocks shown separately from reporter assertions; proposal states effect, scope and expiry, never executes merely because the report asks. |
| Apply bounded control | `amail-ops policy hold-account ACCOUNT --case ID --reason CODE --until …` | Restricted credential, documented evidence condition, idempotency key, audit and read-back. Global hold/unhold or clearing suppressions is a **distinct high-impact verb** requiring an explicit operator instruction or independently configured objective circuit-breaker; untrusted case text cannot be that authorization. |

Normal stdout is compact, stable-versioned JSON Lines for pipes; diagnostic and retry guidance goes to stderr. An optional `--human` changes presentation only. Every record carries schema version, environment and opaque request/trace ID; field names and typed error codes are documented. List pagination uses an opaque cursor; default limits are small but no case is unreachable. `--help` and a public internal skill expose the command tree progressively, with deeper reference only for evidence export, holds and incident recovery. An agent must be able to resume a page or case by ID after interruption without reprocessing or resending mail. Do **not** copy the public `amail` login or mail ZIP workflow into this privileged service.

### Default triage versus consequential action

1. An authenticated scheduled agent obtains a **summary**, then pages only new/open or aging cases. It records that a case was noticed and evaluates route, age and trusted provider correlations. Report content is opened only when summary/event evidence cannot resolve the case. Deterministic Worker checks may tag duplicates, correlate known lifecycle event IDs and age cases without an LLM.
2. A provider-authenticated complaint event may already have caused an account hold/recipient block in the outbound D1 policy engine. The operator agent verifies the recorded event and audit; it does **not** reapply a speculative hold or clear provider suppression to make a test green. A reporter email that merely alleges abuse is untrusted and cannot by itself hold another user's account—otherwise anyone could cause denial of service by emailing `abuse@`.
3. For a credible but uncorroborated report, the agent records a structured `needs_investigation` disposition, gathers narrowly scoped evidence, and escalates if it cannot identify the sender or evaluate harm. If there is corroborated immediate risk, a **bounded account hold** may be authorized under a written, testable rule and audited with case ID; a high-impact global hold may be triggered by a separate objective circuit breaker (for example, trusted provider outage/complaint flood), not by report prose. Global **unhold**, broad recipient suppression changes and deletion of evidence always require explicit privileged approval/read-back; silence is not approval.
4. Agent response to a report is a separate, deliberate outbound operator action with the exact destination reviewed; never use the sender header blindly. The system must support `postmaster` technical delivery inquiries as well as abuse complaints. Triage outcomes include `duplicate`, `not_ours`, `needs_investigation`, `action_taken`, `resolved` and `escalated`; these are classifications, not substitutes for case state or policy state.

The sharpest boundary is **data versus instruction**. MIME headers, body, embedded HTML, attachments, URLs and reporter-supplied account IDs are hostile inputs. Display them as quoted evidence only; do not let an LLM tool-call or shell/HTTP command be sourced from them. Verify account ownership, outbound provider ID and message correlation against trusted D1/provider records. If evidence is insufficient, prefer `needs_investigation` over an irreversible action. The exported original remains in the dedicated restricted R2 store plus an intentional temporary protected path; delete only that temporary copy after use, never the case's durable source. Any model used for classification must have a documented privacy boundary and minimal input; no default third-party embedding of report content.

## Scheduling, alerts and accountability

The unused prototype's five-minute Worker cron is designed to repair D1/R2 intake inconsistencies and retry **content-free** notifications; it is not itself an AI agent and is **not part of the forwarding release**. A future replacement needs a separate scheduled runner or pull consumer for the operator agent, with durable checkpoints and idempotent case claims. The agent checks on a bounded cadence and on urgent signals. Alerts carry only environment, role, count/priority, oldest age and opaque case IDs/links—not raw headers or mail. An HTTP `202` from an alert sender proves acceptance, not delivery or human attention. The operational health surface must expose `last_agent_success`, oldest unreviewed case, alert failure age, Queue/DLQ backlog and credential-expiry status so that a broken agent is visible. If the agent does not acknowledge within the published response objective (initially one business day for routine intake, urgent credible risk sooner), escalate through a tested owner fallback channel; while no staffed agent/fallback exists, `abuse_contact_verified` stays false and public send remains held. The fallback is an exceptional safety net, not a hidden requirement for the owner to perform everyday mail operations.

Case transitions and policy transitions are **separate append-only audits** linked by opaque case reference. Each includes verified actor, action, timestamp, prior/new state, evidence class and rule/version. A successful `close` must not imply a hold; a successful hold must be read back from the send-policy service. The operational report store stays separate from user D1/R2; bounded retention and legal preservation must be explicit. Current target is closed-case deletion after 180 days, with unresolved cases retained; avoid claiming immediate erasure. Logs, Cloudflare observability, GitHub Actions and alerts contain only code/trace/count metadata. Restrict raw R2 and Queue/DLQ console access to the same operational trust domain.

## Acceptance evidence and deliberate exclusions

- **CLI/API contract:** hosted tests cover list pagination, compact JSONL, `--human` parity, typed denials, idempotent state transitions, least-privilege read-vs-control scopes, and a case whose raw MIME contains instructions to call `policy hold`—the latter must cause no action.
- **Authentication:** Access Service Auth receives a real service token and emits a signed app JWT with expected `common_name` and empty `sub`; Worker accepts only the allowlisted client ID and intended audience. Missing token, wrong audience, retired token, human non-operator, and direct alternate URLs all deny. Rotate the token once without dropping cases. Browser exact-email fallback remains isolated and tested.
- **End-to-end intake:** external SMTP reaches both required `@mail.moesegfault.dev` roles and the apex pair; the agent retrieves summary, deliberately previews/exports one raw report, correlates it, records disposition, and verifies separated audit. No user CLI/search/ZIP can see the case. A legitimate controlled provider complaint demonstrates automatic hold independently from report text.
- **No silent queue:** deliberately stop the agent/alert runner and prove aging/backlog alerts reach the tested fallback before the response objective. A green Worker health or a present webpage alone is insufficient. Only then attest `abuse_contact_verified` and consider the ordinary send gate.

Future-design exclusions: no public web mailbox for operational roles, no general-purpose human ticketing product, no amail-user access to the ops CLI, no automatic action based solely on complaint prose, no arbitrary report-body semantic search, and no requirement that the owner routinely clear a dashboard. An operator-accessible page may remain as break-glass only; if maintaining it adds risk or work without recovery value, a restricted CLI plus Cloudflare console recovery is preferable. **Migration precondition:** never replace a verified forwarding rule with this future service until its own authentication, storage, alerting, agent runner and external SMTP canaries all pass; preserve the operational role addresses and avoid a gap in accepted reports.
