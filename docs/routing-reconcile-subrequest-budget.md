# Routing reconciliation subrequest budget

Status: design and static workload model, 2026-09-29. No account subscription or deployed latency measurement has been obtained; the Workers plan is **unknown**. This note does not identify the historical staging address-add HTTP 500. It complements [disabled-rule adoption](disabled-routing-rule-adoption.md) and the address repair scheduler, and deliberately treats Workers Free as the safety floor.

## Actual workload and bottleneck

`scheduled()` runs every five minutes. It can select 30 due address rows, and `rules_for_address_typed` presently performs a **zone-wide, paginated** Email Routing Rules GET separately for each row. The API supports only `enabled`, `page`, and `per_page` filters, not an exact recipient filter; `per_page` is at most 50. A selected address therefore costs the number of *all zone* rule pages, not one rule. The published Email Routing ceiling is 200 rules **per domain**, while production and staging mail domains share the same Cloudflare zone. At the planned 198 user aliases plus two operator rules on each mail domain, plus four apex role routes, the zone has up to about 404 rules: nine pages at 50/page. One full 30-row address batch would issue up to **270 Rules GETs** before any DELETE. Even one full 200-rule domain would cause 120 GETs. These are analytical counts from the current loop, not measured network timings.

The same Cron invocation then processes up to 20 semantic-index work items, each with one OpenRouter `fetch`. Reconciliation may DELETE duplicate or retired provider routes; those are external `fetch` calls too. `reconcile_outbound`, storage, and garbage-collection paths use R2/D1 rather than additional external HTTP in the inspected source; their internal-service work still has its own limits. Cloudflare's current [Workers limits](https://developers.cloudflare.com/workers/platform/limits/) specify 50 external subrequests per invocation on Free and 10,000 by default on Paid (with separate internal-service limits). The [Email Service limits](https://developers.cloudflare.com/email-service/platform/limits/) specify 200 routing rules per domain; the [Rules list API](https://developers.cloudflare.com/api/resources/email_routing/subresources/account_rules/methods/list/) specifies `per_page <= 50`. Redirects also consume subrequests. Thus the current code is structurally unsafe at launch capacity if the account uses Free; even Paid incurs unnecessary provider latency and rate-limit exposure. We should not assume the account plan from zone DNS or existing deployment success.

## Small, safe batching model

1. Select the same bounded due rows in the same fair due-time order. If none exist, do not list Rules.
2. Conditionally claim/rotate the selected due rows **before** provider I/O, preserving the existing cross-state fairness when a Rules GET fails. Then fetch **one complete zone Rules inventory before any provider DELETE or address state transition**. Keep the existing `success`, response-shape, page-count, and 200-page safety checks; add a Cron-specific cap of ten pages. At most 500 zone rules fit, covering the planned roughly 404-rule two-mail-domain topology with slack. Exceeding ten pages, malformed pagination, or a provider failure aborts address reconciliation without treating a partial inventory as absence. The already claimed rows merely wait for their next due slot. This is a deliberate operational capacity alarm, not a claim that all 30 Cloudflare email domains can share the same zone indefinitely on Free.
3. In memory, index only rules whose name, literal `to` matcher, and Worker action match an address in the selected D1 batch. Preserve provider order and **all** exact-owned IDs with `enabled: Option<bool>`; only `Some(true)` can prove an adoptable/committed route. No arbitrary provider address, token, or rule payload enters telemetry.
4. Apply the current state machine to each row against that snapshot. Cap Rules DELETEs for the whole Cron tick at ten. Never clear an active duplicate marker, advance a `deleting` row to `retired`, or clear a retired marker while its address still has undeleted exact-owned IDs (including disabled or status-unknown IDs). If a row reaches the delete budget partway through, leave its repair journal intact for the next tick. Conditional D1 state checks remain required because user add/delete can race the snapshot.
5. With at most ten Rules GETs, ten Rules DELETEs, and 20 OpenRouter embeddings, the expected external call bound is 40 per tick, leaving ten calls of headroom below Free's 50. This bound assumes no redirects or newly added external Cron work; it is not a network latency estimate or a guarantee against a provider redirect chain. A small explicit budget should accompany future Cron features rather than allowing unrelated jobs to silently consume the slack.

The full-zone snapshot is not atomic with concurrent rule changes. That was already true for individual paginated scans, but a single early snapshot widens the interval before the last row's decision. In particular, an empty snapshot must not authorize a `provisioning -> pending` transition after an in-flight add creates a rule. Preserve the existing ten-minute age gate and add a state/claim fence or a fresh exact recheck before this absence-based transition. Similarly, any saved route deletion must remain state-aware. A shared inventory is valuable only if it reduces redundant reads **without changing failure and race semantics**.

## Verification and decision bar

Use hosted synthetic tests for 1, 50, 51, **198**, 200, 201, 400, 500, and 501-rule inventories; multi-page exact ownership; disabled and omitted `enabled`; duplicate cleanup interrupted by the delete budget; a deleting row with saved ID plus a provider orphan; provider GET failure on a later page; concurrent add after snapshot; and 30 selected rows with a full 20-item embedding backlog. Count calls in the test fixture, not just returned IDs. The 198-rule fixture should assert four zone-page GETs rather than 30×4 when all 30 due addresses are present, and no D1 activation from a disabled/unknown rule. Deployed acceptance should separately observe one staging Cron at a realistic generated rule count without exposing addresses, rule IDs, or provider payloads. No mutation of live routes is authorized by this design note.

Do not interpret fewer GETs as a measured performance win before comparable hosted/deployed observations. The benefit that already follows from the code-level bound is elimination of a deterministic Free-limit failure mode at planned capacity; latency and rate-limit reductions are plausible but still unmeasured.
