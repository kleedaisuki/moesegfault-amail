# Routing reconciliation subrequest budget

Status: design and static workload model, 2026-09-29. No account subscription or deployed latency measurement has been obtained; the Workers plan is **unknown**. This note does not identify the historical staging address-add HTTP 500. It complements [disabled-rule adoption](disabled-routing-rule-adoption.md) and the address repair scheduler, and designs the **external-fetch portion** for Workers Free's 50-call ceiling. That alone does not establish that every other Free-plan resource limit is met.

## Current source correction (2026-10-01)

The late-provider orphan implementation replaces the per-row list model below with one complete provider-first inventory on **every** maintenance tick, including zero due rows. Address work now shares a hard twenty-exchange budget, counting list pages, fresh provisioning absence rechecks, current scoped ID GETs and DELETEs. Ten full pages without terminal metadata are not complete. Strict names/source/single matcher/single action and current D1 state are required before destructive work. Remaining work keeps its journal and fair future retry slot.

See [implementation contract](address-late-provider-orphan-implementation-2026-10-01.md). These are source bounds, not hosted/deployed acceptance or proof of the unknown account plan. The old no-due early exit and unvalidated saved-ID append below are superseded; the whole-Cron D1 concern remains unresolved and is a deployment gate.

## Historical workload and bottleneck

`scheduled()` runs every five minutes. It can select 30 due address rows, and `rules_for_address_typed` presently performs a **zone-wide, paginated** Email Routing Rules GET separately for each row. The API supports only `enabled`, `page`, and `per_page` filters, not an exact recipient filter; `per_page` is at most 50. A selected address therefore costs the number of *all zone* rule pages, not one rule. The published Email Routing ceiling is 200 rules **per domain**, while production and staging mail domains share the same Cloudflare zone. At the planned 198 user aliases plus two operator rules on each mail domain, plus four apex role routes, the zone has up to about 404 rules: nine pages at 50/page. One full 30-row address batch would issue up to **270 Rules GETs** before any DELETE. Even one full 200-rule domain would cause 120 GETs. These are analytical counts from the current loop, not measured network timings.

The same Cron invocation then processes up to 20 semantic-index work items, each with one OpenRouter `fetch`. Reconciliation may DELETE duplicate or retired provider routes; those are external `fetch` calls too. `reconcile_outbound`, storage, and garbage-collection paths use R2/D1 rather than additional external HTTP in the inspected source; their internal-service work still has its own limits. Cloudflare's current [Workers limits](https://developers.cloudflare.com/workers/platform/limits/) specify 50 external subrequests per invocation on Free and 10,000 by default on Paid (with separate internal-service limits). The [Email Service limits](https://developers.cloudflare.com/email-service/platform/limits/) specify 200 routing rules per domain; the [Rules list API](https://developers.cloudflare.com/api/resources/email_routing/subresources/account_rules/methods/list/) specifies `per_page <= 50`. Redirects also consume subrequests. Thus the current code is structurally unsafe at launch capacity if the account uses Free; even Paid incurs unnecessary provider latency and rate-limit exposure. We should not assume the account plan from zone DNS or existing deployment success.

There is a separate unresolved **D1** documentation boundary: the current [D1 limits page](https://developers.cloudflare.com/d1/platform/limits/) lists 50 queries per Worker invocation on Free and 1,000 on Paid, while the newer [Workers limits page](https://developers.cloudflare.com/workers/platform/limits/) and [subrequest changelog](https://developers.cloudflare.com/changelog/post/2026-02-11-subrequests-limit/) describe 1,000 Free internal-service subrequests. These may be a product-specific D1 limit or stale wording; do not silently pick the larger number. The current 30-row address scan alone can consume one selection plus 30 claims and additional state writes, before other Cron D1 work. Account-plan verification and a hosted high-backlog D1 test are required before calling the **whole Cron** Free-safe.

### Whole-Cron D1 call inventory

The following are code-derived **call counts**, not observed latency or D1 `rows_read` measurements. Concurrent row changes can reduce completed work; errors can stop a phase early. A D1 `batch()` is not assumed to erase per-statement limits.

| Scheduled phase | Bound from inspected source | Why the peak matters |
| --- | --- | --- |
| Address repair | One select, up to 30 due-time claims, then zero to roughly two state writes per row | A busy 30-row sweep can approach 91 D1 statements before other phases. |
| Outbound recovery | Two setup queries, then one `messages` insert, one ledger update and one `send_requests` update per item, **plus one chunk INSERT for each text part after the first** | `validate_draft` permits a text-only draft near 4,000,000 bytes; 60,000-byte parts mean about 66 chunk INSERTs. Twenty such accepted rows could use roughly `2 + 20 × (66 + 3) = 1,382` D1 statements in this phase alone, exceeding even the published Paid 1,000-query invocation bound. This is a feasible stress shape, not a measured production backlog. |
| Semantic retry | Two initial reads and up to 20 claimed items; each item performs a claim, owner-schedule update, leased-content read, then success/failure persistence | At least about 62 D1 statements if all 20 items progress; the actual failure/success paths can do more. Also up to 20 external OpenRouter calls. |
| Deleted-content collection | One list, then three D1 deletes per row for up to 20 rows | Up to 61 D1 statements, besides R2 operations. |
| Orphan-object collection | One list, then a send-state read and two D1 deletes per processed row, up to 20 | Up to 61 D1 statements, besides R2 operations. |
| Other maintenance | One storage update, three abuse-retention statements, and three search-job cleanup statements | Seven more D1 statements before any future maintenance work. |

Therefore batching provider inventory removes a real external-fetch failure mode but **does not** make this combined Cron safe at 50 D1 queries and cannot by itself guarantee the 1,000-query Paid bound under a backlog of large outbound recovery items. Two actionable paths are: (a) verify Workers Paid, give the combined invocation a conservative D1 call budget, and stop each phase before its next row would cross it, leaving durable work for another tick; or (b) if Free is required, split address repair, outbound recovery, semantic retry, and storage cleanup into separate invocations (for example, dedicated scheduled Workers or Queue consumers), each with a much smaller row/chunk budget and durable continuation. Merely changing the address `LIMIT 30` to five is insufficient if the same invocation still runs all remaining phases. For outbound recovery, estimate the chunk count **before writing**, and permit only work that fits the remaining query budget; otherwise a large item can be retried forever without progress. A continuation cursor or another per-item invocation boundary is needed if a single valid item exceeds the budget.

## Historical batching proposal (superseded by provider-first audit)

1. Select the same bounded due rows in the same fair due-time order. If none exist, do not list Rules.
2. Conditionally claim/rotate the selected due rows **before** provider I/O, preserving the existing cross-state fairness when a Rules GET fails. Then fetch **one complete zone Rules inventory before any provider DELETE or address state transition**. Keep the existing `success`, response-shape, page-count, and 200-page safety checks; add a Cron-specific cap of ten pages. At most 500 zone rules fit, covering the planned roughly 404-rule two-mail-domain topology with slack. Exceeding ten pages, malformed pagination, or a provider failure aborts address reconciliation without treating a partial inventory as absence. The already claimed rows merely wait for their next due slot. This is a deliberate operational capacity alarm, not a claim that all 30 Cloudflare email domains can share the same zone indefinitely on Free.
3. In memory, index only rules whose name, literal `to` matcher, and Worker action match an address in the selected D1 batch. Preserve provider order and **all** exact-owned IDs with `enabled: Option<bool>`; only `Some(true)` can prove an adoptable/committed route. No arbitrary provider address, token, or rule payload enters telemetry.
4. Apply the current state machine to each row against that snapshot. Cap Rules DELETEs for the whole Cron tick at ten. Never clear an active duplicate marker, advance a `deleting` row to `retired`, or clear a retired marker while its address still has undeleted exact-owned IDs (including disabled or status-unknown IDs). If a row reaches the delete budget partway through, leave its repair journal intact for the next tick. Conditional D1 state checks remain required because user add/delete can race the snapshot.
5. With at most ten Rules GETs, ten Rules DELETEs, and 20 OpenRouter embeddings, the expected **external** call bound is 40 per tick, leaving ten calls of headroom below Free's 50. This bound assumes no redirects or newly added external Cron work; it says nothing about the separate D1 query limit, is not a network latency estimate, and is not a guarantee against a provider redirect chain. A small explicit budget should accompany future Cron features rather than allowing unrelated jobs to silently consume the slack.

The full-zone snapshot is not atomic with concurrent rule changes. That was already true for individual paginated scans, but a single early snapshot widens the interval before the last row's decision. In particular, an empty snapshot must not authorize a `provisioning -> pending` transition after an in-flight add creates a rule. Preserve the existing ten-minute age gate and add a state/claim fence or a fresh exact recheck before this absence-based transition. Similarly, any saved route deletion must remain state-aware. A shared inventory is valuable only if it reduces redundant reads **without changing failure and race semantics**.

## Verification and decision bar

Use hosted synthetic tests for 1, 50, 51, **198**, 200, 201, 400, 500, and 501-rule inventories; multi-page exact ownership; disabled and omitted `enabled`; duplicate cleanup interrupted by the delete budget; a deleting row with saved ID plus a provider orphan; provider GET failure on a later page; concurrent add after snapshot; and 30 selected rows with a full 20-item embedding backlog. Count calls in the test fixture, not just returned IDs. The 198-rule fixture should assert four zone-page GETs rather than 30×4 when all 30 due addresses are present, and no D1 activation from a disabled/unknown rule. Deployed acceptance should separately observe one staging Cron at a realistic generated rule count without exposing addresses, rule IDs, or provider payloads. No mutation of live routes is authorized by this design note.

Do not interpret fewer GETs as a measured performance win before comparable hosted/deployed observations. The benefit that already follows from the code-level bound is elimination of a deterministic Free-limit failure mode at planned capacity; latency and rate-limit reductions are plausible but still unmeasured.
