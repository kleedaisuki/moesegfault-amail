# amail v0.1.0 product acceptance gap ledger

Status: source/CI audit on 2026-09-28, not a claim of deployed acceptance. Scope is the original user journey: a person authorizes Identity login once, then an agent registers an address, finds mail, exchanges content through ZIP, sends, updates, and deletes through the CLI. A release site and downloadable native binaries complete onboarding. This ledger distinguishes a source-level defect from a live proof still missing. It does not replace `docs/validation.md` or re-run previously passed checks. Heavy build and cross-platform tests belong in GitHub Actions; local smoke may use a CI-built amail binary under repository `.temp/`.

## P0 — must close before public v0.1.0

1. **Mailbox-address telemetry — source fix landed; runtime privacy gate open.** Originally `crates/amail/src/api.rs::delete_address` placed the full address in `DELETE /v1/addresses/{address}`, which Cloudflare's automatic [invocation logs](https://developers.cloudflare.com/workers/observability/logs/workers-logs/) and [trace spans](https://developers.cloudflare.com/workers/observability/traces/spans-and-attributes/) would retain as a URL. Commits `109d590` and `72703d3` changed CLI and Worker to `DELETE /v1/addresses` with JSON `{address}`; the short `amail address delete` command remains. The CLI route/body test, cross-platform CLI matrix and Worker Wasm job passed at `955a3c5` in run 36419037567. **Acceptance probe:** inspect a real staging deletion's invocation log/span using a recognizable disposable address. The address must be absent from URLs, logs and spans while a CLI trace ID remains correlatable to Worker diagnostics. Do not disable all useful Worker observability merely to make the leak disappear.
2. **Native login storage and refresh — narrow live passes; API/logout still gates.** A first live production browser callback exposed a Windows keyring limit: serialized tokens exceeded 2,560 UTF-16 characters, the CLI failed to persist them, and the browser falsely displayed “Login complete”. Commit `5152f7b` changed the design to a small OS-protected key and encrypted SQLite token storage, with success shown only after persistence. A later CI-built Windows artifact completed real `auth login` with exit 0 and `authenticated: true`; a new process also returned authenticated status. After access-token expiry, `address list` triggered a successful production Identity refresh before its mail API connection failed; another process observed a later token expiry. A coarse SQLite scan found no obvious token markers. **Still-open acceptance probe:** after mail API deployment, prove an authorized API response; test logout/revocation and restart behavior; inspect storage with recognizable canaries for absence of plaintext tokens/key material; and induce a persistence failure to verify browser and CLI both report failure. Do not mistake successful Identity refresh for mail-service authorization.
3. **Live mail lifecycle and release gates.** [Run 36424923690](https://github.com/kleedaisuki/moesegfault-amail/actions/runs/36424923690) passed CLI (Windows/macOS/Linux), Worker Wasm, Astro, infrastructure and OpenRouter predeploy checks, and deployed the isolated staging launch site. Staging mail failed its pre-install secret precheck because the single required zone-scoped `CF_EMAIL_ROUTING_TOKEN` was empty; ingress and production jobs were skipped. Nothing in a successful site `200` or eventual mail `/health` would prove mail delivery. **Acceptance probe:** with that scoped routing secret, deploy staging, authorize a CI-built CLI in the browser, register an address, verify a literal Cloudflare rule, send an external multipart/CID/attachment fixture into it, search and retrieve/unpack its ZIP, explicitly mark read/unread, send a ZIP-authored reply to an unverified external recipient, verify received MIME and SPF/DKIM/DMARC, then delete and verify rule removal. Observe only sanitized statuses/trace IDs in committed evidence. Repeat production-relevant smoke after merge; only then tag and verify v0.1.0 release artifacts and production HTTPS site routes.
4. **Transactional delivery, official sender, and abuse containment.** The owner clarified amail's scope as agent-workflow replies and notifications, **not** general-purpose unsolicited first-contact correspondence. Cloudflare's [FAQ](https://developers.cloudflare.com/email-service/reference/faq/) limits Email Service to transactional mail, while its [agent-email announcement](https://blog.cloudflare.com/email-for-agents/) explicitly covers agent replies and notifications; `docs/outbound-policy.md` records the calibrated product interpretation. Written approval for arbitrary multi-tenant cold outreach is **not** a v0.1 blocker because that is not the offered product. **Acceptance probe:** deliver a ZIP-authored workflow reply/notification from an active owned `@mail.moesegfault.dev` address to a controlled external inbox and a separate operator canary from `mail@moesegfault.dev`; check external receipt, sender, MIME, SPF/DKIM/DMARC and provider delivery status. Verify fail-closed account/global holds, bounded burst and recipient attempts, ownership, abuse-report intake, recipient-attributed bounce/complaint/suppression feedback and a tested operator stop path. The preferred Cloudflare native Event Subscription → Queue/Rust consumer/DLQ path in `docs/outbound-abuse-design.md` is being implemented but has no deployed proof. If provisioning blocks it, an owner-approved, measured and time-bounded operational fallback or deferral is required as specified in `docs/outbound-policy.md`; never silently call a manual dashboard glance equivalent. A provider `202` or DNS-only check is insufficient; do not infer unlimited unsolicited mail permission from success.

### Product decision: official sender without artificial notification machinery

The user's `mail@moesegfault.dev` rule is a **sender-identity invariant for messages representing the site**, not a request to invent a welcome email, newsletter, or web-mail UI. The v0.1 site is static and sends no messages; the current production `OFFICIAL_EMAIL` binding is correctly constrained to that address, but `crates/mail-worker/src/platform.rs::send` uses only the user-mail `EMAIL` binding. Thus the binding is a policy guardrail and **not evidence that the site has sent mail**. Do not add a user-triggerable official-mail endpoint or automatic welcome mail solely to exercise it: those create consent, abuse, deliverability and support obligations unrelated to the core agent-mail journey. Instead, before claiming the official sender works, perform one operator-controlled canary through Cloudflare's documented [Email Sending REST API](https://developers.cloudflare.com/email-service/api/send-emails/rest-api/) using a narrowly scoped send credential and `from: mail@moesegfault.dev`; confirm external receipt and [delivery/authentication logs](https://developers.cloudflare.com/email-service/observability/logs/). Keep the canary out of public CLI mailboxes and CI logs. If a real site-originated notification is later justified, route it through an internal sender-constrained path and test that path separately; never let user-authored ZIPs select the official identity. This is the smallest complete policy plus operational proof, not a new v0.1 product feature.

## P1 — important quality and confidence gaps

1. **Human detailed metadata — source fix landed; live UX probe open.** Initially `amail --human get ID` dropped `metadata`, `attachments` and other fields after rendering a nine-field summary. Commit `955a3c5` now prints remaining fields and escapes terminal control characters; the focused test and Windows/macOS/Linux CLI jobs passed in run 36419037567. **Acceptance probe:** once the API is live, compare a detailed `get ID` JSON response with `--human get ID`: all user-useful fields must appear without leaking terminal control effects or making compact JSONL verbose.
2. **Resumable exact search needs discriminating deployed fixtures.** `search_jobs.rs` replaced terminal 2,000/100,000 scan cutoffs with owner-scoped continuation jobs; a slow request returns `202` and CLI polling should eventually yield only a complete exact page. Per-step resource limits, admission quotas, mutation-generation staleness and 24-hour job expiry remain explicit failure/recovery states, not permission to silently truncate. Hosted CLI and Worker CI for this revision passed in [run 36424923690](https://github.com/kleedaisuki/moesegfault-amail/actions/runs/36424923690); that is not a live D1 result. **Acceptance probe:** seed a deployed D1 mailbox with controlled mail including a hand-calculated vector-order fixture, dates exactly on each boundary, case/regex distinguishers, metadata attachment names, read/unread states, and a unique older match beyond the first 2,000 newest rows. Verify lexical and semantic results include eligible old mail, cosine scores/rank match a reference calculation, continuation survives multiple polls without duplicate/partial output, cursors do not duplicate or skip, quota/expiry/stale conditions report typed errors, and a single embedding outage later reindexes without mail re-ingest.
3. **Privacy/correlation is not proved by schema review.** Even after URL repair, automatic tracing may retain user-agent, provider URL and other attributes; CLI journal redaction and HTTP trace propagation need runtime proof. **Acceptance probe:** use a synthetic canary in subject/body/search text and a disposable address, inspect local `telemetry.sqlite3`, Worker logs/traces and any exported event payload, require absence of canary/address/token/path, require a usable trace correlation, then test `AMAIL_TELEMETRY=off` prevents new CLI event rows/upload without blocking mail operations.
4. **HTML and archive fidelity needs a receiving client, not only Rust tests.** **Acceptance probe:** native `pack` of an HTML-only directory produces a text fallback; deliver ZIP-authored multipart with `cid:` image, CSS, attachment, reply threading and non-ASCII headers to an external mailbox. Inspect received MIME and render in at least one mainstream mail client; inbound archive must include safe text/HTML/assets, including an attachment-only message. Verify reading the archive does not flip `read`.
5. **Onboarding truth must follow deployment.** The site already links directly to a not-yet-published v0.1.0 Release and describes it as downloadable. This is acceptable as release-candidate source, not as a live public page. **Acceptance probe:** after tag publication, all homepage/manual links resolve to all five binaries and the agent skill ZIP; SHA256SUMS verifies six archives; `/`, `/manual/`, `/changelog/` each return intended content over HTTPS and their TOC anchors resolve. A later release requires appending a new Markdown entry without rewriting prior entries.

## Non-goals and guardrails

- Do not add a web inbox or web address-registration surface. Agent-friendly CLI commands, not browser mailbox UI, are the product.
- Do not request a Cloudflare rule-limit increase now; clearly return capacity exhaustion and watch actual remaining capacity. The chosen first launch is bounded by provider rules, not unlimited account count.
- Do not replace exact cosine with approximate nearest-neighbor ranking just to speed up a benchmark. If a production workload exceeds the current exact-scan envelope, measure it and revise the user-visible limit or prove exact result completeness.
- Do not call native unit/CI builds or synthetic provider probes a successful deployed email product. Conversely, do not rerun already-passing unrelated jobs merely to collect another green badge; exercise only the failed or previously unverified contract.
