# Contingency: direct installed-Chrome control for staging Identity

Status: **design only; not authorized for implementation or another account/address attempt**. The existing 45-second Chrome DevTools Protocol (CDP) startup correction is awaiting hosted validation. Use this design only if a later, explicitly reviewed hosted run still fails at the browser boundary. No Chrome plugin, browser extension, downloaded browser, local test run, account registration, or route change is part of this note.

## What would change, and what would not

Replace only the custom WebSocket/CDP `Browser` transport in `infra/tests/staging_identity_cdp.py` with the official [Playwright Python browser API](https://playwright.dev/python/docs/api/class-browsertype). Playwright launches the **already installed Google Chrome** directly through its `chrome` channel (or an explicitly validated installed executable path); it does not depend on a user's flaky Chrome-use plugin. Keep the existing `Browser` facade and all normal first-party registration, OIDC authorization-code/PKCE, Windows DPAPI, CLI loopback, exact route-cleanup, and fixed-stage-error contracts. This is a test-harness transport substitution, not an Identity or amail authentication redesign.

Playwright documents `launch_persistent_context(user_data_dir, channel="chrome", env=..., headless=True)` and that closing the returned context closes the browser. Use one **new**, `mkdir(exist_ok=False)` profile below the run's repository `.temp` directory per phase, never the operator's Chrome profile; suppress any default trace, video, screenshot, HAR, console, request/response logging or uploaded browser artifact. Pass the existing minimal `browser_environment()` allowlist to Chrome; the CI job's Python process may hold secrets, but Chrome must not inherit them. An ephemeral `browser.new_context()` would also isolate cookies; a fresh persistent profile is preferable here because the current helper's profile-location invariant and cleanup boundary remain explicit. Neither approach should share a context between registration and login. Avoid `launch(..., executable_path=...)` unless channel resolution fails on the runner and the exact installed path is checked: Playwright warns that controlling a different browser build is not guaranteed to work.

| Existing Browser operation | Proposed Playwright operation | Invariant |
| --- | --- | --- |
| launch + attach to localhost CDP | `sync_playwright().start()`, `chromium.launch_persistent_context(..., channel="chrome", env=..., headless=True)`, select/create one page | Startup/teardown bounded; browser process and Playwright driver both closed on constructor failure. No remote debugging TCP port or plugin. |
| `navigate(url)` | Verify parsed origin is exactly staging issuer or Login, then `page.goto(url, wait_until="domcontentloaded", timeout=...)` | Authorization URL is validated in memory before navigation; no token injection or raw URL in exceptions/logs. |
| `wait_dom`, `require_login_origin` | Locator wait; `page.evaluate("location.origin")` immediately before every credential/OTP fill | Input occurs only at the reviewed first-party Login origin; do not treat a matching selector on another origin as trusted. |
| `fill`, `click` | [Locator](https://playwright.dev/python/docs/api/class-locator) `.fill()`/`.click()` with bounded timeouts | Browser event flow, cookies, CSRF, and password form remain authentic. No raw Identity API calls. |
| `response(predicate)` | Install [response wait](https://playwright.dev/python/docs/api/class-page#page-expect-response) **before** the click, matching `response.request.method == "POST"`, exact issuer origin, and only the three reviewed paths | CORS `OPTIONS` 204 and unrelated responses can never satisfy registration/verification checks. Registration 201 and the automatically initiated verification-start 201 may race; install both waits before the registration click, not one after the other. Retain only bounded matched response objects/statuses in memory. |
| `response_body` | After the matched completion response finishes, call `response.json()` only for that response and inspect `verification_state` | No generic body capture, raw response output, or network trace. Verify HTTP 200 **and** `verified`. |
| `close` | Close context and Playwright driver in separate `finally` branches | Browser failure cannot skip the existing exact-route audit/removal or CLI loopback-process teardown. |

Do not pass raw `PlaywrightError` text to public logs: it can contain authorization URLs, selectors, browser arguments, or provider data. Translate at the `Browser` boundary to fixed labels (for example, `chrome_startup_failed`, `first_party_field_missing`, `identity_response_missing`); preserve the existing safe HTTP-status labels for recognized POSTs. A fixed startup deadline must fit the CLI's 300-second loopback lifetime, and every wait/call must have a finite timeout. Whether Playwright's installed-Chrome compatibility succeeds on a particular GitHub Windows image remains an **empirical** question, not a promise from its API documentation.

## Hosted-only validation before adoption

1. Update the **hosted** `staging-e2e` job to install pinned, reviewed `playwright` and `pywin32` Python packages instead of `websocket-client`; do **not** run `playwright install` or download a browser. Use the runner's installed Chrome. Keep `PYTHONDONTWRITEBYTECODE=1` and no browser artifacts.
2. Replace synthetic CDP frames in `test_staging_identity_cdp.py` with mocked Playwright response/locator/browser cases: POST versus OPTIONS, exact issuer/path, both responses arriving before the first result is read, unexpected navigation origin, credential-origin guard, constructor failure, and teardown that still closes the exact route. Run these through GitHub Actions; do not run them on the development machine.
3. Only after hosted static/synthetic checks pass, use one separately approved **login-only** run with an existing verified staging account to prove installed Chrome, first-party password form, loopback PKCE, and cross-process Mail resource access. Do not register a new account or address merely to validate a browser transport. If the Chrome launch fails, stop at that named boundary; never lengthen timeouts or silently retry a mutating operation to hide it.

The immediate next step is **not** this migration: first inspect the current hosted CI result and one guarded use of the 45-second CDP fix. This contingency becomes actionable only with failure evidence pointing at CDP/browser attachment rather than Identity, CLI, provider routing, or network state.
