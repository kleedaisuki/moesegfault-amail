# Platform feasibility and integration constraints (2026-09-28)

## Decision summary

The requested system is implementable on Workers for HTTP API, storage, outbound email, and semantic search, but **unbounded public inbound mailboxes at `*@mail.moesegfault.dev` are not supported by Cloudflare Email Routing in the parent zone**. Cloudflare permits catch-all only at the zone apex; routing a subdomain requires one literal rule per address and currently caps routing rules at **200 per domain**. A delegated `mail.moesegfault.dev` child zone could make that hostname an apex, but Cloudflare's child-zone setup is Enterprise-only. Thus, do not claim that a pure standard-plan Cloudflare Email Routing deployment satisfies a publicly open mailbox product. Either (a) secure a documented Cloudflare exception/capacity and accept per-address provisioning, (b) obtain Enterprise child-zone setup and test catch-all, or (c) use another inbound SMTP gateway that delivers to a Worker webhook. Option (c) retains Workers for all application logic but introduces a mail transport dependency.

## Inbound and DNS

* [Email Service subdomains](https://developers.cloudflare.com/email-service/configuration/subdomains/) says routing subdomains are onboarded separately under Email Routing settings; Cloudflare adds required DNS records, but only literal routing rules can be created for subdomain addresses. Catch-all is apex-only.
* [Routing rules and addresses](https://developers.cloudflare.com/email-service/configuration/email-routing-addresses/) describes `addresses` in Wrangler; `*@example.com` works only for an apex, while `support@mail.example.com` must be explicit. A dynamic CLI registration flow would therefore require backend-controlled [routing-rule REST API](https://developers.cloudflare.com/api/resources/email_routing/subresources/rules/) calls, not a static Wrangler deployment. The API credential must never reach the CLI. Registration across D1 and Cloudflare Rules is not atomic: use a pending/provisioning state, reconcile retries, and only expose an address as active after Cloudflare acknowledges its rule.
* [Email Service limits](https://developers.cloudflare.com/email-service/platform/limits/) documents 200 routing rules per domain, 25 MiB inbound messages, and Workers plan CPU/memory applicability. Maximum ten aliases per account is a user policy, not a solution to the global 200-rule cap.
* [Cloudflare child-zone setup](https://developers.cloudflare.com/dns/zone-setups/subdomain-setup/setup/) is Enterprise-only; generic [NS delegation support](https://developers.cloudflare.com/dns/manage-dns-records/how-to/subdomains-outside-cloudflare/) does not imply that an ordinary Cloudflare account can onboard a child zone with Email Routing catch-all.
* The inbound Worker `email(message, env, ctx)` receives envelope sender/recipient, headers, `raw` MIME ReadableStream, and raw size per [Workers email handler](https://developers.cloudflare.com/email-service/api/route-emails/email-handler/). R2 accepts a stream in `put`; store immutable raw MIME in R2, D1 metadata and parsed/searchable text. The `worker` Rust crate has `ForwardableEmailMessage` bindings, but its current `#[event]` macro [does not list an `email` handler](https://docs.rs/worker/latest/worker/attr.event.html). An intentionally tiny JS event bridge into Rust/Wasm is the most realistic route pending an upstream SDK change; do not write full business logic in the bridge. Confirm with a deploy/build probe.

## Outbound transport and deliverability

* [Workers native Email Service binding](https://developers.cloudflare.com/email-service/api/send-emails/workers-api/) provides structured `send()` with `text`, `html`, inline and regular attachments, and headers, plus legacy raw MIME. Structured sending is preferable: Rust should compile the ZIP manifest/assets into a validated typed email object; bridge to the binding only at the platform boundary. Preserve ZIP format as CLI/server contract, not as wire-format SMTP payload.
* The sending domain must be separately onboarded for **both** `mail.moesegfault.dev` (user From) and `moesegfault.dev` (site `mail@moesegfault.dev` From). [Subdomain onboarding](https://developers.cloudflare.com/email-service/configuration/subdomains/) and [sending setup](https://developers.cloudflare.com/email-service/get-started/send-emails/) cause Cloudflare to add/verify bounce MX, SPF, DKIM, and DMARC. DNS values must be obtained from account-specific onboarding; never invent static DKIM keys or selectors. `mail.moesegfault.dev` is both HTTPS application host and mail domain: use Worker Custom Domain for HTTP and MX/TXT for mail; these are separate DNS record types, but actual deployment must test collision handling. [Custom Domains](https://developers.cloudflare.com/workers/configuration/routing/custom-domains/) can provision HTTP DNS/cert automatically.
* [Pricing](https://developers.cloudflare.com/email-service/platform/pricing/) requires Workers Paid for arbitrary recipient sends; 3,000 monthly sends included and account-based daily limits apply. [Limits](https://developers.cloudflare.com/email-service/platform/limits/) state 5 MiB total outbound message size (including attachments), max 50 recipients, and conservative initial daily quota. Thus, validate compiled size before invoking `send`, not ZIP size alone. The transport is intended for transactional mail per [Email Service FAQ](https://developers.cloudflare.com/email-service/reference/faq/); product abuse controls, per-account send quotas, suppression handling, rate limits, and complaints are required for public use.
* **Usage classification is unresolved**: the [service overview](https://developers.cloudflare.com/email-service/) and FAQ explicitly call outbound “transactional”; Cloudflare's [agent email announcement](https://blog.cloudflare.com/email-for-agents/) demonstrates an Agentic Inbox that receives and replies, but does not clearly authorize an open, person-to-person mailbox service with arbitrary user-composed messages. Treat general-purpose P2P sending as unapproved until Cloudflare confirms it in writing or a provider with an explicit mailbox-use policy is selected. This is a product/service-contract blocker, not merely an API gap.

## Search and storage

* [D1 supports SQLite FTS5 and JSON](https://developers.cloudflare.com/d1/sql-api/sql-statements/). D1 can hold mailbox ownership, metadata, read status, and searchable text; R2 holds raw MIME and larger assets. [D1 limits](https://developers.cloudflare.com/d1/platform/limits/) include 10 GB/database on Paid, 2 MB per row/BLOB, 100 bound parameters, and one-at-a-time query execution per database. Avoid storing whole messages as D1 blobs.
* [OpenRouter embeddings API](https://openrouter.ai/docs/api/api-reference/embeddings/create-embeddings) accepts `model`, `input`, and optional `dimensions`; [Qwen official model repository](https://github.com/QwenLM/Qwen3-Embedding/blob/main/README.md) confirms 8B, maximum 4096-dimensional output, and Matryoshka custom dimensions. Use model `qwen/qwen3-embedding-8b`, request 256 dimensions, and validate response vector length, finite values, and stable model identifier before storing. Provider routing may affect adherence; the presence of an API field is not proof that each provider honors it. An authenticated live probe is decisive.
* `Vectorize` offers cosine and high-precision scoring (`returnValues: true`), but its query selects candidates approximately; [Vectorize query documentation](https://developers.cloudflare.com/vectorize/best-practices/query-vectors/) does not establish exact global top-k. For the user's explicit **exact cosine** requirement, perform exhaustive scoring of all authorized, filter-matching 256-D vectors server-side and sort deterministically (score then ID). This is O(256N) per semantic query, acceptable only within measured mailbox sizes; D1 scan cost, pagination, Worker CPU, and memory need workload testing. Vectorize can later serve as optional candidate acceleration only if exactness is relaxed or followed by a proven exact candidate-completeness mechanism.
* Security/privacy: embedding inputs expose message body text to OpenRouter and its selected upstream provider. Document that data flow, retention and opt-out policy; send only bounded sanitized text, never secrets in telemetry. An incoming email may be adversarial HTML: render to text in an isolated parser and sanitize any later HTML projection.

## Identity trust boundary

The in-repository [Identity skill](../.agents/skills/moesegfault-identity/SKILL.md), [onboarding reference](../.agents/skills/moesegfault-identity/references/application-onboarding.md), and [OIDC integration reference](../.agents/skills/moesegfault-identity/references/oidc-integration.md) are the current local contract. `amail` is a registered public/native OAuth client: system browser, Authorization Code + S256 PKCE, fresh state and nonce, exact registered loopback callback (or platform-bound HTTPS), no embedded client secret, platform-protected refresh storage. The service accepts access tokens only with exact issuer and current client-ID audience, validates RS256 JWKS, token kind and scopes, and maps users by `(issuer, sub)`. The current issuer has no client-credentials grant or separate resource audience; a CLI-to-service token works only if that exact `client_id` is the intended accepted audience. Refresh tokens rotate and require serialized, atomic replacement. Registration is deployment-owned, not a runtime endpoint. Re-check live OIDC discovery before claiming production readiness.

**Observed integration status reported by the integration team (2026-09-28):** the actual issuer is `https://identity.moesegfault.dev`; its `/.well-known/openid-configuration` responds HTTP 200 `application/json` and advertises that issuer. `https://login.moesegfault.dev` is the human-facing Login SPA, not the OIDC issuer; an HTML response from a discovery-shaped path there does **not** indicate broken Identity discovery. However, no reviewed native-client ID was found in this repository or configured GitHub secrets. The CLI and API must fail closed for login/authorization until that client is registered and configured. Do not substitute a made-up client ID or point issuer validation at the Login SPA.

## Observability

[Workers traces](https://developers.cloudflare.com/workers/observability/traces/) auto-instrument handlers, fetch and bindings when `[observability.traces] enabled = true`; logs require the Workers Logs setting. Trace sampling is independent of logging. [OTLP export](https://developers.cloudflare.com/workers/observability/exporting-opentelemetry-data/) is beta and Paid-only. Cloudflare auto-traces do not by themselves join a native CLI SQLite trace to a Worker invocation: explicitly propagate a W3C `traceparent`/correlation ID from CLI to HTTP Worker, preserve the Identity `x-moesegfault-correlation-id`, and instrument semantic operations with safe IDs and counts. Never record address, subject, body, ZIP contents, token, authorization code, cookie or raw recipient in traces/logs. A stable keyed hash of account or message identifiers can support debugging without direct PII leakage, but key management and re-identification risk must be acknowledged. As of this note, tracing beta billing is planned for 2026-10-01; verify again before production budgeting.

## Deployment acceptance gates

1. Confirm account plan, zone control, Email Service Sending availability, and actual DNS/provisioning permissions without printing credentials.
2. Prove at least one real CLI login against the registered native client; validate live discovery and complete token lifecycle.
3. Prove actual external inbound to `test@mail.moesegfault.dev` and dynamic routing-rule creation; measure remaining rule capacity. Do not market an unbounded public mailbox while capped at 200 aliases.
4. Prove outbound user-domain and site-domain From addresses to an external recipient; verify delivered SPF/DKIM/DMARC and attachments under 5 MiB.
5. Probe OpenRouter 256-D output and compare exact cosine results against a small hand-calculated corpus; test long/multilingual mail.
6. Run end-to-end traces and test privacy redaction using an intentionally recognizable test subject/body that must not appear in logs or telemetry.
