# Mail API privacy-safe trace implementation (2026-09-29)

This records the code contract and verification boundary for the implementation of [the privacy decision](mail-trace-privacy-decision.md). It does **not** assert that deployed settings or retained records are safe: deployment readback and a restricted synthetic-canary inspection are separate gates. No private logs, mail, tokens, or production settings were accessed for this work.

## Data model and causal graph

The CLI creates one W3C version-00 `traceparent` per API operation: trace ID `T` and client span ID `C`. After authentication, the API accepts only exact lower-case ASCII v00 syntax, nonzero 32/16-character hex IDs, and flags `00` or `01`. It creates its own server span `S`, recording `T` and `parent_span_id=C`. Invalid or absent context receives a new server trace. Authentication failures never inspect or retain the caller's trace header. The private ingress path applies the same rule only after shared-secret validation. `tracestate` is neither copied nor forwarded.

The API emits one fixed-schema request-exit event with its server-generated `request_id=R`; selected inbound D1/R2 operations and outbound R2/provider calls emit child phase IDs whose parent is `S`. Each event contains only version, typed service/operation/phase/outcome/error code, W3C IDs, `R`, status class, bucketed duration, and an optional measured byte bucket. There is no dynamic attribute bag. No URL, path, query, envelope, address, subject, body, archive name, R2 key, token, SQL binding, provider exception, or raw `Error`/`Debug` is serialized. Errors use coarse fixed codes. The serializer falls back to a fixed warning and cannot alter the mail result.

The CLI SQLite journal adds nullable `span_id` in place; existing rows remain `NULL` and upload without the new JSON key. New rows upload `T,C,R` (where `R` came from the existing response header). The server accepts historical `/v1/telemetry` payload shapes: historical IDs/status/byte buckets are not newly rejected. Only strict safe IDs and valid status values enter retained client trace events, and byte counts are re-bucketed. Thus old clients remain accepted without allowing arbitrary legacy text into logs. `AMAIL_TELEMETRY=off` still suppresses local journaling/upload and does not invent a CLI span in the server event.

This is **causal application-event tracing**, not Cloudflare's native Traces waterfall or automatic dependency spans. External providers are not automatically joined. The current Rust `console_log!` path emits JSON text; staging must verify that Workers Logs indexes it suitably, or a later reviewed JS-object console bridge can preserve the schema.

## Effective configuration and gates

Both production and staging `crates/mail-worker/wrangler.toml` explicitly set top-level `redact_query_string=true`, app logs enabled at full rate, invocation logs disabled, and native traces disabled. This is defense against automatic URL and dependency capture, including rejected paths that application code cannot sanitize before persistence. The ingress and event-consumer Workers remain fully unobserved. Cloudflare documents the automatic root-span URL and Email envelope fields, and the independent invocation-log toggle: [automatic span attributes](https://developers.cloudflare.com/workers/observability/traces/spans-and-attributes/), [Workers Logs](https://developers.cloudflare.com/workers/observability/logs/workers-logs/).

`crates/mail-worker/check_observability.py --realm staging|production` is a no-mutation fail-closed readback gate. It checks local intent plus both the deployed script/version `/settings` and script-level `/script-settings` API responses. It requires the four critical privacy booleans, full sampling, and no unreviewed Logpush, Tail Worker, or external destination. The platform's built-in `"cloudflare"` destination is allowed; arbitrary export destinations are not. The endpoint and response fields follow [Cloudflare's script-settings API](https://developers.cloudflare.com/api/resources/workers/subresources/scripts/subresources/settings/methods/get/) and [script/version settings API](https://developers.cloudflare.com/api/resources/workers/subresources/scripts/subresources/script_and_version_settings/methods/get/). Deployment CI must call this checker immediately after each mail API deploy before reporting success.

## Reproducible checks and remaining acceptance

Focused local checks on 2026-09-29: `cargo check -p amail-worker --lib -p amail --bin amail`; `cargo test -p amail-worker --lib trace::tests` (3 passed); `cargo test -p amail --bin amail telemetry::tests` (2 passed); `python -m unittest discover -s crates/mail-worker -p 'test_check_observability.py'` (3 passed). These cover strict parser/UTF-8 rejection, fixed event schema and child parentage, SQLite migration and legacy wire shape, and static/mocked settings. Hosted CI should rerun affected tests and the Wasm build. A pre-existing unrelated `archive.rs` unused-mut warning remains.

Before claiming deployed privacy or searchability, deploy via existing gates, check the effective settings in each realm, and run a **restricted** synthetic canary: normal request with distinctive address/subject/body plus rejected URL containing distinctive query **and path** canaries; inspect retained Workers Logs without copying private records into CI/docs. Confirm absence of every canary and presence of `T,C,S,R` and phase parentage. Exercise malformed `traceparent`, unauthenticated requests, provider/storage failures, and uncaught exceptions. Static config and unit tests cannot prove retained-log behavior or a platform exception path. Never re-enable native traces merely because query redaction passes; path and dependency attributes remain independently sensitive.
