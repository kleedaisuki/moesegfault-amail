# Independent integration review: staging Identity test inbox

Reviewed 2026-09-28 after the OTP Worker/CI wiring freeze. Scope: `workers/identity-test-inbox/{Cargo.toml,wrangler.toml,src/lib.rs,check_config.py,ensure_route.py,test_*.py}`, root Cargo manifests/lockfile, `.github/workflows/{ci.yml,deploy-identity-test-inbox.yml}`, and the contract in `docs/staging-test-account.md`. This is a **static integration review**, not a hosted build, Cloudflare state readback, or delivered Identity-code test. No production files were changed by this reviewer.

## Material findings from initial integration snapshot

| Priority | Finding and reproducible condition | Impact / required correction |
| --- | --- | --- |
| P1, conditional on provider shape | `ensure_route.py::owned()` uses `rule.get("source", "api") == "api"`. A rule with the exact alias/action/enabled fields but **no `source` key** is treated as API-owned. `reconcile(..., "remove")` can then DELETE it, despite the stated requirement to refuse any rule whose ownership is not proved. A mock rule `{id, enabled:true, matchers:[exact literal], actions:[exact Worker]}` without `source` returns true. | Require an explicit `source == "api"` before deletion. If Cloudflare's real list response omits `source` for API rules, fail closed and use another trustworthy ownership proof rather than defaulting missing evidence to ownership. Add a missing-source regression test. |
| P1, conditional on paginated list behavior | `list_rules()` returns when `len(batch) < 50` **even when** `result_info.total_pages` says another page exists. Mock page 1 with one unrelated rule and `total_pages=2`, page 2 with a conflicting alias rule: `list_rules()` never fetches page 2, so `--apply` may create an unnecessary/conflicting exact rule. | When provider pagination metadata is present and valid, follow it to the last page; use short-page termination only when metadata is absent. Fail closed on inconsistent metadata or a bounded-page overrun. Test the short-first-page/two-page conflict. |
| P2 | `reconcile(..., "remove")` accepts 204 as a possible successful DELETE status but then requires `payload.success is True`. A normal HTTP 204 has no JSON body, so the helper raises *after* the provider may already have deleted the route. | Treat 204 with an empty body as provisional success and require the existing post-delete list/readback to prove absence. Test 204 + empty body + absent readback. If a response explicitly reports failure, still fail closed. |
| P1 privacy gate | `check_config.py` checks the tracked Wrangler binding and absence of HTTP publication, but neither CI staging deployment nor the standalone deploy workflow reads **live R2 bucket** public-domain/r2.dev state. `docs/staging-test-account.md` records a one-time local audit, which can become stale if a domain/dev URL is later enabled. The bucket stores raw verification codes. | Before enabling the exact route, and ideally before every Worker deployment, use scoped Cloudflare read APIs/commands to assert the bucket still has no public custom domain/dev URL and the one-day `verification/` lifecycle rule still exists. If the deployment token lacks read permission, require an independently recorded operator check; do not infer privacy from Wrangler config. Never print bucket objects. |
| P2 deployment gate | The standalone `deploy-identity-test-inbox.yml` runs Rust tests and route-helper tests but omits the explicit `python workers/identity-test-inbox/check_config.py` guard before `wrangler deploy`. The candidate `ci.yml` staging job does run it. A later manual deployment from `main` could therefore accept a bad tracked config if only that workflow is invoked. | Add the same config guard to the standalone workflow immediately before bundling/deploying. Preserve `main`-only dispatch and the alias-absent pre/post checks. |

The first two findings were *fail-closed control-plane* issues, not evidence that an actual Cloudflare rule was changed. Their impact depended on real provider response shape and inventory.

### Targeted follow-up after integration patch

The staging-account owner patched the shared worktree after this review. Reinspection confirms:

| Initial finding | Follow-up source evidence | Residual validation |
| --- | --- | --- |
| Missing `source` accepted as ownership | `owned()` now requires `rule.get("source") == "api"`; POST declares API source; route tests include missing-source conflict. | Hosted Python regression test and a live provider readback still required. |
| Short page skips later pages | `list_rules()` now follows a valid `result_info.total_pages` before using short-page fallback; tests exercise a short first page with later conflict. A second patch rejects `total_pages=0`, with regression coverage. | Hosted test and live inventory still required. |
| Empty 204 deletion false failure | 204 now provisionally succeeds and final list readback must show alias absent; tests cover that combination. | Hosted test and one disposable live route remove required. |
| Bucket public-state drift | `check_config.py --live` now reads the managed r2.dev enabled flag, custom-domain list, **and** the R2 lifecycle rule through bounded Cloudflare API calls. It requires one enabled `amail-test-expire` rule on `verification/` with Age ≤86,400 seconds, fails closed on public/unreadable/missing/long-retention state, and is invoked by both deploy paths before `wrangler deploy`. Tests cover private, public, 403 and excessive age responses. | Hosted deployment must establish the real Cloudflare API shape/permissions and current bucket posture. Lifecycle deletion is still a backstop, not an exact erasure SLA; operator deletes exact objects after use. |
| Standalone manual config-guard omission | `deploy-identity-test-inbox.yml` now invokes `check_config.py --live` immediately before bundle/deploy. | Manual dispatch is feasible only once that workflow exists on the default branch. |

No further source-level production-deploy path was found: the Worker name/bucket are fixed to staging, CI's branch/staging predicate excludes production, and the manual job is `main`-only but still deploys the staging config. These facts do not substitute for inspecting the actual Cloudflare Worker bindings/triggers after deployment.

## Integration facts checked, not a pass claim

- The workspace includes `workers/identity-test-inbox`; the lockfile includes `amail-identity-test-inbox`. Candidate CI runs native Rust tests, Wasm check, `worker-build`, Python route/config tests, and a staging-only deploy job after Worker/DNS gates. No heavy local tests were run for this review; hosted outcomes must be inspected once the integration commit lands.
- Both deploy jobs are pinned to `amail-identity-test-inbox-staging` and `amail-identity-test-inbox-staging` R2 with `workers_dev=false`, `preview_urls=false`, no HTTP route/trigger in tracked config, and automatic observability off. The Rust module has only an Email handler, rejects nonmatching recipient and >64 KiB raw MIME, and uses one UUIDv4 private object key per accepted message. These source properties do not prove the live Worker has no older route or the bucket has remained private.
- `ci.yml` candidate push and staging manual-dispatch predicates do not select production; the standalone deploy workflow is additionally `main`-only. Before the standalone workflow file exists on the default branch, GitHub manual dispatch is not feasible; the candidate branch-push job is the intended initial deployment path. This is already described in `docs/staging-test-account.md`, not a newly found production-deploy bug.
- Both deployment paths audit that the exact alias is absent before/after Worker deployment, and neither automatically creates the Email Routing rule. The rule must be opened separately for a short verification window and removed in `finally`. An alias-absent audit cannot by itself prove that no *other* public HTTP route or R2 public access exists in Cloudflare state.
