# Independent review: protected v5 exact-cosine oracle

**Decision (2026-09-30): GO to run the guarded hosted exact E2E, not GO to claim it has passed.** I found no substantive source defect in `9bf65f3` plus `58af96e` that should prevent this bounded staging attempt. No local tests, live calls, push, or production edits were performed in this review.

## Evidence

- Inspected the two diffs, the complete oracle and synthetic tests, the staging caller and `finally` cleanup, the native CLI search JSONL/poll path, v5 origin/cursor/rank code through `bc0fc29`, and the `98ef479` design. The reviewed Cloudflare D1 [Query API](https://developers.cloudflare.com/api/resources/d1/subresources/database/methods/query/) documents the result wrapper used by `d1_rows`.
- `OWNER_SQL` resolves only an active staging address; `COUNT_SQL` requires precisely two active owner messages; `VECTOR_SQL` is parameterized by issuer, subject, address, and the two run-owned IDs. The origin query is a fixed projection filtered by **origin UUID, issuer, and subject**, and does not select `cursor_key`, `request_json`, or the full `state_json`. It requires `done`, `is_origin`, matching origin ID/model/input version/commitment, and unexpired TTL. The two document snapshots and owner generation are checked before and after both CLI pages.
- The first page runs through the native CLI with a `limit=1` semantic AND-filter request. Its JSONL cursor is captured in memory, parsed as v5, and checked against the expected owner/request hash and initial generation. The oracle then reads **that completed first-page origin's actual rounded vector**, recomputes the Worker's byte-level commitment, and submits the unchanged cursor for page 2. There is no second OpenRouter request or provider-repeatability premise. Successful page 2 is evidence that the deployed Worker accepted its MAC; this operator cannot independently recompute the HMAC because it deliberately never reads the key.
- The shared checker independently recomputes both exact cosine scores from the origin and stored document vectors, checks score/time/ID order and two-page union without duplication, and rejects a third-page cursor. The positive fixture requires a discriminating score gap. Added negative tests cover an incompatible second-page score, generation/vector drift, origin TTL and owner-scope failure, exact tie order, and a near tie whose score gap is smaller than display tolerance. These are synthetic checks, not hosted evidence.
- CLI stdout/stderr, vectors, message IDs, cursor, and D1 responses are captured but not printed by this path. The harness emits fixed failure labels or bounded numeric score error; its existing `finally` cleanup runs even when the oracle fails. The Actions oracle step no longer receives a separate provider key.

## Claim boundary and execution gates

1. **Pin provenance before interpreting a live result.** Confirm the 100%-serving staging Worker contains the reviewed v5 source and that the hosted CLI binary comes from the intended commit. A green result on an unknown deployment is not a source-attributed attestation.
2. **Do not claim hosted tie, three-page, or independent HMAC coverage from this run.** The live fixture deliberately has two distinguishable scores; tie and near-tie assertions in `58af96e` exercise the independent Python checker only. The operator observes Worker acceptance of one unmodified cursor, not tamper rejection or a known-answer MAC. The broader controlled fake-provider, replay, expiry, and three-page gates in the v5 design remain separate.
3. **Interpret success narrowly:** exact scores and deterministic two-page membership for this two-message, owner-scoped, nonmutating staging snapshot. It does not establish large-corpus completeness, all filter combinations, or that a future OpenRouter request would reproduce the same vector.

Hosted failure labels should drive a focused diagnosis rather than relaxing the oracle or replaying already passed SMTP/ZIP stages without new evidence.
