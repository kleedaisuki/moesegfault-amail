[Hosted CI run 36424923690](https://github.com/kleedaisuki/moesegfault-amail/actions/runs/36424923690) passed Worker native search-job contract tests, Wasm build, and bundler checks. **Deployed D1 search performance remains unmeasured**. ## Committed implementation checkpoint (static inspection, 2026-09-28)

Static inspection of the committed `crates/mail-worker/src/{lib.rs,search_jobs.rs}` and migration `0005_search_jobs.sql` shows the design is implemented in source; the hosted CI checks above validate contracts/build integration, **not workload latency, D1 row cost, or production memory behavior**. The fast path runs nonsemantic scans in memory and writes no `search_jobs` row when it completes; only continuation is durable. This matters because an earlier development version inserted/updated/deleted an indexed D1 job even for a normal newest-page `200`, adding several D1 round trips and writes to the dominant workflow. The current direct path performs a generation read, typically one 64-row D1 scan page for a default 20-result newest list, one bounded summary hydration query, and a final generation read. The body loader skips the chunk-table query when the first slice is shorter than 59,997 bytes, which is a sound consequence of the 60,000-byte UTF-8-aware split and avoids one D1 round trip per ordinary short body. These are **query-count deductions from code**, not measured latency improvements.

The implemented continuation is owner-scoped with a 24-hour job TTL and mutation-generation checks. Each `scan_batch` invocation stops before 400 D1 calls, 32 MiB of projected transfer, 64 MiB of reconstructed bodies, or 20 seconds elapsed and checkpoints its ordered marker plus bounded rank keys; the API returns `202` until exhaustive completion. Semantic search reserves a daily provider quota, embeds the query once into the job state, then scans all eligible candidates across polls. The current top-`K` structure is a bounded `Vec` with linear worst-hit replacement, **not a binary heap**; with `K <= 101`, this is `O(NK)` rank comparisons on top of `O(256N)` cosine arithmetic. Replace it with a heap only if deployed CPU profiling identifies rank selection as material. No hard 2,000/100,000 candidate cliff remains in this code path, but platform/job quotas and a no-progress `search_resource_limit` remain explicit failure modes.

The implementation uses semantic tie order `(score DESC, received_at DESC, id DESC)`, matching the current Worker comparator. The earlier [search/privacy research note](search-privacy-research.md) mentions ID ascending; that inconsistency must be reconciled in tests/docs before release, without silently changing established cursor order. The sections below retain the broader migration and benchmark rationale; where they describe a heap, that is an optional next optimization, not a claim about the current code.

## Target workload and contract

The user-visible task is agent retrieval of mail, normally the newest 20 summaries, sometimes a selective title/sender/time query, and less often an exhaustive body/regex/semantic query. The supported per-account archive budget is 1 GiB and an individual text projection may reach 25 MiB. It is therefore wrong to infer a small message count from the storage budget: a mailbox can contain very many small messages. The practical target is low-latency p95 for recent/filter-selective pages **without making results incorrect for large mailboxes**. The exact-match contract is all caller-owned, nondeleted deliveries satisfying every predicate; semantic ranking calculates exact cosine for every surviving indexed vector, not an ANN or prefix sample. A resource ceiling must return an explicit incomplete/error state, never a normal-looking partial page.

Representative CI/deployed fixture: accounts with 1k, 10k, 100k compact messages (where feasible within D1 budget); 20% read, 10 addresses, variable body length (mostly 0.5–10 KiB, some 60 KiB–1 MiB, a few up to the supported 25 MiB), 256-D normalized embeddings; newest-page, selective mailbox/time/read, 1%-selective title, 10%-selective body, pathological match-all regex, semantic-only and semantic+body workloads. Seed deterministically and isolate each run's account/database. A 100k fixture is a **scale probe**, not a new quota or an assumption that every CI run should pay to create it.

### Initial pre-rewrite baseline: causal bottlenecks, not guesses about its timings

Before the committed `search_jobs.rs` rewrite described above, `search()` in `lib.rs` obtained index-ordered D1 pages of 200 but appended all post-filter rows into a `Vec`. Its nonsemantic cursor was an **offset into that filtered vector**, so page 2 repeated the earlier scan/match work. Semantic search held up to `MAX_SCAN = 2000` rows and sorted them, yielding a hard product cliff despite an account budget that allowed many more messages. The scan limit of 100,000 was a second unrelated cliff. `SearchMatcher::test()` rebuilt every regex for every field of every candidate; case-insensitive literal matching lowercased the complete body for every term. `full_text()` performed one extra query per matching body candidate and fetched long chunks, which could dominate D1 subrequests and memory. The SQL used nullable `(? IS NULL OR column=?)` predicates, which could inhibit composite-index selection; this needs `EXPLAIN QUERY PLAN` confirmation before claiming an observed regression. No baseline timings were recorded. This paragraph records the motivation for the rewrite, **not the current implementation**.

## Platform bounds and consequence

As documented on 2026-09-28, D1 on Workers Paid permits 1,000 queries per Worker invocation (50 Free), at most 100 bound parameters per query, a 30 s maximum SQL query, and up to 2 MiB for one string/BLOB/table row. Workers have a 128 MiB isolate memory limit; Paid HTTP CPU defaults to 30 s, configurable to 5 min, and Free has 10 ms CPU. D1 bills rows read/written and reports `meta.rows_read`, `rows_written`, and duration. A 60,000-byte chunk layout requires about 417 chunk rows for one 25 MiB body. These are real mechanisms; **there is no honest unbounded synchronous full scan on Workers**. A streaming algorithm removes arbitrary *count* cliffs and controls memory, but an exact large search needs a continuation protocol if one invocation's resource budget is exceeded. Sources: [D1 limits](https://developers.cloudflare.com/d1/platform/limits/), [Workers limits](https://developers.cloudflare.com/workers/platform/limits/), [D1 pricing and query metadata](https://developers.cloudflare.com/d1/platform/pricing/).

| Workload | Synchronous plan | Bounded state | Worst-case honest behavior |
| --- | --- | --- | --- |
| Recent list or selective nonsemantic query | Keyset scan in time order until `limit+1` **matches** | One D1 page + `limit+1` summaries | Continue in a search job if byte/CPU/query budget is reached; never cut after 100k rows and call it complete. |
| Broad literal/regex query | Same keyset scan; projection only when necessary | One D1 page plus one body being checked | Continue from persisted scan marker; regex may force full 25 MiB body. |
| Semantic query | Scan **all** filter survivors; bounded top-`limit+1` heap ordered by score/time/ID | One D1 page + heap | Continue job until end; a page cannot be emitted before all survivors have been scored. |
| Later semantic pages | Re-scan all survivors but accept only ranks after the previous page's exact tuple | Same bounded heap | Higher read/CPU cost proportional to pages; materialize results only if measured repeated-page use justifies writes/storage. |

## Concrete migration path

### 1. Keyset rather than offset; push only sound filters into SQL

Canonicalize default values (`regex=false`, `case_sensitive=false`, `limit=20`) before hashing, not raw JSON spelling. Retain owner binding in every query. Use `after` inclusive and `before` exclusive. A lexical cursor should encode an opaque, integrity-protected version, canonical predicate hash, owner binding, sort tuple `(received_at, id)`, and a freshness marker. `received_at` is an integer millisecond and `id` is an opaque string; both descending, consistent with the existing index and response order. Apply `AND (received_at < ? OR (received_at = ? AND id < ?))`, then `ORDER BY received_at DESC,id DESC LIMIT ?`; consume pages until `limit+1` **matching** messages or true end of scan. Do not use SQL `OFFSET`. Return the final **returned match** as the next cursor, not the last scanned candidate; that avoids skipping matches already read ahead.

Build a few static SQL variants or an internal allowlisted query builder for provided mailbox/read/time predicates. Avoid the current `(? IS NULL OR ...)` shape when a filter is present. Candidate indexes to test, not create blindly: existing `(owner_iss,owner_sub,received_at DESC,id DESC)`; `(owner_iss,owner_sub,address,received_at DESC,id DESC)`; add read-state variants only if `EXPLAIN QUERY PLAN` and measured rows read justify their write/storage cost. `from`, `to`, `title`, regex and Unicode substring semantics stay in Rust unless an index can be proven a sound superset; SQL `LIKE` is neither a general Unicode case-folding contract nor suitable for >50-byte patterns on D1. Source: [Cloudflare D1 index guidance](https://developers.cloudflare.com/d1/best-practices/use-indexes/).

Example query shape for the mailbox+read variant (omit clauses rather than binding nullable ORs):

```sql
SELECT id,address,direction,sender,recipients_json,subject,body_text,
       metadata_json,received_at,is_read,has_html,has_text,attachment_count,
       r2_key,size_bytes,embedding_json
FROM messages
WHERE owner_iss=?1 AND owner_sub=?2 AND deleted_at IS NULL
  AND address=?3 AND is_read=?4
  AND received_at>=?5 AND received_at<?6
  AND (received_at<?7 OR (received_at=?7 AND id<?8))
ORDER BY received_at DESC,id DESC LIMIT ?9;
```

For a no-body, no-semantic search, do **not** load `body_text`, `embedding_json` or `r2_key` just to discard them; return compact candidate projection and fetch only fields needed for summaries. Use a 32–128 row D1 page size chosen by measured serialized response bytes, not 200 by habit. Preserve the existing `message_text_chunks(message_id,chunk_index)` primary key. Only if `body` is supplied should full text be read; batch bounded chunks by `(message_id,chunk_index)` rather than issuing one query for every chunk or returning many large bodies in one page. Keep each chunk response well below the isolate's 128 MiB; 16×60 KiB is about 1 MiB before JSON overhead. This is a bound to measure, not a promised safe constant for every runtime.

### 2. Compile matchers once and use bounded-memory top-k

Compile every regex once in `SearchMatcher::new` with a size/DFA budget and preserve a structured `invalid_pattern` error. Escaped literal patterns can use the same case-insensitive regex engine, avoiding repeated full-body lowercase copies; verify that the chosen Unicode folding semantics match the contract (notably Turkish `İ/i`, `ß`, accents and CJK). Metadata keys remain an allowlist and values are never concatenated into SQL. A regex that matches across chunk boundaries requires the full logical text or a provably equivalent streaming engine; per-chunk matching alone is incorrect.

For semantic search: validate query vector and stored vector model/dimension/input version, decode each eligible vector, calculate cosine with f64 accumulation (the existing `cosine_exact` already does the core arithmetic), and hold only `limit+1` `(score,received_at,id)` tuples in a min-heap whose root is the worst retained result. At end, sort this small heap by score descending, time descending, ID descending; fetch summaries for retained IDs. Persist score as its IEEE-754 bits (or a lossless serialization) in cursors; rounded decimal values can duplicate/skip near-ties. The next-page predicate is lexicographic **strictly after** `(score,time,id)`. Missing or corrupt vectors must fail with the current typed semantic errors, never silently disappear. Exact scoring is separate from semantic quality of the 256-D projection.

For fixed `K=limit+1`, search CPU is `O(N·256 + N log K)` over eligible vectors and heap memory `O(K)`. A later semantic page costs another exhaustive scan unless a materialized result set is chosen. JSON-encoded 256-D vectors are approximately kilobytes apiece, so a 100k-account full scan can transfer/parse hundreds of MiB *cumulatively* even though page memory stays bounded. A future 1,024-byte little-endian f32 BLOB representation would cut transfer and parser CPU, but requires an additive schema migration, versioned decoder, dual-read backfill and `EXPLAIN`/end-to-end measurements; do not silently change persisted representation or vector precision.

### 3. Continuation jobs instead of a disguised 10k cap

Fast path: try the bounded synchronous scan while monitoring D1 query count, bytes materialized, `performance.now()`/CPU proxy and elapsed time; stop **before** platform termination. On a budget boundary, persist an opaque search job scoped to `(issuer,sub)` with a short TTL: canonical filter hash, scan marker, account generation, page-after tuple, bounded top-k heap, examined rows/bytes, and `state=running`. Return HTTP `202` with `{job_id,state,request_id}`; CLI polls a job endpoint, whose authenticated calls each advance one bounded batch. The CLI still prints only final compact JSONL summaries on stdout and progress/diagnostics on stderr. Client-driven continuation is simplest and wholly Rust Worker-owned; a Queue/Workflow can be added later for detached progress without altering final results. An abandoned job expires; never persist body/query text or vectors in logs/telemetry. Search job storage necessarily includes the query/filter for continuation, so encrypt or keep it in account-scoped D1 data with strict TTL/access rather than pretending it is telemetry.

Do not return a semantic page while any candidate remains unscored. Persist the job checkpoint and heap atomically with respect to each advance (D1 batch/conditional version update); retrying a batch must be idempotent. `marker` is the last **examined** row, not the last match; write checkpoint only after all its body chunks and score are processed. Polls may race; guard with `UPDATE ... WHERE state='running' AND version=?`, and permit only one successful advance. Use `expires_at` and bounded periodic cleanup. A stateless cursor can be retained for small lexical pages, while long searches use a job transparently.

Freshness is a separate correctness issue. A hash binding owner and filters prevents cursor substitution but not concurrent message/read/index changes. A monotone per-account `search_generation` incremented on insert, delete, read-state update, full-text completion and embedding update can make the job fail/restart with `cursor_stale` if it changed during or between scans. Check generation at job start **and after completion**; if it changed, do not publish exact results. An optimistic generation check still has a tiny post-check race; define results as of the validated generation and require later page cursors to revalidate it. The current writes store chunks before inserting the message, which helps avoid exposing incomplete text; ensure future code preserves that ordering. If maintaining a generation is out of scope, explicitly document *live pagination* rather than promising a stable snapshot. A time high-watermark alone cannot freeze read/delete/embedding changes or same-millisecond inserts.

The schema/API additions are additive: `search_jobs` table, optional `search_generation` table/triggers or conditional increments, and `GET /v1/messages/search/jobs/{id}` for polling. Existing `POST /v1/messages/search` can still return `200` for quick searches; `202` is a new result, so CLI and API must be deployed compatibly. Do not change existing IDs or response field meaning. A new `v2` cursor prefix is preferable to interpreting existing offset cursors as keyset markers; reject old cursors with a clear typed error or support them during an announced transition. Because v0.1 has no established external users yet, deploy CLI+Worker together, but never silently misread an old cursor.

### 4. Optional substring prefilter, not a correctness shortcut

D1 supports SQLite FTS5, including trigram tokenizer. A trigram index can help frequent >=3-Unicode-character literal body/title patterns, but it incurs storage/write costs and does not accelerate 1–2 character CJK terms or all regex. SQLite's `LIKE`/`GLOB` trigram behavior depends on tokenizer case settings; use it only to select a **sound superset**, then apply the exact Rust matcher. Build separate test oracle before adoption; use `EXPLAIN QUERY PLAN` and rows-read/rows-written to show net improvement. Do not index every 25 MiB body without measuring database growth against D1's 10 GiB database and account storage budget. Sources: [D1 supported SQL extensions](https://developers.cloudflare.com/d1/sql-api/sql-statements/), [SQLite FTS5 trigram specification](https://www.sqlite.org/fts5.html), [D1 index guidance](https://developers.cloudflare.com/d1/best-practices/use-indexes/).

## Fair verification and stop/go criteria

Run toolchain builds, host-platform tests and large fixture generation in GitHub Actions, not on Klee's development machine. Use a small pure Rust/SQLite oracle test with deterministic seeded messages for every predicate combination, compare exact ordered IDs and every page against the implementation; then run deployed D1/Worker probes with a separately allocated test account. Include same-time ID ties, insert/delete/read/index update between pages, Unicode and null-byte literals, regex crossing chunk boundaries, large 25 MiB text, corrupt/missing 256-D vector, cursor tampering, expired job, concurrent polls, and empty/limit=100. Assert nonsemantic search does **not** call OpenRouter or load vectors. Assert semantic search embeds query once per completed job (not once per poll).

Measure p50/p95/p99 total CLI-to-result latency and per-poll latency, D1 rows read/written and query count, CPU time, Worker peak memory/1102 failures, bytes returned from D1, OpenRouter query latency/cost, and job completion/expiry rate. Use at least 30 randomized-order repetitions for small fixed fixtures after warm-up and report median plus bootstrap 95% confidence intervals; for expensive 100k jobs, use several runs and report all raw observations rather than a misleading narrow CI. Compare baseline and candidate on the same deployed environment and fixture, with logs/trace sampling held fixed; diagnostic instrumentation and production-like timing are separate runs. Avoid speculative target thresholds: choose the fast-path budget from actual p95 resource headroom and classify any path as not shippable if it can return incomplete results with HTTP 200. Cache and D1 placement can change wall time; record colo/region and deployment SHA. D1 metadata and Cloudflare traces provide rows/cost/CPU evidence; they do not supply a memory peak directly, so use platform failures plus controlled batch-size probes as a bound.

Decision rule: prioritize removing the correctness cliffs, offset replay, regex recompilation and unnecessary projection immediately because they reduce cost without a new semantic trade-off. Add continuation before advertising exact search over large mailboxes; if jobs are deferred, expose the measured supported bounds and typed error honestly. Add FTS or binary vectors only when deployed measurements show the read/CPU savings exceed migration, storage and write complexity.
