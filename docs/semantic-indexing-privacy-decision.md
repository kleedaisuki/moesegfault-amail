# Semantic indexing: transfer boundary and release decision (2026-09-29)

Status: **Product choice made: automatic indexing with conspicuous disclosure. P0 implementation/release gate remains.** The owner explicitly chose automatic indexing to keep later semantic searches fast. This is an architecture decision, not a deployed change or a claim that prior provider transfers can be undone. Do not release the current site text and Worker together. No live provider call was made for this review.

## Observed contract and failure

- `site/src/pages/manual.md` says that not using `--semantic` avoids sending mail content to a third-party model provider. `.agents/skills/amail/SKILL.md` and `docs/architecture.md` similarly associate the content transfer with semantic search.
- In fact, `crates/mail-worker/wrangler.toml` schedules the API Worker every five minutes; its `scheduled()` handler calls `reindex()` without user/account opt-in. That SQL selects the first 20 **all-owner** active messages lacking `embedding_json`, and `platform::embed(..., "search_document")` sends their subject plus stored first body-text segment to OpenRouter. This happens whether anyone has invoked semantic search. Both inbound and outbound messages enter D1 with a NULL embedding. It is not telemetry; `AMAIL_TELEMETRY=off` cannot stop it. The ZDR/no-collection/cache controls in `platform.rs` reduce retention risk but **do not prevent transfer** to OpenRouter and an upstream provider. [OpenRouter ZDR explanation](https://openrouter.ai/blog/insights/zero-data-retention/), [response-cache limitation](https://openrouter.ai/docs/guides/features/response-caching).
- The old `source.get(..source.len().min(12_000)).unwrap_or(&source)` had a separate correctness fault: if byte 12,000 splits a UTF-8 scalar, it passes the full source instead of a bounded prefix. A source longer than 12,000 bytes is then rejected locally by `platform::embed` and retried on each Cron run. Since SQL always selects the oldest 20 null vectors, 20 such rows can starve all later indexing and make semantic search fail `semantic_index_incomplete`. This is **not** a provider oversize disclosure in the present code, because the size check precedes Fetch. Root reports that the narrow safe-boundary fix was committed as `a7d679f`; hosted tests and deployment remain separate evidence gates.
- Search already has a useful safety property: an eligible message with no vector returns typed `semantic_index_incomplete`, not a falsely complete ranked result. Exact cosine applies to stored vectors, not to a message section omitted by the 12 KB input projection. `message_text_chunks` preserve full literal-body search separately.

## Product choice, not an invisible implementation detail

| Choice | Privacy contract | First semantic search | Background/cost behavior | Compatibility and risk |
| --- | --- | --- | --- | --- |
| **A. Automatic indexing (selected)** | Every accepted inbound/sent mail may have bounded subject/body text sent to OpenRouter shortly after storage, even without `--semantic`. State this before login/address registration and in the manual/skill; do not say avoidance of the flag prevents transfer. | Usually fast if indexing caught up; typed incomplete while lagging. | Provider use for users who never search semantically; needs durable retries/fairness and an index-lag SLO. | Meets the owner's latency preference and original server-side semantic requirement, but has the broadest third-party processing scope. The disclosure is part of the product contract. |
| B. Explicit-command, on-demand indexing (rejected for this release) | Only an explicit `--semantic` sends selected mail/query. | First query may require a corpus-scale durable preparation job. | No provider work for never-semantic users. | Best data minimization but high, variable first-query latency; not the owner's chosen product. |
| C. Account-level persistent opt-in (rejected for this release) | First `--semantic` enables future automatic indexing for that account. | Backfill before complete results. | Avoids work for never-semantic accounts. | Extra consent/revocation state and agent-first UX complexity; first use would silently change future processing unless explained prominently. |

Decision: **A**. The semantic model is a service-level processing feature, not a side effect of a particular search command. This can be a coherent product, but only if the first-use documentation says so plainly. Do not add a misleading consent toggle whose server-side mail acceptance path ignores it. The UK's ICO privacy-by-default guidance is a useful engineering signal, not a legal determination for this service: default processing should be appropriate to the purpose and risk, and it does not mechanically require every feature to be off. [ICO guidance](https://ico.org.uk/for-organisations/uk-gdpr-guidance-and-resources/accountability-and-governance/data-protection-by-design-and-by-default/).

## Selected A: precise transfer contract

The data owner remains `(owner_iss, owner_sub)` in D1. A message vector is a **derived, reusable projection** of that owner's normalized message, with model/dimension/input-version metadata. The background worker sees **all owners'** pending rows, not only accounts whose agents have requested semantic search. It is not a user-specific consent state. The search job separately sends the user's `--semantic` query to the same provider and stores its query vector in restricted TTL-bound D1 state. Preserve existing `POST /v1/messages/search` `200`/`202`, `GET /v1/messages/search/jobs/{id}`, CLI syntax, and exact score/time/ID ordering.

**Exact document payload today:** For each accepted inbound or indexed outbound message, use D1 `messages.subject`, then one literal newline, then D1 `messages.body_text`. `body_text` is the first UTF-8-safe up-to-60,000-byte segment of the normalized body; inbound prefers the first non-attachment `text/plain` part, otherwise converts sanitized HTML to text, and outbound uses the compiled draft's text projection. Send the **longest valid UTF-8 prefix of at most 12,000 bytes of that combined string** as one `search_document` embedding input. This may be the whole short text; a long subject can consume most or all of the byte budget and leave little/no body. The present implementation sends no explicit sender, recipient, address, metadata JSON, full MIME, ZIP, HTML markup, later body chunks or attachment bytes to the embedding endpoint. Such data can nevertheless occur *inside* an authored subject/body, so do not promise semantic redaction of personal information. `--semantic` query text is a separate provider input capped by the same 12,000-byte `platform::embed` contract. The 12,000 limit is **bytes, not characters or tokens**. Full literal-body search and downloadable archives retain their existing independent storage semantics.

**Timing today:** A message is accepted/persisted with a NULL vector; the scheduled API Worker runs `*/5 * * * *` in UTC and attempts at most 20 oldest pending rows per invocation. Thus provider transfer can occur without any search command, not necessarily immediately on receipt. Cron is not a five-minute indexing SLA: scheduling, backlog, provider failure and poison-row retries can delay it. The next semantic query can return typed `semantic_index_incomplete` while eligible rows are pending; it must never silently omit them. [Cloudflare Cron Trigger semantics](https://developers.cloudflare.com/workers/configuration/cron-triggers/).

**Recommended durable automatic path:** Keep the existing Cron as a recovery sweep, but make D1 the authoritative work ledger and, if the measured five-minute latency is unacceptable, use an opaque-ID Cloudflare Queue notification after the message transaction as a low-latency wake-up. Queue messages contain only message ID (and a version), not content; the D1 row is the source of truth. D1 `AFTER INSERT` creates work atomically with message insertion, including outbound reconciliation inserts; soft-delete cancels eligibility. A failed Queue publish does not lose the D1 work, because Cron rediscovers it. The consumer claims a short lease by conditional D1 update, reads one still-active message, calls OpenRouter, and conditionally stores a validated vector only if the row remains active and at the expected input version. Queue delivery is at least once, so idempotent claims/writes are mandatory. Do not use `waitUntil()` as the sole durability mechanism: it has a bounded post-response lifetime. [Cloudflare Queues delivery guarantees](https://developers.cloudflare.com/queues/reference/delivery-guarantees/), [Worker context/waitUntil](https://developers.cloudflare.com/workers/runtime-apis/context/).

An additive `embedding_work(message_id PRIMARY KEY, next_attempt_at, attempts, lease_until, state, fixed_error_code, input_version)` table is enough to express pending/leased/backoff/quarantined work; do not duplicate subject/body there. Old NULL-vector rows are backfilled once by migration or a bounded operator job. `embedding_input_version` and `embedding_truncated` on `messages` make representation changes visible without changing existing API fields. Existing vectors that already used the same valid prefix may be marked version 1 without re-upload; malformed/unknown vectors are retried or quarantined, not silently compared. Search must reject missing/model/dimension/version-incompatible vectors with a typed incomplete/corrupt state instead of mixing spaces. A future projection change requires a versioned backfill and either a safe dual-read transition or explicit semantic-unavailable window; literal search remains available.

**Fairness and failure:** The current global `ORDER BY received_at LIMIT 20` can be monopolized by one account or by permanently bad rows. Select due work with a small per-owner cap (for example four) and a global cap (initially 20) using an owner-partitioned due-order query; validate actual D1 cost before adopting the SQL shape. Transient timeout/429/5xx gets bounded exponential backoff with jitter (for example 5 minutes, 15 minutes, 1 hour, 6 hours, then at most one day). Deterministic invalid input or repeated malformed 256-D response becomes `quarantined` after a bounded number of attempts, with a fixed error code and operator alert. A provider-wide 401/403 or no eligible ZDR route should trip a global dependency backoff, not retry once per message and consume the corpus. Quarantined rows remain semantically **incomplete**, not secretly omitted; the agent may still use ordinary search. Publish lag, due, leased, retry and quarantined counts by bounded buckets, without addresses, subjects, text, vectors or raw provider errors. Use an account/global provider budget so one abusive account cannot exhaust the shared route. The exact cap/backoff values are initial controls to tune from hosted measurements, not claims of a proven throughput target.

**Retention boundary:** `provider: {"zdr": true, "data_collection": "deny"}` and `X-OpenRouter-Cache: false` are already set in `platform.rs`; keep them, and verify on the actual Qwen route that a provider remains eligible and returns 256 finite normalized coordinates. The payload still reaches OpenRouter and its chosen upstream for processing. ZDR is a provider-retention policy, not local inference, end-to-end erasure, or a guarantee about our own D1/Cloudflare copies. OpenRouter says per-request ZDR does not disable its response cache, hence the explicit cache header (account-level ZDR is an additional defense). Do not log provider request bodies or raw errors. [OpenRouter ZDR](https://openrouter.ai/blog/insights/zero-data-retention/), [provider controls](https://openrouter.ai/docs/guides/get-started/sovereign-ai), [cache behavior](https://openrouter.ai/docs/guides/features/response-caching).

**Interaction example.** An agent registers an address, receives mail, and only uses literal search. Its accepted mail is nevertheless automatically selected for bounded embedding at the next successful background opportunity; later semantic searches reuse stored vectors and send their query. If the provider is unavailable, the message remains searchable literally, while semantic search reports a typed incomplete/dependency state until recovery. Deleting a message before it is claimed prevents a new embedding call for that message; deletion after a call cannot undo the prior transfer.

## Immediate containment, migration and verification

**Immediate release block:** do not let the current misleading manual claim go live. The bounded UTF-8 prefix fix should use `end = min(input.len(), 12_000); while !input.is_char_boundary(end) { end -= 1; } &input[..end]` (at most three bytes of retreat for valid UTF-8), not `unwrap_or(full_source)`. Test ASCII exactly/over 12,000 bytes and CJK/emoji straddling that boundary; assert provider input length <=12,000, valid UTF-8 and deterministic prefix, with no starvation across 20+ messages. The reported narrow fix `a7d679f` needs the normal hosted CI/deployed evidence, not another local heavy test.

**Deployment order:** first change home/first-use/CLI help, manual and both skill copies so the automatic transfer is unambiguous, or disable auto-indexing while any public page still carries the false promise. Then deploy the Worker retry/fairness schema and code to staging, test on synthetic mail, and deploy the matching public page/Worker together for production. Existing vectors stay readable if representation/version matches, avoiding wasteful re-upload; they are not evidence of user consent. Existing search jobs can continue only if their vectors and checkpoint semantics remain compatible; otherwise fail/restart them with a typed stale error. Staging may already have auto-indexed synthetic mail: record counts/policy version in restricted operator evidence, never claim the historical transfer can be reversed. No production external-user contract exists yet, but future changes preserve the public `--semantic` command and stable errors.

**Public wording:** "amail automatically sends up to 12,000 UTF-8 bytes of each accepted mail's subject plus body-text projection to OpenRouter and a selected embedding provider for semantic indexing, whether or not you run semantic search. Plain-text parts are preferred; HTML-only mail is converted to text. Raw MIME, ZIP and attachments are not intentionally sent to the embedding API. Semantic queries themselves are also sent when you use `--semantic`. `AMAIL_TELEMETRY=off` affects diagnostics only." Put a concise version beside the home-page semantic feature, in first-use/login help, manual privacy section, and skill. Ordinary lexical search itself does not send a new query to OpenRouter; it also does not prevent the independent background indexing of mail.

**Release tests (hosted CI plus controlled staging, no customer data):** fake the provider and count calls for zero semantic commands (automatic calls **must still occur** after mail acceptance), ordinary search, newly delivered inbound/outbound messages, deleted-before-claim messages, and `AMAIL_TELEMETRY=off` (no effect on embeddings). Assert exact input composition and <=12,000 UTF-8 bytes; raw MIME, HTML markup, ZIP and attachment canaries must not appear in the provider payload, while subject/body canaries do. Exercise 20+ long CJK/emoji messages, one permanently invalid row before valid rows, provider 429/5xx and malformed vector responses, concurrent consumers/leases, per-owner fairness, poison-row quarantine, duplicate Queue delivery, lost Queue notification recovered by Cron, deletion during provider call, 256-D shape and exact ranking against an independent oracle. A staging canary should verify observable request *counts and bounded sizes only*; do not persist canary subject/body in CI logs. Treat a successful embedding shape probe as insufficient evidence that the disclosure and retry policy are respected.

## Why not a cleverer shortcut?

Exact cosine scoring cannot repair a missing or badly truncated representation. Long-document retrieval work shows that fixed-size chunking can lose relevant context; it motivates a later held-out email retrieval study, not an untested change to multi-vector storage at the privacy boundary. [EMNLP Findings 2024 long-document study](https://aclanthology.org/2024.findings-emnlp.150/). Do not solve the transfer-contract conflict by merely renaming Cron work "telemetry", by adding an opt-out env var that the server cannot see for incoming mail, or by returning only ranked indexed items. The design must make **who authorized third-party processing of which mail, when** answerable from the actual state transition and command path.
