# Semantic query-vector stability: evidence and design boundary (2026-09-30)

## Decision

Do not equate a repeat `qwen/qwen3-embedding-8b`, 256-dimensional OpenRouter query with the vector used by an earlier request, even when text, model slug, dimensions and `search_query` match. If the observed guarded run [36699356379](https://github.com/kleedaisuki/moesegfault-amail/actions/runs/36699356379) reports differing normalized IEEE-754 `f32` coordinates, that is evidence of **cross-request output variation**, not evidence of a particular provider switch, weight update, nondeterministic GPU kernel, quantization path, input preprocessing difference, or serialization bug. Assigning a mechanism needs request/provider trace or a controlled route-specific reproduction; neither is established here. No live calls or local tests were made for this note.

For the existing exact-score/pagination contract, keep the v4 cursor's bitwise vector commitment and typed 409 on drift. For seamless continuation despite empirically frequent drift, reuse the **actual first-page vector** from owner-scoped, expiring server state rather than relaxing the commitment to a numeric tolerance. A tolerance is useful for approximate scientific comparisons or diagnostic score error, not for claiming that a cursor boundary belongs to the same ranking function. This extends the [exact-cosine oracle design](staging-exact-cosine-oracle.md) and [v4 review](review-semantic-cursor-v4.md), not a claim that run 36699356379 passed exact cosine.

The Qwen3 model literature concerns representation quality and variable output dimensions, not an API-level guarantee of repeated bit-identical inference. It cannot diagnose this live observation. Provider routing, floating-point implementation differences, model deployment changes, and preprocessing are hypotheses to discriminate later, not findings.

## Why tolerance cannot repair an exact cursor

For unit-normalized query vectors `q,q'` and a unit document `d`, Cauchy–Schwarz gives `|q·d - q'·d| <= ||q-q'||_2`. For two documents, their score gap can change by at most `2||q-q'||_2`. This gives a *sufficient* stability certificate only if the original gap around every relevant page boundary is strictly larger than that bound and no exact tie or other state change intervenes. A generic coordinate/score tolerance does not establish such a global margin, especially when the database has not been scanned yet.

A two-dimensional counterexample embeds into 256 dimensions by appending zeros: let `q+ = (sqrt(1-e²),e)`, `q- = (sqrt(1-e²),-e)`, and documents `d+ = (sqrt(1-a²),a)`, `d- = (sqrt(1-a²),-a)` for positive small `e,a`. The query vectors are only `2e` apart in L2, but `q+` ranks `d+` above `d-` by `2ea`, while `q-` reverses the order by the same margin. Both differences can be arbitrarily small. With page size one, a page-1 boundary scored under `q+` cannot be safely applied to a page-2 scan under `q-`: skip or duplication is possible despite a tolerance pass. `f32`-representable nearby values suffice for practical near-ties; rounding changes the exact threshold, not the argument.

Thus distinguish (a) a `1e-5`-type *score assertion tolerance* for a known fixed vector, accounting for arithmetic/serialization, from (b) *vector identity* needed to bind exact pagination. Different vectors may produce practically indistinguishable scores on a particular two-mail fixture, but that is not a universal exact-pagination contract. Conversely, a one-bit vector difference may be immaterial to most result sets yet still correctly triggers the current fail-closed 409.

## Practical options and next discriminator

| Option | Exact continuation | Cost / compatibility |
| --- | --- | --- |
| Current v4 bit commitment + restart on 409 | Yes for pages accepted under identical `f32` vector; drift becomes visible failure rather than silent mixing. | Another provider call per page; repeated 409 hurts usability. Preserve the actionable error and never auto-append a restarted first page. |
| Numeric-tolerance commitment/acceptance | No unconditional guarantee; needs a full boundary-margin certificate and still changes exact scores. | Small code change but weakens the contract invisibly. Do not ship as an exactness fix. |
| Reuse first-page vector via opaque, owner-scoped server cursor state | Yes, if every page and resumed batch scores against those same bytes, with generation/filter/model/version checks. | New state lifecycle, TTL/GC, quota, privacy and rollout/migration work; avoids repeated embedding calls. Cloudflare D1 limits are not the blocker at 1,024 raw vector bytes, but aggregate state and lifecycle need measurement. |

First decide whether the observed drift is operationally frequent enough to justify state: record privacy-safe counts of `search_cursor_vector_changed` by model/configuration and cursor page (no vector, query, digest, raw cursor or provider response in telemetry). If the failure rate is material, prototype server-owned vector reuse under synthetic staging load, measure D1 reads/writes/storage/expiry and continuation success, then migrate with versioned cursors. To investigate mechanism separately, compare repeated requests under a pinned provider *only if the gateway documents and verifies that restriction for this endpoint*, record provider/route identity in a restricted ephemeral diagnostic, and compare raw response versus normalized `f32` bits without retaining customer text or vectors. Such a probe may narrow the cause; it is not required to choose the exact-pagination invariant.
