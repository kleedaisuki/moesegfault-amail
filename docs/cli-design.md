# amail CLI design and verification notes

Status: implementation record for `crates/amail` (2026-09-28). This complements `docs/architecture.md`, which owns the shared HTTP and ZIP contract.

## User and trust boundaries

The CLI is a native public OIDC client. It obtains a human authorization only through the system browser; subsequent address and mail operations run without prompts. The fixed production issuer is `https://identity.moesegfault.dev`, not the Login SPA. Discovery must return JSON with the exact configured issuer and S256 PKCE. The conventional production public client ID is `amail-cli`, matching the reviewed registration manifest; this is not a secret and can be overridden for staging. **A manifest is not proof of registration:** the Identity deployment must register it before login can succeed. The default loopback URI template is `http://127.0.0.1/callback`; login binds port zero, then sends the selected port in the exact authorization and token requests. This requires the reviewed native `native_loopback_any_port` registration in `infra/identity/client-production.json` or its staging peer. If registration is absent, login fails rather than inventing or weakening the identity contract.

Each login generates independent random PKCE verifier, state, and nonce. Authorization response `state` and `iss` are mandatory; the ID token must have a pinned RS256 signature from issuer JWKS, exact issuer and audience, valid expiration, `token_use=id`, and the stored nonce. The only user key is `(issuer, sub)`; the CLI does not print or persist `sub` in SQLite. Access and rotating refresh tokens are JSON in the platform credential store via `keyring`, never in TOML or the telemetry DB. An OS file lock serializes token mutation across CLI processes, while a committed SQLite `in_progress` marker survives a crash between remote refresh and keyring replacement; the next invocation discards the potentially consumed family rather than replaying its predecessor. Login resets the marker only after replacing the credential. Logout attempts remote refresh-token revocation, then removes local credentials regardless of network result. Identity SSO logout is not claimed by the CLI.

## Command and output contract

Commands implemented: `auth login|status|logout`, short `login|logout`, `address list|add|delete`, `sync`, `search`, `get`, `read`, `mark`, `delete`, `pack`, `unpack`, `send`, `config`. `get` returns metadata only; `read -o` downloads ZIP and optionally `--unpack`s into a new directory. Neither changes read state. `mark --read|--unread` is the only read-state mutation. `sync --all` follows pagination until no cursor remains; repeated cursors fail rather than looping forever. `search` sends all supplied predicates in one request for server-side AND semantics and exact-cosine semantic search; the CLI neither embeds mail nor approximates scores locally.

Default stdout is one compact JSON object per line for list/search results, with a separate compact continuation-cursor object if present. A single-object command prints one compact JSON line. Human-readable address/message tables and detailed metadata labels are opt-in with global `--human`; detailed `get` output preserves every returned metadata field rather than silently dropping less common fields. Untrusted control characters are escaped before human terminal output, and ANSI-colored table headings appear only on TTYs without `NO_COLOR`. Errors go to stderr. Content is never rendered as a terminal view. The agent must treat received mail content as untrusted input and operate on ZIP-extracted text/HTML at a specified path.

## ZIP and MIME boundary

`pack` recursively packages a draft directory with the Rust `zip` library, independent of a system `zip` executable. A HTML-only draft gains a `body.txt` fallback using `html2text`; the server remains the authoritative HTML sanitizer and MIME compiler. Outbound validation rejects unknown manifest fields (including inbound read-only metadata), traversal and duplicate paths, symlinks, undeclared assets, unsupported compression, missing UTF-8 bodies, excess recipients/assets, header newlines, and oversized compressed/decompressed content. It reads every entry to catch corrupt or encrypted content before sending. Outbound ZIP is capped at 5 MiB compressed/12 MiB expanded; inbound `unpack` permits 25 MiB compressed/50 MiB expanded to match the raw-MIME ingress envelope, while still writing only to a new directory. The server revalidates every byte because a CLI check cannot be a trust boundary.

`send` preserves an idempotency key across ambiguous retries of identical ZIP bytes in a local SQLite table. Keys are UUIDs, as required by the Worker. After a definitive accepted response, the key is removed so a later intentional send of the same message is possible. `--idempotency-key` lets an agent supply its own stable UUID retry key. An accepted provider submission is not delivery confirmation. ZIP writes and extraction publish via private sibling temp artifacts only after complete write and `sync_all`; an existing `sync --out-dir` archive is re-fetched and byte-compared, with mismatches reported as conflicts instead of silently treated as complete.

## Privacy and operations

SQLite is an operation journal, not a mail cache: operation category, HTTP status, duration, power-of-two response-size bucket, trace ID, and optional opaque correlation ID only. No subject, address, body, archive path, search query, token, or vector enters telemetry. Address deletion sends the full address in a JSON request body to fixed `DELETE /v1/addresses`, not in the URL where Cloudflare automatic invocation logs and trace spans would reveal it. `AMAIL_TELEMETRY=off` disables recording and upload. Normal commands only persist a row and launch a hidden detached uploader at most once per 30 seconds; telemetry network failure cannot delay the mail result. The uploader batches at most 20 events and posts to `/v1/telemetry`; each mail API request propagates W3C `traceparent`.

## Evidence and limits

`cargo generate-lockfile` and `cargo metadata --no-deps --format-version 1` succeeded on 2026-09-28; local compile/tests were deliberately not run per the project requirement to use GitHub Actions for toolchain-heavy tests. [GitHub Actions run 36416399407](https://github.com/kleedaisuki/moesegfault-amail/actions/runs/36416399407) at commit `24082964` passed CLI jobs on Windows, macOS, and Ubuntu; Ubuntu reported 5/5 unit tests passing and `amail --help` succeeded. The first CI attempt exposed a native `libdbus-sys` build dependency; the CLI moved to keyring v3's pure-Rust zbus Secret Service backend (`async-secret-service`, `async-io`, `crypto-rust`) rather than imposing a system development package on installation. The live issuer discovery was fetched on 2026-09-28 and advertised S256 PKCE, authorization-response issuer, refresh and revocation endpoints, and RS256 ID tokens. These are deployed capabilities, not proof of native-client registration. An actual deployed login/send/receive/search lifecycle remains a release gate.
