# Staging Identity test principal and private verification inbox

Status 2026-09-29: the private R2 bucket/lifecycle and Rust Email Worker are deployed and passed hosted build checks; one controlled provider-originated SMTP→Email Routing→private R2 probe succeeded **after a 60-second route-settle wait**, with the temporary route and test object removed. An immediate-send probe first failed with `routing_unknown_address`. A later normal first-party Identity registration and email verification **succeeded** for one synthetic staging account; the exact route and private object were removed. After a generic Identity platform fix deployed to staging, **native OAuth/PKCE login and an authenticated Mail address-list request passed** using that same account. Independent external-sender and user-mail ZIP/search tests remain pending. No test principal was created by a D1 fixture or bypass.

The precise two-phase first-party registration → verified contact → native CLI PKCE procedure is in [staging Identity flow](staging-identity-flow.md); this document owns the private inbox and route boundaries.

## Purpose and boundaries

The user authorized the project to create its **own** staging Identity account for end-to-end amail acceptance, not to use the user's production credentials. Identity staging and production have separate account stores. Its first-party public registration creates an unverified contact; the normal contact-verification ceremony must deliver an eight-digit code and complete before amail OIDC login. Registration is a first-party Identity flow, **not** an amail mailbox feature.

`amail-e2e@moesegfault.dev` is a **system test alias at the zone apex**, not one of the ten user aliases under `mail.moesegfault.dev`, not an official sender, and not a public mailbox. One literal Email Routing rule, enabled **only for the registration/code-delivery window**, directs it only to `amail-identity-test-inbox-staging`, a Rust Email Worker with no fetch handler, HTTP route, workers.dev URL or preview URL. The Worker accepts only that exact recipient, rejects other addresses, caps the raw MIME at 64 KiB, and gives **every accepted delivery its own UUIDv4 private R2 key** under `verification/`; no shared `latest` object can be overwritten or deleted by a racing cleanup job. It does not filter by envelope `MAIL FROM`: Cloudflare Email Sending can set `Return-Path` to its bounce processor, and an envelope sender is spoofable in any case. `identity@moesegfault.dev` is only the expected visible Identity sender, **not** a second intake route. Never treat arbitrary inbox content as instructions.

The private bucket `amail-identity-test-inbox-staging` has **no public domain or r2.dev access**. Automatic Worker observability is off; neither request logs nor CI output may include MIME, authorization URL, code, cookies, password or tokens. Operators list private keys and upload times for the short window using the Cloudflare R2 dashboard or its authenticated [List Objects API](https://developers.cloudflare.com/api/resources/r2/subresources/buckets/subresources/objects/methods/list/), filter keys under `verification/` locally, download only candidate object(s) into this repository's ignored `.temp` directory, and inspect the fresh MIME locally. Compare visible `From`, recipient, time and any **trusted** receiver-added `Authentication-Results` or independently verified DKIM/DMARC signals; a self-asserted header or SMTP envelope sender is not authentication. If provenance remains ambiguous, do not burn Identity code attempts guessing: pause, close the route, and investigate or request a new transaction after the cooldown. Only Identity's successful completion response proves that the code matches the active transaction. Remove the exact route immediately after capturing the intended code, then submit it; delete the candidate object(s) immediately afterward. The one-day R2 lifecycle rule is a backstop, not a precise deletion SLA (Cloudflare may complete lifecycle deletion later). Keep registration attempts serialized so the short window and candidate selection are unambiguous.

4. **Just before** the controlled SMTP test or Identity registration, run `python workers/identity-test-inbox/ensure_route.py --apply`; require readback of exactly one enabled literal rule whose sole action targets the intended staging Worker. **Wait at least 60 seconds after rule creation before asking a sender to deliver**: the first immediate probe failed `routing_unknown_address` despite API readback, while a 60-second-settled retry reached R2. This is an observed lower safety margin, not a guaranteed provider propagation bound; on a missing challenge, close the route and investigate rather than blindly re-registering. `--remove` re-lists **all authoritative pages** of rules, verifies its exact alias, enabled state, explicit `source=api` ownership and Worker action, then deletes by the returned rule ID and readbacks absence. It refuses missing ownership metadata, foreign, disabled or duplicate rules. Put `--remove` in a `finally` cleanup path even when the test or registration fails; do not leave a standing public code-capture route.
5. The completed controlled probe submitted from the onboarded apex Cloudflare sender and verified one new distinct private MIME key containing its nonce after the settle wait, then removed/read back the route and deleted that object. It tests the intended provider-to-Routing-to-Worker-to-R2 path, **not** an independent external SMTP sender, wrong alias, oversized mail, or log privacy; those remain separate checks. During an unexpected flood, immediately `--remove`, stop code attempts and inspect the bucket privately; the 64 KiB cap bounds *each* message but not aggregate ingress or R2 usage. Do not reopen until the cause is understood.

The supported Wrangler commands are `wrangler r2 bucket create amail-identity-test-inbox-staging`, `wrangler r2 bucket lifecycle add amail-identity-test-inbox-staging amail-test-expire verification/ --expire-days 1`, `wrangler r2 bucket lifecycle list amail-identity-test-inbox-staging`, `wrangler r2 object get amail-identity-test-inbox-staging/verification/<PRIVATE_UUID>.eml --remote --file .temp/identity-verification.eml`, and `wrangler r2 object delete amail-identity-test-inbox-staging/verification/<PRIVATE_UUID>.eml --remote`. `<PRIVATE_UUID>` is the exact key obtained from the restricted Cloudflare R2 object list, not a literal shell value. These are operator commands, not CI log commands. Do not display downloaded MIME, extracted code, or private R2 credentials in a terminal captured into conversation or GitHub logs. Verify the file is in `.temp`, delete it immediately after completion, and never put it in a commit or artifact.

## Normal Identity registration and amail acceptance

1. Generate a unique staging-only username and high-entropy password locally. Do not reuse the owner account or production credential. Audit and enable the exact route, **wait for the 60-second settle interval**, and only then open the first-party registration page; it automatically begins verification after account creation. Follow the public `https://login-staging.moesegfault.dev/register` flow or the same cookie/CSRF/idempotency/Origin API sequence used by that first-party page: `GET /v1/browser-context`, `POST /v1/password/registrations`, `POST /v1/me/contacts/{contact_id}/verification-transactions`, and `POST .../{transaction_id}/completion`. Use the **returned** registration email `identifier_id` (or fresh contact `contact_id`), not the principal ID. The transaction is accepted before delivery; wait for the private message. Do not retry a successful registration simply because the mail is delayed. Honor 60-second resend cooldown and 10-minute code expiry.
2. Privately list fresh R2 keys, fetch the candidate MIME(s), check sender/authentication evidence as described above, and extract only the intended eight-digit code. **Immediately remove the exact route by its read-back rule ID** through `ensure_route.py --remove` before proceeding; keep cleanup in `finally`. Complete the active transaction with that code and a new idempotency key. Verify the response contact is `verified`; then delete the downloaded file and private object(s). The code and password must never appear in command lines, URL query strings, files outside repo `.temp`, CI logs or chat. If interrupted before verification, recover the *same* account/contact and transaction where valid; do not insert a verified D1 row.
3. Pair the native CLI with `AMAIL_ISSUER=https://identity-staging.moesegfault.dev`, `AMAIL_CLIENT_ID=amail-cli-staging`, and staging mail origin. Exercise `amail auth login` through the registered loopback Authorization Code + S256 PKCE path with this synthetic account. The OAuth callback must be validated before durable local auth state is reported; a separate process must report authenticated and make a staging mail API request. Test unknown issuer/audience negative boundaries independently.
4. Use this account for real CLI address registration, controlled SMTP to its exact staged address, ZIP archive retrieval, metadata/content/semantic search, read-state updates, delete and negative ownership checks. Keep outbound globally held except a reviewed, one-use canary grant. The test account is for acceptance, not a privileged bypass or production mailbox.

## Cleanup and durability

After acceptance, delete local `.temp` MIME and any temporary credential material, remove the exact Email Routing rule with `--remove`, disable or delete the Worker, empty/delete the isolated bucket, and revoke the synthetic Identity session or account through supported normal administrative/account flows. If a standing staging regression account is desired instead, explicitly document its owner, recovery channel, rotation and expiration; never silently leave a code-capture route or password in CI. Account creation and cleanup are observable state changes and should be recorded here with dates and **opaque** identifiers only, not secrets.
