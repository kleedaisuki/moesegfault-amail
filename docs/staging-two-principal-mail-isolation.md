# Hosted two-principal mailbox isolation acceptance

Status (2026-09-30): **design only**. No second Identity principal, route, login, mail, or hosted isolation run is established by this document. Run the first ordinary SMTP-to-ZIP staging acceptance and reconcile its exact run-owned alias before enabling this extension. The existing ten-address campaign in [`staging-address-isolation-e2e.md`](staging-address-isolation-e2e.md) remains a separate, higher-mutation quota/routing test.

## Decision

Extend one explicitly confirmed `staging-e2e` **Windows GitHub Actions run**, rather than launching the ten-route quota harness or trying to inspect an earlier run's already-deleted messages. Give it an opt-in two-principal mode and perform the foreign-access checks while A's existing two SMTP fixtures are live, **after** A has verified the ZIP and ordinary search and **before** A marks or deletes either message. This adds one verified Identity login but **zero extra mail routes, SMTP submissions, or messages**. The normal one-principal mode and its existing output/cleanup contract remain unchanged.

The test is a subject-swap relation: the same live object ID and query that succeed for A must not disclose or mutate anything for authenticated B; A must then still see the same unread object and active address. [OWASP's object-level authorization guidance](https://api-security.owasp.org/editions/2023/en/0xa1-broken-object-level-authorization/) calls for authorization on every ID-taking endpoint, and its [testing guide](https://wstg.owasp.org/latest/4-Web_Application_Security_Testing/12-API_Testing/02-API_Broken_Object_Level_Authorization/) specifically recommends two accounts and checking GET, mutation, DELETE and bulk listings. The relation also resembles the security-test oracle approach in [Mai et al., *Metamorphic Security Testing for Web Systems*](https://arxiv.org/abs/1912.05278); that paper motivates the method, not a claim that this one probe proves all possible authorization paths.

## State and trust boundaries

| State | Owner | Invariant |
| --- | --- | --- |
| A/B verified contacts and `(issuer, sub)` | staging Identity | Two **different** verified synthetic contacts resolve to distinct pairwise subjects at the same staging issuer. A second CLI home, username, or password alone is not proof. |
| A/B native sessions | separate run-local `AMAIL_HOME` directories under repository `.temp` | Each is created by normal Login Authorization Code + S256 PKCE on the same hosted runner. Never copy auth SQLite, inject bearer tokens, or use a production account. |
| A's run-owned address and two messages | staging Mail D1/R2 and one exact provider route | B owns neither. Only A's existing E2E `finally` may retire this address or delete verified fixture IDs. The isolation helper performs no success-path resource creation. |
| B's attempted ZIP path | B's run-local `.temp` directory | It must not exist before the call and must not exist after denied `read`; unlink it in `finally` even if an erroneous CLI wrote it. Never upload it as an artifact. |
| Diagnostic evidence | Actions fixed labels and restricted operator notes | No subjects, addresses, message IDs, bodies, raw CLI output, ZIP paths, credentials, tokens, authorization URLs, OTPs or pairwise subjects in logs/artifacts. |

Use the [second-principal provisioning runbook](staging-second-principal.md) first: the second exact **Identity contact** needs its own short-lived, settled, audited route into the private verification Worker, normal first-party registration and code verification, route/object removal, then native CLI login. This is not a user mail alias. Provision B **once**; ambiguous registration is recovered for that same account, not retried with another identity. Put only B's synthetic username/password in protected staging Environment secrets, separate from A's. A restricted Identity readback should attest that both exact verified contacts map to **different** staging `(issuer, sub)` values, outputting booleans only. If that readback is unavailable, the live A-address/B-list differential is valuable behavioral evidence, but report independent subject attestation as unverified, not implicitly passed.

## Hosted sequence and oracles

1. **Preflight without mutation.** Hosted CI and deployed staging Mail/Ingress/Identity/Login version pins are current. Require the ordinary `RUN_STAGING_E2E` confirmation **plus a distinct** isolation confirmation/boolean; no push or ordinary staging deploy may execute this. Require B's protected secrets before browser work. Read back absence of the two temporary Identity challenge routes and the configured private-inbox Worker. Check A and B credentials in memory for different usernames, but do not mistake this for subject attestation. Use independent run directories/profiles and `store_credential(..., address=<B contact>)`; `native_login(..., expected_address=<B contact>)` must pass for B, including separate-process `auth status` and Mail `address list`. A's existing native login remains as-is. Require B's initial `address list` and `sync --all` empty (new regression principal); do not delete B data to force this precondition.
2. **A creates the ordinary fixture.** Reuse `staging_mail_e2e.main`: exact route and D1 readback, two SMTP DATA receipts, CLI-visible delivery, owner `get`, both ZIP contracts and composed search. Do not run B before those positive controls; an empty/missing A fixture would make B's negative result vacuous. Keep A's Signal and Distractor IDs/oracles private in process memory.
3. **Foreign list/search.** B's `address list` must not contain A's active address. B's `sync --all` must contain neither A message ID nor either run-unique subject. Search B by exact run-unique subject and by the provider-assigned `message_id` metadata; each must yield no A row. Compare B's result with A's immediate positive result, not merely with a hardcoded empty mailbox. `sync --all` is bounded by the small, initially empty synthetic B mailbox; fail if output exceeds the existing harness cap instead of silently accepting a truncated page.
4. **Foreign ID operations, ordered from observation to mutation.** For A's Signal ID, B's `get` and `read -o <B fresh ZIP path>` must each return the existing typed HTTP `404/not_found`, no stdout record and no output file. B's `mark --read`, `mark --unread`, and `delete` must return that same typed denial. B's `address delete <A address>` must also return `404/not_found`. A second, well-formed nonexistent ID should produce the same public status/code for ID-taking operations, so a foreign ID is not an existence oracle; do not compare unstable human prose, latency or request IDs. If any denied operation instead succeeds or writes a ZIP, stop subsequent B operations, remove the B-local output, and let A's existing verified-fixture cleanup run; classify a security failure, not a flaky CI result.
5. **Owner-after-foreign oracle.** A's `get` still returns the same Signal row and `read=false`; its search still finds both fixtures; A's address list still shows its address `active`, and the exact enabled provider rule still targets staging ingress. Only after this check does the ordinary harness proceed to A's mark/read-state search/delete and existing bounded cleanup. The unchanged owner observation is needed because a rejected B request might still have caused a side effect.
6. **Final evidence.** Retain checkout SHA, deployed version IDs, Actions URL, UTC, booleans for distinct-subject attestation, two native logins, A-positive/B-negative/owner-unchanged operations, exact route cleanup and fixed first-failure label. A green ordinary inbound run without the opt-in mode remains **not** an isolation pass. A green B denial without A's positive controls or A's final unchanged-state check is likewise not a pass.

The helper should return only fixed, source-owned labels and never render `CalledProcessError`, CLI stderr/stdout, provider replies or Python exception text. Reuse `staging_mail_e2e.cli_env`, `amail`, `rows`, and its typed negative-HTTP parser where possible. A small standalone `assert_foreign_isolation(binary, home_a, home_b, address, signal_id, distractor_id, subjects, provider_message_id)` is preferable to repurposing the ten-route `staging_address_isolation_e2e.execute` function, which adds avoidable quota, reserved-name and SMTP-retirement side effects. Keep the wrapper's `finally` responsible for removing **both** run-local auth homes; the mail harness retains exclusive responsibility for the A address/message/provider-rule reconciliation. A cancelled runner still needs the existing exact HMAC-alias recovery procedure; B has no new mail resources to reconcile.

## Implementation and validation order

1. Complete the existing B registration/verification/runbook and separately attest distinct Identity subjects without exposing them. Until then, implement/test only source fixtures; do **not** create another account from the hosted mail job.
2. Add isolated helper tests on GitHub Actions that simulate: B equals A (A address appears and preflight fails), one missing A positive, each foreign operation returning 404, an accidental 200 or leaked stdout/ZIP, a rejected mutation that nevertheless changes A state, truncated B listing, and `finally` cleanup after a mid-sequence failure. No test should contact live staging during ordinary CI.
3. Add the explicit opt-in workflow path and B native login with staging Environment secrets. Pin the exact Worker/Identity/Login versions before the one guarded live dispatch. Reuse the existing single route/two-message run; do not replay SMTP simply because a negative check failed.
4. Record the hosted result in `docs/validation.md`. If it stops after fixture creation, first reconcile the **same** run-owned alias and provider rule/D1 counts before any new dispatch. If the owner oracle fails, treat it as a security incident and keep public send/release held.

This slice covers the existing CLI list/search/get/archive/mark/delete and address-retire surfaces with a real authenticated second subject. It does **not** establish quota/race behavior, semantic-index owner isolation, raw API paths absent from the CLI, outbound sender ownership while sending is held, or a proof against every future authorization regression. Those claims need separate targeted probes, not a larger and riskier first isolation run.
