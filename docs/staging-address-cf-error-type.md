# Request-local Cloudflare error category for a future staging address add

Status: instrumentation only; **no new address-add attempt or release-gate pass**. The fourth incident's historical response did not capture this header, so it cannot be retroactively classified. This change is for an independently approved, guarded normal staging E2E, not an authorization to retry.

Cloudflare documents `cf-error-type` as a diagnostic response header on **Cloudflare-generated error pages**, not on errors forwarded from an origin. `1101` denotes a Worker unhandled exception; `1102` denotes resource exhaustion. See [Cloudflare error diagnostic headers](https://developers.cloudflare.com/support/troubleshooting/http-status-codes/cloudflare-error-headers/) and [Workers errors](https://developers.cloudflare.com/workers/observability/errors/). The header is more causally useful than an aggregate invocation metric because the CLI observes it on the **actual address-add HTTP response**, but it still does not identify a source line or establish that a particular provider call returned.

For `addresses.add` server errors only, the CLI now appends `cf_error=1101|1102|other|absent` to its existing compact stderr failure. `other` covers an unrecognized, malformed, or duplicated present header; `absent` means the header was not present, **not** that the Worker did not trap. No raw header, response body, URL, address, account, token, request ID, or error page is newly exported. Existing HTTP status, public code, optional Worker phase diagnostic, and correlation contracts remain in place. Other operations and non-5xx address-add failures retain their previous format.

The hosted harness accepts only those four exact categories from the CLI's fixed grammar and appends `_cf_<category>` to the existing fixed address-failure label. It never prints CLI stderr directly. Unrecognized suffixes are discarded or fall back to a generic safe label. If the CLI cannot read the response body at all, the existing `body_*` failure wins and this category is not available; do not infer absence. If a future response reports `cf_error=1101`, that is direct evidence that Cloudflare classified *that response* as a Worker exception. If it reports `other` or `absent`, examine the separate HTTP/code/phase evidence before interpreting. The fourth incident's aggregate `scriptThrewException` bucket remains non-attributable to its add request.

Verification is deliberately synthetic: Rust unit coverage checks absent, 1101, 1102, unknown, and duplicated headers; Python harness coverage checks four accepted categories, simultaneous phase diagnostics, hostile bytes, and old stderr compatibility. Hosted CI owns compilation and cross-platform execution; there is no new alias, provider write, or local heavy test associated with this instrumentation.
