# Review: remove the deferred operator Worker from v0.1.0

Date: 2026-09-28. Scope: **source-tree and release-path decision only**; no provider resource, routing rule, or deployment was changed for this cleanup. The owner chose exact Cloudflare Email Routing **forward** rules to one verified confidential external operator destination for system abuse/postmaster mail. Do not print that destination in a repository, CI log, route name, diff, or status response. [Current operational decision](operator-intake.md) and [forwarding review](review-role-forwarding.md) are the governing records.

## Recommendation

**Remove `workers/mail-ops` and its local operator skill from the v0.1.0 source/CI graph, rather than retaining a dormant prototype.** Keep its architectural history in Git and the clearly labelled future-design notes. The Worker is not the selected data path, its Access/ticket-store resources are empty and unused per the current operations record, and its `ensure_routes.py` creates `worker` actions—the *opposite* of the chosen `forward` action. An inactive but compiled privileged service creates false confidence, test/build cost and a future accidental-route hazard. Keeping it outside the Cargo workspace but still in-tree would preserve the most dangerous route helper and confusing local skill while merely hiding build failures; that is a worse middle state. If future autonomous intake becomes valuable, revive deliberately against a new owner-approved contract rather than treating this prototype as a standing extension point.

This cleanup is safe only after a **read-only live inventory** confirms no current role rule points to `amail-ops`/its staging counterpart and no existing operator report objects require migration. The docs say the resources are empty and the Worker is not deployed, but that statement is not a substitute for checking live Cloudflare state. Source removal itself does not delete a deployed Worker or Cloudflare rule. If inventory contradicts the docs, pause deletion and plan a separate delivery-preserving cutover; do not run `wrangler addresses=[]`, delete routes, or remove provider resources as part of repository cleanup.

## Safe integration order

1. **Read-only provider inventory** (GitHub runner or provider dashboard, with sanitized output): enumerate exact role rules and their action type, confirm no route references the prototype Worker, check Worker deployment presence, and verify whether the dedicated D1/R2 pairs truly contain no reports. Never echo the forwarding target. If any real report exists, stop and preserve it; no automatic deletion.
2. **Clean source graph in one reviewable change**: remove `workers/mail-ops/`, remove the Cargo workspace member and local privileged skill, remove the four CI steps, regenerate `Cargo.lock` on GitHub-hosted tooling, and adjust active/future documents as above. Keep all mail API/ingress/event Worker source and send-policy migration intact. Avoid a half-state where Cargo still names a removed crate or CI still builds an absent folder.
3. **Hosted verification**: `cargo metadata --locked`, existing cross-platform CLI tests, remaining Rust Worker native/Wasm/bundle checks, infrastructure Python tests, release-source/gate tests, and a repository reference scan for `mail-ops`, `amail-ops`, old Worker route actions and missing documentation links. Remaining occurrences should be explicitly historical/future only. Do not run heavy tests or install toolchains on the development machine.
4. **Forwarding acceptance remains separate**: verify the confidential destination through Cloudflare, reconcile only exact `forward` rules with fail-closed conflicts, prove external receipt for every role and a monitored response owner, then audit-set `abuse_contact_verified`. Until then leave the global send policy held. A green CI run, HTTP health response or source cleanup is not SMTP delivery evidence.

Rollback of the repository-only cleanup is a Git revert and lockfile restoration; it must not mutate live role routes. If a later operator service is introduced, design a cutover that keeps the old verified forward path until new receipt, alerting and review are proven, then switch exact rules under an audited change. This respects the user-visible role addresses while allowing internal architecture to evolve.

## Execution record (source cleanup only)

The root agent's read-only Cloudflare inventory found **zero** exact production role rules, **zero** deployed ops Worker scripts, **zero** objects in each dedicated ops R2 bucket (not truncated), and **zero** `cases` tables in both dedicated ops D1 databases. This satisfies the safety precondition for removing unused source, but it also confirms forwarding is not yet an accepted live contact path. This subtask did not read, change, or delete those provider resources or the forwarding workflow.

The tracked files under `workers/mail-ops/` and `.agents/skills/amail-operator/` were removed from the release tree. Root `Cargo.toml` and the four ops-only `ci.yml` steps were updated. Lightweight `cargo generate-lockfile --offline` removed only the obsolete `amail-ops` package entry (15 lines), and `cargo metadata --offline --locked` returned success; **no Rust/Wasm build or local test was run**. The active forwarding and future-design docs were reworded to identify the Worker as historical source, not an available deployment. Hosted CI and live forwarding acceptance remain the next independent gates. No commit or push occurred in this subtask.
