# v0.1.0 release-site product acceptance review

Status: 2026-09-29 source and live-HTTP review of the **isolated staging** site, not a production launch or visual/browser accessibility certification. This review is deliberately limited to release-site product behavior and one cross-component privacy contradiction. It does not reopen already-passed Astro builds or table-of-contents smoke checks.

## User journey and what already works

The intended visitor is a person who will authorize Identity login, then delegate mail operations to an agent. The site should explain that relationship, let the person choose a native binary and Agent Skill, and leave them with a truthful, executable first-run path. It is not a web mailbox or API reference.

The current homepage puts that distinction in its first screen: human login, agent-owned address/search/ZIP operations, and no mandatory inbox UI. The manual gives a plausible first-run sequence (`auth login` → address → search/read ZIP → pack/send), describes ten aliases, the bounded shared-domain capacity, read-state semantics, send holds, and normal-versus-human output. The changelog is version-file based (`src/content/releases/v0.1.0.md`), validated by the Astro collection schema and given a generated version-anchor table of contents; the manual table of contents is generated from headings. These are appropriately product-facing rather than an exposed internal API specification.

On 2026-09-29 a bounded unauthenticated GET of each staging route returned 200 with expected page titles: `/` (8,440 response bytes), `/manual/` (23,575), and `/changelog/` (6,653). These are live availability observations, **not** visual or keyboard/screen-reader passes. The pre-existing CI and validation ledger already records the staging `noindex` header and three-route/TOC smoke; this review did not rerun those completed checks. The GitHub v0.1.0 Release URL returned 404 at review time, consistent with the intentionally gated/unpublished release. A staged CTA to that URL is acceptable only while the staging site remains non-public/noindex and the production deployment gate remains closed.

## Prioritized changes before public v0.1.0

| Priority | Finding and evidence | Required observable acceptance |
| --- | --- | --- |
| **P0** | **Privacy choice described by the manual does not exist.** `site/src/pages/manual.md` says a user unwilling to send content to a third-party model can avoid semantic search. In fact, `crates/mail-worker/src/lib.rs::scheduled` unconditionally calls `reindex`; `reindex` selects every active message with a missing embedding and sends its subject plus body text to OpenRouter, independent of whether the owner invokes `--semantic`. A normal lexical-only user can therefore still have mail content transferred. The manual's preceding clause that indexing sends text to the provider is true, but its proposed opt-out is false. | Decide a coherent product privacy contract and align both service and user-facing wording. Options include **automatic indexing with explicit disclosure before address use** (no claim that avoiding semantic search prevents provider transfer), or a real per-owner indexing opt-out/default-off policy that also handles already-indexed data. A user who follows the stated avoidance instruction must actually avoid third-party content transfer, or the instruction must be removed before release. Test with a non-semantic account/message and observe whether provider calls occur; update the manual accordingly. Do not silently remove semantic indexing to fix copy. |
| **P0 source-adjacent, fix pending hosted validation** | At review start, `reindex` attempted a 12,000-byte text bound using `source.get(..min(12_000)).unwrap_or(&source)`. If 12,000 fell inside a UTF-8 code point, the fallback selected the **full** subject/body string. A separate Worker owner has since committed `a7d679f` to take a valid bounded prefix and added multibyte tests; this review did not compile or execute that change. | Require the queued GitHub-hosted tests and deployment of the corrected Worker before treating the transfer bound as effective. The site should still describe the actual data category/provider behavior rather than relying on a byte count alone. |
| **P1 at release cutover** | The `v0.1.0` changelog says real external delivery, bounce and complaint feedback are still awaiting post-deploy acceptance. That is an honest candidate-stage caveat, but after the release gate is met it will read as stale or contradictory; if the gate is bypassed, the page would advertise an unfinished mail product. The homepage/header/manual and changelog link to a currently nonexistent v0.1.0 Release and skill ZIP. | Keep the production site gated on published, verified assets and real-mail acceptance. At publication, revise the version entry to describe **what actually passed** and any still-relevant limitation, without retroactively pretending the first failed staging run never happened. Follow the visible homepage/header/manual/Skill links to existing assets and verify downloaded bytes against the published checksums; an HTTP 200 on the page or asset-name listing alone is insufficient. |
| **P1 onboarding friction** | The manual says to download a platform archive and put the binary on `PATH`, but does not map the five release filenames to common systems/CPU architectures or show safe extraction/first-run commands. This makes the first human authorization step less self-contained than the marketing narrative suggests, especially for Windows and Apple Silicon/Intel choices. | Before launch, a clean user on each OS family should be able to identify the right archive, verify checksum using an OS-native method, install without building Rust, run `amail --version`, and reach `amail auth login` from the manual alone. A small platform table and short verified commands are preferable to a large troubleshooting section. Keep archived file names synchronized with `release.yml`. |
| **P1 role-boundary wording, source copy corrected** | At review start, the homepage correctly said the person authorizes login and the agent operates the CLI, but the manual told the person to **personally execute** `amail auth login`. The native CLI may be launched by the agent; the browser Identity authorization and credential entry require human action. The pending manual edit now uses `amail login` as the agent-issued command and reserves browser authorization for the person. | Preserve this role boundary through production publication. On a clean native first run, confirm the agent can initiate login and the human completes the branded browser flow without exposing password, token, or session to the agent. This is a copy correction, not a new live-login pass. |

## Responsive and accessibility boundary

The source has a viewport tag, semantic header/main/nav/footer landmarks, a skip link, visible keyboard focus, heading-derived navigation, narrow-screen breakpoints at 850/580/420 px, and reduced-motion handling. The manual and changelog each expose their contents as a labeled navigation region. This is a promising baseline, not proof of mobile readability or assistive-technology behavior. The hero illustration uses `aria-label` on a generic `div` while its cards also carry textual content; whether a screen reader announces a useful single diagram or repeated fragments has not been inspected. More importantly, the detailed manual includes non-wrapping table cells inside a horizontally scrollable article; verify narrow-screen reading at 320/390 px instead of assuming the media queries suffice. These are **targeted acceptance checks**, not blockers asserted from source alone.

The smallest useful visual/interaction check belongs in hosted CI or a controlled staging browser session: at 320, 390, 768 and desktop widths, confirm no clipped CTA, no page-level horizontal overflow, readable manual tables, working sticky/inline TOC navigation, keyboard focus and skip-link behavior, and a reasonable screen-reader reading order. Do not regenerate assets or redesign the site on speculation. If this passes, preserve the current page structure.

## Deliberate scope and success evidence

Do not add a web mailbox, account-registration frontend, live message preview, feature dashboard, or unbounded routing promise. The site is successful when a new person can understand the authorization boundary, install a real binary and Skill, authorize in their own browser, and hand the documented command/ZIP workflow to an agent without discovering a privacy contradiction or dead release CTA. The launch evidence should pair an actual published v0.1.0 Release with production HTTPS/link checks and at least one clean-install first-run check per OS family; the mail data-plane evidence is tracked separately in `docs/release-gap-audit.md` and must not be inferred from the site.
