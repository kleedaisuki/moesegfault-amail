# Durable exact search continuation

Status: implemented in source as of 2026-09-28, pending remote CI and deployed verification. Complements [the measured-search plan](perf-search.md) and [backend operations](backend-operations.md).

## Why a job is necessary

The synchronous Worker now returns a typed resource error rather than a false partial page when a query needs more than one invocation's D1-query, transfer, or reconstructed-body budget. This preserves correctness but leaves a large account unable to obtain an exact semantic result at all. A 1 GiB archive can contain many small messages; an exhaustive 256-dimensional cosine scan may need multiple invocations even with bounded top-K memory. A durable, owner-scoped continuation converts the budget boundary into progress, not a terminal limitation.

## Wire contract

`POST /v1/messages/search` still returns final HTTP 200 `{messages,next_cursor,request_id}` when one invocation suffices. Otherwise it returns HTTP 202 `{job_id,state:"running",retry_after_ms:500,request_id}`. Authenticated `GET /v1/messages/search/jobs/{opaque UUID}` advances one bounded batch and returns the same 202 or final 200. A job belongs to immutable `(iss,sub)`; another user receives 404 rather than existence disclosure. Expired jobs receive 410 `search_job_expired`, and changed search generation receives 409 `search_job_stale`. CLI polls transparently, emits only final result rows on stdout, and can resume by ID. The path contains an opaque random UUID, not an address or query.

## Minimal durable checkpoint

One D1 row stores `id`, owner, canonical `request_json` (filter text is mail-sensitive), the query vector (for semantic search, 256 validated f32 values), creation-time high watermark, account search generation, last **fully examined** `(received_at,id)` keyset marker, bounded top-`limit+1` hit triples `(id,time,exact score bits)`, state, lease generation/time, timestamps and expiry. It does **not** store mail body, ZIP, attachments, full candidate rows, or a potentially >2 MiB materialized result. Hits are rehydrated through owner-scoped, subject-preview SQL on completion and replay. A query vector is persisted once to keep every batch on the same embedding, avoiding repeated OpenRouter transfer and drift; it is cleared from the completed checkpoint. D1 already contains mail-derived text; this job is account data, never telemetry. No terms, vectors, addresses or subjects enter logs.

For a semantic query, atomic `preparing` INSERT first reserves one of five active slots, then D1 daily budgets reserve one of 500 per-account and 50,000 global embedding requests before OpenRouter is called. Provider failure deletes the preparing row, while reserved daily credits remain conservative. Cron removes any preparation stranded for more than ten minutes. This ordering prevents a concurrent burst of requests from all billing OpenRouter before only five win a later admission race. A cheap count precheck is advisory; the INSERT and daily-usage upserts are the admission authority. A normal lexical query can insert directly as `running` without the preparation round-trip.

Title/from/to/body/regex/metadata or semantic predicates require potentially broad Rust-side filtering, so an atomic D1 `search_work` reservation precedes their first scan: 300 requests per owner and 20,000 globally per UTC day. A 429 `search_work_quota` is explicit; failed attempts conservatively spend a reservation. Indexed newest/mailbox/date/read listing has no `search_work` write and remains cheap. This is a request-admission guard, not a proven per-query CPU guarantee; deployed traffic measurements should guide whether to replace it with weighted page-level admission. Semantic searches additionally have the provider-specific daily budget above.

`running -> advancing -> running|done` uses a compare-and-swap version to allow one poll to own a batch. If a Worker dies, an expired lease reverts to `running` without changing the last committed checkpoint; rescanning a batch is safe because no provider side effect occurs. A late former lease holder cannot overwrite a newer checkpoint. A checkpoint is written only after all text chunks of its last examined row and any vector scoring are done. On a budget boundary **inside** a fetched D1 page, the marker remains the previous fully processed row, so the unprocessed suffix is revisited. The result page is not published until the scan reaches true EOF and the account generation still matches.

A monotone `search_generation` row per account is incremented by a D1 trigger on message insert/update/delete (read changes, tombstones, embedding updates included). At job start and completion, generation is read; checkpoint and completion writes also require the same generation atomically in SQL. Mismatch returns `search_job_stale`, not a mixed-epoch ranking. Cursor v3 binds the generation so a later page cannot silently straddle mutations. A 24-hour TTL permits CLI resume; at expiry cron scrubs filter text/vector, retaining only an opaque 410 tombstone for another day. No indefinitely retained query copies. Five preparing/running/advancing jobs and 256 total retained **preparing, running, completed, or stale** jobs per owner are allowed within the 24-hour period, with quick 200 responses removing their transient row immediately. Stale jobs are scrubbed on detection but still count toward the total cap, so read toggles cannot bypass the storage guardrail.

## Failure and measurement gates

Only platform/resource limits pause a job; invalid pattern/date, unauthorized mailbox, corrupt/missing semantic index, and OpenRouter unavailability remain typed failures. An exhausted 24-hour TTL is explicit; it is not a truncated 200. D1 checkpoint write failure is a 503 and leaves the preceding checkpoint intact. Unknown race outcomes should be retriable, not silently completed. Before claiming production readiness, hosted tests must exercise multiple batch boundaries (including one midway through a 25 MiB text), concurrent polls, lease expiry, generation invalidation, no duplicate/skip across equal timestamps, score near-ties and replay of a completed poll. Stage deployment must then run a real large-fixture search and inspect D1 query counts, rows read, CPU, memory and latency; no such measurements have been collected yet.

The platform rationale and query ceilings are documented with primary Cloudflare references in [perf-search.md](perf-search.md). The design follows the production pattern of checkpointed, idempotent batch processing rather than assuming a Worker invocation can be unbounded; exact top-K ranking is the mathematical invariant, not an approximate-nearest-neighbor shortcut.
