# Review: hosted staging role SMTP acceptance gate

Reviewed `workers/role-monitor/hosted_acceptance.py`, its offline tests, the manual `staging-role-smtp` job in `.github/workflows/ci.yml`, the underlying ID-bound `acceptance.py`/route helper, and `docs/staging-role-monitor-acceptance.md`. This was a source and read-only historical log review; **no workflow dispatch, route mutation, SMTP submission, or deployment was performed**.

## Provenance finding and disposition

The initial wrapper checked a successful GitHub deployment job plus a Cloudflare version whose creation time fell inside that job window. That timestamp correlation alone did **not** prove the current version was produced by that job; an out-of-band deploy in the same interval could have been misattributed. This was reported as a material provenance defect and corrected in `c602b66`.

The revised gate selects one successful deployment step in the successful run/job, privately downloads that exact job's bounded log, extracts exactly one `Current Version ID` emitted within the step interval, and requires equality with both the operator-pinned UUID and Cloudflare's latest single 100%-serving Worker version. Cloudflare documents that the first deployment listed is the latest actively serving traffic; GitHub documents the job-log endpoint's redirect and Actions-read permission ([Cloudflare deployments](https://developers.cloudflare.com/api/resources/workers/subresources/scripts/subresources/deployments/methods/list/), [GitHub workflow jobs](https://docs.github.com/en/rest/actions/workflow-jobs)). A read-only inspection of the previously successful role deploy job's `Current Version ID` line, with UUID redacted, confirmed the actual GitHub log shape includes a tab before the UTC timestamp and therefore matches the parser. The parser rejects missing or duplicate candidate lines; offline tests cover those branches and the selected-step requirement.

The first exact-step implementation (`c602b66`) still had a real precision mismatch: GitHub's step `completed_at` is second-resolution, while its log line can be at that same second plus a fractional part. A real completed step ending at `06:15:00Z` had a version line at `06:15:00.839...Z`, which the strict upper bound excluded despite being its own deploy output. `f45d932` adds only a one-second timestamp tolerance and a fractional-end regression test. This fixes the demonstrated false rejection without substituting the earlier broad job-window correlation for the exact log UUID.

The GitHub bearer is used only on the API request. Redirect following is disabled for that request, the returned HTTPS storage host is allowlisted, and the second request carries no Authorization header. Both the API object and raw log read have byte caps. The log is parsed in memory and neither logged nor uploaded. Failure labels contain no provider body, mail data, token, route ID, or nonce.

**Disposition:** no remaining substantive blocker identified in the reviewed hosted gate after `c602b66` and `f45d932`, **conditional on committing the shared `.github/workflows/ci.yml` hunk, hosted CI, and an actual guarded dispatch**. The source review cannot establish that the chosen Cloudflare token supports SMTP AUTH: the job currently maps the existing staging API token as the SMTP token, and a failed AUTH must remain a failed/ambiguous probe rather than an invitation to resend. The manual `role_freeze` input attests an externally enforced deployment freeze; GitHub's shared concurrency group serializes its own role deploy and probe jobs, but does not lock out-of-band Wrangler deployments or prevent operator cancellation. The documentation and fixed-result output correctly state those limits.

## Evidence boundary

- A green wrapper result establishes only one authenticated SMTP submission, the harness's bounded D1 accepted/alerted state and fresh lease, route absence, and a stable pinned Worker version. It deliberately prints `machine_d1_only`.
- Cron Past Events, provider forwarding/digest delivery, and destination Inbox/Junk remain separate oracles. Neither this review nor offline tests satisfy them, and public sending must remain held.
- If the runner is canceled or cleanup leaves a marker, the artifact is limited to the private exact-route marker when the failure upload step can execute. A canceled runner may upload nothing; restricted exact-route inventory and recovery are still required before another probe or deployment.
