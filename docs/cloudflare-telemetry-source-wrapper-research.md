# Workers Observability event payload wrapper: evidence and decision

Status: researched 2026-09-29; **the exact REST `source` object for this Rust string log is not documented or yet verified**. No private event row was opened, no new provider query was made, and this note does not change the fail-closed retained-log privacy canary.

## Decision-relevant finding

The [Cloudflare-generated TypeScript API schema](https://github.com/cloudflare/cloudflare-typescript/blob/main/src/resources/workers/observability/telemetry.ts) types a telemetry event's `source` as `string | { [key: string]: unknown }` and describes it as the *raw log payload*, dependent on emission. It does **not** specify a stable field set, a discriminator, or a `source.message` rule (see `TelemetryQueryResponse.Events.Event`, currently around lines 852–887). The same schema separately defines optional indexed `$metadata.message: string` (around lines 940–947) and `$metadata.type` (around lines 1033–1039). Thus `$metadata.message` is not an authoritative serialization of `source`, and `type` alone cannot authorize accepting an otherwise unknown payload. The [REST Query API](https://developers.cloudflare.com/api/resources/workers/subresources/observability/subresources/telemetry/methods/query/) exposes this same broad contract.

The [Cloudflare Workers Logs guide](https://developers.cloudflare.com/workers/observability/logs/workers-logs/) illustrates `console.log("user_id: " + 123)` as a partial event `{message: "user_id: 123"}` and `console.log({user_id: 123})` as a structured object. This is evidence for a *possible* single-field message wrapper, **not** a guarantee that the REST response `source` object is exactly `{message: string}`. That guide also states that invocation, custom, error, and uncaught-exception logs can coexist, and invocation logs may include URL-bearing metadata. The project correctly disables invocation logs for the mail API, but the documented event union still allows other shapes.

The [upstream `workers-rs` `console_log!` macro](https://github.com/cloudflare/workers-rs/blob/main/worker-sys/src/lib.rs) calls `web_sys::console::log_1(&format_args!(...).to_string().into())` (lines 17–23). Therefore the project's [`emit()`](../crates/mail-worker/src/trace.rs) submits **one JavaScript string** containing JSON, not a JavaScript object. Cloudflare may index/normalize it, but neither the macro nor the API contract specifies the eventual REST wrapper. Treat a directly returned object with application trace fields as a separately validated representation, not an assumption that string logging always produces it.

The [historical read-only diagnostic](https://github.com/kleedaisuki/moesegfault-amail/actions/runs/36544143133) accepted a completed bounded events view but stopped on an unreviewed payload; a subsequent fixed label `unreviewed_source_object` further narrows the observed failure to an object in `source` that is neither an application trace nor the parser's exact `{message: ...}` wrapper. It does **not** identify its keys or contents, whether it came from a static `console_warn!`, or the address-registration root cause. Do not infer a `level` sibling or any particular platform wrapper from this label.

## Safe interpretation and one bounded discriminator

`infra/tests/staging_trace_canary.py::embedded_events()` recognizes an exact application trace object, exact `{message: value}`, or a single-element array/string encoding of those shapes; it rejects unknown siblings. This is conservative and appropriate for the **full privacy canary**: accepting `{message: valid_trace, arbitrary: private_text}` by reading only `message` would silently bless a private sibling. `$metadata.message` matching the nested trace does not make unreviewed `source` siblings safe. Likewise, JSON marker absence checks only the two synthetic markers; it cannot prove that unknown fields never contain other user data.

If historical diagnosis remains valuable, perform **one** narrowly scoped, already-approved, dry, exact-service and 33-second-window REST query with complete pagination, but reduce each unreviewed row **in memory** to fixed categories only. Suggested output: `source` type (`object`), key-count bucket (`1`, `2`, `3+`), presence booleans for a *predeclared* set (`message`, `level`, `logs`, `event`), whether each present candidate has the reviewed trace/static-warning structure, `$metadata.type` as only a predeclared classifier (`cf-worker-log`, `cf-worker-event`, `other`, `absent`), and `unknown_key_present` boolean. No raw key names, values, record IDs, times, addresses, warning text, JSON snippets, or downloaded artifacts should be printed. If all rows match a single small candidate, review that candidate's **entire** object and synthetic adversarial tests before adding an exact-key parser to the *incident diagnostic only*. The full privacy canary must still fail on arbitrary sibling keys or unrelated platform payloads. If `unknown_key_present` remains true, stop shape probing and use a restricted private human review of that one row or keep the incident unverified; more broad query retries do not add safety.

This probe distinguishes an index/transport wrapper from a genuinely unknown shape without exposing content. It does **not** itself authorize loosening the privacy canary or prove that the full production log corpus is private. A future more robust design would emit a JavaScript object intentionally rather than JSON encoded as a string, but that is an internal implementation change needing a new deployed canary and cannot reinterpret historical rows retroactively.
