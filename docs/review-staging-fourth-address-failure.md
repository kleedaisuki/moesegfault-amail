# Fourth hosted address-add failure: evidence and correction review

Status: independent source-and-reported-evidence review, 2026-09-29. The reviewed checkout is `7638f70`; the reported hosted run is [36567571204](https://github.com/kleedaisuki/moesegfault-amail/actions/runs/36567571204). This review did not issue a provider query, mutate a route, or test mail delivery. The run's private alias, provider response, rule ID, request ID, and credentials are deliberately absent.

## What the observation supports

The reported add outcome is a non-JSON HTTP 500 without the staging address diagnostic header. The immediate **pre-cleanup** readback found one exact, enabled, API-sourced `amail` rule whose literal `to` matcher and Worker action match the run's alias, while the D1 row was `provisioning` with `cf_rule_id=NULL`. The harness had previously required a complete inventory and no matching rule for this run alias. Its `route_snapshot` recognizes the rule only after checking exact name, source, enabled bit, action, matcher and ID shape; its `row_snapshot` reduces a parameterized D1 read. This is materially stronger than the three prior post-cleanup-only observations.

Conditional on the complete preflight/snapshot being contemporaneous and no independent actor creating the same private HMAC-derived alias, a provider rule **creation side effect** occurred between those observations. This does **not** show that the Worker's Rules POST received 2xx, that its response body was valid, that `platform::create_rule` returned an ID, that the current Worker secret is the same as the GitHub probe token, or that the D1 activation SQL failed. A control-plane read is not data-plane delivery. The row and rule are separate, non-atomic snapshots and can race with Cron or the original invocation. The exact rule is not proof that the CLI got a Worker-generated response.

`add_address` claims `provisioning`, lists rules, creates a rule only if none is found, and only then stores `active` plus `cf_rule_id` (`crates/mail-worker/src/lib.rs`). Consequently `provisioning`/null-ID plus a rule places the **observable side-effect gap** between claim and completed activation, but not a unique failing instruction. The POST may have committed while its response was lost or malformed; `create_rule` may have obtained an ID but the invocation then aborted; D1 activation may have failed; an independent reconciler could have raced. Do not infer a static Rules Write denial from this run. The earlier valid disabled-rule probe independently establishes Write for the GitHub job's token at its own time, not the current Worker response path.

## Primary finding: non-JSON 500 bypasses the normal error/diagnostic contract

**Priority: blocking for diagnosis and subsequent E2E; confidence: high in the contract gap, low in a specific runtime cause.** In the reviewed source, every ordinary `AppError` returned from `add_address`, including a typed Rules failure or a D1 `?`, is converted by `dispatch` into `problem()` and—when the staging diagnostic flag is active—a `x-amail-address-diag` header. `main` then sets `x-amail-request-id`. A non-JSON 500 with no diagnostic header is therefore not explained by the ordinary `RuleCreateFailure` or D1 error conversion paths *under the intended staging deployment*. It is consistent with an uncaught Worker/runtime abort, an edge-generated response, a serving-version/configuration mismatch, or headers lost before the CLI; the current evidence does not select among them. The reported result does **not** establish whether `x-amail-request-id` was present. `platform::create_rule` reads and classifies the POST response before D1 activation, so a provider-side create with missing/invalid reply is specifically plausible, not established. Treat this as **unknown execution outcome after side effect**, never as safe-to-retry rejection.

**Correction criterion:** verify the exact version serving at the failure time (point-in-time pin is not historical proof), and use privacy-bounded provider/runtime invocation metadata for this run only, if available: HTTP status and Cloudflare error class, script version, whether Worker terminated exceptionally, and only a validated request correlation. Do not print exception text, URL, headers, body, alias, SQL or provider rule data. Source-level synthetic tests should cover successful rule creation followed by malformed/missing provider response, D1 activation error, and ordinary `AppError` conversion; each should either produce bounded problem+diag or explicitly document why a platform abort lies outside this contract. These tests cannot by themselves prove the hosted cause. Avoid adding another address or a new route-write probe to exercise diagnostics.

## Cleanup and next discriminating gate

**Priority: blocking safety gate; confidence: high.** This run left a real enabled rule in the pre-cleanup snapshot. The harness's `cleanup_run` calls CLI address delete and waits for route absence plus address-list absence, but its own comments note that a `provisioning` row can remain `deleting` until Cron. A route-absent/CLI-list-absent result is not the same as an exact D1 `retired` tombstone with `needs_reconcile=0`. Before any further creation, independently repeat the existing **read-only exact alias** reconciliation after the cleanup/Cron window: complete paginated Rules inventory must find no exact or name-conflicting rule, and parameterized D1 read must find absent or a correctly owned `retired` row with null `cf_rule_id` and `needs_reconcile=0`. If cleanup failed or an ambiguous rule remains, freeze and use ID-bound, ownership-verified recovery; never delete by matcher alone or replay `address add`.

The highest-value discriminator is a bound **termination classification** for this exact invocation, not another wider opaque retained-log parser or a fifth alias. If privacy-safe invocation metadata confirms uncaught Worker exception, inspect the create-response/activation boundary and fix the underlying exception while preserving the external error contract. If it confirms a gateway response with no Worker invocation, investigate routing/serving instead. If neither can be established, record cause as unverified; the observed rule side effect still requires the clean audit above. Public send and release gates remain held.
