# Independent source review: semantic cursor v5 (`503c322`)

Status (2026-09-30, updated through `bc0fc29`): **GO for the reviewed source boundary; no deployed acceptance claim.** This reviews `503c322` and corrective source commits `f32920c` and `bc0fc29` against ADR `98ef479`, prior v4 code, callers, and SQL contract tests `d05d1ff`, `5970c59`, and `cf935a6`. It is not a hosted D1/Worker, provider, or live-mail test. The origin retains the same serialized `f32` query vector used to score page 1, and v5 continuation copies it without another `platform::embed` call or semantic-query quota reservation. The two original source findings and a follow-up page-job privacy finding are corrected; independent hosted acceptance remains.

## Findings

### Resolved P2 — A first-page completion could publish an already-expired origin cursor

In `503c322`, a first-page poll starting just before its 24-hour deadline could finish after expiry and commit `done` with an already-dead `next_cursor`. `f32920c` adds `search_jobs.expires_at>?7` to **both** completion CAS branches (`search_jobs.rs:786-807` after `bc0fc29`) and returns typed 410 `search_job_expired` if that row's deadline has passed on CAS failure (`:811-818`). `d05d1ff` exercises the exact SQL predicate at the deadline, plus owner/version/generation guards. This fixes publication of a cursor already expired at commit. Expiry between a valid commit and the caller's next POST is intrinsic to a 24-hour token and is documented.

### Resolved P2 — Generation-invalidated origins were not promptly scrubbed

In `503c322`, v5 generation mismatch returned before loading the origin; its query, vector, and key survived until cron. `f32920c` defers only v5's generation decision until `verified_origin` loads the owner-scoped row, recomputes the vector commitment, and validates the MAC, then scrubs under owner/version CAS (`search_jobs.rs:176-248,327-335,657-690`). Thus a forged or foreign UUID cannot revoke a valid origin. `5970c59` exercises the owner/version SQL scrub. Races after initial verification have a second `generation()` check and `scrub_invalidated_origin` call. A transient D1 write failure remains a best-effort scrub (the caller receives an error rather than a valid continuation); cron still bounds retention.

### Resolved follow-up P2 — An invalidated continuation page could retain its copied vector

After the origin fix, a 202 continuation page already holding a vector could see `verified_origin` scrub its origin and return `search_cursor_stale`. The old `release` treated that error as retryable, returning the page job to `running` with `request_json` and `state_json` intact. `bc0fc29` now classifies cursor stale/expired (and other non-resumable rank errors) as terminal, and `release` scrubs both JSON fields with owner/version CAS (`search_jobs.rs:643-677,729-733`). The completed-202 replay branch uses the same classifier and `scrub_done` (`:712-719`), closing the analogous retained-query path. `cf935a6` covers the terminal lease SQL, owner, and version guard. This keeps the original typed error visible while removing the page copy.

## Baseline source properties and review limits

The line ranges in this section refer to original commit `503c322`; corrective references above refer to the later source tree.

- **Owner/query/model/generation:** `search:360-368` and `origin_state:176-215` check owner-scoped ID, cursorless semantic origin, request hash, generation, high-water, input version, model/vector commitment, and expiry before v5 admission. The origin is never fetched by bare UUID. Recheck before each scan occurs at `advance_claimed:689-702`.
- **Cursor integrity:** `cursor_mac:141-174` signs version, hash, high-water, generation, full score/time/ID rank boundary, commitment, origin UUID, model, and input-version under a random per-origin 256-bit key. `verified_origin:217-235` compares the fixed-length lowercase hex MAC in constant time. The hash and digest are fixed-length syntax checked by `decode_cursor_at:274-305`. No direct vector or key field is serialized into `SearchCursor` (`lib.rs:1731-1748`). This source review did **not** independently attest the canonical MAC bytes against a known-answer fixture or test a real tampered cursor through D1.
- **Rank and replay:** `scan_batch:833-879`, `result_page:898-949`, and `semantic_rank` (`lib.rs:1827-1832`) use score/time/ID descending consistently; page jobs hold only `limit+1` hits. Completed origin replay can regenerate its cursor from its retained key; continuation replay re-reads the origin. `advance_claimed:720-754` clears the page-job vector/key on completion while retaining them only for an origin with `next_cursor`.
- **Quotas/provider:** `search:443-489` inserts continuation as `running`, reserves search work, and branches around the embedding call and provider quotas. Its copied vector is bit-checked against the origin again at `advance_claimed:693-701`. A race before the final continuation CAS is guarded by origin `done`/expiry existence (`:726-752`). This is source evidence, not a measured one-provider-call assertion.
- **Compatibility/privacy/bounds:** lexical v3 and semantic v4 decoding remain at `decode_cursor_at:274-308`; v4 re-embedding/check-vector remains at `search:477-500`. Cleanup scrubs request and state JSON at expiry (`:986-1005`). A 256-dimensional `f32` vector is small relative to the existing JSON state and D1 row limit; this review did not measure rows read, bytes, active-job cap incidence, or hosted race behavior.

**Remaining gate for a deployed GO:** run hosted tests covering three pages with a drifting fake provider, 200 versus 202/poll replay, expired-origin and generation races, tampering/owner isolation, v3/v4 compatibility, and D1 quota/cap behavior. The SQL tests reproduce the conditional statements but do not exercise the Rust handler and D1 binding/response lifecycle together. The prior protected exact-cosine staging run stopped at provider repeatability and cannot certify this new v5 path. No further material defect was identified in the narrowed corrective source review.
