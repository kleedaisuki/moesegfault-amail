# Independent source review: semantic cursor v5 (`503c322`)

Status (2026-09-30): **NO-GO for an unconditional v5 acceptance claim.** This is a source review of `503c322` against ADR `98ef479`, prior v4 code, and its callers; it is not a hosted D1/Worker, provider, or live-mail test. The principal correctness idea is sound: the origin retains the same serialized `f32` query vector used to score page 1, and v5 continuation copies it without another `platform::embed` call or semantic-query quota reservation. Two bounded corrections and independent hosted acceptance remain.

## Findings

### P2 — A first-page completion can publish an already-expired origin cursor

`advance_claimed` constructs a v5 cursor in `result_page` and, for first-page origins, commits `done` through the generic SQL branch with **no `expires_at > now` predicate** (`crates/mail-worker/src/search_jobs.rs:715-754`, particularly `:728-730`). `claim` checked expiry at the *start* of that invocation (`:573-579`), before a potentially 20-second `scan_batch` (`:783-785`). If a long-running 202 job is polled just before its 24-hour expiry and that final scan completes after expiry, the Worker can return HTTP 200 with `next_cursor`, yet the next POST immediately returns `search_cursor_expired` at `origin_state:190-195`. The continuation completion branch does check its origin in SQL (`:726-740`), so this is specific to the origin's initial publication. The unavoidable case where expiry occurs *after* a valid commit should be documented, but the Worker should not commit a cursor already expired at commit time. Add an expiry predicate to the first-page `done` CAS, then return a typed expiry/restart error on zero changes; test with a controlled clock or hosted boundary harness.

### P2 — Generation-invalidated origins are not promptly scrubbed

ADR `docs/semantic-pagination-vector-snapshot-decision.md` explicitly calls for scrubbing vector, query, and MAC key on “generation-invalidated stale detection”. Yet a cursorful search reads the new generation, and `decode_cursor_at` returns `search_cursor_stale` immediately at `search_jobs.rs:305-307`; it never loads or scrubs the origin. If mutation races later, `origin_state:196-197` also returns stale without scrubbing. `scrub_done` (`:628-635`) is reached only when replaying/polling the origin job itself (`:647-665`), not through the normal cursorful request. Thus an origin that can no longer support any cursor may retain `request_json`, `query_vector`, and `cursor_key` until 24-hour cron cleanup (`:994-1000`). This does not appear to extend retention *beyond* the disclosed 24-hour maximum, but it violates the ADR's early-minimization rule and retains private data unnecessarily after a detected invalidation. Scrub an owner-scoped origin on a **verified** generation mismatch, taking care not to let an unauthenticated forged UUID revoke another active origin; preserve the fixed foreign/missing-origin response.

## Confirmed source properties and review limits

- **Owner/query/model/generation:** `search:360-368` and `origin_state:176-215` check owner-scoped ID, cursorless semantic origin, request hash, generation, high-water, input version, model/vector commitment, and expiry before v5 admission. The origin is never fetched by bare UUID. Recheck before each scan occurs at `advance_claimed:689-702`.
- **Cursor integrity:** `cursor_mac:141-174` signs version, hash, high-water, generation, full score/time/ID rank boundary, commitment, origin UUID, model, and input-version under a random per-origin 256-bit key. `verified_origin:217-235` compares the fixed-length lowercase hex MAC in constant time. The hash and digest are fixed-length syntax checked by `decode_cursor_at:274-305`. No direct vector or key field is serialized into `SearchCursor` (`lib.rs:1731-1748`). This source review did **not** independently attest the canonical MAC bytes against a known-answer fixture or test a real tampered cursor through D1.
- **Rank and replay:** `scan_batch:833-879`, `result_page:898-949`, and `semantic_rank` (`lib.rs:1827-1832`) use score/time/ID descending consistently; page jobs hold only `limit+1` hits. Completed origin replay can regenerate its cursor from its retained key; continuation replay re-reads the origin. `advance_claimed:720-754` clears the page-job vector/key on completion while retaining them only for an origin with `next_cursor`.
- **Quotas/provider:** `search:443-489` inserts continuation as `running`, reserves search work, and branches around the embedding call and provider quotas. Its copied vector is bit-checked against the origin again at `advance_claimed:693-701`. A race before the final continuation CAS is guarded by origin `done`/expiry existence (`:726-752`). This is source evidence, not a measured one-provider-call assertion.
- **Compatibility/privacy/bounds:** lexical v3 and semantic v4 decoding remain at `decode_cursor_at:274-308`; v4 re-embedding/check-vector remains at `search:477-500`. Cleanup scrubs request and state JSON at expiry (`:986-1005`). A 256-dimensional `f32` vector is small relative to the existing JSON state and D1 row limit; this review did not measure rows read, bytes, active-job cap incidence, or hosted race behavior.

Before a deployed GO: correct or explicitly accept the two findings; run hosted tests covering three pages with a drifting fake provider, 200 versus 202/poll replay, expired-origin and generation races, tampering/owner isolation, v3/v4 compatibility, and D1 quota/cap behavior. The prior protected exact-cosine staging run stopped at provider repeatability and cannot certify this new v5 path.
