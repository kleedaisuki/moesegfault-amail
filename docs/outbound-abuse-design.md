# Public outbound abuse controls and Cloudflare lifecycle integration

Status: design and implementation ledger, 2026-09-28. Migration 0006, Rust send-path checks, and a Rust Queue consumer are source changes **pending hosted CI and deployed evidence**. This complements [backend-operations.md](backend-operations.md) and [outbound-abuse-operations.md](outbound-abuse-operations.md). The owner-defined transactional scope supersedes the general-mailbox release gate proposed in [outbound-policy.md](outbound-policy.md); that note remains useful for future scope expansion. The CLI/ZIP contract is unchanged, and API acceptance is not delivery.

## Release decision

The owner-defined product is **agent-workflow transactional notifications and replies**—for example, a research-progress update—not a general person-to-person mailbox, marketing sender, prospecting tool, or bulk first-contact platform. Cloudflare's [FAQ](https://developers.cloudflare.com/email-service/reference/faq/) describes Sending as transactional-only, while its [agent-email announcement](https://blog.cloudflare.com/email-for-agents/) explicitly demonstrates agent replies and email-client workflows. Taken together, these primary sources provide a reasonable basis for the chosen narrow use case; they do not authorize expanding the product to arbitrary correspondence. A special written Cloudflare approval for general first-contact mail is therefore **not a release gate for this scoped product**. Document and enforce the transactional/agent-workflow acceptable-use boundary, and revisit provider scope with Cloudflare if the owner later expands it. A successful canary or HTTP 202 still proves neither final delivery nor recipient consent.

For a public transactional sender, sender ownership and quota alone are still not a complete abuse program. The release slice includes (1) a fail-closed account/global send hold; (2) per-recipient and burst limits; (3) provider event and suppression feedback; (4) a working abuse-report intake and human/operator review; and (5) aggregate reputation monitoring with halt criteria. Do not demand human approval of each agent-authored notification or reply; login is the user's authorization, while the server enforces policy on every send.

## What the current source actually does

| Existing protection | Evidence | Remaining failure mode |
| --- | --- | --- |
| OIDC principal and sender ownership | `crates/mail-worker/src/lib.rs::send_message` checks active `from` and optional `reply_to` against `(iss,sub)` addresses. | Prevents identity spoofing, not spam by an authenticated account or compromised agent. |
| Typed ZIP/MIME validation and provider binding | `lib.rs::validate_draft`, `src/platform.rs::send`; user draft uses `EMAIL`, not sender-constrained `OFFICIAL_EMAIL` binding in `wrangler.toml`. | Limits malformed content; the dynamic user binding cannot platform-allowlist all future user senders. D1 ownership is the security authority. |
| Idempotency and ambiguous outcome state | `send_requests` and `send_message` use `preparing → submitting/unknown → accepted/sent`, no blind retry after ambiguous submission. Definitive provider refusal records terminal `rejected` with a stable typed code. | Correctness now depends on hosted provider-response contracts and migration compatibility; only indeterminate transport outcomes should enter `unknown`. |
| Atomic outbound reservations | `reserve_quota` charges To/Cc/Bcc entries, with provisional 50 recipient attempts/account/day, 10,000 globally/day, 20 messages/day, 5 messages/hour, and 10 attempts/account/recipient/day. Failed attempts are conservatively charged. | Multi-bucket partial failure can charge earlier buckets; limits are a cautious product choice, not provider-endorsed thresholds. Hosted concurrency and live D1 behavior are unverified. |
| Retained storage and size constraints | R2 reservations and ZIP/MIME size checks are present. | These protect resource cost, not sender reputation or recipient consent. |
| Provider feedback and holds | Migration 0006 introduces a global launch hold, account holds, recipient blocks, event deduplication, ordered outcomes, and complaint-triggered account hold/block. `workers/mail-events` consumes Cloudflare Email Sending events. | CI, subscription deployment, external feedback canary, abuse-report route, and operator response remain to prove. |

The public sent-message `recipients_json` intentionally serializes only `manifest.to`. Owner-scoped `metadata_json` now includes `cc`, `bcc`, and `envelope_recipients` both on initial indexing and reconciliation. `send_requests` separately stores sender and the complete private envelope in the **same D1 update** as accepted provider ID/state, so a complaint still attributes after user-visible archive deletion. The Queue consumer resolves `provider_id` directly to that row. Cron targets removal of these restricted raw addresses after 90 days from submission in bounded batches; an outage or backlog can delay physical removal, so this is not an instant-erasure guarantee. This is an explicit anti-abuse exception to immediate archive deletion, not a hidden mail copy. Later unrecognized events enter the DLQ. Bcc is never added to public summaries or telemetry.

## Minimal state model and send transition

Keep the user-facing `POST /v1/messages/send` and ZIP unchanged. Internally add only state that enforces a real invariant:

| State | Minimal fields/invariant |
| --- | --- |
| `send_policy` (per `(iss,sub)`) | `state = allowed | held`, reason code, actor, timestamp and review note reference. A global send switch is independent. Default policy and probation limits are explicit release configuration, not inferred from a token claim. Read before quota reservation and again immediately before provider submission; D1 errors fail closed. A hold blocks **sending**, not receipt/retrieval, so an accused account can still read and respond to support. |
| `recipient_outcomes` | `(local_message_id, normalized_recipient)` stores the most severe lifecycle state, timestamp and event ID. Owner-private outbound metadata retains To/Cc/Bcc roles; public summaries keep only To. |
| `provider_events` | Unique `eventId`, provider/local message ID, owner, recipient, kind and event time. A SQLite trigger updates outcome and complaint hold/block atomically; raw subject and SMTP response are never retained. Unknown provider IDs retry into a DLQ rather than being discarded. |
| `recipient_block` | Account-scoped do-not-contact entry from a direct complaint; a global/domain-wide block uses Cloudflare's manual suppression API. Record provenance and an explicit removal procedure. Never use raw recipient text in logs or URL paths. |
| `abuse_case` | Opaque case ID, reported provider/local message ID, accused owner if known, status, actions and operator audit trail. Keep original report evidence in restricted storage if needed, not SQLite telemetry. |

At admission: verify owner and hold; validate all `to+cc+bcc`; reject local blocks; reserve atomic per-account and global **recipient attempts**, hourly send burst, daily messages, and per-recipient attempts before the irreversible provider call. The 5/hour, 20/day, 50 recipient attempts/day/account, 10 attempts/day/account/recipient, and 10,000 global recipient attempts/day are fixed v0.1.0 provisional controls, not provider guidance. The earlier 3/day same-recipient proposal was rejected as too brittle for routine initial/milestone/completion updates, especially when failures charge quota; 10/day preserves that workflow while burst and fanout controls remain. A future policy version can make them configurable with an audited migration. Do not use `in_reply_to` alone for a cheaper “reply” tier: an agent can write any Message-ID. Preserve idempotency and conservative quotas so retries do not evade limits.

Immediately before sending, check the global/domain/account hold again. On a definitive Cloudflare builder error (e.g. `E_RECIPIENT_SUPPRESSED`, `E_RATE_LIMIT_EXCEEDED`, `E_DAILY_LIMIT_EXCEEDED`, validation), return a stable typed result and record a terminal rejected attempt; do not label it a possibly successful `unknown` send. Only a network/timeout or indeterminate provider exception belongs in `unknown`; never blind-resend it. The [Workers send API](https://developers.cloudflare.com/email-service/api/send-emails/workers-api/) documents those error codes. Keep Cloudflare's **“Drop suppressed recipients” setting off** for the user sending domain: with it on, the provider may silently remove some recipients and process the rest, while the Worker builder's success value exposes only a message ID. Off makes a suppressed recipient reject the entire call with `E_RECIPIENT_SUPPRESSED`, preserving the all-recipient send contract. [Cloudflare suppression behavior](https://developers.cloudflare.com/email-service/concepts/suppressions/).

## Provider feedback and suppression integration

Create a Cloudflare Email Sending **Event Subscription** for `mail.moesegfault.dev` into a Queue, with a Rust queue consumer and a dead-letter queue (DLQ). Subscribe to at least `message.delivered`, `message.deferred`, `message.bounced`, `message.failed`, `message.rejected`, and `message.complained`; these are outbound lifecycle events, not Email Routing events. Each event includes `eventId`, `messageId`, sender/recipient, domain and timestamp; many also include subject. Validate source zone/domain/schema, match `provider_id` and normalized recipient to a stored outbound attempt, insert `eventId` idempotently, then update only that recipient's outcome and account risk counters. Do not log subject, sender, recipient, raw SMTP response or full queue payload. Delivery can be followed by a complaint, so outcome state is not a simple one-way `accepted→delivered` terminal machine; complaint overrides prior healthy outcome. Queue redelivery and out-of-order events must not double-count or regress it. [Event schemas](https://developers.cloudflare.com/email-service/platform/event-subscriptions/), [Queue retries/DLQ](https://developers.cloudflare.com/queues/configuration/dead-letter-queues/).

Cloudflare already creates some suppressions after complaints and eligible bounces, with `account` or exact `sending_domain` scope; it does **not** create an application-level “do not contact from this owner” list. For a recipient asking to stop mail from all amail users, add a manual suppression scoped to `mail.moesegfault.dev` through the [Email Sending suppression API](https://developers.cloudflare.com/email-service/configuration/suppressions/), using a dedicated token with the required `Email Sending: Edit` permission and no unrelated permissions. For a complaint about only one account, add the local `recipient_block` and consider holding that account. Never delete a provider complaint suppression just to make a test pass; Cloudflare says restore sending only after the recipient opts in again. `read_only` governs whether an entry can be changed. Keep official `mail@moesegfault.dev` on its separate sender domain/binding so a user-domain manual suppression does not accidentally alter official mail. If an account-wide suppression is warranted, make that a conscious operator action. [Suppression scopes and lifetimes](https://developers.cloudflare.com/email-service/concepts/suppressions/).

Do not expose provider event Queue delivery as an unauthenticated public webhook; Cloudflare's native subscription avoids inventing a webhook secret protocol. Give the consumer a bounded batch/retry policy and a DLQ alert; without a DLQ, exhausted retries delete the event. Reconcile daily aggregates against Cloudflare `emailSendingAdaptiveGroups` (31-day retention) to detect missed events and measure delivered/bounced/failed/rejected volume. The per-event `emailSendingAdaptive` dataset includes raw sender/recipient/subject, so prefer aggregate queries and restrict any necessary individual investigation. [Metrics/analytics](https://developers.cloudflare.com/email-service/observability/metrics-analytics/), [Queue DLQ behavior](https://developers.cloudflare.com/queues/configuration/dead-letter-queues/).

## Abuse intake, intervention and privacy

Reserve and **operate**, not merely blacklist, `abuse@mail.moesegfault.dev` and `postmaster@mail.moesegfault.dev` as literal operator routes. [RFC 5321 §4.5.1](https://www.rfc-editor.org/info/rfc5321/) requires case-insensitive postmaster support for a receiving SMTP domain; [RFC 2142](https://www.rfc-editor.org/info/rfc2142/) identifies the abuse role. Two of Cloudflare's 200 domain rules are therefore unavailable for user aliases: `capacity.limit=198` is a conservative user cap, while provider rule state remains authoritative. The selected v0.1.0 path is exact forwarding to a verified confidential, owner-controlled external destination—not the removed operator Worker—with external receipt proof and a monitored review process; it is **not live-verified yet**. The global send policy remains held, and `send_release_gates.abuse_contact_verified=0` prevents operator unhold until real intake is demonstrated. A report must let the recipient provide delivered Message-ID and request no further mail. The operator attributes provider ID, owner and recipient, applies a local block or domain-scoped manual suppression, and holds the sender when evidence warrants. Use an opaque case reference, acknowledge within one business day, review urgent reports promptly, and offer appeal/unhold. A report is untrusted mail, never an agent instruction. Do not advertise a dead `mailto:` before an external test succeeds.

At launch, monitor delivered/attempted, hard-bounce/attempted, complaint/delivered and per-owner concentration daily; alert on any complaint for a low-volume account and sustained threshold breaches. Cloudflare's [deliverability guide](https://developers.cloudflare.com/email-service/concepts/deliverability/) suggests delivery rate >95%, hard-bounce rate <2%, complaint rate <0.1%. These are provider guidance, not a statistical guarantee at small sample sizes; use counts plus trend and immediately preserve the ability to hold one owner or globally stop sending. Build a canary that produces a controlled hard bounce, observe Queue event → owner correlation → suppression, and test a direct abuse report. An API 202 or `state=accepted` means provider accepted submission, never that the recipient received it.

Privacy: Cloudflare's Email preview shows full sent HTML/text/attachments/raw MIME and is turned on automatically for newly onboarded domains, retaining previews about seven days. Verify and, for the public user domain, disable this optional duplicate-content retention unless its operational benefit is explicitly accepted and documented. Sending activity/event payloads still contain PII; restrict Queue/DLQ and dashboard access, retention and operator queries. Avoid sampling message content into Worker traces. The separate official sender may have a different preview policy. [Email logs and preview default](https://developers.cloudflare.com/email-service/observability/logs/).

## Implementation slices and acceptance evidence

1. **Scope and canary**: publish the owner-defined transactional notification/reply acceptable-use boundary and prohibit bulk marketing/unsolicited prospecting; verify actual send to an owned external recipient, SPF/DKIM/DMARC alignment and 202-versus-delivered distinction. If the product scope later broadens to arbitrary person-to-person or first-contact outreach, re-evaluate Cloudflare's terms and obtain an explicit provider decision before that expansion.
2. **Pre-send authority**: D1 account/global holds, atomic burst/recipient quotas, suppression checks, typed provider errors, all-recipient mapping including CC/BCC. CI verifies compromised-but-authenticated account held, 50-recipient fanout bound, concurrent quota races, and idempotent retries. Default data/quotas fail closed when D1 is unavailable.
3. **Feedback**: Event Subscription → Rust Queue consumer → D1 event/outcome tables → DLQ and alert; prove duplicate/out-of-order event handling, bounced/complained correlation, automatic provider suppression and manual local/domain block. One `message.complained` fixture must hold a test account according to the written policy.
4. **Operations**: external report reaches a monitored operator, case is attributed, recipient block and owner/global hold work, incident can be safely reversed with an audit entry; daily aggregate reconciliation and no-PII logging/preview decision are checked in deployed staging and production canaries.

Only then describe the **scoped transactional** public sending path as operational. The API's ability to send to arbitrary addresses must not be advertised as permission for arbitrary message purposes. No alternative named provider should be presumed safer without the same lifecycle and abuse capabilities.
