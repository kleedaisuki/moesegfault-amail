# Hosted staging address-add failure: non-mutating diagnosis

Status: investigation of hosted run [36524101354](https://github.com/kleedaisuki/moesegfault-amail/actions/runs/36524101354), attempt 1, on 2026-09-29. No rule, alias, mailbox or message was created by this investigation. Keep the run-owned address and all credentials private.

## Observed boundary

The hosted Windows native PKCE step passed, then the inbound harness reported only `mail_address_register_failed_cleanup_address_or_route_cleanup_failed`. The operator independently reconstructed **only** the run-owned address in memory and observed zero matching Cloudflare rules, zero CLI-list entries, and one D1 row with `state=retired`, `cf_rule_id=NULL`, `needs_reconcile=1`. These are **post-cleanup** observations, not a record of the original HTTP response or provider operation. Do not rerun address creation to infer the first failure.

At 05:15 UTC, another read-only check of that **same** run-owned address found the route and CLI list still absent, `state=retired`, `cf_rule_id=NULL`, and `needs_reconcile=0`. This is consistent with the scheduled reconciler completing the remaining tombstone after the hosted harness's 90-second cleanup deadline; it does not identify why the original add failed. The cleanup deadline has been widened to seven minutes so a future provisioning failure is not prematurely reported as an orphan before the five-minute Cron can run. Even then, a timeout remains a failed acceptance requiring exact readback, never a reason to create a replacement alias blindly.

At the checked-out source revision, `infra/tests/staging_mail_e2e.py::amail` captures CLI stdout/stderr and replaces all nonzero exits with `address_register_failed`; `infra/tests/staging_hosted_e2e.py::safe_stage_code` preserves only fixed labels. `cli_env` sets `AMAIL_TELEMETRY=off`, so the local operation journal was not written. The host removes its run directory in `finally`. Thus Actions logs and local CLI state cannot recover the original status/error code. The Worker wraps a Cloudflare rule-creation non-capacity failure as public HTTP 503 `routing_unavailable`, and capacity-text failure as HTTP 409 `capacity_exhausted` (`crates/mail-worker/src/lib.rs::add_address`). Its `platform::create_rule` discards the actual Cloudflare POST status and body, so even a recovered outer 503 would **not** distinguish provider 403 from 400 or 5xx. A failure in `rules_for_address` before POST is also possible; the harness's own successful Rules list uses the GitHub secret, whereas the deployed Worker uses its separately installed secret.

The POST JSON shape in `crates/mail-worker/src/platform.rs::create_rule` conforms to the published Cloudflare schema: `worker` action with a one-element string `value`, `literal`/`to` matcher with an address string, `enabled=true`, `source=api`. This lowers, but does not eliminate, the likelihood of a schema error; server-side constraints, Worker availability, and domain configuration remain untested. Cloudflare's [create-rule API](https://developers.cloudflare.com/api/resources/email_routing/subresources/rules/methods/create/) explicitly requires **Email Routing Rules Write**, whereas a successful list proves only read authority.

## Safe next discriminating probe

1. **Recover the provider and outer status if retained:** with restricted Cloudflare operator access, inspect the *staging mail Worker* trace for the one `POST /v1/addresses` in the hosted job window (step ran approximately 05:02:10–05:04:00 UTC). The top-level `crates/mail-worker/wrangler.toml` enables tracing and logs; no staging override appears, but confirm the **effective deployed** staging setting rather than presuming inheritance. Cloudflare [Workers Traces](https://developers.cloudflare.com/workers/observability/traces/) automatically instruments outbound `fetch`, and the [span inventory](https://developers.cloudflare.com/workers/observability/traces/spans-and-attributes/) lists `http.request.method`, `url.path`, and `http.response.status_code`. A retained child span for `POST /zones/{zone}/email/routing/rules` could directly identify the historic Cloudflare POST status; its absence, together with a Rules GET span, could locate an earlier failure. Inspect the parent invocation's response status too. The [Workers Observability Query Builder](https://developers.cloudflare.com/workers/observability/query-builder/) searches historical telemetry in the private dashboard. Its [telemetry query API](https://developers.cloudflare.com/api/resources/workers/subresources/observability/subresources/telemetry/methods/query/) uses an HTTP `POST` **only to run a read-only query** and requires `Workers Observability Write`; use `dry=true`, `view=traces` or `invocations`, a narrow millisecond timeframe, and private filters for the staging service and request method/path. Use the UI if the required API permission is unavailable. Cloudflare [Workers Logs](https://developers.cloudflare.com/workers/observability/logs/workers-logs/) documents a maximum seven-day log retention; verify trace availability separately. Report only method, endpoint category, numeric status, fixed public error code if present, and opaque request ID. Do not export raw spans or invocation records: automatic `url.full` and metadata may contain sensitive values. Missing records or sampled-out spans do not prove no request.
2. **Check permission without mutation:** in the Cloudflare owner UI or using a separate token with API Tokens Read (or Account API Tokens Read), use the relevant [user-token details](https://developers.cloudflare.com/api/resources/user/subresources/tokens/methods/get/) or [account-token details](https://developers.cloudflare.com/api/resources/accounts/subresources/tokens/methods/get/) endpoint. Inspect privately the policy's `permission_groups`, `resources`, `effect`, expiration/IP conditions for the *GitHub routing token* and the *actually deployed staging Worker routing secret*. Cloudflare [verify-token](https://developers.cloudflare.com/api/resources/user/subresources/tokens/methods/verify/) returns ID/status/validity only; active is not Write proof. Never print token values, token IDs, policy resources, or other metadata publicly. A missing zone-scoped Rules Write grant would explain creation denial; a valid grant would shift attention to provider validation/configuration, and the original POST code still cannot be recovered from current application logs.
3. Do **not** use `POST /zones/{zone}/email/routing/rules` with `{}` as a purported non-mutating permission probe. It is a mutating endpoint regardless of the current validation outcome; an HTTP 400 does not reliably prove Write because validation/auth ordering is not contractual, and a future/defaulted payload could have an unintended effect. If neither historic log nor policy metadata resolves the cause, report it as indeterminate. The next future authorized hosted probe should capture *bounded numeric provider HTTP status and numeric Cloudflare error code inside the Worker* through privacy-reviewed instrumentation before another mutation; no fresh rule or SMTP traffic is justified solely to reconstruct this run.

For the next harness revision, `amail` already converts non-2xx responses into a stable `code=<public_code>` and an HTTP status in its own stderr (`crates/amail/src/api.rs::execute_with_status`). A pending harness change extracts **only** a bounded, allowlisted numeric status and known public code from captured stderr, then emits a fixed label such as `address_register_failed_http_503_routing_unavailable`; all unmatched or malformed output remains `address_register_failed`. Never print raw stderr, response body, alias, URL, subject or token. This improves the outer-failure boundary but still cannot recover the Cloudflare POST status unless the Worker separately preserves a safe diagnostic classification. GitHub-hosted tests and a future live attempt have not yet verified the change.

## Evidence limits

Cloudflare token verification tests validity, not effective permission. A GitHub secret's policy does not prove the already-deployed Worker's secret value or policy; the deployment history must be checked separately. A `retired` D1 row with `needs_reconcile=1` is consistent with cleanup after several different add failures and should not be interpreted as proof that POST was sent. The API's example request is schematic and not an executable acceptance test; the documented field definitions are the relevant shape comparison.
