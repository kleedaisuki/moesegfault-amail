The independent valid disabled-rule probe [36563397248](https://github.com/kleedaisuki/moesegfault-amail/actions/runs/36563397248) reported `routing_write_probe=created` and `routing_write_cleanup=removed`; delayed read-only audit [36563581654](https://github.com/kleedaisuki/moesegfault-amail/actions/runs/36563581654) reported `absent`. ## Actual add path and failure surfaces

1. `crates/amail/src/api.rs:215-222` sends JSON `{"local_part":...}` to `POST /v1/addresses`; `execute_with_status` authenticates, sends `traceparent`, records a status/body length, and formats non-2xx as `mail API addresses.add failed: HTTP <status>, code=<public-code>, correlation_id=<id>` (`api.rs:100-177`). The CLI prints only this top-level error (`main.rs:672-678`). An HTTP transport failure, missing body, or successful response with malformed JSON instead takes a different path.
2. The Mail Worker authenticates *before* routing (`lib.rs:687-713`); an auth failure becomes JSON 401 `unauthorized`. `GET /v1/addresses` passed in each hosted E2E, so the principal and D1 binding worked for that preceding call. It does not prove the later POST reached `add_address`, and the harness does not preserve an HTTP status for an unrecognized CLI failure.
3. `add_address` validates the local part and performs D1 existing-row/zone-count queries, then a conditional insert and a `pending`→`provisioning` claim (`lib.rs:1193-1275`). Its first provider request is a zone-wide, paginated Rules GET in `platform::rules_for_address` (`lib.rs:1276-1284`, `platform.rs:98-149`). Only after a successful GET with no exact owned rule does it POST the enabled rule (`lib.rs:1285-1304`, `platform.rs:151-180`), then transition D1 to `active` (`lib.rs:1308-1345`). Thus a later `retired` tombstone after harness cleanup proves an inserted row but does **not** prove a provider POST.
4. `platform::rules_for_address` takes `CF_ZONE_ID`, `EMAIL_INGRESS_WORKER_NAME`, and `CF_EMAIL_ROUTING_TOKEN` from the **Worker runtime** (`platform.rs:100-109,234-245`). Any binding missing, outbound transport failure, non-200 GET, `success=false`, or JSON type mismatch fails before POST. `AppError::from(worker::Error)` maps these to JSON 503 `service_unavailable` (`lib.rs:64-70`); the new trace records a `routing_list` success boolean but not a D1 phase (`lib.rs:1276-1284`). The six current rules' types were separately checked and fit the parser ([second incident](staging-address-add-incident-36533465672.md)); that narrows, but does not eliminate, an inventory-shape issue.
5. `create_rule` uses the same provider URL, zone and source/action/matcher schema as the successful disabled probe, but sets `enabled=true` and the user alias/name (`platform.rs:151-180`; `infra/provider/probe_routing_effective_write.py:231-244`). An explicit provider refusal becomes 503 `routing_unavailable`, or 409 `capacity_exhausted` if the existing text heuristic sees a limit phrase (`lib.rs:120-129`, `platform.rs:184-216`). A network exception, malformed successful body, or missing returned rule ID also becomes `routing_unavailable`, and may be an uncertain side effect, not a safe retry. Enabled-rule constraints and the Worker's effective request context are **not** exercised by a disabled GitHub-hosted POST.
6. The staged deployment reads the same *named* GitHub secret into `worker-staging-secrets.json` and runs `wrangler deploy --env staging --secrets-file` (`.github/workflows/ci.yml:901-971`); both the valid probe job (`ci.yml:275-301`) and deploy target select the `staging` Environment. This is a strong source-level intended path, not a runtime secret-value readback. A secret drift, Cloudflare-side condition dependent on request origin, or failed runtime binding remains possible until checked at the Worker boundary.

## What the bare hosted failure label means

`infra/tests/staging_mail_e2e.py:124-154` turns any nonzero CLI exit into `address_register_failed` unless stderr matches its narrow pattern **and** the code is in `SAFE_API_CODES`. The allowlist includes the present address failures (`routing_unavailable`, `service_unavailable`, conflicts) but not `unauthorized` or `http_error` (`staging_mail_e2e.py:116-142`). A bare label across the three hosted runs therefore raises the relative importance of a transport/parse/auth/Worker-exception path or another unlisted public code; it is **not** evidence that any particular path happened. The Worker normally emits fixed problem JSON for `AppError` (`lib.rs:783-792`), but an exception outside that conversion may instead yield a platform-generated non-JSON response. The harness disables local telemetry and removes its temp home, so neither CLI status nor journal survives (`staging_mail_e2e.py:95-113`; [first incident](staging-address-add-incident-36524101354.md)).
