# Review: one controlled staging acceptance without a live-tail observer

Status: independent risk assessment, **not an execution authorization** (2026-09-29). No test, token readback, deployment, route mutation, address registration, or SMTP submission was performed for this review. The historical retained-event diagnostic should finish before this contingency is considered. The owner's direction is to test the existing single routing token ourselves rather than ask for its policy or introduce a second token.

## Decision

**Conditionally yes for product acceptance; no for conclusive provider-phase diagnosis.** If the corrected, bounded historical read-only query still yields no accepted causal record, a single real `staging-e2e` run can be a proportionate way to test whether the *effective* deployed staging path can register an address. A live-tail observer is helpful for explaining a failure, but not inherently required to establish a successful address/route/SMTP-to-ZIP outcome. Requiring an unfinished observer or unavailable token-policy readback as an absolute gate would block the only legitimate end-to-end test even though the experiment already has a unique run-owned alias, exact Cloudflare rule preflight/readback, fixed CLI failure codes, and bounded cleanup. This differs from the more conservative contingency in [the second incident](staging-address-add-incident-36533465672.md); that incident's observer/policy gates should be amended explicitly by the owner before dispatch rather than silently ignored.

The single-token read-only check [36543355938](https://github.com/kleedaisuki/moesegfault-amail/actions/runs/36543355938) established that the configured token is active, but its separate policy-reader credential got 403/9109. It did **not** show whether Rules Write is granted. The staging deployment and E2E job both resolve `CF_EMAIL_ROUTING_TOKEN` in the staging Environment and the Worker deploy passes it through `wrangler deploy --secrets-file`; this is strong source-level evidence of intended credential parity, but cannot exclude a changed secret between deploy and test, a deploy injection failure, or restrictions on Worker egress. A successful real address creation plus exact active literal-route readback is a practical positive test of effective Write for that operation. A failed CLI call is **not** a negative permission proof.

## Gates for exactly one attempt

| Gate | Required pre-dispatch evidence or action |
| --- | --- |
| Historical evidence first | Finish the current fixed-window, dry retained-event query. If it yields a complete causal result, act on that result; do not create a new alias merely to reproduce an understood failure. If it remains unavailable/malformed/empty, record `UNVERIFIED` and move to this controlled acceptance decision. |
| Prior-attempt isolation | Privately reconstruct **both** earlier run-owned aliases from protected staging credentials and run coordinates. For each, check exact Cloudflare rule absent, authenticated CLI list absent, and D1 row `retired` with `cf_rule_id=NULL` and `needs_reconcile=0` (or securely established no row). The first alias had such readback; the second's public `address_route_retired` marker alone does not attest D1. Any ambiguity blocks a new attempt until that exact alias is reconciled. Do not delete unrelated rules or create a replacement alias. |
| Current deployment and capacity | Pin the serving staging Mail Worker source/version and confirm its observability/privacy settings; confirm the same named staging secret is configured at the deploy and E2E workflow boundaries without displaying its value. Check normal Rules GET under the E2E token, the new candidate's exact route absence, synthetic account address state, sufficient rule capacity, and a quiet address-write window. Do not infer Write from GET. Avoid a push/redeploy or secret rotation across the pinned test window. |
| Reviewed output boundary | Pin a checkout containing `service_unavailable` in `SAFE_API_CODES`, fixed-only `cli_failure`, and the seven-minute exact-route/CLI cleanup readback. The hosted step must continue to suppress raw CLI stderr/stdout, Cloudflare responses, addresses, auth URL, token, and local ZIP artifacts. Ensure the complete job is within its 40-minute deadline and no debug tracing is enabled. |
| One deliberate operation | Use the existing `RUN_STAGING_E2E` manual dispatch on a pinned ref with the existing synthetic principal. Do not add a separate rule-create POST, invalid `{}` POST, or a second nonce. The harness must run native PKCE, preflight, and only then its one `amail address add`; SMTP is conditional on active address and exact literal route. The automatic OpenRouter embedding policy applies to any accepted synthetic message even if `semantic=0`; use only synthetic non-sensitive fixture content. |
| Cleanup and stop | On any outcome, require both the seven-minute exact route and CLI-list absence markers and then privately verify this run's D1 row/reconciler state. A crashed/cancelled runner requires reconstruction of **only** this run's HMAC-derived alias and exact manual reconciliation. Missing cleanup, changed rule state, retained `provisioning/deleting`, or an uncertain provider response freezes further creation. No automatic retry after a transient 5xx. |

These gates should be recorded as a short preflight/readback artifact with run URL, source SHA, deployed version, fixed boolean classifications, and timestamps only. Do not record alias, destination, secret, raw response, or full event. The GitHub job's `staging-native-mail-acceptance` concurrency only serializes that job family; it is not a platform-wide routing lock. An operator must also prevent unrelated address campaigns during the window.

## Interpretation matrix

| Observed outcome | Defensible conclusion | What remains unknown |
| --- | --- | --- |
| `address_and_literal_route_verified`, then SMTP-to-ZIP/search passes | The deployed Worker, its effective credential, Cloudflare Routing and the CLI worked for this one synthetic address at that time. This is a legitimate Rules Write *functional* test without policy introspection. | Exact token policy clauses and both prior failure causes; no claim about all users, quota races, or future revocation. |
| `address_register_failed_http_503_service_unavailable` with clean route/D1 state | Registration failed before or outside a completed successful flow; current source makes a pre-create Rules-list error plausible. | Provider phase/status and Write grant; CLI public code alone is not a complete trace. |
| `address_register_failed_http_503_routing_unavailable` with clean route/D1 state | The Worker exposed a create-boundary failure under its public mapping, assuming deployed code is pinned. | Whether Cloudflare returned 403, 400, 5xx, malformed 2xx, or transport error. Do **not** claim Write is missing. |
| Generic `address_register_failed`, other fixed failure, or cleanup uncertainty | Staging acceptance failed; retain only the fixed evidence and privately reconcile exact state. | Root cause. Do not dispatch again until the specific defect is isolated or instrumentation is improved. |

The live-tail prototype is still offline-only and lacks transport, server-side filter verification, a readiness handshake and CLI-request-ID binding. Its absence lowers **diagnostic resolution**, not necessarily **mutation safety**, provided the above cleanup/isolation gates hold. Conversely, the prior two failed creations raise the cost of another ambiguous failure: if the objective is *to identify the precise provider 403/code* rather than to complete acceptance, first add a reviewed private provider-phase diagnostic or finish the live observer. A new attempt must not be described as proving the historical root cause.
