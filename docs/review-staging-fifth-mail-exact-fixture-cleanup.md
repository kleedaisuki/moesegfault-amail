# Review: fifth hosted E2E exact-fixture cleanup

Scope: source-only review of the proposed `infra/tests/staging_fifth_mail_cleanup.py`, synthetic tests, manual `staging-fifth-mail-cleanup` CI target, and related design, on 2026-09-30. No local test, CLI login, Cloudflare request, mail mutation, workflow dispatch, push, or deployment was performed by this reviewer.

## Assessment

No remaining concrete wrong-delete blocker was found in the revised source. The initial fresh route/D1 gate requires the exact HMAC-derived retired address, expected issuer, no reconciliation, exactly one Signal and one Distractor across active/deleted rows, no other inbound or outbound rows, and the expected embedding state. Native authentication is followed by complete exact-mailbox CLI pagination. Active row counts and subjects must agree with D1; title searches are post-filtered and cross-checked by ID; owner-scoped `get` verifies exact mailbox, direction, subject, sender, recipient, submitted Message-ID, and MIME-shape fields. A second complete inventory, fresh control gate, and serving-version pin precede per-ID CLI deletion. Each deletion is attempted only once, then checked via owner-scoped `get` and full mailbox inventory. Unknown delete results stop further mutation. Final route, aggregate, inventory, and version reads are required. The workflow is manual, exact-run/attempt confirmed, staging-scoped, and does not invoke address creation, SMTP, or deployment jobs.

The first draft required deleted fixture rows to remain present throughout cleanup. That was a completion bug because Worker Cron physically purges soft-deleted rows; it could turn a successful first deletion into a failed run before deleting the second fixture. The revised post-mutation `allow_purge` gate permits a deleted row to disappear while still requiring active counts and complete CLI inventory to agree. The initial gate remains strict. This concern is resolved in the reviewed revision.

Minor fail-closed limitation: the initial `embedding_succeeded == 2` and `embedding_no_work == 0` guard can reject an otherwise safe partial-soft-delete state if a prior deletion removed pending embedding work before it completed. This narrows the documented idempotent behavior but cannot select an unsafe row for deletion. If partial-state recovery is actually needed, the embedding status should be treated separately from exact fixture identity rather than as an authorization gate.

## Limits and operational condition

The aggregate joins message ownership to the address row and checks issuer, not exact authenticated `owner_sub`; it also omits foreign-owner rows at the address. This is not by itself a demonstrated path to deleting another owner's mail: Worker search, `get`, and delete all scope to the authenticated principal, and only exact verified fixture IDs from that complete inventory are selected. It *does* limit any final claim: success means no active **owner-visible** mail at this alias plus the reported aggregate state, not global absence of foreign-owner rows or independent SMTP provenance. Matching submitted Message-ID and headers are corroboration, not cryptographic authentication; an adaptive same-header spoof remains outside what this historical run can prove. The design documents the stronger optional private owner/foreign-row attestation and the explicit residual risk.

This assessment does not establish the actual hosted aggregate values, deployed version, provider behavior, native login success, or test pass status. Do not dispatch if the fresh preflight disagrees, and do not interpret cleanup success as acceptance of the original failed E2E run.
