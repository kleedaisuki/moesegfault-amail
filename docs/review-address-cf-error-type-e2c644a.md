# Review: request-local Cloudflare error category (`e2c644a`)

Status: independent source and official-contract review on 2026-09-29. **No substantive blocker found for the instrumentation change.** This does not authorize a new address, provider write, deployment, or release acceptance. I reviewed the commit diff, adjacent `Api::execute_with_status` error flow, the hosted E2E parser and tests, the fourth-incident record, and Cloudflare's current [error diagnostic header contract](https://developers.cloudflare.com/support/troubleshooting/http-status-codes/cloudflare-error-headers/) and [Workers error documentation](https://developers.cloudflare.com/workers/observability/errors/). I did not run a live request or local heavy test.

## Assessment

- `cf_error_type` accepts only one response-header value and maps only exact bytes `1101` and `1102` to those labels. Every other present value, including a duplicate header, becomes `other`; missing is `absent`. No attacker-controlled header bytes are echoed to CLI output. This is a meaningful privacy improvement over exposing raw error pages or headers.
- `Api::execute_with_status` computes the category only for `addresses.add` with a 5xx status. It retains the existing HTTP status, closed address problem code, validated correlation ID, and optional validated Worker phase diagnostic. Other operations and 4xx add errors do not gain the suffix. The category is unavailable if response-body reading fails first, as the note states.
- Cloudflare documents `cf-error-type` on Cloudflare-generated error pages, with `1101` for an unhandled Worker exception and `1102` for resource exhaustion; forwarded origin errors do not get Cloudflare's diagnostic headers. Thus a **trusted Cloudflare-generated** 1101/1102 response is more request-specific than the incident's 69-second aggregate. Header classification still does not identify an instruction or prove the Email Routing POST returned to the Worker. A generic HTTP client cannot cryptographically attest the header's producer, so the note's inference assumes the configured Mail endpoint and network path are trusted.
- The hosted harness retains only the four closed categories in a fixed label, never CLI stderr. Its previous exact status/code and optional phase grammar remain intact, and old CLI stderr without the new suffix still parses. Rust synthetic tests cover missing, recognized, unknown, and duplicate headers; Python synthetic tests cover allowed categories, phase co-occurrence, hostile strings, and CR rejection. No test or source evidence retroactively classifies the fourth request.

## Minor consistency improvement (non-blocking)

`infra/tests/staging_mail_e2e.py::cli_failure` accepts the four `_cf_*` suffixes whenever the parsed operation is `addresses.add`, including a synthetically supplied HTTP 4xx line. The actual `Api` cannot currently produce that combination, so this is not a demonstrated deployed false diagnosis. Still, the harness is intended to be independently fail-closed; add a 5xx guard to its suffix branch and a 4xx-with-suffix regression if the grammar is next revised. This keeps its accepted evidence exactly aligned with the documented “address-add server errors only” contract.

## Limits and next gate

The tests exercise the classifier and harness parser, not a real Cloudflare-generated error response. A later independently approved, normal staging E2E may report `cf_error=1101`, `1102`, `other`, or `absent`; interpret only that actual request's category. `absent` cannot disprove a Worker exception, particularly if response handling or body reading failed. The earlier aggregate `scriptThrewException` remains unattributed to the fourth add request. Hosted CI owns compilation and cross-platform execution; no local toolchain run or alias attempt was performed in this review.
