# Independent review: reqwest recovery for the staging trace canary

Status: **source-level GO, conditional on hosted CI and a fresh guarded staging run**. Reviewed the implementation change following [hosted transport comparison 36688418919](https://github.com/kleedaisuki/moesegfault-amail/actions/runs/36688418919). Implementation commit: `3c8c1b3`. This review did not run a local heavy test, send a live probe, or inspect retained Cloudflare logs.

## Scope and evidence

The hosted comparison observed Python `urllib` returning HTTP 403 without a canonical application request ID, while the amail-equivalent Rust `reqwest` client returned HTTP 401 with one on the same synthetic staging route. The recovery replaces only the canary's anonymous Python GET with the existing feature-gated Rust helper; the normal CLI address-list operation and retained-log query remain in place.

I inspected the diff and callers in `crates/amail/src/bin/staging_http_compare.rs`, `infra/tests/staging_trace_canary.py`, `infra/tests/staging_trace_http_compare.py`, `infra/tests/staging_hosted_trace_canary.py`, `.github/workflows/staging-trace-canary.yml`, and the new synthetic tests. The helper still accepts only `https://mail-staging.moesegfault.dev/v1/messages/amail_path_canary_<32 lowercase hex>?probe=amail_query_canary_<same hex>`, with no explicit port, credentials, or fragment. It sends a single anonymous GET and stops rather than follows a redirect. Its private mode emits an ID only on exact 401, no redirect, and exactly one header parsable as a canonical lowercase hyphenated UUID; all other outcomes return a fixed failure line. Ordinary diagnostic mode continues to expose only fixed status and boolean labels, not the ID.

The Python checker invokes the helper with the synthetic URL on stdin, receives its stdout through `subprocess.PIPE`, discards stderr, and never interpolates child output or exceptions into a diagnostic. It accepts only one bounded exact private-ID line on process success; malformed output, a nonzero exit, missing helper, timeout, or transport failure becomes a fixed `UNVERIFIED` code. The subprocess receives only the pre-existing OS/proxy allowlist, not Cloudflare query or deploy tokens. The outer hosted wrapper likewise captures the checker output and emits only allowlisted fixed labels. There is no artifact upload or shell echo of the private ID, URL, path/query marker, response body, header set, Ray value, or provider error.

The workflow builds and tests the feature-gated helper only for explicitly confirmed canary mode on the protected staging Windows job. Its privacy-settings/service-key preflight remains ahead of login and probe. The existing bounded, service-filtered, fully paginated retained-event query, all-row schema/marker checks, and CLI-to-Worker parentage and anonymous-denial-record requirements were not relaxed. A valid immediate 401 cannot alone pass retained-log privacy.

## Findings and limits

No material defect was found in the reviewed change. The helper executable under `target/debug` is treated as a trusted result of the same hosted source checkout/build; this is a normal CI trust boundary, not an independent attestation of the binary. `subprocess.run` captures child stdout without an OS-level output quota, although the reviewed helper has bounded fixed output; a compromised executable would already be able to access the runner's OS/proxy environment. The canary remains a point-in-time test of one staging service and one bounded log window, not a proof about other telemetry sinks or all future traffic.

**Disposition:** GO to hosted CI, followed by one explicit, version-pinned staging canary. A CI failure, 403, redirect, absent/duplicate/malformed ID, missing retained denial record, unreviewed retained payload, or failed causal parentage remains `UNVERIFIED`. Do not infer the historical `urllib` 403's producer or declare retained-log privacy accepted from this source review.
