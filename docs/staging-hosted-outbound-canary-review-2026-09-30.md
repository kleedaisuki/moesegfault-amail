# Review of dormant hosted outbound canary (`a92c276`)

**Decision: NO-GO for a live grant/dispatch; acceptable as dormant source preparation.** This is a source review, not hosted validation. No local build, test, grant, dispatch, or email send was performed. The reusable workflow has only `workflow_call`, no direct dispatch trigger; `ci.yml` has no outbound call site. Its job requires the explicit literal confirmation and a `main` or `codex/amail-v0.1.0` ref, binds the `staging` Environment, and places mailbox/Identity/Cloudflare secrets only on the final Python step. The wrapper checks hosted Windows, performs native PKCE through the existing helper, and delegates the one-send/global-hold/recipient-pinned-grant checks to `staging_outbound_canary.py`. No sender, recipient, or subject is passed as a workflow input or shell argument. The child CLI/Chrome helpers use environment allowlists. The existing canary checks only IMAP `INBOX`, and its authentication header remains a *claim* pending independent receiver-side provenance review, as the readiness document correctly states.

## Required corrections before enabling a dispatch hook

1. **P1 — Ambiguous send loses its reconciliation key.** `infra/tests/staging_outbound_canary.py` creates the UUID idempotency key immediately before `amail send` (around line 321). A timeout or ambiguous 5xx becomes `canary_send_uncertain`, but `infra/tests/staging_hosted_outbound_canary.py:85-91` unconditionally deletes the entire run directory. Neither the key nor run nonce is then retained in a restricted operator-readable channel. When the provider may already have accepted the request but the grant is not yet visibly consumed, the operator cannot reliably inspect the *exact* D1/provider request or follow the documented “preserve the original key” recovery rule. An immediate blind re-grant or new-key rerun risks a second delivery. Persist a minimal private recovery record (key, nonce, stage, runner coordinates) before submission in a protected, bounded operator channel; retain it on uncertain/partial failure and delete only after reconciliation. Do not log raw sender/recipient/subject, upload the ZIP/MIME/session, or rely on public Actions output for this record. Add a hosted offline test that simulates an uncertain send and proves recoverability without replay.

2. **P2 — The grant timing in the documented handoff does not match this job.** `docs/staging-outbound-readiness-2026-09-30.md` says to finish same-runner native login *before* issuing the 15-minute grant. The new workflow instead runs `rustup update`, `cargo test`, `cargo build`, then native login and immediately enters the canary in one step (`.github/workflows/staging-outbound-canary.yml:36-58`); there is no protected handoff point after login at which an operator can review and issue the grant. Granting before dispatch can expire during queue/environment approval/build/login, and granting while it is running races a noninteractive preflight. The existing `<120 s` denial prevents unsafe submission, but it does not make a reliable one-run procedure. Add a guarded post-login wait/approval rendezvous or split build/login from the one-send invocation while preserving the same authenticated runner/session and exact reviewed ref. Grant only after the inbox, owner, provider, Queue/DLQ and hold preflights; do not silently auto-grant.

3. **P2 — The new denial contracts are not run by the canary workflow itself.** Its test step runs only Rust tests (`.github/workflows/staging-outbound-canary.yml:38-42`), while `infra/tests/test_staging_hosted_outbound_canary.py` and the existing canary contract are Python. `ci.yml` has Python unittest discovery, but that is separate and may not have covered the exact dispatched commit or a later hook change. Run the two targeted Python modules in the hosted build/test stage before exposing the final step's secrets. These tests are source contracts only; even green results cannot substitute for an IMAP/provider/D1 live oracle.

## Residual execution gates (not defects of this dormant commit)

The missing guarded `ci.yml` dispatch hook, consenting controlled external IMAP oracle, protected secret set, active owned staging sender, one-use recipient-digest grant, fresh Sending/Event Subscription/Queue/DLQ readback, and manual `Authentication-Results` provenance check remain prerequisites. `grant-send-canary.yml` still uses `owner_sub` as a workflow input on `main`; that privacy gap must be separately resolved or a restricted audited grant path used. A staged success must not unhold global send, imply production readiness, or attest mailbox delivery from provider `delivered` alone.
