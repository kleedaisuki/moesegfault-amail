## Required corrections before enabling a dispatch hook

1. **P1 — Ambiguous send loses its reconciliation key.** `infra/tests/staging_outbound_canary.py` creates the UUID idempotency key immediately before `amail send` (`:330-333`). A timeout or ambiguous 5xx becomes `canary_send_uncertain`, but `infra/tests/staging_hosted_outbound_canary.py:85-91` unconditionally deletes the entire run directory. Neither the key nor run nonce is then retained in a restricted operator-readable channel. When the provider may already have accepted the request but the grant is not yet visibly consumed, the operator cannot reliably inspect the *exact* D1/provider request or follow the documented “preserve the original key” recovery rule. An immediate blind re-grant or new-key rerun risks a second delivery. Persist a minimal private recovery record (key, nonce, stage, runner coordinates) before submission in a protected, bounded operator channel; retain it on uncertain/partial failure and delete only after reconciliation. Do not log raw sender/recipient/subject, upload the ZIP/MIME/session, or rely on public Actions output for this record. Add a hosted offline test that simulates an uncertain send and proves recoverability without replay.

2. **P2 — The grant timing in the documented handoff does not match this job.** `docs/staging-outbound-readiness-2026-09-30.md` says to finish same-runner native login *before* issuing the 15-minute grant. The new workflow instead runs `rustup update`, `cargo test`, `cargo build`, then native login and immediately enters the canary in one step (`.github/workflows/staging-outbound-canary.yml:36-58`); there is no protected handoff point after login at which an operator can review and issue the grant. Granting before dispatch can expire during queue/environment approval/build/login, and granting while it is running races a noninteractive preflight. The existing `<120 s` denial prevents unsafe submission, but it does not make a reliable one-run procedure. Add a guarded post-login wait/approval rendezvous or split build/login from the one-send invocation while preserving the same authenticated runner/session and exact reviewed ref. Grant only after the inbox, owner, provider, Queue/DLQ and hold preflights; do not silently auto-grant.

3. **P2 — The new denial contracts are not run by the canary workflow itself.** Its test step runs only Rust tests (`.github/workflows/staging-outbound-canary.yml:38-42`), while `infra/tests/test_staging_hosted_outbound_canary.py` and the existing canary contract are Python. `ci.yml` has Python unittest discovery, but that is separate and may not have covered the exact dispatched commit or a later hook change. Run the two targeted Python modules in the hosted build/test stage before exposing the final step's secrets. These tests are source contracts only; even green results cannot substitute for an IMAP/provider/D1 live oracle.

## Narrow follow-up of `8a10c94` (2026-09-30)

**Decision: GO for hosted source CI; previous P2 resolved for the guarded wrapper. Live send remains NO-GO.** No local or hosted test, grant, dispatch, or email send was performed in this review. The wrapper now takes one D1 statement snapshot of both current canary expiry and maximum release-gate audit ID *after* native login and before printing the ready marker. `grant_ready()` requires the currently unused grant to match the owner, recipient digest and run-derived case reference, to expire at least 120 seconds in the future, to have an expiry strictly greater than the snapshot, and to have a matching audit row with ID greater than the snapshot. The audit trigger records each gate update; an unrelated attestation of an old grant cannot satisfy the expiry increase, even if it copies the same case reference. The operator grant command writes both the new expiry and case reference in one `UPDATE`. A same-second regrant can fail closed because its expiry may not increase; the runbook explicitly says so.

The wrapper passes the same immutable watermark to the final `execute()` preflight, so the grant is rechecked after polling and before ZIP packing or `amail send`. The new negative tests cover an old exact grant and a newer expiry without a matching audit row; the workflow already runs those Python suites before exposing secrets. This does not make the preflight and provider send atomic: grant expiry or operator revocation between those actions must fail safely in the Worker, not be interpreted as delivery. A separate guarded `ci.yml` dispatch hook, protected mailbox/secret provisioning, manual grant privacy review, receiver-side `Authentication-Results` provenance and deployed external-inbox plus provider-feedback evidence remain required before any live-send claim.
