# Independent review: current hosted address-add retained-log diagnostic

Scope: static review of the proposed one-run manual workflow target, `infra/tests/staging_current_address_failure_logs.py`, its synthetic tests and incident note, plus the reused retained-query and historical-classifier contracts. No local test, Cloudflare query, route or address mutation, workflow dispatch, or production-code edit was performed.

## Assessment

No substantive source-level blocker was found for **one read-only dispatch after hosted CI passes**. The target is manual, branch-limited and requires an exact run-specific confirmation. Cloudflare credentials are scoped to its final query step. The script performs the established deployed-privacy/key preflight followed by a dry query for only the staging mail service in the fixed 10:11:40–10:16:07 UTC window; the reused reader checks completion, response echoes, cursor progression, stable total count and a 1600-record cap. Neither the target nor its call graph contains a Mail API, D1, SMTP or Email Routing Rules write. The Observability query itself uses POST as a read operation; it is not a routing-rule POST.

The shape discriminator emits only a finite set of declared type/presence categories and a coarse source-object key bucket. It never emits provider-supplied key names or values, record counts, event IDs, request IDs, addresses or exception text. It also requires each returned row's service metadata to equal the staging mail Worker before printing source shape. An unknown source wrapper remains rejected by the historical classifier; the type probe does **not** silently authorize that wrapper for causal classification or weaken the separate full retained-log privacy canary. The new tests cover private-key/value non-disclosure, wrong-service rejection, unknown-wrapper rejection and a failed query, though hosted CI has not yet exercised them.

The chosen window is wider than the add call because the hosted harness discarded its request identifier and did not retain an add-stage timestamp. It is nevertheless the narrowest observed superset of the complete mail step, with two-second margins. The existing classifier requires one failed request-exit event and linked routing phases; multiple candidate roots, missing/ambiguous phases, incomplete pagination or unreviewed records fail closed. A positive result is explicitly prefixed `window_consistent_`, not presented as identity proof. In particular, an unobserved create phase is not proof that no provider POST occurred, and the absence of D1 phase events cannot explain a D1 failure. A classification must not by itself authorize another registration or production sending.

## Evidence limits and next gate

This review does not show that Cloudflare retained the relevant event, that the provider `source` wrapper is reviewed, that the queried events belong to the failed CLI invocation, or that the routing token has Write authority. The prior historic query returned `unreviewed_source_object`, so a similar **UNVERIFIED** result is plausible and should not be treated as a script failure to work around by broadening the parser. The next meaningful check is hosted infrastructure CI followed by one explicit, bounded read-only dispatch. If it returns only a shape category, any exact-wrapper interpretation requires a separate privacy review before changing the causal parser.

## Follow-up review: positive-only metadata-message candidate

The first hosted read-only query, [run 36557318817](https://github.com/kleedaisuki/moesegfault-amail/actions/runs/36557318817), returned a complete, dry, exact-scope event view but mixed opaque source-object shapes. The strict classifier correctly stayed `UNVERIFIED (unreviewed_source_object)`; the run did not reveal a routing cause or establish retained-log privacy. I reviewed the proposed positive-only fallback against that result and the incident-deployed Worker source (`6004dc3`). At that source revision, the Worker's only dynamic `console_log!` calls serialize the fixed `trace.rs` event schemas; other console emissions in the mail Worker are fixed warning literals. Cloudflare's official telemetry schema documents an optional indexed `$metadata.message`, opaque `source` map/string and top-level millisecond `timestamp`. These facts make a narrowly qualified trace-shaped console message plausible evidence, not an authenticated request identity or a license to parse the remaining source object.

**No substantive source-level blocker was found in the revised fallback for reporting an observed candidate phase.** It first requires the unchanged bounded/cursor-complete staging-service query and keeps the strict classifier as the primary path. Only on the known `unreviewed_source_object` outcome does it parse a one-line, ASCII, at-most-4096-UTF-8-byte `$metadata.message` JSON object with duplicate-key rejection. A positive candidate additionally requires the exact string echoed at `source.message`, compatible `log` levels when present, exact service and per-record timestamp, the allowlisted producer fields, one observed failed `addresses_add` root, and linked, ordered routing child spans with matching request/trace/parent IDs. Numeric provider facts remain bounded by the existing event validator. Unknown extra source keys are neither inspected nor printed. The script emits a `candidate_window_consistent_*` label, emits retained privacy `UNVERIFIED`, and exits nonzero even if the candidate chain is present. Absence of a child remains `UNVERIFIED`, never “no POST” or a D1 diagnosis. The synthetic tests cover the conditional label, duplicate keys, mismatched echo, wrong parent, duplicate roots, timestamp rejection and multibyte bounds; they remain unexecuted until hosted CI.

**Interpretation limit:** Opaque rows can conceal another address-add request or contradict an observed chain, and the failed CLI's request ID was discarded. Therefore a candidate phase supports only “this staging Worker appears to have emitted a coherent matching trace in the mail-step window,” not “this was the E2E request,” “the log set is private/exhaustive,” or “the routing token lacks Write.” The exact source-message echo is a useful cross-field consistency check, not a cryptographic provenance guarantee. A positive candidate should guide the next read-only or controlled product test, not independently authorize another alias or production sending. If hosted CI fails or the actual provider wrapper lacks the exact echo, retain `UNVERIFIED` rather than weakening the source contract.
