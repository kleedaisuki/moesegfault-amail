# Review: historical staging role Cron phase-log oracle (`0b5c360`)

Verdict: **NO-GO for dispatch pending one small evidence-integrity correction**. This is a source review only: no Cloudflare query, local heavy test, or historical phase observation was performed. The read-only provider call, hard-coded failed-run coordinates, strict fixed-output boundary, bounded response, cursor checks, and GitHub secret scoping are directionally sound. Cloudflare's [telemetry API schema](https://developers.cloudflare.com/api/resources/workers/subresources/observability/subresources/telemetry/methods/query/) documents `eventType`, optional `requestId` and `scriptVersion`, and raw `source`; none is guaranteed present in each retained row, so their absence must remain `UNVERIFIED`.

## Necessary correction: reject contradictory labels in the digest invocation

`infra/tests/staging_role_phase_logs.py:249-255` rejects two distinct failed phases and `healthy` together with `health_failed`, but does **not** reject `healthy` together with a failed phase. A completed, syntactically valid returned page containing the same request ID on `role alert digest accepted groups=1`, `role monitor phase=destination failed`, and `role monitor healthy pending=0` returns `same_invocation_destination_failed`. This is impossible for the reviewed `run_monitor` control flow: `phase("destination", ...)?` returns on error before the final healthy log. Likewise, `digest_accepted` followed by `phase=digest failed` is impossible because the accepted log is the last action in `flush_alerts` before `Ok(())`. A provider schema/correlation anomaly would thus become a specific historical failure claim rather than `UNVERIFIED`. Reject every failed-phase/healthy pairing, and reject the digest-failed/digest-accepted pairing, with a closed `invocation_phase_ambiguous` label. Add synthetic tests for both contradictions. This does not assert that Cloudflare actually returned such records; it preserves the oracle's promised fail-closed semantics when evidence conflicts.

## Secondary, worthwhile hardening

`classify()` checks `$metadata.service` and the exact version but not `$workers.scriptName`, although the [telemetry API schema](https://developers.cloudflare.com/api/resources/workers/subresources/observability/subresources/telemetry/methods/query/) exposes `scriptName` on Worker records. The indexed service filter makes accidental cross-service attribution unlikely, so this is not independently a dispatch blocker. Requiring `scriptName == amail-role-monitor-staging` for scheduled rows (and preferably every row) would provide an independent scope check; a missing field should yield `UNVERIFIED`, not a fabricated name. The established fourth-address metadata probe already uses this invariant (`docs/review-staging-fourth-exception-metadata-probe.md`). Add one wrong-name and one missing-name synthetic case if changed.

## Scope and residual uncertainty

- The hard-coded UTC milliseconds match the documented failed job window, and source labels match `workers/role-monitor/src/lib.rs` at historical SHA `337925f`. `historical_run()` checks the exact completed, failed workflow-dispatch run and SHA before querying. The version UUID is a previously pinned fact, not independently re-extracted from the run by this script.
- Every page is a new `dry=true` query with exact service/time echo; unchanged count plus unique cursor IDs protects against ordinary partial pagination, but cannot prove logs were ingested or not sampled. `no_reviewed_invocation`, `digest_not_observed`, and digest-only remain inconclusive as documented. Cloudflare [Workers Logs retention](https://developers.cloudflare.com/workers/observability/logs/workers-logs/) is short; a safe query should not be postponed longer than necessary after correction and hosted tests.
- Raw event bodies, IDs, private destination and provider errors remain in process memory and are not printed; all public outcomes are fixed labels. `CF_OBSERVABILITY_TOKEN` is a capability-bearing token and `dry=true` constrains the **operation**, not the token's authority. The workflow gives that token only to the final classifier step, does not provide the forwarding or routing secrets, and rejects redirects. The runner and token are still trusted surfaces; no log/artifact dumping should be added.
- Even a same-invocation phase label localizes execution only; it does not prove downstream delivery. A `healthy` label conflicts with the D1 snapshot and calls for reconciliation, not retroactive acceptance.
