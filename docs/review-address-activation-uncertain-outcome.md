# Review: uncertain D1 address activation

Scope: uncommitted `crates/mail-worker/src/lib.rs` activation change, `infra/tests/worker-boundary/address-add.test.mjs`, `docs/worker-address-boundary-tests.md`, and the decision in `address-activation-uncertain-outcome.md`. Source and test-fixture inspection only; no live Cloudflare call and no hosted or local runtime test. This review does not identify the cause of the fourth staging HTTP 500.

## Blocking finding: duplicate pruning still precedes ownership confirmation

**Location:** `add_address`, `crates/mail-worker/src/lib.rs:1370-1376`; interacting Cron path at `:301-316`. **Confidence:** high in the executable race; conditional on two exact owned rules and different observed first-rule ordering or rule-set snapshots. **Impact:** an `active` D1 address can lose the rule named by `cf_rule_id`, causing silent inbound mail loss. Current Cron normally selects `provisioning`/`deleting`, not a healthy-looking `active` row, so it will not automatically repair this state.

The patch correctly stops deleting `rule_id` after an uncertain activation result, but `add_address` still executes `delete_rule` for every `existing_rules` item after the first **before** its conditional D1 UPDATE or exact owned readback. With duplicate exact routes `A` and `B`, Cron may list/adopt `A` as the active `cf_rule_id` while add observes `B` first and `A` as an extra. Add deletes `A`, its UPDATE affects zero rows, and readback sees active `A` rather than its chosen `B`; it returns `503 address_provision_unknown` while the D1 active row now names a deleted route. Provider list ordering is not an ownership lock, and both operations perform independent GETs. A similar race exists in Cron's own `UPDATE ... state='provisioning'` followed by extra deletion without checking whether it changed a row or which rule an already-active row names.

**Correction:** never prune an exact duplicate in add before a state-aware activation decision. Make the D1 active row's actual `cf_rule_id` authoritative and preserve it. Duplicate cleanup should be a separate reconciliation step that first confirms current row state and ID, and should not delete the active ID even if another actor chose a different first rule. Because D1 and provider deletion are non-atomic, re-read/reconcile after deletion where feasible; avoid treating a stale snapshot as permission to remove the chosen route. The uncertain-outcome fix can first omit opportunistic duplicate deletion; that is safer than preserving this eager cleanup. Extend hosted fixtures with two exact rules and an interleaving where Cron's adopted ID differs from add's selected ID; the current fake GET returns `[]`, so it cannot detect this path.

## Other checks and limits

- The new activation classification preserves `Err` and missing metadata as unknown rather than coercing them to `changes=0`; exact owner-scoped readback gates `201` on `active` plus matching `cf_rule_id`. This meets the central decision's non-destructive uncertain-write rule. Confirmed zero plus `deleting`/`retired` still maps to the old `409 address_state_changed`; other unconfirmed mismatches remain `503 address_provision_unknown`. No private provider body, alias, or rule ID enters the new diagnostic output.
- The injected SQLite trigger rejects the asynchronous activation write while leaving allocation/claim available. The resulting `503`, `provisioning` row, and unused DELETE fixture realistically guard this one D1 boundary through the real Wasm Worker. It cannot model a committed write whose acknowledgement was lost, a synchronous `prepare` trap, a Cron/delete interleaving, or actual Cloudflare D1/Rules behavior. These are limits, not reasons to call the historical 500 fixed.
- Readback `.prepare()`/`.bind()` still uses `?`, so those returned errors map to the generic existing service error rather than `address_provision_unknown`; they do not delete the route. A synchronous worker-rs `prepare` throw is outside this patch's safety guarantee and remains a separate hypothesis for the historical 500.

## Revised diff assessment

The implementation subsequently removed add's eager duplicate DELETE and added a distinct `active` plus `needs_reconcile=1` Cron path. That path checks that the committed `cf_rule_id` is present in the exact owned provider-rule list, deletes only IDs different from it, and clears the flag with an `active`/ID-conditional UPDATE. The provisioning Cron path no longer prunes extras after an unverified UPDATE; it records a duplicate flag for a successful adoption. The previous blocking route-loss race is **resolved in the revised diff**, conditional on the hosted scheduled-event test passing. The new test dispatches the actual scheduled Worker with two exact owned routes and checks that the selected active rule's DELETE fixture remains unused; this is a meaningful regression guard, though it does not simulate competing requests or Cloudflare consistency.

**Nonblocking follow-up:** when add observes multiple exact rules but its activation returns `NoChange` or `Unknown`, its readback may see an `active` row with a **different** saved ID. It returns uncertainty without marking `needs_reconcile`; if the other actor adopted from a one-rule snapshot and therefore did not set the flag, an extra exact route can remain indefinitely. This is a recoverable duplicate/capacity leak, not the original mail-loss failure. A guarded `UPDATE ... SET needs_reconcile=1 WHERE address=? AND owner_iss=? AND owner_sub=? AND state='active'` after that readback, when add's exact list had duplicates, would close the gap; failure to set it must not trigger provider deletion. Likewise, `active` plus flag with missing saved provider ID currently stays flagged but makes no repair or alert; that is fail-safe for deletion, but should become a separately observable anomaly if seen live. Do not “fix” it by deleting other listed routes.

## Final static pass on monotonic duplicate flag

The further revision records `needs_reconcile=1` before a provisioning Cron activation when multiple exact rules were observed, uses `MAX(needs_reconcile, duplicate_rules)` during both Cron/add activation, and best-effort marks a mismatched active readback after add observed duplicates. These changes close the previously noted active-duplicate flag gap without changing the committed rule ID. However, they create one **new blocking state-machine path** unless the generic Cron deletion branch is narrowed.

**Location:** `reconcile_addresses`, especially the `provisioning` premark, its `provisioning -> pending` timeout, and the final state-agnostic deletion branch (`crates/mail-worker/src/lib.rs:323-355` in the final diff). **Trigger:** Cron sees two exact rules and sets `provisioning.needs_reconcile=1`; activation then fails or remains uncertain. If a later exact lookup sees no rules after the ten-minute timeout, Cron changes the row to `pending` but leaves `needs_reconcile=1`. The next Cron selects this `pending` row due to the generic `OR needs_reconcile=1` predicate and treats it as a deletion candidate. A concurrent same-alias retry can create an exact route after Cron's stale pending selection but before its provider GET; Cron then deletes that route while the retry may activate the D1 row and return 201. This is again an active address without its route. The route disappearance and interleaving are conditional, but every transition is executable under the current code; the generic branch has no state check before provider DELETE.

**Correction:** only `deleting` and `retired` should enter the provider-removal branch; `pending` must not be interpreted as a deletion state, even if a stale flag remains. Clear `needs_reconcile` when intentionally returning a ruleless provisioning row to `pending` to avoid repeated selection. A hosted synthetic fixture for `pending + needs_reconcile=1` and a provider rule should assert that scheduled reconciliation does not DELETE it. Do not rely solely on clearing the flag: Cron can already have selected a stale pending snapshot, and explicit state-scoped destructive behavior is the stronger invariant.

### Follow-up revision

The implementation now clears `needs_reconcile` on the ruleless `provisioning -> pending` timeout, handles a selected `pending` row without provider DELETE (clears a stale empty flag, or returns a row with exact rules to `provisioning`), and restricts the destructive Cron loop to explicit `deleting`/`retired` states. This closes the pending-state route-loss path even under a stale Cron selection. The add path also best-effort marks an exact owner-scoped active row after a failed provider-create response or mismatched active readback; the marker is only for safe reconciliation and never licenses inline deletion.

**Final static verdict:** no remaining concrete blocker found in the revised uncertain-activation and duplicate-pruning paths. A hosted scheduled-event regression fixture for `pending + needs_reconcile=1` with a concurrent-looking exact rule would improve coverage of the safety invariant, but the source fix is not contingent on that fixture for this static verdict. Cloudflare deployment and actual D1/Rules behavior remain unverified by this review; the full hosted suite must pass. No local heavy test or live call was performed.
