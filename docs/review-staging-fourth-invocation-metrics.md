## Assessment

**No remaining source-level blocker found for one read-only diagnostic run**, provided the new infrastructure test job passes on GitHub and the workflow dispatch uses its exact confirmation. The initial status allowlist included undocumented `other`; the implementation and runbook now admit only Cloudflare's five documented invocation statuses, and reject any unknown label as `UNVERIFIED`. Cloudflare's [Workers Metrics GraphQL tutorial](https://developers.cloudflare.com/analytics/graphql-api/tutorials/querying-workers-metrics/) supports the selected `viewer.accounts` / `workersInvocationsAdaptive` shape, account and script/time filters, dimensions, and sums. Its [invocation-status documentation](https://developers.cloudflare.com/workers/observability/metrics-and-analytics/#invocation-statuses) confirms that status is distinct from HTTP response status.

The fixed UTC interval `2026-09-29T12:24:32Z`–`12:25:41Z` matches the GitHub-hosted **execution-step** bounds of run `36567571204`, not an invented timestamp for the add request. The query is explicitly account-scoped, script-scoped to `amail-mail-staging`, and selects only timestamp/script/status and aggregate request/error counts. The parser checks that returned script names and timestamps match the requested scope, rejects multiple accounts, unknown fields/statuses, duplicate dimension rows, invalid counters, empty results, and a full 100-row page that could hide truncation. The GraphQL API has dataset-specific limits; treating the limit as ambiguous is appropriate. See [Cloudflare GraphQL limits](https://developers.cloudflare.com/analytics/graphql-api/limits/).

The workflow is manual `workflow_dispatch` only, restricted to the intended branches and staging environment. It does not run on push/PR, does not modify routing/mail state, and passes the observability credential only to the query step. The helper makes one HTTPS POST to the GraphQL read API, refuses redirects, never retries, keeps the bounded response in memory, and emits only fixed reason/status labels plus capped counts. HTTP/GraphQL error bodies, exception text, account ID, credential, timestamp, URL, and raw JSON are not printed. The synthetic tests cover unexpected provider fields, duplicate JSON keys, status/scope/count failures, a simulated private exception, and confirmation gating; the hosted infrastructure job discovers the new test file.

## Interpretation boundary

The whole 69-second execution step also contains login and other Mail Worker traffic. Even a single non-success status bucket is **not** evidence that the add invocation had that status; a `success`-only bucket does not prove the target invocation is represented, nor rule out an application-generated or edge HTTP 500. A mixed, empty, schema-incompatible, permission-denied, or limit-exhausted response remains `UNVERIFIED`. The output is useful as a coarse discriminator and for choosing a later privacy-reviewed investigation, not as per-request root-cause attribution. Do not replay address creation on the strength of this aggregate alone.

Validation still required: GitHub-hosted synthetic tests and, if those pass, one guarded read-only GraphQL query. A query result must be recorded separately with its run ID and the above limits; this static review must not be cited as a live observation.
