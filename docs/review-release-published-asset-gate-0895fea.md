## Verdict

The tag workflow now downloads assets by the exact preflight-derived tag and repository, requires exactly the six versioned archive names plus `SHA256SUMS`, rejects path-like/duplicate/noncanonical checksum entries and symlinks, and recomputes SHA-256 over the downloaded archive bytes. Its read-only `GH_TOKEN` scope is sufficient for its Release read path and cannot publish assets. `launch-site` depends on this verification job, so a failed tag-job download or digest blocks **that** launch path. The bounded parser output does not print asset contents, URLs, or credentials. Offline tests cover the main name/manifest/hash rejection cases and run in hosted infrastructure CI.

This is a useful corruption/completeness gate, **not** authentication of the Release bytes to the build or an invariant for every production-site deployment. The two findings below matter before describing it as a universal public-launch integrity gate.

## Findings

1. **P1 — the existing manual production-site path bypasses byte verification.** `.github/workflows/ci.yml:808-855` sets `release-ready=true` for any non-draft version-matching Release containing seven expected *names*; `deploy-site` then builds published copy. If `publish` succeeds but the new `verify-published` job fails because an archive is corrupt, a wrong extra asset exists, or GitHub download is temporarily unavailable, a later manual `ci.yml` production dispatch can still deploy the public site from `main`. The new dependency in `.github/workflows/release.yml:216` constrains only the tag workflow. This violates the stronger claim in `docs/operations.md:184-191` that the public site cannot deploy when the byte check fails. Make the manual production path perform the same bounded download-and-verify (or consume a trusted, tag/source-bound verification status) before its site deploy. Do not treat asset-name presence as equivalent. This is an executable alternate path, not a hypothetical compromise.

2. **P1, conditional security limitation — a replacement archive plus replacement manifest passes.** `infra/release/verify_published_assets.py:56-77` verifies only that the six *downloaded* archives agree with the *downloaded* `SHA256SUMS`; it has no trusted comparison with `assemble`'s workflow artifact/digests or the existing per-archive/skill attestations. Anyone able to replace Release assets and the manifest before this gate runs can supply a self-consistent malicious seven-file bundle, and `release_asset_integrity=verified` will be printed. The code/docstrings correctly say the manifest is not a trust root; the misleading operational wording is the universal “byte check”/“integrity” implication. If malicious Release mutation is within the intended threat model, compare the downloaded manifest (or every digest) with the same-run assembled artifact, or verify subject digests against the provenance attestations bound to this run/tag; then also protect subsequent public links against later mutation via immutable Releases/operational controls. If the intended scope is only accidental incomplete/corrupt upload, say so explicitly and do not count this as provenance verification. No current asset tampering is evidenced.

## Additional operational note (not a blocker)

`gh release download` immediately follows `gh release create` with no bounded retry. A transient API/CDN propagation or network failure will fail closed before site launch. Rerunning **failed jobs** should recover the read-only verification without recreating the already-successful Release; nevertheless, a short retry limited to download/network failure would reduce false cutover failures. Never retry away a parsed name/digest mismatch. This note does not establish that GitHub propagation actually failed.

The exact-tag selection is good: `preflight` derives the tag from CLI/site versions and requires the tag's source commit to be on `origin/main`; `gh release download "$RELEASE_TAG" --repo "$GITHUB_REPOSITORY"` does not select “latest”. The verifier's filename character class and equality with generated exact expected names prevent checksum-path traversal. Local `directory.iterdir()` and `read_bytes()`/`file_digest()` operate only on a fresh runner directory, so filesystem TOCTOU inside the job is not a practical risk absent a compromised runner; release mutation **after** verification is a distinct lifecycle risk. Python 3.12 provides `hashlib.file_digest`, and `dict_keys == set` correctly checks exact checksum coverage.
