# Staging address-add: runtime-boundary decision after valid Rules Write

Status: **design decision, not permission to create another address** (2026-09-29). No live state was changed by this investigation. This note follows the [three address-add incidents](staging-address-add-incident-36524101354.md), the [current-run incident](staging-current-address-incident-36553799873.md), and the [one-use valid disabled-rule probe](staging-routing-valid-write-self-test.md). The executed probe and delayed audit are recorded in [validation](validation.md#one-use-valid-disabled-rule-write-probe-and-independent-absence-audit).

## Facts, bounded inferences, and the next question

The hosted native login, Mail authorization, authenticated `address list`, and complete exact-rule preflight passed in the third E2E; `address add` emitted only `mail_address_register_failed`, and no SMTP step ran. That bare label is **not** a provider response: `infra/tests/staging_mail_e2e.py::cli_failure` exposes only a regex-matched HTTP status plus an allowlisted public API code; it collapses a transport timeout, non-problem HTTP body, authentication/client failure, and unrecognized code into the same label. The worker's ordinary Routing Rules GET error maps to HTTP 503 `service_unavailable`; its typed Rules POST error maps to HTTP 503 `routing_unavailable` or 409 `capacity_exhausted`. These were allowlisted at the third run's source, so an ordinary formatted response on those paths **would normally have been classified more specifically**. This is a source-level inference about the parser, not evidence that either provider call did or did not happen. The CLI has a 30-second HTTP timeout inside the harness's 90-second subprocess cap; both are plausible boundaries, not an observed cause.

The valid disabled rule probe returned `created`, strict readback, `removed`, and a delayed exact-rule `absent` audit. This proves that the **GitHub job's** present `CF_EMAIL_ROUTING_TOKEN` could create/delete one staging rule at that moment. The Worker receives the same *named* secret through the staging deploy job, but neither a name nor a successful deploy proves the currently serving Worker's secret bytes, effective egress/IP conditions, or runtime request behavior. The probe also did not exercise `enabled=true`, D1 slot allocation, or the CLI. Therefore it lowers the priority of a **shared static policy lacks Rules Write** hypothesis; it does not eliminate Worker-specific permission, token drift, GET/schema, D1, transport, or response-format failure.

The third alias was route-absent but D1-not-clean shortly after cleanup, then exact-route-absent/D1-clean after a later read. Those observations are compatible with the `provisioning → deleting → retired` reconciler, but the first readback did not expose a state and was **after** the harness's delete; it cannot identify the original add stage. In particular, deleting a `provisioning` row with no saved rule skips `rules_for_address`, so `address_route_retired` alone does not prove the runtime routing token could list rules.

The practical next question is: **for one causally bound, normal authenticated staging `address add`, did the CLI receive a Worker problem response, and if so which first failing boundary—D1, Rules GET, Rules POST, or post-create activation—produced it?** A retrospective Workers Logs query remained `UNVERIFIED` on opaque `source` objects; do not weaken its privacy parser or infer absence of a span. [Cloudflare Workers Logs](https://developers.cloudflare.com/workers/observability/logs/workers-logs/) can contain automatic invocation data and custom logs, while trace-sampling research such as [TracePicker (FSE 2025)](https://doi.org/10.1145/3729351) demonstrates why missing sampled spans are not reliable negative evidence. The production-grade lesson is to make one operation's *own bounded result* diagnostic, with independent exact-state readback, rather than keep widening a retrospective log query. The research direction—selectively retaining high-value spans—is promising for later telemetry design, but not a substitute for this one-use acceptance oracle.

## Recommended instrumentation before any further address mutation

1. **Make the CLI failure boundary machine-classifiable without printing stderr.** Preserve its default human error text and API wire contract. Internally classify `auth_before_request`, `transport_timeout`, `transport_other`, `http_problem_known`, `http_non_problem`, `http_problem_unknown_code`, `success_body_invalid`, and `subprocess_timeout`; carry only exact 3-digit HTTP status when one exists, a fixed allowlisted public code, presence/absence of `x-amail-request-id`, and a privately held valid UUID correlation ID. Do not copy the HTTP body, arbitrary error string, URL, token, address, or request ID to Actions output. Prefer a typed CLI error/optional machine-readable diagnostic over extending the current regex by accepting arbitrary text. Synthetic hosted tests must feed malformed/hostile bodies and stderr and assert fixed-only output. A transport failure is **not** proof that the Worker did not receive the request.
2. **Tag the first failure boundary in the Worker, once.** Use a closed enum, not a growing collection of free-form log strings: `input`, `d1_lookup`, `d1_allocate`, `d1_claim`, `routing_list`, `routing_create`, `d1_activate`, `d1_readback`, `response_encode`. Set it at each `?` or explicitly mapped failure in `add_address`. Keep existing HTTP statuses and public `code`s unchanged. For `routing_list`, distinguish request/transport, non-200 HTTP status, `success=false`, and malformed list; retain only numeric HTTP status if available. `routing_create` already has a typed numeric provider status/first numeric Cloudflare code. Do not treat a malformed successful POST response as a definitive rejection: it may have created a rule. Do not log a D1 statement, bound values, address, rule ID, provider body/message, or error `Display`/`Debug`.
3. **Return a narrowly bounded diagnostic on the existing authenticated add response, not a public new endpoint or raw Cloudflare log.** The least new mechanism is an optional staging-only response header (or equally constrained optional problem extension) containing the closed phase, a numeric provider HTTP status/code **only for an observed response**, and a fixed `unknown` when unavailable. The normal `x-amail-request-id` remains the causal key. The CLI/harness validate the header grammar and emit only fixed phase/status classifications; they keep the correlation ID in memory for a private exact query. Production need not enable the extra header. No new privileged route-write endpoint, no secret reuse, and no public mutation oracle are justified. If a non-Worker gateway returns 5xx, the diagnostic and request ID may be absent; that is a useful separate classification, not a false `routing_create` result. This header is evidence only for the **same** HTTP response; it does not establish all backend side effects after a timeout.
4. **Add pre-cleanup exact-state observation to the hosted harness.** Immediately after the one CLI add outcome and **before** `finally` retires the alias, perform the existing complete Cloudflare Rules inventory and a parameterized D1 `SELECT` for this run's HMAC-derived alias, using the reviewed read-only techniques in `staging_prior_alias_reconcile.py`. Reduce in memory to `route_absent|one_exact_owned|conflict|unverified` and `row_absent|pending|provisioning|active|deleting|retired|unverified`, plus whether `cf_rule_id` is null and `needs_reconcile` is set. Do not print the alias, row, ID, owner, or raw API response. A D1 row is a state snapshot, **not** proof of which request performed a provider call; it may race with Cron. Prefer the bound request's response phase when available. If either readback is uncertain, still run cleanup but report its uncertainty separately rather than masking the primary failure.

This is an additive diagnostic, not a change to user-visible address semantics. Avoid storing another permanent diagnostic table in D1: the response and exact readback suffice for one-use diagnosis and avoid a new retention/cleanup surface. Avoid a new public `/diagnostics/routing` endpoint: it would validate only GET and duplicate the existing path while increasing attack surface. Avoid relying on live Tail until its transport and privacy gates are operational; the current offline prototype is not an observer. These alternatives add more moving parts or weaker evidence than the bounded response plus state snapshot.

## One-use staged acceptance and stopping matrix

**Before dispatch:** land an independent review of the enum/header/parser privacy contract and hosted synthetic tests; deploy it to staging; pin the sole 100%-serving Mail Worker version and effective observability/bindings; privately check the staging secret injection path and that the GitHub token has not rotated since the successful valid-rule probe. Reconfirm all previous exact aliases and the new run candidate are route-absent/D1-clean, account quota/capacity is available, outbound is held, and a quiet routing window exists. The HMAC password must remain stable for crash recovery. Document a separately available exact-run read-only reconciliation target and cleanup window. These are gates, not assertions already passed.

**One normal call:** use the existing Windows hosted native PKCE path and one HMAC-derived staging alias. Do **not** run a parallel direct API POST, replay `address add` after a timeout, or synthesize a second alias as a control. Capture the CLI outcome and request ID only in memory, then immediately take the pre-cleanup D1/rule snapshot above. On success, retain the current active/literal-rule/SMTP→ZIP→search acceptance flow. On failure, allow no SMTP; retire only this run's alias and require exact Cloudflare route and D1 reconciliation, including a delayed separate read-only audit if Cron has not settled. Cancellation or any conflicting rule/row freezes further creates.

| Observed single-call facts | Supported diagnosis | Immediate action |
| --- | --- | --- |
| CLI `http_problem_known`, stage `routing_list`, bounded GET status or shape reason | Worker reached Rules GET and failed before a *normal* create branch | Inspect runtime credential/egress/provider response privately; do not infer historic failures. |
| CLI `http_problem_known`, stage `routing_create`, numeric provider status/code | Rules POST boundary was reached; numeric result distinguishes authorization/validation/provider response class | Correlate with the exact pre-cleanup rule snapshot; `2xx` malformed remains ambiguous. No blind retry. |
| CLI problem, stage `d1_*`, exact row snapshot consistent | Worker failed at a named D1 boundary | Investigate the specific SQL/binding/migration; the snapshot is corroboration, not a causal trace by itself. |
| CLI transport timeout or subprocess timeout, with/without a row/rule | The client did not obtain a conclusive response; side effects are unknown | Freeze, privately reconcile exact row/rule and request ID if present; no second alias. |
| HTTP non-problem response with no Worker request ID | An edge/gateway/non-Worker response is plausible, not proven | Check pinned route/service and numeric status using restricted provider observability; no provider POST inference. |
| CLI success, D1 active and exactly one enabled owned literal rule | Current address provisioning passed | Continue the *same run* to SMTP→ZIP/search; production stays held until remaining gates pass. |
| Any contradictory provider/D1 ownership, duplicate rule, failed cleanup, or unreviewed output | No safe causal conclusion | Stop campaign; exact ID-proven operator resolution and separate clean audit precede any new create. |

Record source SHA, deployed version, run URL, bounded phase/status/code, pre-cleanup and final state labels, cleanup/audit timings, and whether request correlation was available in `validation.md`. This one-use result can validate the **current** runtime path; it cannot retroactively identify the three older failures. No production send, release, or v0.1.0 promotion follows from the valid disabled-rule probe alone.
