# Review: exact first role SMTP timeout audit

Reviewed commit `11189f9` (success-shape amendment of `ba598b6`) and corrective commit `024441a` against the role D1 migration, Email Worker, route inventory helper, staging deployment reader, and GitHub workflow. This is a source review, not a live dispatch or provider observation.

## Resolved finding: bearer tokens followed provider redirects

`infra/tests/staging_role_timeout_audit.py:query` calls the default `urllib.request.urlopen` on a POST with `Authorization: Bearer <CLOUDFLARE_API_TOKEN>`. Python's default `HTTPRedirectHandler` follows a 302 and copies that header onto a redirected GET, including a cross-host URL. A local, network-free standard-library probe reproduced `GET Bearer private https://other.example/`. The audit's `provider_state` also invokes `workers/role-monitor/staging_route.py:call` and `infra/deploy/verify_role_monitor_staging.py:api_get` through `hosted_acceptance.active_version`; both helpers use default `urlopen` with a bearer token. A Cloudflare-side or intermediary redirect, even an accidental one, could therefore expose the powerful deployment or routing token to a different origin. This is not an observed live redirect, but the credential-forwarding path is demonstrated and violates the project's existing `staging_mail_e2e.control_open` no-redirect contract.

Commit `024441a` corrects the D1 POST, Routing Rules reader, and Worker deployment reader with no-redirect openers and fixed 3xx failures. It also hardens the GitHub Actions JSON bearer reads while retaining the separately allowlisted, tokenless signed job-log fetch. Synthetic 302 tests cover all four bearer paths. The tests mock opener errors rather than exercising a real HTTP redirect server, so the no-forward property is supported primarily by inspection of `HTTPRedirectHandler.redirect_request -> None` and the standard-library behavior demonstrated above. No redirect leak remains in the new audit path.

## Scope and verified aspects

- The new job is manual-only, branch-restricted, exact-run-confirmed before its secret-bearing step, and does not invoke deployment or SMTP. Its D1 HTTP POST contains a bound aggregate `SELECT` only; the SQL reads role/forward/alert/health metadata, not mail contents or destination. The 17:13:08–17:30:41 and 17:30:41–17:45:00 UTC bounds decode correctly, and the schema stores timestamps in milliseconds. The 90-day purge policy does not invalidate a next-day snapshot.
- The top-level and batch D1 `success` checks, one-row shape, state-count partitions, and fixed-label output appear fail-closed. A later singleton `checked_at` is correctly classified as historical-health `overwritten`; this cannot prove Cron success or failure during the old window. Counts above one are bucketed, and a diagnostic result is not per-message attribution or Inbox delivery proof.
- `standard_rules()` verifies four enabled API-owned literal direct forwards to one common target, **not** that their IDs or destination are unchanged from the failed run. Current docs/label `four_direct` are appropriately narrow; retain that wording. The serving-version check observes current 100% traffic only and cannot establish historical serving provenance.

Verdict at `024441a`: **GO for one guarded, read-only hosted dispatch** from the reviewed branch, subject to its exact confirmation/run/version gates. This is an implementation review only: hosted CI and the actual D1/provider result must still be checked. Do not treat a green diagnostic as SMTP, Cron, forwarding, private-destination, or public-send acceptance.
