## Read-only diagnostic contract

`infra/tests/staging_current_address_failure_logs.py` is a one-run sibling to the older historical diagnostic. The manual `staging-current-address-diagnostic` workflow target requires `READ_STAGING_ADDRESS_INCIDENT_36553799873`. It performs the existing deployed-privacy and indexed-service-key preflight, then a `dry=true`, top-level `view=events`, exact service-filtered Cloudflare Workers Observability query with the fixed interval, at most 200 rows/page, 1600 rows total, 2 MB/response, and cursor-complete checks. The script makes **no Mail API, D1, Routing Rules, Tail, SMTP, address, or deployment mutation**. The [official query API](https://developers.cloudflare.com/api/resources/workers/subresources/observability/subresources/telemetry/methods/query/) documents the event view, dry query, cursor and that a `source` may be a string or an object. The [Workers Logs documentation](https://developers.cloudflare.com/workers/observability/logs/workers-logs/) warns that retention and sampling limit inference from absent records.

Cloudflare documents `source` as an opaque map, not an application-trace wrapper. The older classifier rejected a `source` object in the previous incident; copying or printing that map would risk leaking arbitrary provider or user content. This diagnostic first reduces **only predeclared field presence/types** inside `source` (`message`, `level`, `logs`, `event`, `timestamp`, `data`), a boolean for any other keys, and a four-valued key-count bucket (`zero`, `one`, `two_to_four`, `five_or_more`). It also reports only the source/message primitive type and a closed metadata type category. It never prints actual keys, field values, counts of records, IDs, addresses, URLs, JSON, or exception text. This shape-only report is **not** approval to parse or ignore unknown objects; a later exact-wrapper parser change would require separate review. Full retained-log privacy canary behavior is unchanged.

Only if *every* returned row belongs to the exact staging Worker, every payload is already covered by the strict historical trace/warning parser, the page set is complete, and exactly one failed `addresses_add` root has coherent linked routing phases may the script emit `window_consistent_...` with a bounded status class/provider numeric code. `window_consistent_routing_list_failed` would show a failed Rules GET phase; `window_consistent_routing_create_phase_failure` would show a failed create phase and any producer-recorded numeric provider status/code. It would **not** prove the same CLI invocation without the missing request ID. An absent `routing_create` event is merely “not observed,” never proof there was no POST.

`addresses_add` currently emits `routing_list` and `routing_create` phases but **does not emit D1 read/write phases**. A missing routing phase cannot distinguish an earlier D1 failure from an unlogged branch, sampling loss, an unreviewed wrapper, or another failure; the only safe result is `UNVERIFIED`. Retrofitting D1 spans for future attempts could improve diagnosis, but cannot recover them for this run and should be reviewed as a product observability change, not made merely to rationalize this historic incident. A successful query is not a full privacy-canary pass. No current-run query has yet been dispatched for this script.
