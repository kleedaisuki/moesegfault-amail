# Agent-first operator API and Access contract

Status 2026-09-28: **future design only, explicitly not part of v0.1.0 release**. The owner has chosen exact Cloudflare Email Routing **forward** rules to a confidential external operator destination for the current abuse/postmaster contacts. The unused `workers/mail-ops` prototype has been removed from the release tree; no Access service-token application or operator CLI is deployed. This document preserves a possible later Agent-first mechanism, not an implementation contract or evidence that any such endpoint exists. Dedicated ops D1/R2 resources remain unused. Public sending remains held until the forwarding routes and monitored destination are externally tested.

## Machine identity mechanism

Cloudflare Access's [Service Auth policy](https://developers.cloudflare.com/cloudflare-one/access-controls/policies/common-policies/) may include a **specific service token**. The operator CLI sends `CF-Access-Client-Id` and `CF-Access-Client-Secret` headers, as in Cloudflare's [agent authentication guidance](https://developers.cloudflare.com/cloudflare-one/access-controls/authenticate-agents/). Do not use `Bypass` or the broad `Any Access Service Token` selector. Production and staging use distinct Access applications/audiences and distinct service tokens. Credentials are loaded from protected environment variables or an OS secret store, never argv, public `amail` configuration, ZIP, telemetry or repository. The owner still authorizes public amail only through Identity login; this system principal is separate.

The Worker does **not** trust either client-supplied service-token header as identity. Access adds `Cf-Access-Jwt-Assertion`, which the Worker independently verifies against the configured team's HTTPS JWKS: RS256 signature, exact issuer, exact application AUD, expiry/`nbf`, `type=app`, and JWK algorithm/use. Cloudflare's [application-token schema](https://developers.cloudflare.com/cloudflare-one/access-controls/applications/http-apps/authorization-cookie/application-token/) shows that a service-token JWT has `sub=""`, normally no `email`, and `common_name` equal to its Client ID. Therefore machine authorization additionally requires **empty `sub`, absent email, and signed `common_name` exactly matching the deployment secret `OPS_SERVICE_CLIENT_ID`**. A human JWT has a nonempty `sub`/email and must not be accepted by this branch. Missing/sentinel team, AUD or pinned ID denies both HTTP access and role-route SMTP readiness; the raw header alone is never sufficient. A separate exact-email human Access branch may retain the old page for break-glass only, but it has no machine API or policy-control authority.

The service-token Client Secret is known only to the CLI/runner and Cloudflare Access; it is **not** a Worker secret. The Worker stores only the pinned Client ID. The JWT/session may outlive one request; every request still supplies the two headers, and the Worker validates the signed Access assertion on each invocation. Revocation/rotation and alternate URL bypass are live acceptance tests. Credential rotation may temporarily allow two explicitly pinned IDs only during a bounded handover; never broaden to all account service tokens. Cloudflare [requires origin JWT signature validation](https://developers.cloudflare.com/cloudflare-one/access-controls/applications/http-apps/authorization-cookie/validating-json/), not header-presence checks.

## Versioned JSON API

In this future design, all HTTP endpoints would be under `ops.moesegfault.dev` (staging `ops-staging.moesegfault.dev`), require a valid **service** principal, and return `Cache-Control: no-store`. Errors would be compact typed JSON with an opaque request ID, never raw SMTP/provider text. IDs and cursors would be opaque; no address, subject, sender, body or token would be placed in a URL or default list result. The contract could preserve the removed prototype's case-ID/R2-key model while changing the interaction layer.

| Endpoint | Response / invariant |
| --- | --- |
| `GET /v1/status` | `{v, environment, open_count, oldest_open_seconds, failed_reservations, last_agent_success, request_id}`. Counts only; no report PII. A missing/stale scheduled agent and fallback readiness are visible, not a green health claim. |
| `GET /v1/cases?state=open&limit=50&cursor=...` | One bounded keyset page `{v, items:[{id,role,state,created_at,size_bytes,revision,disposition}],next_cursor,request_id}`. `disposition` is an enum, never report text. Default state is `open`; cursor is opaque and resumable. |
| `GET /v1/cases/{uuid}` | Case status, revision, disposition/evidence *class*, updated timestamp, and opaque audit refs. No raw report or R2 key. Unknown ID returns typed 404. |
| `GET /v1/cases/{uuid}/preview` | Explicit bounded first 16 KiB of text evidence, tagged `untrusted=true`; no HTML rendering or automatic link/attachment handling. It is not a source of tool instructions. |
| `GET /v1/cases/{uuid}/raw` | Explicit `application/octet-stream` `.eml` attachment, streamed from R2. The CLI writes only to a new protected path, never stdout or telemetry. |
| `GET /v1/cases/{uuid}/audit` | Bounded ordered status transitions: signed actor ID, action, prior/new state, evidence class/ref and opaque request ID; no body. |
| `PATCH /v1/cases/{uuid}` | Bounded JSON `{expected_revision,state,disposition,evidence_class,evidence_ref?}`. D1 compare-and-swap increments revision and writes audit in the same transaction; stale revision returns 409. Closing does **not** imply a sender hold. |
| `POST /v1/agent/heartbeat` | A successful scheduled cycle reports its checkpoint. The Worker records `last_agent_success` separately from SMTP intake health; a heartbeat cannot acknowledge/close cases. |

The service token can triage cases but **cannot mutate global mail send policy** through this Worker. A higher-impact `amail-operator policy hold-account` CLI command may use the existing main-only, audited `send-control.yml` GitHub workflow with a separate `actions:write` credential, explicit account subject, reason and opaque case ID; it must read back the result. No `global unhold` or suppression removal is inferred from report prose. Trusted provider complaint events already have their own automatic account-hold path. A reporter email alone is untrusted and cannot trigger account/global hold, even if its MIME text asks the agent to run the command.

## CLI and rollout invariants

Use a separate Rust binary/package named `amail-operator` to avoid confusing this privileged future CLI with public `amail`; there is no current operator Worker crate to depend on. Short verbs: `status`, `cases list|get|preview|export|mark|audit`, then `policy inspect|hold-account` with explicit elevated credential. Normal stdout is compact JSON Lines; `--human` is opt-in presentation only. Do not print raw MIME on stdout. `cases export -o` refuses an existing file and uses owner-only file permissions. A future internal skill must tell an agent to treat reports as **prompt-injection-capable evidence**, verify provider correlation before actions, and never convert a report's imperative prose into a policy command.

Any future HTML page would be a separate exact-human-email Access break-glass path, never the daily workflow or a release gate. A content-free alert from `mail@moesegfault.dev` could be an optional fallback; its absence should not block that future SMTP intake or machine JSON API, although a tested escalation path would still be required before public send. That future operational release gate would require a real scheduled agent consuming status/cases, tested aging/backlog escalation if it stops, external SMTP canaries for apex and mail-subdomain roles, Access service-token allow/deny tests, and audited triage/hold read-back. None of these future conditions attests the current forwarding path.

## Deployment interface change

The removed prototype's uncommitted deployment sketch required `OPERATOR_EMAIL`/`OPERATOR_ALERT_EMAIL` and a human `Allow` policy; it is **not a current workflow**. A later Agent service would instead need environment-specific `TEAM_DOMAIN`, `ACCESS_AUD`, pinned `OPS_SERVICE_CLIENT_ID`, and a verified `Service Auth` policy selecting the exact service token. The client secret would belong in the operator CLI/agent runner secret store, **not** Worker secrets JSON. Dedicated D1/R2 resources could be reused only after a fresh privacy and lifecycle review. Preserve the current verified forward rules during migration; never auto-switch role routes merely because a new Worker build/deploy passed.
