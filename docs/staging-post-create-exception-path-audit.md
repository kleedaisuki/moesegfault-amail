# Staging address registration: exception-path audit after provider create

Status: source-only audit at `5882060` on 2026-09-29; **no exception site identified**. This extends the [incident record](staging-fourth-address-incident-36567571204.md) and [initial code audit](staging-post-create-500-code-audit.md), without creating an address, querying private logs, or changing live state. Do not store the run alias, rule ID, account, request ID, token, provider body, or raw exception here.

## Branch-by-branch result contract

The observed pre-cleanup state was one exact enabled provider route and a D1 `provisioning` row with null `cf_rule_id`; the CLI got non-problem HTTP 500 and no accepted staging diagnostic. The route is a **side effect**, not proof that the original Worker received or decoded a successful POST response. In `platform::create_rule` (`crates/mail-worker/src/platform.rs:211-240`), the POST is followed by `response.text().await` and `classify_create_response`. Every **returned** request/read/parse error becomes `RuleCreateFailure`; `add_address` maps it to `routing_unavailable` 503 or `capacity_exhausted` 409 and a staging `routing_create` diagnostic. The provider may have committed the route before any of these outcomes. The pure decoder has unit cases for success, malformed 200, and provider refusal (`platform.rs:546-600`), but these do not exercise the Worker JS fetch/body boundary.

If a rule ID is returned, `add_address` emits `trace.routing_create` **before** `D1Activate` (`lib.rs:1344-1375`). An existing exact rule follows the same activation path without a new POST. The application's activation `prepare` call is infallible at the Rust API type level, but the dependency's implementation can panic as described below. Returned `bind` errors flow through `?`; `run().await` is retained as a `Result`, and a failed/mismatched transition returns an explicit 409/503 after best-effort cleanup (`lib.rs:1370-1406`). Readback and response-encoding errors likewise return through `?` when their called libraries return errors. The authenticated staging dispatch then converts returned errors to `application/problem+json` with a bounded diagnostic header (`lib.rs:715-732`); `main` adds `x-amail-request-id` after dispatch (`lib.rs:130-152`). Therefore **no ordinary returned branch in this post-create interval intentionally produces a bare 500**. The missing header is evidence against a normally returned `RuleCreateFailure` or D1 error *if* the pinned staging gate was serving and the response reached the CLI intact. It does not distinguish a Wasm/JS throw, a Cloudflare-generated response, a header lost in transit, or configuration drift.

Our **application source** contains no `unwrap`/`expect` in the production registration and provider-create interval. The locked `worker` dependency is **0.8.7** (`Cargo.lock`), despite the compatible `0.8.3` manifest requirement. In its local registry source, `worker-0.8.7/src/d1/mod.rs:59-61`, `D1Database::prepare` calls `self.0.prepare(&query.into()).unwrap().into()`: a synchronous rejection from the underlying JavaScript D1 `prepare` binding would panic rather than return through this application's `?`. On the branch that just created a rule, the activation `database.prepare(...)` at `lib.rs:1370` is the first such D1 prepare **after** the provider-create return and trace call. Earlier prepares succeeded in this invocation to allocate and claim the row. This is a concrete dependency-level exception pathway consistent with a bare 500 and pre-cleanup null rule ID, **not evidence that the binding rejected this static activation SQL in the historical request**. D1 binding behavior and any exception record have not been observed. If `prepare` succeeds, the subsequent `bind` and `run` returned errors follow the handled paths described above.

Other exceptional boundaries remain possible: JS fetch/body consumption, `trace.routing_create` serialization and `console_log!` (`trace.rs:236-320`), response construction, memory, or runtime limits. A D1 `Result` only covers failures that the library returns, not every runtime trap. Conversely, the Worker Metrics aggregate found one `scriptThrewException` and 13 `success` invocations in the 69-second window, but no per-request association; it cannot prove the exception was this add.

## What would separate the remaining explanations

| Safe evidence or test | Discriminating result | Limit |
| --- | --- | --- |
| Closed, request-correlated retained application event for `routing_create`, if the **entire** historical source wrapper passes privacy review | A success event would show `create_rule` returned an ID and `trace.routing_create` ran; a failure event would show a normally classified create response was reached. | Missing event is not negative evidence; opaque source wrappers and sampling make absence ambiguous. An event does not prove subsequent D1 success. |
| Request-local `cf-error-type` captured as a fixed 1101/1102/other/absent classifier from a *future normal* hosted attempt | Differentiates Cloudflare exception/resource pages from an app-produced 500 without exporting the body. | The historical CLI did not capture this; do not create a fifth alias only to get it. |
| Hosted synthetic Worker-level test with a fake Cloudflare Rules endpoint and D1 binding, following one `POST /v1/addresses` dispatch | Assert malformed/missing 2xx provider body, body-read rejection, provider 4xx/5xx, D1 activation rejection/mismatch each yield the expected problem/status/diagnostic and never blindly POST again. Specifically inject a synchronous JS D1 `prepare` rejection at activation, separately from async `run` rejection; the locked dependency's `unwrap` predicts only the former can panic through this site. | Pure `classify_create_response` unit tests cannot exercise fetch/JS/D1/response boundaries; synthetic behavior is not the historical root cause. No live route or user address should be created. |
| Restricted exact-request Workers exception outcome, only if a privacy-reviewed indexed query can isolate it without raw event export | Can causally assign `scriptThrewException` or a different termination to this request. | The existing GraphQL `workersInvocationsAdaptive` bucket is aggregate; its one exception cannot be assigned to this request. |

The first implementation gate should be the synthetic hosted Worker-boundary matrix, because it is repeatable and does not consume another user address. If it reproduces an exception, fix that line and retain the external error codes. If not, the historical cause remains unresolved; a subsequent one-use live acceptance would need a separate reviewed plan, exact ownership/readback and delayed cleanup audit. Never retry provider creation merely because a client saw 500: the route side effect proves that outcome can be uncertain.
